# व्यवस्थापन कमान्ड सन्दर्भ

- लक्षित पाठक: IT सञ्चालकहरू
- दायरा: यस रिपोजिटरीका Ninefruits एपहरूले दर्ता गरेका सबै कमान्ड (`ninefruits/*/management/commands/`) र सञ्चालनमा प्रयोग हुने Django का आफ्नै कमान्डहरू। नयाँ कमान्ड थपिँदा यस कागजातमा पनि `### \`command\`` प्रविष्टि थप्नुपर्छ (सबै 16 भाषामा), नत्र CI असफल हुन्छ (`tests/tooling/test_command_documentation.py`)।

## साझा नियमहरू

हरेक कमान्ड `uv run manage.py {command}` का रूपमा चल्छ। Docker विकास वातावरणमा `docker compose exec app uv run manage.py {command}`।

| वस्तु | नियम |
|---|---|
| नाम | मूल `{context}:{action}` लाई `{context}_{action}` बनाइन्छ (Django कमान्डको नाममा `:` राख्न मिल्दैन)। उदाहरण: `term:close` → `term_close` |
| अडिट अभिलेख | डेटा परिवर्तन गर्ने कमान्डहरूले (तल "अडिट: अभिलेख हुन्छ") हरेक पटक चल्दा कमान्ड, आर्गुमेन्ट, विकल्प, OS प्रयोगकर्ता, निकास कोड र नतिजा गतिविधि लग (लग `command`) मा लेख्छन्। प्रशासन प्यानलको **अडिट > गतिविधि लग** मा जाँच्नुहोस् |
| रन ID | हरेक रनले अनुरोध ID को सट्टा `cmd-` बाट सुरु हुने ID पाउँछ। गतिविधि लग, त्यस रनले गरेका डेटा परिवर्तन र त्यसले पठाएका Celery कार्यहरू सबैमा उही ID हुन्छ, त्यसैले "यो परिवर्तन कुन कमान्डले गर्‍यो" भन्ने प्रश्नको उत्तर ID ले दिन्छ। `--actor` सञ्चालकले दिएको मान हो, त्यसैले यसलाई डेटा परिवर्तनको प्रयोगकर्ता स्तम्भमा राखिँदैन (वास्तविक कर्ता OS प्रयोगकर्ता हो) |
| `--actor=<email>` | अडिट हुने सबै कमान्डमा साझा। जिम्मेवार प्रशासक खाता अभिलेख गर्छ। अज्ञात इमेलले रन रोक्छ |
| `--dry-run` | केही परिवर्तन नगरी नतिजा देखाउँछ। फर्काउन गाह्रो कार्यहरूमा उपलब्ध |
| `--force` | पुष्टि प्रश्नबिना चलाउँछ (तालिका र डिप्लोय स्क्रिप्टका लागि) |
| `--reason=` | कारण चाहिने कमान्डहरूमा उपलब्ध |
| निकास कोड | 0 सफल, 1 असफल वा रद्द, 2 जाँच कमान्डले समस्या भेट्टायो |
| DB सन्दर्भ | कमान्ड चलिरहँदा DB सत्रको कर्ता `system:command:{command}` मा सेट हुन्छ र डेटा परिवर्तन (trigger) मा देखिन्छ |

## Django का आफ्नै कमान्डहरू

### `migrate`

- प्रयोजन: डेटाबेस migration लागू गर्छ। Django कमान्डमाथिको Ninefruits र्‍यापर: `--database` नदिएमा स्किमा मालिकको जडान (`migrator`, भूमिका `app_migrator`) प्रयोग गर्छ। एप्लिकेसनको जडान (`app_runtime`) सँग DDL अधिकार छैन। `showmigrations` र `sqlmigrate` ले पनि पूर्वनिर्धारित रूपमा `migrator` जडान प्रयोग गर्छन्।
- कहिले: पहिलो स्थापनामा र हरेक डिप्लोयमा (`setup_install` ले पनि यसलाई चलाउँछ)।
- विकल्पहरू: Django `migrate` कै (`app_label`, `migration_name`, `--plan`, `--check`, `--database`)।
- अडिट: अभिलेख हुँदैन (स्किमा परिवर्तनहरू migration इतिहास `django_migrations` मा रहन्छन्)
- उदाहरणहरू

  ```bash
  uv run manage.py migrate
  uv run manage.py migrate --plan
  ```

- असफल भएमा: अनुमति त्रुटिका लागि [स्थापना पुस्तिका](installation.md) को डेटाबेस भूमिका तयारी (`db/sql/roles/`) जाँच्नुहोस्।

### `collectstatic`

- प्रयोजन: Vite बिल्ड आउटपुट (`static/dist/`) र Django तथा unfold का स्थिर फाइलहरू `STATIC_ROOT` (`staticfiles/`) मा सङ्कलन गर्छ। वेब सर्भर (Nginx) ले यो डाइरेक्टरी सेवा गर्छ।
- कहिले: हरेक डिप्लोयमा, `npm ci && npm run build` पछि।
- विकल्पहरू: `--noinput` (प्रश्न नसोध्ने), `--clear` (सङ्कलन गर्नुअघि विद्यमान फाइलहरू मेटाउने)।
- अडिट: अभिलेख हुँदैन
- उदाहरणहरू

  ```bash
  npm ci && npm run build
  uv run manage.py collectstatic --noinput
  ```

### `compilemessages`

- प्रयोजन: अनुवाद फाइलहरू (`.po`) लाई रनटाइमको `.mo` फाइलमा कम्पाइल गर्छ। `.mo` फाइलहरू रिपोजिटरीमा राखिँदैनन्, त्यसैले हरेक स्थापना र डिप्लोयमा यो चलाउनुहोस्। प्रणालीमा `gettext` स्थापना भएको हुनुपर्छ।
- कहिले: हरेक डिप्लोयमा र अनुवाद फाइल सम्पादन गरेपछि।
- विकल्पहरू: `--locale=` (जस्तै `ko`, `zh_Hans`, `lo`), `--ignore=.venv`।
- अडिट: अभिलेख हुँदैन
- उदाहरणहरू

  ```bash
  uv run manage.py compilemessages --ignore=.venv
  ```

### `createsuperuser`

- प्रयोजन: **प्रयोग गरिँदैन।** Django superuser ले भूमिका र अनुमति क्याटलग तथा अडिट ट्रेललाई छल्छ, त्यसैले यो कमान्ड त्रुटि (निकास कोड 1) सहित अन्त्य हुन्छ र `security_create_administrator` तर्फ सङ्केत गर्छ।
- सट्टामा: पहिलो प्रशासक `security_create_administrator` बाट बनाउनुहोस् (प्रणाली प्रशासक भूमिका तोकाइ र अडिट अभिलेख समावेश)।
- अडिट: लागू हुँदैन

## स्थापना र डेमो (चरण 1)

### `setup_install`

- प्रयोजन: नयाँ स्थापना र अद्यावधिक। क्रमैसँग चलाउँछ: migration, आवश्यक डेटा (भूमिका टेम्प्लेट र अनुमति सिङ्क, देशहरू, भाषाहरू, कोड सूचीका प्रकारहरू, संगठन एकाइका प्रकारहरू), संस्था सेटिङ, ग्रेड स्केल, स्थापना प्रोफाइलहरू र पहिलो प्रशासक। फेरि चलाउन सुरक्षित छ (विद्यमान डेटा र प्रशासकले परिवर्तन गरेका मानहरू कायम रहन्छन्)।
- कहिले: पहिलो स्थापनामा र हरेक डिप्लोयमा।
- विकल्पहरू: `--institution-name=`, `--locale=` (पूर्वनिर्धारित भाषा), `--timezone=` (जस्तै `Asia/Seoul`), `--profile=` (स्थापना प्रोफाइलको कुञ्जी, दोहोर्‍याउन सकिन्छ: `korean-university`, `yust-legacy`), `--grade-scale=` (ग्रेड स्केल `4.5` वा `4.3`; एक पटक सेट भएपछि स्थिर; खाली भनेको पहिलो प्रोफाइलको स्केल), `--admin-email=`, `--admin-name=`, `--force` (प्रश्न नसोध्ने; प्रशासकको पासवर्ड standard input बाट पढिन्छ)।
- अडिट: अभिलेख हुन्छ (लागू गरिएका प्रोफाइल, प्रशासक बनाइयो कि बनाइएन)
- उदाहरणहरू

  ```bash
  uv run manage.py setup_install
  echo "$ADMIN_PASSWORD" | uv run manage.py setup_install --force --locale=ko --timezone=Asia/Seoul \
      --institution-name="Demo University" --profile=korean-university \
      --admin-email=admin@example.ac.kr --admin-name="Administrator"
  ```

- आउटपुट पढ्ने तरिका: प्रत्येक चरणमा `DONE`। `Administrator exists` भनेको प्रणाली प्रशासकको तोकाइ पहिले नै छ, त्यसैले नयाँ बनाउने काम छोडियो।
- असफल भएमा: कुञ्जी नभएको त्रुटि आएमा `DJANGO_SECRET_KEY` र `pii_generate_key` का मानहरू वातावरणमा सेट गर्नुपर्छ। migration असफल भएमा: डेटाबेस भूमिकाहरू जाँच्नुहोस् ([स्थापना](installation.md))। `The grade scale is fixed` भनेको `--grade-scale` पहिले नै स्थिर गरिएको स्केलभन्दा फरक छ।

### `setup_demo`

- प्रयोजन: काल्पनिक विश्वविद्यालय बनाउँछ (संगठन एकाइ, कार्यक्रम, भवन र कोठा, आजको वरिपरिका अघिल्लो, हालको र अर्को सेमेस्टर तिनका कार्य अवधिसहित, कोरियाली विश्वविद्यालय प्रोफाइल)। भूमिकाअनुसार स्थिर डेमो खाताहरू (`registrar@demo.test` आदि, पासवर्ड `demo-password`) देखाउँछ। ठूलो परिमाणको डेटा bulk insert बाट बनाइन्छ।
- कहिले: विकास, तालिम र प्रदर्शन वातावरण। **उत्पादन (`DJANGO_ENV=production`) मा `--force` दिए पनि कहिल्यै चल्दैन।**
- विकल्पहरू: `--size=tiny|small|medium|large` (लगभग 20/100/2,000/20,000 विद्यार्थी; `tiny` परीक्षण र छिटो जाँचका लागि), `--seed=` (उही मान, उही डेटा), `--force` (पुष्टि नसोध्ने)।
- `--student-accounts`: हरेक अध्ययनरत विद्यार्थीलाई खाता दिन्छ र लोड परीक्षणका लागि निजी भण्डारणमा `load-accounts.csv` (इमेल, पासवर्ड) लेख्छ ([लोड परीक्षण](load-testing.md))।
- अडिट: अभिलेख हुन्छ (आकार, seed, अवधि)
- उदाहरण: `uv run manage.py setup_demo --size=small --seed=42 --force`
- असफल भएमा: आवश्यक डेटा नभएमा डेमो खाताहरू छोडिन्छन् (तिनका भूमिका हुँदैनन्); पहिले `setup_install` चलाउनुहोस्। उही डेटाबेसमा फेरि चलाउँदा भइरहेको डेमो डेटा छोडिन्छ।

## सन्दर्भ डेटा र सेमेस्टरहरू (चरण 1)

### `reference_import`

- प्रयोजन: प्रशासन प्यानलको **CSV आयात गर्नुहोस्** कै नियमअनुसार CSV बाट सन्दर्भ डेटा आयात गर्छ (पङ्क्तिहरू कोडद्वारा फेला पारेर अद्यावधिक गरिन्छन्, खाली अनुवाद कक्षले विद्यमान मान कायम राख्छ, असफल पङ्क्तिहरू छुट्टै राखिन्छन्)।
- आर्गुमेन्टहरू: `type` `org_units`, `programs`, `buildings`, `rooms`, `lookup_values`, `students` (विद्यार्थी अभिलेख), `instructors`, `courses` (विषय संस्करण), `registration_holds` (दर्ता रोक) / `file` हेडर पङ्क्तिसहितको UTF-8 CSV।
- विकल्पहरू: `--actor=` (अनिवार्य; आयात यही खाताअन्तर्गत अभिलेख हुन्छ र यसको नतिजा त्यस खाताको **CSV आयातहरू** स्क्रिनमा देखिन्छ), `--chunk=100` (प्रति Celery कार्य पङ्क्ति), `--dry-run` (हेडर जाँच र पङ्क्ति गन्ती मात्र)।
- अडिट: अभिलेख हुन्छ (प्रकार, फाइल नाम, पङ्क्ति, आयात नम्बर, असफल पङ्क्ति)
- स्तम्भको ढाँचा: [प्रशासक पुस्तिका अध्याय 9](../admin/09-csv-import.md)।
- निकास कोड: कार्यहरू तुरुन्तै चल्दा (eager worker) नतिजा देखाइन्छ र असफल पङ्क्ति भए 2। आयात क्युमा मात्र राखिएमा 0। नतिजा र असफल पङ्क्तिहरूको CSV प्रशासन प्यानलको **सन्दर्भ डेटा > CSV आयातहरू** मा हुन्छ।
- उदाहरण: `uv run manage.py reference_import org_units /srv/import/org-units.csv --actor=admin@example.ac.kr --dry-run`

### `term_inspect`

- प्रयोजन: कुनै समयमा चलिरहेका सेमेस्टर र खुला कार्य अवधिहरू (प्रकार, सेमेस्टर, सत्र, नाम, योग्यता, बन्द हुने समय) देखाउँछ। सेमेस्टर र कार्य अवधिका सेटिङ जाँच्न, वा "विषय दर्ता किन खुलेको छैन?" जस्ता प्रश्नका लागि प्रयोग गरिन्छ।
- विकल्पहरू: `--at=` (पूर्वनिर्धारित अहिले; जस्तै `"2027-02-15 09:00"`; समय क्षेत्र नभएमा सर्भरको समय क्षेत्र (UTC) लागू हुन्छ; `"2027-02-15 09:00 Asia/Seoul"` वा `2027-02-15T09:00+09:00` ले समय क्षेत्र तोक्छ)।
- अडिट: अभिलेख हुँदैन (पढ्ने मात्र)
- आउटपुट पढ्ने तरिका: मितिहरू संस्थाको समय क्षेत्रमा निर्धारण गरिन्छन्। योजनाबद्ध वा संग्रह गरिएका सेमेस्टरका कार्य अवधि कहिल्यै खुल्दैनन्। बन्द हुने समय संस्थाको समय क्षेत्रमा देखाइन्छ।

## सुरक्षा (चरण 0, 2)

### `security_create_administrator`

- प्रयोजन: प्रणाली प्रशासक भूमिकासहितको खाता बनाउँछ। सामान्यतया `setup_install` ले बोलाउँछ।
- विकल्पहरू: `--email=`, `--name=`, `--password-stdin` (standard input बाट पासवर्ड। अन्तरक्रियारहित रनका लागि अनिवार्य)।
- अडिट: अभिलेख हुन्छ (बनाइएको प्रयोगकर्ताको ID)
- उदाहरण: `uv run manage.py security_create_administrator --email=admin@example.ac.kr --name="Administrator"`
- उदाहरण (अन्तरक्रियारहित): `printf '%s\n' "$ADMIN_PASSWORD" | uv run manage.py security_create_administrator --email=admin@example.ac.kr --name="Administrator" --password-stdin`
- असफल भएमा: `system_administrator role is missing` भनेको पहिले `setup_install` चलाउनुपर्छ। पासवर्ड कम्तीमा 12 अक्षरको हुनुपर्छ।

### `security_sync_permissions`

- प्रयोजन: DB को अनुमति सूचीलाई कोडको अनुमति क्याटलगसँग मिलाउँछ। नयाँ अनुमतिहरू बनाइन्छन्; क्याटलगमा नभएका अनुमतिहरू मेटाइन्छन् (र सबै भूमिकाबाट हटाइन्छन्)। प्रणाली भूमिकाहरूले सधैँ सबै अनुमति पाउँछन्।
- कहिले: डिप्लोयपछि (`setup_install` ले आवश्यक डेटा चरणको भागका रूपमा यो गर्छ)।
- विकल्पहरू: `--dry-run` (बनाउने/मेटाउने सूची मात्र देखाउँछ), `--force` (मेटाउने पुष्टि छोड्छ)।
- अडिट: अभिलेख हुन्छ (बनाइएका/मेटाइएका अनुमति)
- आउटपुट पढ्ने तरिका: `create` र `delete` पङ्क्तिहरू। मेटाउनुपर्ने भएमा पुष्टि प्रश्न देखिन्छ।
- असफल भएमा: पुष्टिमा "no" भन्दा निकास कोड 1 सहित बाहिरिन्छ र केही परिवर्तन हुँदैन।

### `security_reencrypt_secrets`

- प्रयोजन: `DJANGO_SECRET_KEY` परिवर्तन (rotation) पछि, त्यसबाट निकालिएको कुञ्जीले सुरक्षित गरिएका गोप्य मानहरू (प्रमाणीकरण एपका TOTP गोप्य मान, रिकभरी कोडका seed, SSO client secret) नयाँ कुञ्जीले फेरि इन्क्रिप्ट गर्छ। त्यसबेलासम्म तिनलाई `DJANGO_SECRET_KEY_FALLBACKS` मा रहेको अघिल्लो कुञ्जीले पढिन्छ। अघिल्लो कुञ्जी हटाउनुअघि यो चलाउनुहोस् ([कुञ्जी व्यवस्थापन](security-keys.md))।
- आर्गुमेन्ट/विकल्पहरू: `--dry-run` (अझै अघिल्लो कुञ्जीले इन्क्रिप्ट गरिएका गोप्य मान गन्ती मात्र गर्छ)।
- अडिट: अभिलेख हुन्छ (सङ्ख्या)
- आउटपुट पढ्ने तरिका: `Dry run: 0 authenticator(s) and 0 SSO client secret(s) use a previous key.` भनेको अघिल्लो कुञ्जी हटाउन सकिन्छ। `cannot be decrypted` भनेको कुनै मान सेट गरिएको कुनै पनि कुञ्जीले पढ्न सकिँदैन: अघिल्लो कुञ्जी `DJANGO_SECRET_KEY_FALLBACKS` मा राखेर फेरि चलाउनुहोस्।
- उदाहरण: `uv run manage.py security_reencrypt_secrets --dry-run`

### `security_reset_mfa`

- प्रयोजन: प्रयोगकर्ताको दुई-चरण प्रमाणीकरण (प्रमाणीकरण एप, इमेल कोड, रिकभरी कोड, सम्झिएका उपकरण) रिसेट गर्छ। प्रयोगकर्ताले अर्को साइन इनमा फेरि दर्ता गर्छन्। कुनै पनि प्रशासकले प्रशासन प्यानलमा साइन इन गर्न नसक्दा प्रयोग गर्नुहोस् (उदाहरणका लागि एक मात्र प्रशासकको फोन हरायो)। अन्यथा प्रशासन प्यानलको **प्रयोगकर्ताहरू > दुई-चरण प्रमाणीकरण रिसेट गर्नुहोस्** प्रयोग गर्नुहोस्।
- आर्गुमेन्ट/विकल्पहरू: `{user}` प्रयोगकर्ताको इमेल, `--reason=` (अनिवार्य), `--actor=` (अनिवार्य। रिसेटको निर्णय गर्ने प्रशासक)।
- अडिट: अभिलेख हुन्छ (गतिविधि लग र सुरक्षा लग दुवैमा, कारणसहित)
- उदाहरण: `uv run manage.py security_reset_mfa admin@example.ac.kr --reason="Phone lost, identity verified by phone call" --actor=it-lead@example.ac.kr`

### `security_unlock_user`

- प्रयोजन: बारम्बार गलत पासवर्डले लक भएको खाता लक अवधि सकिनुअघि अनलक गर्छ। प्रशासन प्यानलको **प्रयोगकर्ताहरू > साइन इन अनलक गर्नुहोस्** जस्तै।
- आर्गुमेन्ट/विकल्पहरू: `{user}` प्रयोगकर्ताको इमेल, `--reason=` (अनिवार्य)।
- अडिट: अभिलेख हुन्छ (सुरक्षा लगमा पनि)
- आउटपुट पढ्ने तरिका: `The account is not locked.` भनेको केही परिवर्तन भएन।
- टिप्पणी: लकका सीमाहरू (असफल प्रयास, लक अवधि) प्रशासन प्यानलको **सेटिङ > साइन इन विधिहरू** मा सेट गरिन्छन्।

- त्यसपछि: प्रत्येक समूहलाई प्रशासन प्यानलको **व्यक्तिहरू** मा समीक्षा गर्नुहोस् र एउटै व्यक्ति भएमा राख्ने व्यक्तिको पृष्ठबाट **दोहोरो गाभ्नुहोस्** चलाउनुहोस्। गाभ्ने काम फर्काउन सकिँदैन ([प्रशासक पुस्तिका अध्याय 14](../admin/14-merge-and-invitations.md))।

## भर्ना (चरण 3)

### `admission_matriculate`

- प्रयोजन: भर्ना चरणका पुष्टि भएका आवेदकहरूका लागि विद्यार्थी अभिलेख (नयाँ विद्यार्थी नम्बर) बनाउँछ। प्रशासन प्यानलको **भर्ना > आवेदनहरू** मा थोक **विद्यार्थी अभिलेख बनाउनुहोस्** जस्तै (`MatriculateApplicant`)। प्रत्येक आवेदक छुट्टाछुट्टै प्रशोधन हुन्छ, त्यसैले एउटा असफल हुँदा बाँकी रोकिँदैनन्।
- आर्गुमेन्ट/विकल्पहरू: `cycle` भर्ना चरणको कोड, `--term=` (अनिवार्य; भर्ना सेमेस्टरको कोड, जस्तै `2027-SP`; भर्ना मिति सेमेस्टरको पहिलो दिन हुन्छ), `--actor=` (अनिवार्य; `भर्ना स्वीकृत आवेदकका विद्यार्थी अभिलेख बनाउने` अनुमति भएको खाता; त्यस खाताको दायराभित्रका आवेदक मात्र प्रशोधन हुन्छन्), `--dry-run` (सूची मात्र)।
- अडिट: अभिलेख हुन्छ (चरण, सेमेस्टर, सम्भावित, बनाइएका, असफल आवेदन नम्बरहरू)। प्रत्येक आवेदकले व्यावसायिक अडिट प्रविष्टि (`application.matriculated`) पनि पाउँछन्।
- निकास कोड: चरण वा सेमेस्टर कोड अज्ञात भएमा वा `--actor` नभएमा 1, कुनै आवेदक असफल भएमा 2।
- उदाहरण: `uv run manage.py admission_matriculate DEMO-2027-REG --term=2027-SP --actor=admissions@example.ac.kr --dry-run`
- असफल भएमा: `Only accepted offers without a student record ...` भनेको आवेदकको पहिले नै अभिलेख छ वा पुष्टि गरेका छैनन्; `The program is not in effect on the admission date.` भनेको कार्यक्रम भर्ना मितिमा मान्य छैन (सन्दर्भ डेटा > कार्यक्रमहरू मा कार्यक्रमको मान्यता जाँच्नुहोस्); `not in your scope` भनेको आवेदन `--actor` खाताको दायराबाहिर छ।

### `admission_expire_drafts`

- प्रयोजन: बन्द भएका चरणका मस्यौदा आवेदन र तोकिएको अवधि (**सेटिङ > भर्ना > नछोइएका मस्यौदा यति दिनपछि म्याद सकिन्छ**, पूर्वनिर्धारित 90) सम्म परिवर्तन नगरिएका मस्यौदालाई **म्याद सकिएको** चिन्ह लगाउँछ। म्याद सकिएका आवेदनले उही चरणमा नयाँ आवेदन दिन रोक्दैनन्।
- कहिले: हरेक दिन 03:10 मा निर्धारित (Celery beat कार्य `admission.expire_drafts` ले यो कमान्ड चलाउँछ)।
- विकल्पहरू: `--dry-run` (गन्ती मात्र)।
- अडिट: अभिलेख हुन्छ (म्याद सकिएको सङ्ख्या)
- उदाहरण: `uv run manage.py admission_expire_drafts --dry-run`

## विषयका सेक्सनहरू (चरण 4)

### `section_copy`

- प्रयोजन: अघिल्लो सेमेस्टरका सेक्सनहरूबाट नयाँ सेमेस्टरको योजना सुरु गर्छ। प्रशासन प्यानलको **सेक्सनहरू > अर्को सेमेस्टरबाट प्रतिलिपि गर्नुहोस्** जस्तै (`CopySections`)। रद्द नभएका सेक्सनहरूलाई मस्यौदाका रूपमा, प्राध्यापक (अझै कार्यरत भए), कक्षा समय र कोठा, सिट बाँडफाँड (खुल्ने समय सेमेस्टर सुरु मितिहरूको फरकले सारिएको) र पाठ्यविवरण (निजी मस्यौदाका रूपमा) सहित प्रतिलिपि गर्छ। विषय संस्करणलाई नयाँ सत्र सुरु हुँदा लागू रहेको संस्करणले प्रतिस्थापन गरिन्छ।
- आर्गुमेन्ट/विकल्पहरू: `from-term`, `to-term` सेमेस्टर कोडहरू (उदाहरणका लागि `2026-FA`), `--org-unit=` (यस संगठन एकाइ कोडका सेक्सन मात्र; दोहोर्‍याउन सकिन्छ), `--dry-run` (ट्रान्ज्याक्सनमा प्रतिलिपि गरेर rollback गर्छ, त्यसैले प्रतिवेदन ठ्याक्कै हुन्छ), `--actor=` (अनिवार्य। त्यस खाताको `सेक्सन योजना गर्ने` अनुमतिको दायराभित्रका सेक्सन मात्र प्रतिलिपि हुन्छन्)।
- अडिट: अभिलेख हुन्छ (स्रोत र लक्ष्य सेमेस्टर, प्रतिलिपि गरिएका, छोडिएका र समीक्षा चाहिने सङ्ख्या; वास्तविक प्रतिलिपिले व्यावसायिक अडिट घटना `sections.copied` पनि अभिलेख गर्छ)
- आउटपुट पढ्ने तरिका: `skipped` भनेको लक्ष्य सेमेस्टरमा उही सेक्सन कोड पहिले नै छ वा लागू रहेको विषय संस्करण छैन; `note` भनेको सेक्सन प्रतिलिपि भयो तर केही कुरा छुट्यो (कोठा पहिले नै लिइएकाले कोठाबिना प्रतिलिपि, सेवानिवृत्त प्राध्यापक, आदि)। सत्रहरू कोडद्वारा मिलाइन्छन्; नभएमा सेक्सन पूर्ण सेमेस्टर सत्रमा जान्छ।
- निकास कोड: अज्ञात सेमेस्टर कोड वा `--actor` नभएमा 1।
- उदाहरण: `uv run manage.py section_copy 2026-FA 2027-FA --actor=academic@example.ac.kr --dry-run`

### `schedule_check_conflicts`

- प्रयोजन: समयतालिका प्रकाशित गर्नुअघि सेमेस्टरका सेक्सनहरू जाँच्छ। कोठा र प्राध्यापकको दोहोरो बुकिङ DB ले पहिले नै रोक्छ; यसले DB ले अनुमति दिने समस्याहरू पत्ता लगाउँछ: कोठाको क्षमताभन्दा बढी क्षमता, सत्र सुरु मितिमा लागू नभएको विषय संस्करण, सेवानिवृत्त प्राध्यापक, क्षमताभन्दा बढी सिट बाँडफाँड, सत्रबाहिरका कक्षा मिति। ब्याकअप पुनर्स्थापनाजस्ता बाध्यताबिना आएका डेटामा कोठाको टकराव पनि जाँच्छ।
- आर्गुमेन्टहरू: `term` सेमेस्टर कोड।
- अडिट: अभिलेख हुँदैन (पढ्ने मात्र)
- निकास कोड: समस्या भएमा 2, अज्ञात सेमेस्टर कोडमा 1। अझै प्राध्यापक, कोठा वा कक्षा समय नभएका सेक्सनहरू जानकारीका लागि मात्र देखाइन्छन् (`Note`)।
- उदाहरण: `uv run manage.py schedule_check_conflicts 2027-SP`

## विषय दर्ता (चरण 5)

### `registration_preflight`

- प्रयोजन: विषय दर्ता खोल्नुअघि सेमेस्टर जाँच्छ। विषय दर्ता र थप/हटाउने कार्य अवधि, नियम सेट, प्रकाशित सेक्सनको सङ्ख्या, क्षमता 0 भएका सेक्सन, क्षमताभन्दा बढी सिट बाँडफाँड, सत्र सुरु मितिमा लागू नभएका विषय संस्करण, क्रेडिट सीमाले नसमेटेका सक्रिय विद्यार्थीको सङ्ख्या, र दर्ता रोक भएका विद्यार्थीको सङ्ख्या देखाउँछ।
- आर्गुमेन्टहरू: `term` सेमेस्टर कोड (उदाहरणका लागि `2027-SP`)।

### `registration_simulate`

- प्रयोजन: विद्यार्थीले अहिले (वा तोकिएको समयमा) सेक्सनमा दर्ता गरेमा के हुन्छ भन्ने नियमअनुसार देखाउँछ। केही पनि सुरक्षित हुँदैन र कुनै प्रयास अभिलेख हुँदैन। "म किन दर्ता गर्न सक्दिनँ?" भन्ने प्रश्नका लागि प्रयोग गर्नुहोस्।

- आउटपुट पढ्ने तरिका: प्रत्येक नियमका लागि पास/असफल, रोक/चेतावनी र सन्देश। छुटले समेटेको नियम असफल देखिन्छ तर रोक्दैन। क्षमता नियम तालिकामुनि छुट्टै देखाइन्छ।
- निकास कोड: दर्ता अस्वीकार हुने भएमा 2।

### `waitlist_promote`

## ग्रेड (चरण 6)

### `term_close`

- प्रयोजन: सेमेस्टर बन्द गर्छ। सेमेस्टरका सबै ग्रेड अन्तिम भएका हुनुपर्छ। विद्यार्थीको प्रत्येक समूह (100) का लागि यसले सेमेस्टर अभिलेख (क्रेडिट, सेमेस्टर र सञ्चित GPA) गणना गर्छ र शैक्षिक स्थिति (सामान्य, शैक्षिक चेतावनी, निष्कासन समीक्षा) र सम्मान योग्यता निर्धारण गर्छ (Celery chord का `grading.close_term_records` कार्यहरू); त्यसपछि अन्तिम कार्य `grading.finish_term_close` ले कार्यक्रमअनुसार सम्मानको क्रम मिलाउँछ, सेमेस्टर अभिलेखलाई आधिकारिक अभिलेखका रूपमा बन्द गर्छ र सेमेस्टरलाई **ग्रेड बन्द** मा सेट गर्छ। प्रगति `job_batches` मा राखिन्छ र **ग्रेड > सेमेस्टर अभिलेखहरू** सूचीमाथि देखाइन्छ। सकिएपछि सुरु गर्ने कर्मचारीले इमेल पाउँछन्। प्रशासन प्यानलको **ग्रेड > सेमेस्टर अभिलेखहरू > सेमेस्टर बन्द गर्नुहोस्** जस्तै।
- आर्गुमेन्ट/विकल्पहरू: `term` सेमेस्टर कोड, `--dry-run` (सेमेस्टर बन्द गर्न सकिन्छ कि सकिँदैन मात्र जाँच्छ), `--reason=` (अभिलेखमा राखिने कारण), `--actor=`।
- अडिट: अभिलेख हुन्छ (विद्यार्थीको सङ्ख्या, अन्तिम नभएका ग्रेड भएका सेक्सनको सङ्ख्या, batch id)। बन्द प्रक्रिया सकिँदा `term.closed` अडिट अभिलेखमा शैक्षिक चेतावनी, निष्कासन समीक्षा र सम्मानका सङ्ख्या हुन्छन्।
- निकास कोड: केही सेक्सनमा अन्तिम नभएका ग्रेड भएमा 2 (प्रति सेक्सन अन्तिम नभएको सङ्ख्या देखाइन्छ)। सेमेस्टर प्रकाशित स्थितिमा नभएमा 1।
- कहिले: ग्रेड प्रविष्टि र अन्तिम गर्ने काम पूरा भएपछि। batch लाई Flower र सेमेस्टर अभिलेख स्क्रिनमा पछ्याउनुहोस्। Celery worker बिना सेमेस्टरको स्थिति बदलिँदैन। डेटाबेस त्रुटिले असफल भएको समूह 3 पटकसम्म फेरि प्रयास गरिन्छ; त्यसपछि पनि असफल भएमा batch असफल नै रहन्छ र सेमेस्टर बदलिँदैन (कारण सच्याएर फेरि चलाउनुहोस्; फेरि चलाउँदा उही नतिजा आउँछ)।
- उदाहरणहरू: `uv run manage.py term_close 2026-FA --dry-run`, `uv run manage.py term_close 2026-FA --reason="Fall 2026 grades closed" --actor=registrar@example.ac.kr`

### `grades_recalculate`

- प्रयोजन: अन्तिम ग्रेडहरूबाट सेमेस्टर अभिलेख (क्रेडिट, सेमेस्टर र सञ्चित GPA) फेरि गणना गर्छ। परिवर्तित ग्रेडिङ नीति (GPA दशमलव स्थान, पुनः लिएको विषयको व्यवस्थापन) विगतका सेमेस्टरमा लागू गर्न प्रयोग गर्नुहोस्। शैक्षिक स्थिति र सम्मानले सेमेस्टर बन्द हुँदा निर्धारण भएका मान कायम राख्छन्। स्वीकृत ग्रेड परिवर्तनले त्यो विद्यार्थीलाई स्वतः फेरि गणना गर्छ, त्यसैले त्यसका लागि यो कमान्ड चाहिँदैन।
- विकल्पहरू: `--term=` (त्यस सेमेस्टरमा ग्रेड भएका विद्यार्थी, त्यस सेमेस्टरदेखि अगाडि), `--student-number=` (एउटा विद्यार्थी), `--reason=` (अनिवार्य), `--actor=`।
- अडिट: अभिलेख हुन्छ (विद्यार्थीको सङ्ख्या, कारण)
- निकास कोड: कारण नभएमा, वा अज्ञात सेमेस्टर कोड वा विद्यार्थी नम्बरमा 1।
- उदाहरण: `uv run manage.py grades_recalculate --term=2026-SP --reason="GPA changed to three decimal places"`

### `grades_remind_missing`

## LMS एकीकरण (चरण 12)

### `lms_sync`

- प्रयोजन: प्रकाशित सेक्सनहरू प्लेटफर्ममा पठाउँछ (विषय सिर्जना र लिङ्क, प्राध्यापक, भर्ना भएका विद्यार्थी)। प्रशासन प्यानलको **विषय लिङ्कहरू > फेरि सिङ्क गर्नुहोस्** ले गर्ने काम पूरै सेमेस्टरका लागि गर्छ। पहिले नै जोडिएका सेक्सनहरू फेरि सुनिश्चित मात्र गरिन्छन् (idempotent)। हरेक चरण **सिङ्क लगहरू** मा राखिन्छ।
- आर्गुमेन्ट/विकल्पहरू: `{platform}` प्लेटफर्म कोड, `--term=` (सेमेस्टर कोड, पूर्वनिर्धारित अन्त्य नभएका सबै सेमेस्टर), `--section=` (एउटा विषय कोड-सेक्सन कोड, उदाहरणका लागि `CSE2010-01`), `--dry-run` (पठाइने कुरालाई "skipped" का रूपमा अभिलेख मात्र गर्छ), `--actor=`।
- अडिट: अभिलेख हुन्छ (प्लेटफर्म, सेक्सन, सदस्य, असफलता)
- निकास कोड: अज्ञात प्लेटफर्म वा सेमेस्टर कोडमा 1, कुनै सेक्सन असफल भएमा 2 (प्रति सेक्सन त्रुटि देखाइन्छ)।
- कहिले: सेमेस्टर सुरु हुनुअघि, नयाँ प्लेटफर्म सक्रिय गरेपछि।
- उदाहरण: `uv run manage.py lms_sync DEMO --term=2026-FA --dry-run`

### `lms_reconcile`

- प्रयोजन: प्लेटफर्मका विषयका विद्यार्थी सूचीलाई विद्यार्थी सूचना प्रणालीका भर्ना सूचीसँग दाँज्छ, छुटेका सदस्य थप्छ र बढी भएका हटाउँछ। अझै नजोडिएका सेक्सनहरू पूरै सिङ्क गरिन्छन्। फरकहरू सिङ्क लगमा राखिन्छन् (`reconcile`, `payload` मा `missing` र `extra`)।
- आर्गुमेन्ट/विकल्पहरू: `{platform?}` (नदिएमा सबै सक्रिय प्लेटफर्म), `--term=` (पूर्वनिर्धारित अन्त्य नभएका सेमेस्टरहरू), `--dry-run` (फरक मात्र अभिलेख गर्छ), `--actor=`।
- अडिट: अभिलेख हुन्छ (प्रति प्लेटफर्म सेक्सन, थपिएका/हटाइएका/असफल सङ्ख्या)
- निकास कोड: अज्ञात प्लेटफर्म वा सेमेस्टर कोडमा वा कुनै प्लेटफर्म सक्रिय नभएमा 1, कुनै सेक्सन असफल भएमा 2।
- कहिले: कार्य `lms.reconcile` (Celery beat) का रूपमा हरेक दिन 02:30 मा निर्धारित। प्लेटफर्म बन्द भएपछि हातैले चलाउनुहोस्।

### `api_issue_token`

- प्रयोजन: खाताका लागि API एकीकरण टोकन जारी गर्छ ([ADR 0004-django](../../../../porting/decisions/0004-django-api-tokens.md)), सामान्यतया आवश्यक अनुमति मात्र भएको सेवा खाताका लागि (LMS: `lms.manage`, BI: `reports.view`)। टोकन standard output को पहिलो पङ्क्तिमा **एक पटक** मात्र देखाइन्छ; डेटाबेसले यसको digest मात्र राख्छ। अनुरोधहरूले यसलाई `Authorization: Token <token>` हेडरमा पठाउँछन्।
- आर्गुमेन्ट/विकल्पहरू: `{email}` खाताको इमेल, `--days=` (अवधि 1 देखि 365 दिन, पूर्वनिर्धारित `API_TOKEN_TTL_DAYS` = 90), `--reason=` (केका लागि हो, अडिटमा अभिलेख हुन्छ), `--actor=`।
- अडिट: अभिलेख हुन्छ (`api.token_issued`: कुञ्जीको उपसर्ग र म्याद; टोकन आफैँ कहिल्यै होइन)
- निकास कोड: अज्ञात वा निष्क्रिय खाता वा दायराबाहिरको अवधिमा 1।
- उदाहरण: `uv run manage.py api_issue_token moodle-sync@example.ac.kr --days=365 --reason="Moodle callbacks" --actor=admin@example.ac.kr`

### `api_revoke_tokens`

- प्रयोजन: खाताका API टोकनहरू रद्द गर्छ (सबै, वा `--key=` सहित एउटा)। `--list` ले टोकनहरू (कुञ्जीको उपसर्ग, जारी र म्याद सकिने समय) सूचीबद्ध मात्र गर्छ।
- आर्गुमेन्ट/विकल्पहरू: `{email}`, `--key=` (कुञ्जीको उपसर्ग), `--list`, `--reason=`, `--actor=`।
- अडिट: अभिलेख हुन्छ (`api.token_revoked`: रद्द गरिएका कुञ्जीका उपसर्ग)
- निकास कोड: अज्ञात खाता वा `--key` सँग मिल्ने टोकन नभएमा 1।
- कहिले: एकीकरण अन्त्य हुँदा, टोकन चुहिएको हुन सक्दा, वा जिम्मेवार व्यक्ति बदलिँदा।

## व्यक्तिगत डेटा इन्क्रिप्सन कुञ्जीहरू (चरण 0)

### `pii_generate_key`

- प्रयोजन: `PII_ENCRYPTION_KEY` र `PII_HASH_KEY` का लागि नयाँ कुञ्जीहरू (32 बाइट, `base64:...`) देखाउँछ। केही सुरक्षित गर्दैन।
- अडिट: अभिलेख हुँदैन
- सावधानी: `PII_HASH_KEY` परिवर्तन गर्दा सबै खोज hash (`*_hash`) अमान्य हुन्छन्। इन्क्रिप्सन कुञ्जी मात्र परिवर्तन गर्नुहोस्: पुरानो कुञ्जी `PII_PREVIOUS_KEYS` मा सार्नुहोस्, त्यसपछि `pii_reencrypt` चलाउनुहोस्।
- उदाहरण

  ```bash
  uv run manage.py pii_generate_key
  ```

### `pii_reencrypt`

- प्रयोजन: कुञ्जी परिवर्तनपछि अघिल्लो कुञ्जीले इन्क्रिप्ट गरिएको व्यक्तिगत डेटा हालको कुञ्जीले फेरि इन्क्रिप्ट गर्छ। अभिलेखका समूहहरूमाथि Celery कार्यहरूको समूहका रूपमा चल्छ। पहिले नै हालको कुञ्जीमा रहेका अभिलेखहरू जस्ताको तस्तै रहन्छन्।
- आर्गुमेन्टहरू: इन्क्रिप्ट गरिएका व्यक्तिगत डेटा फिल्ड भएको मोडेल (`app_label.Model`, जस्तै `person.Person`)।
- विकल्पहरू: `--chunk=500` (प्रति कार्य अभिलेख), `--dry-run` (अघिल्लो कुञ्जी प्रयोग गर्ने अभिलेख गन्ती मात्र), `--force` (पुष्टि नसोध्ने), `--actor=`।
- अडिट: अभिलेख हुन्छ (batch ID, कार्यको सङ्ख्या / पूर्वावलोकन गन्ती)
- प्रमाणीकरण: कार्यहरूलाई Flower मा पछ्याउनुहोस्। सकिएपछि `--dry-run` ले 0 देखाएमा अघिल्लो कुञ्जी `PII_PREVIOUS_KEYS` बाट हटाउनुहोस्।
- उदाहरण

  ```bash
  uv run manage.py pii_reencrypt person.Person --dry-run
  uv run manage.py pii_reencrypt person.Person --force --actor=ops@example.edu
  ```

## स्थानीयकरण (चरण 0)

### `i18n_missing`

- प्रयोजन: `makemessages` ले जस्तै (फाइल नलेखी) स्रोतबाट अनुवाद गर्न मिल्ने स्ट्रिङहरू निकाल्छ, तिनलाई हरेक क्याटलग (साझा `locale/` र प्रत्येक एपको `locale/`) सँग दाँज्छ र भाषाअनुसार छुटेका स्ट्रिङ (क्याटलगमा नभएका, खाली `msgstr`, fuzzy, फरक placeholder) र अप्रचलित प्रविष्टिहरू सूचीबद्ध गर्छ।
- आर्गुमेन्ट/विकल्पहरू: `[locale]` (एउटा भाषा मात्र, जस्तै `ko`, `zh-hans`, `lo`), `--strict` (स्ट्रिङ छुटेमा निकास कोड 2; CI मा प्रयोग हुन्छ), `--no-extract` (क्याटलग मात्र जाँच्छ, स्रोत स्क्यान गर्दैन)।
- अडिट: अभिलेख हुँदैन
- आवश्यक: GNU gettext (`xgettext`, `msguniq`)।
- उदाहरण

  ```bash
  uv run manage.py i18n_missing --strict
  uv run manage.py i18n_missing lo
  ```

### `i18n_export`

- प्रयोजन: अनुवादकहरूका लागि पाना लेख्छ (`.xlsx` वा `.csv`, एक्सटेन्सनले छानिन्छ)। स्तम्भहरू: `catalog` (क्याटलगको स्थान), `context`, `source` (अङ्ग्रेजी msgid), `source_plural`, `translation`, `note` (मूल कुञ्जी)।
- आर्गुमेन्ट/विकल्पहरू: `{locale} {path}`, `--missing` (अनुवाद नभएका स्ट्रिङ मात्र)।
- अडिट: अभिलेख हुँदैन
- उदाहरण: `uv run manage.py i18n_export ko storage/ko.xlsx --missing`

### `i18n_import`

- प्रयोजन: अनुवादकहरूले भरेको पाना क्याटलग (`.po`) मा फर्काएर लेख्छ र कम्पाइल (`.mo`) गर्छ। क्याटलगमा भएका स्ट्रिङ (उही क्याटलग, सन्दर्भ र अङ्ग्रेजी पाठ) मात्र आयात हुन्छन्; खाली अनुवादहरू छोडिन्छन्।
- आर्गुमेन्ट/विकल्पहरू: `{locale} {path}`, `--dry-run` (लेखिने स्ट्रिङहरू सूचीबद्ध गर्छ), `--actor=`।
- अडिट: अभिलेख हुन्छ (भाषा, अनुवादको सङ्ख्या)
- टिप्पणी: क्याटलगहरू रिपोजिटरीमा रहन्छन्। आयातपछि `.po` परिवर्तनहरू commit गर्नुहोस्।

### `i18n_makemessages`

- प्रयोजन: हरेक क्याटलग स्रोतसँग मेल खाओस् भनेर (ko, zh_Hans, lo) रिपोजिटरीको मूलबाट `makemessages` चलाउँछ। एपको आफ्नै `locale/` भएमा स्ट्रिङहरू त्यहाँ जान्छन्, नत्र साझा `locale/` मा। `.venv`, `tests`, `docs` र यस्तै डाइरेक्टरीहरू छोडिन्छन्।
- विकल्पहरू: Django `makemessages` जस्तै (`-l`, `--no-obsolete`, ...)।
- अडिट: अभिलेख हुँदैन
- उदाहरण: `uv run manage.py i18n_makemessages`

## जाँचहरू (चरण 0)

### `pdf_sample`

- प्रयोजन: फन्ट र PDF सेवा (Gotenberg) सँगको जडान जाँच्न हाङ्गुल, CJK, लाओ, थाई, देवनागरी, सिरिलिक र ल्याटिन लिपि मिसिएको तालिका PDF मा बनाउँछ।
- आर्गुमेन्ट: `[path]` (पूर्वनिर्धारित `pdf-sample.pdf`, निजी फाइल भण्डारण `PRIVATE_MEDIA_ROOT` को सापेक्ष)।
- अडिट: अभिलेख हुँदैन
- असफल भएमा: निकास कोड 1। जडान त्रुटिका लागि `GOTENBERG_URL`, `GOTENBERG_TIMEOUT` र Gotenberg कन्टेनर जाँच्नुहोस्।
- उदाहरण: `uv run manage.py pdf_sample`

### `naming_check`

- प्रयोजन: डेटाबेस स्किमा र स्रोतहरूलाई [नामकरण नियमहरू](../../../development/naming.md) अनुसार जाँच्छ। यसले वास्तविक डेटाबेस क्याटलग (स्किमा `public`, `audit`, `reporting`) का तालिका र स्तम्भका नाम, Ninefruits एपहरूका migration फाइलका नाम, व्यवस्थापन कमान्डका नाम (`context_action`) र अनुवाद क्याटलग (`.po`) का msgid र msgctxt जाँच्छ।
- नियमहरू: snake_case, निषेधित पछिल्ला अंश (`_old`, `_new`, `_backup`, `_tmp`, मिति, अङ्क), भाषा कोड भएका नाम, समय क्षेत्र नभएका समय स्तम्भ (`timestamp without time zone`), boolean स्तम्भका नाम (`is_`, `has_`, `can_` वा क्रियापद), मिति स्तम्भका नाम (`_date`), semantic key जस्ता देखिने msgid (`registration.errors.x`)। Django र प्याकेजहरूले परिभाषित गरेका तालिकाहरू (`django_*`, allauth, Celery beat, `settings`, `cache`, `jobs`, `media` आदि) समावेश हुँदैनन्।
- विकल्पहरू: `--database=` (जाँच्ने डेटाबेस जडान, पूर्वनिर्धारित `default`), `--skip-database` (फाइल जाँच मात्र, डेटाबेस होइन)।
- अडिट: अभिलेख हुँदैन
- निकास कोड: समस्या भेटिएमा 2।
- उदाहरण

  ```bash
  uv run manage.py naming_check
  ```
