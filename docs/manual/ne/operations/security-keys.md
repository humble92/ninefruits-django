# कुञ्जी व्यवस्थापन

- लक्षित पाठक: IT सञ्चालकहरू
- सम्बन्धित: [स्थापना](installation.md), [कमान्ड सन्दर्भ](commands.md), [डिप्लोय जाँचसूची](deployment-checklist.md)

| कुञ्जी | प्रयोजन | हराएमा | परिवर्तन (rotation) |
|---|---|---|---|
| `DJANGO_SECRET_KEY` | सत्र, CSRF, हस्ताक्षर (पासवर्ड रिसेट लिङ्क, इमेल प्रमाणीकरण लिङ्क, सम्झिएका उपकरणका cookie), इमेल दुई-चरण कोडका hash, दुई-चरण गोप्य मान (प्रमाणीकरण एपका TOTP गोप्य मान, रिकभरी कोड) र SSO client secret को इन्क्रिप्सन | सबै प्रयोगकर्ता साइन आउट हुन्छन्, पठाइएका लिङ्कले काम गर्न छोड्छन्, दर्ता गरिएका प्रमाणीकरण एप र रिकभरी कोडले काम गर्न छोड्छन् (प्रति प्रयोगकर्ता दुई-चरण रिसेट चाहिन्छ), SSO client secret फेरि प्रविष्ट गर्नुपर्छ | अघिल्लो कुञ्जी `DJANGO_SECRET_KEY_FALLBACKS` मा राखेर परिवर्तन गर्नुहोस् (तलको प्रक्रिया) |
| `PII_ENCRYPTION_KEY` | राष्ट्रिय परिचयपत्र नम्बरजस्ता व्यक्तिगत डेटाको इन्क्रिप्सन (AES-256-GCM) | **इन्क्रिप्ट गरिएको व्यक्तिगत डेटा पुनःप्राप्त गर्न सकिँदैन** | अघिल्लो कुञ्जी `PII_PREVIOUS_KEYS` मा राखेर परिवर्तन गर्नुहोस् (तलको प्रक्रिया) |
| `PII_HASH_KEY` | व्यक्तिगत डेटाको ठ्याक्कै मिल्ने खोजका hash (HMAC-SHA256) | खोजले काम गर्न छोड्छ (डेटा रहन्छ) | नियमतः परिवर्तन गरिँदैन |

`DJANGO_SECRET_KEY` लाई `uv run python -c "import secrets; print(secrets.token_urlsafe(50))"` बाट र दुईवटा व्यक्तिगत डेटा कुञ्जीलाई `uv run manage.py pii_generate_key` बाट बनाउनुहोस्।

भण्डारणका नियमहरू

- तीनै कुञ्जीका कम्तीमा दुई प्रति सर्भर कन्फिगरेसनबाहिर, गोप्य भण्डार (Vault, क्लाउड secret manager आदि) वा सिल गरिएको अफलाइन भण्डारणमा राख्नुहोस्।
- तिनलाई ब्याकअप फाइलहरूको छेउमा नराख्नुहोस्। चुहिएको डेटाबेस ब्याकअप कुञ्जीबिना पढ्न मिल्नु हुँदैन।
- विकासको `.env` वा परीक्षण सेटिङका कुञ्जीहरू उत्पादनमा कहिल्यै प्रयोग नगर्नुहोस्।
- वेब प्रक्रिया (gunicorn), Celery worker र Celery beat सबैले उही कुञ्जी मान पढ्नुपर्छ। कुञ्जी परिवर्तन गरेपछि तीनैलाई सँगै पुनः सुरु गर्नुहोस्।

## `DJANGO_SECRET_KEY` परिवर्तन

निर्धारित परिवर्तन वा कुञ्जी थाहा पाउने व्यक्तिहरू बदलिँदा यो प्रयोग गर्नुहोस्। यो Django को `SECRET_KEY_FALLBACKS` मा आधारित छ, त्यसैले अघिल्लो कुञ्जी राखिएसम्म कोही पनि साइन आउट हुँदैन। मूल प्रणाली (Laravel) को `APP_PREVIOUS_KEYS` कै तरिका हो।

1. नयाँ कुञ्जी बनाउनुहोस्: `uv run python -c "import secrets; print(secrets.token_urlsafe(50))"`।
2. हालको कुञ्जी `DJANGO_SECRET_KEY_FALLBACKS` मा पहिलो स्थानमा (धेरै भए अल्पविरामले छुट्याएर) र नयाँ कुञ्जी `DJANGO_SECRET_KEY` मा राख्नुहोस्।
   ```
   DJANGO_SECRET_KEY=<new key>
   DJANGO_SECRET_KEY_FALLBACKS=<previous key>
   ```
3. gunicorn, Celery worker र beat पुनः सुरु गर्नुहोस् (Docker: `docker compose restart app worker beat`)।
4. दुई-चरण गोप्य मान र SSO client secret नयाँ कुञ्जीले फेरि इन्क्रिप्ट गर्नुहोस्। `uv run manage.py security_reencrypt_secrets --dry-run` बाट सङ्ख्या जाँच्नुहोस्, `--dry-run` बिना चलाउनुहोस्, त्यसपछि `--dry-run` ले 0 देखाउँछ भनी पुष्टि गर्नुहोस्। यो चरणअघि अघिल्लो कुञ्जी हटाइएमा प्रमाणीकरण एप र रिकभरी कोडले काम गर्न छोड्छन्।
5. अघिल्लो कुञ्जी कति समय राख्ने तय गर्नुहोस्। यी कुरा त्यो राखिएसम्म मात्र मान्य रहन्छन्:

   | वस्तु | अघिल्लो कुञ्जी राखिएसम्म | हटाइएपछि |
   |---|---|---|
   | साइन इन सत्र | परिवर्तनपछिको पहिलो अनुरोधमा नयाँ कुञ्जीमा सारिन्छन् | बीचमा प्रयोग नभएका सत्र मात्र साइन आउट हुन्छन् |
   | पासवर्ड रिसेट लिङ्क, इमेल प्रमाणीकरण लिङ्क | मान्य (3 दिन) | फेरि अनुरोध गर्नुपर्छ |
   | सम्झिएका उपकरणका cookie | मान्य (सुरक्षा सेटिङको सम्झने अवधि, पूर्वनिर्धारित 30 दिन) | अर्को साइन इनमा दुई-चरण प्रमाणीकरण फेरि सोधिन्छ |
   | इमेल दुई-चरण कोड | परिवर्तनभन्दा ठीक अघि पठाइएका कोड मेल खाँदैनन् (10 मिनेट मान्य) | उस्तै |

   कम्तीमा 3 दिन, वा सम्झिएका उपकरण कायम राख्न सम्झने अवधिसम्म राख्नुहोस्।
6. अवधि सकिएपछि अघिल्लो कुञ्जी `DJANGO_SECRET_KEY_FALLBACKS` बाट हटाएर चरण 3 जस्तै पुनः सुरु गर्नुहोस्।
7. अघिल्लो कुञ्जी ब्याकअप अवधारण अवधिसम्म सिल गरेर राख्नुहोस्। पुराना ब्याकअपका दुई-चरण गोप्य मान त्यसैले इन्क्रिप्ट गरिएका हुन्छन्। पुरानो ब्याकअप पुनर्स्थापना गर्दा त्यो कुञ्जी `DJANGO_SECRET_KEY_FALLBACKS` मा राखेर चरण 4 चलाउनुहोस्।

### कुञ्जी चुहिएमा

1. चरण 1 देखि 4 तुरुन्तै चलाउनुहोस् (अघिल्लो कुञ्जी चरण 4 को पुनः इन्क्रिप्सनका लागि मात्र चाहिन्छ)।
2. चरण 4 सकिनेबित्तिकै अघिल्लो कुञ्जी हटाएर पुनः सुरु गर्नुहोस्। हरेक सत्र अन्त्य हुन्छ र पठाइएका लिङ्क र सम्झिएका उपकरण अमान्य हुन्छन् (अपेक्षित नतिजा)।
3. खुला रहेको अवधिका साइन इन र प्रशासनिक कामहरू सुरक्षा लगमा समीक्षा गर्नुहोस् ([अडिट र मर्मतसम्भार](audit-and-maintenance.md))।

## व्यक्तिगत डेटा कुञ्जी परिवर्तन

1. `uv run manage.py pii_generate_key` बाट नयाँ कुञ्जी बनाउनुहोस् (आउटपुटको `PII_ENCRYPTION_KEY` मात्र प्रयोग गर्नुहोस्)।
2. हालको कुञ्जी `PII_PREVIOUS_KEYS` मा (धेरै भए अल्पविरामले छुट्याएर) र नयाँ कुञ्जी `PII_ENCRYPTION_KEY` मा राख्नुहोस्।
3. प्रक्रियाहरूलाई कन्फिगरेसन फेरि पढ्न लगाउनुहोस्: gunicorn र Celery worker पुनः सुरु गर्नुहोस् (Docker: `docker compose restart app worker beat`)।
4. व्यक्तिगत डेटा भएको प्रत्येक मोडेलका लागि `uv run manage.py pii_reencrypt {app.Model} --dry-run` (उदाहरणका लागि `person.Person`) बाट अभिलेखको सङ्ख्या जाँच्नुहोस्, त्यसपछि `--force` बिना चलाउनुहोस् (पुष्टिको जवाफ दिनुहोस्)।
5. Flower ले कार्यहरू सकिएको देखाएपछि र `--dry-run` ले 0 देखाएपछि अघिल्लो कुञ्जी `PII_PREVIOUS_KEYS` बाट हटाउनुहोस्।
6. अघिल्लो कुञ्जी ब्याकअप अवधारण अवधिसम्म सिल गरेर राख्नुहोस् (पुराना ब्याकअप पुनर्स्थापना गर्न चाहिन्छ)।

`PII_HASH_KEY` परिवर्तन गर्दा राखिएका सबै खोज hash गलत हुन्छन्, त्यसैले राष्ट्रिय परिचयपत्र वा राहदानी नम्बरको ठ्याक्कै मिल्ने खोज असफल हुन्छ। नियमतः यसलाई परिवर्तन गरिँदैन।
