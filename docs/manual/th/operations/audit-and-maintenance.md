# ความถูกต้องของบันทึกการตรวจสอบและการบำรุงรักษาตามรอบ

- ผู้อ่าน: ผู้ดูแลระบบไอที เจ้าหน้าที่ความปลอดภัย
- เกี่ยวข้อง: [คู่มือผู้ดูแลระบบ บทที่ 4 การตรวจสอบ](../admin/04-audit.md), [คู่มือคำสั่ง](commands.md), [การสำรองและกู้คืนข้อมูล](backup-restore.md)

## ห่วงโซ่แฮชของบันทึกการตรวจสอบ

ตารางบันทึกการตรวจสอบ (`audit.record_changes` สำหรับการเปลี่ยนแปลงข้อมูล, `audit.activity_log` สำหรับการดำเนินงาน, `audit.security_events` สำหรับเหตุการณ์ด้านความปลอดภัย) เพิ่มข้อมูลได้อย่างเดียว (บังคับด้วยทริกเกอร์) นอกจากนี้ยังมีกลไกที่ช่วย **เปิดเผย** การแก้ไขข้อมูลโดยมิชอบ

- ทุกแถวจะได้รับค่า SHA-256 ของเนื้อหา (`row_hash`) เมื่อถูกเพิ่ม
- `audit_seal` (งานตามกำหนดเวลา `audit.seal` ทุกวันเวลา 03:30) จะเชื่อมแถวใหม่เข้ากับห่วงโซ่ตามลำดับ ID: `chain_hash = SHA-256(previous chain_hash || row_hash)` โดยเรียกฟังก์ชันฐานข้อมูล `audit.seal()` ผ่านการเชื่อมต่อของเจ้าของสคีมา (`migrator`)
- `audit_verify_chain` จะคำนวณแฮชของเนื้อหาและห่วงโซ่ของทุกแถวใหม่ ในแต่ละตารางจะแสดงจำนวนแถวที่ตรวจสอบ แถวที่ผนึกแล้ว จำนวนที่ไม่ตรงกัน และ id แรกที่ไม่ตรงกัน แถวที่เนื้อหาถูกเปลี่ยนจะรายงานเป็น "row mismatch" แถวที่หายไปหรือลำดับเปลี่ยนจะรายงานเป็น "chain mismatch" และคำสั่งจะคืนรหัสสิ้นสุดการทำงาน 2

```bash
uv run manage.py audit_seal
uv run manage.py audit_verify_chain
uv run manage.py audit_verify_chain --table=security_events
```

ข้อควรทราบ

- แถวที่ถูกเปลี่ยนก่อนถูกผนึก (ภายในวันเดียวกัน) ห่วงโซ่จะตรวจจับไม่ได้ จึงต้องผนึกทุกวัน และตรวจสอบก่อนการสำรองข้อมูลและระหว่างการทบทวนด้านความปลอดภัย
- เมื่อการลบ (`audit_prune`) นำแถวที่เก่าที่สุดออก จะไม่ตรวจสอบการเชื่อมโยงของแถวแรกที่เหลืออยู่ (ช่วงที่ถูกลบจะเก็บไว้ในบันทึกการตรวจสอบของคำสั่งลบ)
- มีเพียงผู้ดูแลฐานข้อมูล (เจ้าของสคีมา `app_migrator`) ที่ตั้งค่า `app.audit_maintenance = on` ได้ บทบาทของแอปพลิเคชัน (`app_runtime`) ไม่มีสิทธิ์ UPDATE หรือ DELETE บนตารางบันทึกการตรวจสอบ

## ระยะเวลาเก็บรักษาและการลบ

1. กำหนดระยะเวลาเก็บรักษา (ตัวอย่างเช่น การเปลี่ยนแปลงข้อมูล 3 ปี การดำเนินงาน 5 ปี เหตุการณ์ด้านความปลอดภัย 1 ปี)
2. สำรองข้อมูลก่อนลบ ([การสำรองและกู้คืนข้อมูล](backup-restore.md)) และยืนยันว่าห่วงโซ่สมบูรณ์ด้วย `audit_verify_chain`
3. ตรวจสอบจำนวนด้วย `uv run manage.py audit_prune --before=YYYY-MM-DD --table=record_changes --dry-run` แล้วรันโดยไม่มี `--dry-run` (บันทึกบัญชีของผู้ดำเนินการด้วย `--actor=`) แถวที่ยังไม่ผนึกจะไม่ถูกลบเลย ดังนั้นให้รัน `audit_seal` ก่อน
4. รัน `audit_verify_chain` อีกครั้งหลังการลบ

การลบเองก็ถูกบันทึกไว้: ทุกครั้งที่รันจะบันทึกลงในบันทึกการดำเนินงาน (log `command`) ได้แก่ วันที่ตัดรอบ ตัวเลือก ผู้ดำเนินการ และผู้ใช้ระบบปฏิบัติการ รวมทั้งในแต่ละตาราง **จำนวนแถวที่ลบ ช่วง ID ที่ลบ และ chain_hash ณ จุดรอยต่อ** การลบจริงยังถูกบันทึกเป็นเหตุการณ์ด้านความปลอดภัย `audit.pruned` ด้วย (**การตรวจสอบ > เหตุการณ์ด้านความปลอดภัย**) แถวบันทึกนี้เองก็จะถูกเชื่อมเข้าห่วงโซ่ในการผนึกครั้งถัดไป จุดรอยต่อนี้คือเหตุผลที่ `audit_verify_chain` ไม่ตรวจสอบการเชื่อมโยงของแถวแรกที่เหลืออยู่ การเปรียบเทียบแฮช ณ จุดรอยต่อกับบันทึกการลบช่วยให้ยืนยันได้ว่าช่วงที่ถูกลบตรงกับการลบที่มีบันทึกไว้

## การล้างไฟล์

`uv run manage.py media_prune_orphans --dry-run` จะแสดงรายการแถวสื่อที่ไม่มีเจ้าของแล้ว และไดเรกทอรีที่ไม่มีแถวข้อมูล (`PRIVATE_MEDIA_ROOT/<media id>/`) หากรันโดยไม่มี `--dry-run` จะลบรายการเหล่านั้น ครอบคลุมรูปถ่ายบุคคล เอกสารใบสมัคร ไฟล์ PDF หนังสือรับรอง และหลักฐานการสอบ ควรรันทุกเดือนหรือหลังการลบข้อมูลจำนวนมาก

## การตรวจสุขภาพระบบ

| การตรวจสอบ | วิธี | เมื่อไม่ผ่าน |
|---|---|---|
| สถานะบริการ | `GET /api/v1/health/` (ไม่ต้องเข้าสู่ระบบ สำหรับตัวกระจายโหลดและระบบเฝ้าติดตาม) | `unavailable` (503) เมื่อฐานข้อมูลหรือแคชไม่ตอบสนอง `degraded` (200) เมื่อสัญญาณชีพของตัวจัดกำหนดเวลาเก่ากว่า 5 นาที มิฉะนั้น `ok` เมื่อเข้าสู่ระบบด้วยสิทธิ์ `เข้าใช้แผงผู้ดูแลระบบ` จะแสดงผลการตรวจสอบแต่ละรายการด้วย (`database`, `cache`, `scheduler`) |
| การตรวจสอบเต็มรูปแบบ | `uv run manage.py system_health_check [--json]` | 12 รายการ: คีย์ บทบาทของฐานข้อมูล RLS ไมเกรชัน แคตตาล็อกสิทธิ์ Redis worker ของ Celery Gotenberg ที่จัดเก็บไฟล์ สัญญาณชีพของ beat รหัสสิ้นสุดการทำงาน 2 เมื่อมีรายการใดไม่ผ่าน |
| การตั้งค่าระบบใช้งานจริง | `uv run manage.py check --deploy` | คำเตือนเกี่ยวกับ `DEBUG` การเปลี่ยนเส้นทาง HTTPS, HSTS คุกกี้ที่ปลอดภัย คีย์ลับ |
| ไมเกรชัน | `uv run manage.py migrate --check` | รหัสสิ้นสุดการทำงาน 1 เมื่อมีไมเกรชันที่ยังไม่ได้นำไปใช้ |
| แคตตาล็อกสิทธิ์ | `uv run manage.py security_sync_permissions` | นำรายการสิทธิ์ในโค้ดเข้าสู่ฐานข้อมูล (รันซ้ำได้อย่างปลอดภัย) |
| บริการ PDF | `uv run manage.py pdf_sample` | การเชื่อมต่อ Gotenberg ฟอนต์ |
| คำแปล | `uv run manage.py i18n_missing --strict` | รหัสสิ้นสุดการทำงาน 2 เมื่อมีคำแปลที่ขาดหายไป |
| ห่วงโซ่บันทึกการตรวจสอบ | `uv run manage.py audit_verify_chain` | รหัสสิ้นสุดการทำงาน 2 เมื่อไม่ตรงกัน |
| คิว | Flower, `uv run celery -A config inspect ping` | worker ไม่ตอบสนอง |

เชื่อมระบบเฝ้าติดตามเข้ากับสถานะ HTTP และค่า `status` ของ `/api/v1/health/` ส่วนรายการอื่นให้รันเมื่อนำขึ้นใช้งานและใน [การตรวจสอบตามรอบ](deployment-checklist.md#การตรวจสอบตามรอบ)
