# ข้อมูลอ้างอิงคำสั่งจัดการ (management command)

- ผู้อ่าน: ผู้ดูแลระบบไอที
- ขอบเขต: ทุกคำสั่งที่แอป Ninefruits ในรีโพซิทอรีนี้ลงทะเบียนไว้ (`ninefruits/*/management/commands/`) และคำสั่งในตัวของ Django ที่ใช้ในการดำเนินงาน เมื่อเพิ่มคำสั่งใหม่ ต้องเพิ่มรายการ `### \`command\`` ในเอกสารนี้ด้วย (ทั้ง 16 ภาษา) มิฉะนั้น CI จะล้มเหลว (`tests/tooling/test_command_documentation.py`)

## ข้อตกลงทั่วไป

ทุกคำสั่งรันในรูปแบบ `uv run manage.py {command}` ในสภาพแวดล้อมพัฒนาแบบ Docker ใช้ `docker compose exec app uv run manage.py {command}`

| รายการ | กฎ |
|---|---|
| ชื่อ | `{context}:{action}` ของต้นฉบับกลายเป็น `{context}_{action}` (ชื่อคำสั่งของ Django มี `:` ไม่ได้) ตัวอย่าง: `term:close` → `term_close` |
| บันทึกการตรวจสอบ | คำสั่งที่เปลี่ยนแปลงข้อมูล ("บันทึกการตรวจสอบ: บันทึก" ด้านล่าง) จะเขียนคำสั่ง อาร์กิวเมนต์ ตัวเลือก ผู้ใช้ระบบปฏิบัติการ รหัสสิ้นสุดการทำงาน และผลลัพธ์ลงในบันทึกการดำเนินงาน (log `command`) ทุกครั้งที่รัน ตรวจสอบได้ที่ **การตรวจสอบ > บันทึกการดำเนินงาน** ในแผงผู้ดูแลระบบ |
| รหัสการรัน | การรันแต่ละครั้งจะได้รับรหัสที่ขึ้นต้นด้วย `cmd-` แทนรหัสคำขอ บันทึกการดำเนินงาน การเปลี่ยนแปลงข้อมูลที่เกิดจากการรันนั้น และงาน Celery ที่ส่งออกไปจะมีรหัสเดียวกัน คำถามว่า "คำสั่งใดทำให้เกิดการเปลี่ยนแปลงนี้" จึงตอบได้ด้วยรหัสนี้ `--actor` เป็นค่าที่ผู้ดูแลระบบระบุเอง จึงไม่ถูกใส่ในคอลัมน์ผู้ใช้ของการเปลี่ยนแปลงข้อมูล (ผู้ดำเนินการจริงคือผู้ใช้ระบบปฏิบัติการ) |
| `--actor=<email>` | ใช้ร่วมกันในทุกคำสั่งที่มีบันทึกการตรวจสอบ บันทึกบัญชีผู้ดูแลระบบที่รับผิดชอบ หากระบุอีเมลที่ไม่รู้จัก การรันจะถูกยกเลิก |
| `--dry-run` | แสดงผลลัพธ์โดยไม่เปลี่ยนแปลงสิ่งใด มีในการดำเนินการที่ย้อนกลับได้ยาก |
| `--force` | รันโดยไม่มีการขอยืนยัน (สำหรับงานตามกำหนดเวลาและสคริปต์นำขึ้นใช้งาน) |
| `--reason=` | มีในคำสั่งที่ต้องระบุเหตุผล |
| รหัสสิ้นสุดการทำงาน | 0 สำเร็จ, 1 ล้มเหลวหรือยกเลิก, 2 คำสั่งตรวจสอบพบปัญหา |
| บริบทฐานข้อมูล | ระหว่างที่คำสั่งทำงาน ผู้ดำเนินการของเซสชันฐานข้อมูลจะถูกกำหนดเป็น `system:command:{command}` และปรากฏในการเปลี่ยนแปลงข้อมูล (ทริกเกอร์) |

## คำสั่งในตัวของ Django

### `migrate`

- วัตถุประสงค์: นำไมเกรชันของฐานข้อมูลไปใช้ เป็นตัวครอบคำสั่งของ Django โดย Ninefruits: หากไม่ระบุ `--database` จะใช้การเชื่อมต่อของเจ้าของสคีมา (`migrator` บทบาท `app_migrator`) การเชื่อมต่อของแอปพลิเคชัน (`app_runtime`) ไม่มีสิทธิ์ DDL `showmigrations` และ `sqlmigrate` ก็ใช้การเชื่อมต่อ `migrator` เป็นค่าเริ่มต้นเช่นกัน
- เมื่อใช้: เมื่อติดตั้งครั้งแรกและทุกครั้งที่นำขึ้นใช้งาน (`setup_install` ก็รันคำสั่งนี้ด้วย)
- ตัวเลือก: เหมือนกับ `migrate` ของ Django (`app_label`, `migration_name`, `--plan`, `--check`, `--database`)
- บันทึกการตรวจสอบ: ไม่บันทึก (การเปลี่ยนแปลงสคีมาเก็บไว้ในประวัติไมเกรชัน `django_migrations`)
- ตัวอย่าง

  ```bash
  uv run manage.py migrate
  uv run manage.py migrate --plan
  ```

- เมื่อล้มเหลว: หากเป็นข้อผิดพลาดเรื่องสิทธิ์ ให้ตรวจสอบการเตรียมบทบาทของฐานข้อมูล (`db/sql/roles/`) ใน [คู่มือการติดตั้ง](installation.md)

### `collectstatic`

- วัตถุประสงค์: รวบรวมผลลัพธ์จากการ build ของ Vite (`static/dist/`) และไฟล์สแตติกของ Django และ unfold ไว้ใน `STATIC_ROOT` (`staticfiles/`) เว็บเซิร์ฟเวอร์ (Nginx) ให้บริการไดเรกทอรีนี้
- เมื่อใช้: ทุกครั้งที่นำขึ้นใช้งาน หลัง `npm ci && npm run build`
- ตัวเลือก: `--noinput` (ไม่ถาม), `--clear` (ลบไฟล์เดิมก่อนรวบรวม)
- บันทึกการตรวจสอบ: ไม่บันทึก
- ตัวอย่าง

  ```bash
  npm ci && npm run build
  uv run manage.py collectstatic --noinput
  ```

### `compilemessages`

- วัตถุประสงค์: คอมไพล์ไฟล์คำแปล (`.po`) เป็นไฟล์ `.mo` ที่ใช้ขณะทำงาน ไฟล์ `.mo` ไม่ได้เก็บไว้ในรีโพซิทอรี จึงต้องรันทุกครั้งที่ติดตั้งและนำขึ้นใช้งาน ต้องติดตั้ง `gettext` บนระบบ
- เมื่อใช้: ทุกครั้งที่นำขึ้นใช้งานและหลังแก้ไขไฟล์คำแปล
- ตัวเลือก: `--locale=` (เช่น `ko`, `zh_Hans`, `lo`), `--ignore=.venv`
- บันทึกการตรวจสอบ: ไม่บันทึก
- ตัวอย่าง

  ```bash
  uv run manage.py compilemessages --ignore=.venv
  ```

### `createsuperuser`

- วัตถุประสงค์: **ไม่ใช้** superuser ของ Django ข้ามแคตตาล็อกบทบาทและสิทธิ์และร่องรอยการตรวจสอบ คำสั่งนี้จึงจบด้วยข้อผิดพลาด (รหัสสิ้นสุดการทำงาน 1) และแนะนำให้ใช้ `security_create_administrator`
- ใช้แทน: สร้างผู้ดูแลระบบคนแรกด้วย `security_create_administrator` (รวมการกำหนดบทบาทผู้ดูแลระบบและบันทึกการตรวจสอบ)
- บันทึกการตรวจสอบ: ไม่เกี่ยวข้อง

## การติดตั้งและข้อมูลสาธิต (ระยะที่ 1)

### `setup_install`

- วัตถุประสงค์: การติดตั้งใหม่และการอัปเดต ดำเนินการตามลำดับ: ไมเกรชัน ข้อมูลพื้นฐานที่จำเป็น (แม่แบบบทบาทและการซิงค์สิทธิ์ ประเทศ ภาษา ประเภทรายการรหัส ประเภทหน่วยงาน) การตั้งค่าสถาบัน เกณฑ์ระดับคะแนน โปรไฟล์การติดตั้ง และผู้ดูแลระบบคนแรก รันซ้ำได้อย่างปลอดภัย (ข้อมูลเดิมและค่าที่ผู้ดูแลระบบแก้ไขไว้จะคงอยู่)
- เมื่อใช้: เมื่อติดตั้งครั้งแรกและทุกครั้งที่นำขึ้นใช้งาน
- ตัวเลือก: `--institution-name=`, `--locale=` (ภาษาเริ่มต้น), `--timezone=` (เช่น `Asia/Seoul`), `--profile=` (คีย์ของโปรไฟล์การติดตั้ง ระบุซ้ำได้: `korean-university`, `yust-legacy`), `--grade-scale=` (เกณฑ์ระดับคะแนน `4.5` หรือ `4.3` เปลี่ยนไม่ได้เมื่อกำหนดแล้ว หากว่างจะใช้เกณฑ์ของโปรไฟล์แรก), `--admin-email=`, `--admin-name=`, `--force` (ไม่ถามคำถาม รหัสผ่านผู้ดูแลระบบจะอ่านจาก standard input)
- บันทึกการตรวจสอบ: บันทึก (โปรไฟล์ที่ใช้ มีการสร้างผู้ดูแลระบบหรือไม่)
- ตัวอย่าง

  ```bash
  uv run manage.py setup_install
  echo "$ADMIN_PASSWORD" | uv run manage.py setup_install --force --locale=ko --timezone=Asia/Seoul \
      --institution-name="Demo University" --profile=korean-university \
      --admin-email=admin@example.ac.kr --admin-name="Administrator"
  ```

- การอ่านผลลัพธ์: `DONE` ในแต่ละขั้นตอน `Administrator exists` หมายความว่ามีการกำหนดบทบาทผู้ดูแลระบบอยู่แล้ว จึงข้ามการสร้าง
- เมื่อล้มเหลว: ข้อผิดพลาดว่าไม่มีคีย์หมายความว่าต้องตั้งค่า `DJANGO_SECRET_KEY` และค่าจาก `pii_generate_key` ในสภาพแวดล้อม ไมเกรชันล้มเหลว: ตรวจสอบบทบาทของฐานข้อมูล ([การติดตั้ง](installation.md)) `The grade scale is fixed` หมายความว่า `--grade-scale` ต่างจากเกณฑ์ที่กำหนดไว้แล้ว

### `setup_demo`

- วัตถุประสงค์: สร้างมหาวิทยาลัยสมมติ (หน่วยงาน หลักสูตร อาคารและห้อง ภาคการศึกษาก่อนหน้า ปัจจุบัน และถัดไปรอบวันนี้พร้อมช่วงเวลาดำเนินการ โปรไฟล์มหาวิทยาลัยเกาหลี) แสดงบัญชีสาธิตแบบคงที่ของแต่ละบทบาท (`registrar@demo.test` เป็นต้น รหัสผ่าน `demo-password`) ข้อมูลปริมาณมากสร้างด้วยการเพิ่มแบบกลุ่ม (bulk insert)
- เมื่อใช้: สภาพแวดล้อมสำหรับพัฒนา ฝึกอบรม และสาธิต **จะไม่ทำงานในระบบใช้งานจริง (`DJANGO_ENV=production`) แม้ใช้ `--force`**
- ตัวเลือก: `--size=tiny|small|medium|large` (นักศึกษาประมาณ 20/100/2,000/20,000 คน `tiny` สำหรับการทดสอบและการตรวจสอบอย่างรวดเร็ว), `--seed=` (ค่าเดียวกันให้ข้อมูลเหมือนกัน), `--force` (ไม่ขอยืนยัน)
- `--student-accounts`: สร้างบัญชีให้นักศึกษาที่กำลังศึกษาทุกคน และเขียน `load-accounts.csv` (อีเมล รหัสผ่าน) ลงในที่จัดเก็บส่วนตัว สำหรับการทดสอบโหลด ([การทดสอบโหลด](load-testing.md))
- บันทึกการตรวจสอบ: บันทึก (ขนาด seed ระยะเวลา)
- ตัวอย่าง: `uv run manage.py setup_demo --size=small --seed=42 --force`
- เมื่อล้มเหลว: หากไม่มีข้อมูลพื้นฐานที่จำเป็น บัญชีสาธิตจะถูกข้าม (ไม่มีบทบาท) ให้รัน `setup_install` ก่อน การรันซ้ำบนฐานข้อมูลเดียวกันจะข้ามข้อมูลสาธิตที่มีอยู่แล้ว

## ข้อมูลอ้างอิงและภาคการศึกษา (ระยะที่ 1)

### `reference_import`

- วัตถุประสงค์: นำเข้าข้อมูลอ้างอิงจาก CSV ด้วยกฎเดียวกับ **นำเข้า CSV** ในแผงผู้ดูแลระบบ (แถวจะค้นหาด้วยรหัสและปรับปรุง ช่องคำแปลที่ว่างจะคงค่าเดิม แถวที่ล้มเหลวจะเก็บแยกไว้)
- อาร์กิวเมนต์: `type` หนึ่งใน `org_units`, `programs`, `buildings`, `rooms`, `lookup_values`, `students` (ระเบียนนักศึกษา), `instructors`, `courses` (ฉบับรายวิชา), `registration_holds` (การระงับการลงทะเบียน) / `file` ไฟล์ CSV แบบ UTF-8 ที่มีแถวหัวตาราง
- ตัวเลือก: `--actor=` (จำเป็น การนำเข้าจะบันทึกภายใต้บัญชีนี้ และผลลัพธ์ปรากฏในหน้าจอ **ประวัติการนำเข้า CSV** ของบัญชีนั้น), `--chunk=100` (จำนวนแถวต่องาน Celery), `--dry-run` (ตรวจสอบแถวหัวตารางและนับจำนวนแถวเท่านั้น)
- บันทึกการตรวจสอบ: บันทึก (ประเภท ชื่อไฟล์ จำนวนแถว หมายเลขการนำเข้า จำนวนแถวที่ล้มเหลว)
- รูปแบบคอลัมน์: [คู่มือผู้ดูแลระบบ บทที่ 9](../admin/09-csv-import.md)
- รหัสสิ้นสุดการทำงาน: เมื่องานทำงานทันที (worker แบบ eager) ผลลัพธ์จะแสดงออกมา และแถวที่ล้มเหลวจะให้รหัส 2 เมื่อการนำเข้าเพียงถูกนำเข้าคิว จะได้ 0 ผลลัพธ์และไฟล์ CSV ของแถวที่ล้มเหลวอยู่ที่ **ข้อมูลอ้างอิง > ประวัติการนำเข้า CSV** ในแผงผู้ดูแลระบบ
- ตัวอย่าง: `uv run manage.py reference_import org_units /srv/import/org-units.csv --actor=admin@example.ac.kr --dry-run`

### `term_inspect`

- วัตถุประสงค์: แสดงภาคการศึกษาที่กำลังดำเนินอยู่และช่วงเวลาดำเนินการที่เปิดอยู่ (ประเภท ภาคการศึกษา ช่วงการเรียน ชื่อ ผู้มีสิทธิ์ เวลาปิด) ณ จุดเวลาหนึ่ง ใช้ตรวจสอบการตั้งค่าภาคการศึกษาและช่วงเวลาดำเนินการ หรือคำถามเช่น "ทำไมการลงทะเบียนเรียนยังไม่เปิด"
- ตัวเลือก: `--at=` (ค่าเริ่มต้นคือขณะนี้ เช่น `"2027-02-15 09:00"` หากไม่ระบุเขตเวลาจะใช้เขตเวลาของเซิร์ฟเวอร์ (UTC) `"2027-02-15 09:00 Asia/Seoul"` หรือ `2027-02-15T09:00+09:00` ระบุเขตเวลา)
- บันทึกการตรวจสอบ: ไม่บันทึก (อ่านอย่างเดียว)
- การอ่านผลลัพธ์: วันที่ตัดสินตามเขตเวลาของสถาบัน ช่วงเวลาดำเนินการของภาคการศึกษาที่อยู่ในแผนหรือเก็บถาวรแล้วจะไม่เปิดเลย เวลาปิดแสดงตามเขตเวลาของสถาบัน

## ความปลอดภัย (ระยะที่ 0, 2)

### `security_create_administrator`

- วัตถุประสงค์: สร้างบัญชีที่มีบทบาทผู้ดูแลระบบ โดยปกติ `setup_install` เป็นผู้เรียกใช้
- ตัวเลือก: `--email=`, `--name=`, `--password-stdin` (รหัสผ่านจาก standard input จำเป็นสำหรับการรันแบบไม่โต้ตอบ)
- บันทึกการตรวจสอบ: บันทึก (ID ของผู้ใช้ที่สร้าง)
- ตัวอย่าง: `uv run manage.py security_create_administrator --email=admin@example.ac.kr --name="Administrator"`
- ตัวอย่าง (ไม่โต้ตอบ): `printf '%s\n' "$ADMIN_PASSWORD" | uv run manage.py security_create_administrator --email=admin@example.ac.kr --name="Administrator" --password-stdin`
- เมื่อล้มเหลว: `system_administrator role is missing` หมายความว่าต้องรัน `setup_install` ก่อน รหัสผ่านต้องมีอย่างน้อย 12 ตัวอักษร

### `security_sync_permissions`

- วัตถุประสงค์: ปรับรายการสิทธิ์ในฐานข้อมูลให้ตรงกับแคตตาล็อกสิทธิ์ในโค้ด สิทธิ์ใหม่จะถูกสร้าง สิทธิ์ที่ไม่มีในแคตตาล็อกจะถูกลบ (และนำออกจากทุกบทบาท) บทบาทของระบบได้รับสิทธิ์ทั้งหมดเสมอ
- เมื่อใช้: หลังนำขึ้นใช้งาน (`setup_install` ทำในขั้นตอนข้อมูลพื้นฐานที่จำเป็น)
- ตัวเลือก: `--dry-run` (แสดงเฉพาะรายการที่จะสร้าง/ลบ), `--force` (ข้ามการยืนยันการลบ)
- บันทึกการตรวจสอบ: บันทึก (สิทธิ์ที่สร้าง/ลบ)
- การอ่านผลลัพธ์: บรรทัด `create` และ `delete` จะมีการขอยืนยันเมื่อมีการลบ
- เมื่อล้มเหลว: การตอบ "no" ในการยืนยันจะจบด้วยรหัส 1 และไม่เปลี่ยนแปลงสิ่งใด

### `security_reencrypt_secrets`

- วัตถุประสงค์: หลังเปลี่ยน `DJANGO_SECRET_KEY` จะเข้ารหัสข้อมูลลับที่ป้องกันด้วยคีย์ที่สืบทอดจากคีย์นั้น (ข้อมูลลับ TOTP ของแอปยืนยันตัวตน seed ของรหัสกู้คืน ข้อมูลลับไคลเอนต์ของ SSO) ใหม่ด้วยคีย์ใหม่ จนกว่าจะรัน ข้อมูลเหล่านี้จะอ่านด้วยคีย์เดิมใน `DJANGO_SECRET_KEY_FALLBACKS` ให้รันก่อนนำคีย์เดิมออก ([การจัดการคีย์](security-keys.md))
- อาร์กิวเมนต์/ตัวเลือก: `--dry-run` (นับเฉพาะข้อมูลลับที่ยังเข้ารหัสด้วยคีย์เดิม)
- บันทึกการตรวจสอบ: บันทึก (จำนวน)
- การอ่านผลลัพธ์: `Dry run: 0 authenticator(s) and 0 SSO client secret(s) use a previous key.` หมายความว่านำคีย์เดิมออกได้ `cannot be decrypted` หมายความว่ามีค่าที่อ่านด้วยคีย์ที่ตั้งค่าไว้ไม่ได้: ใส่คีย์เดิมใน `DJANGO_SECRET_KEY_FALLBACKS` แล้วรันอีกครั้ง
- ตัวอย่าง: `uv run manage.py security_reencrypt_secrets --dry-run`

### `security_reset_mfa`

- วัตถุประสงค์: รีเซ็ตการยืนยันตัวตนแบบสองขั้นตอนของผู้ใช้ (แอปยืนยันตัวตน รหัสทางอีเมล รหัสกู้คืน อุปกรณ์ที่จดจำไว้) ผู้ใช้จะลงทะเบียนใหม่ในการเข้าสู่ระบบครั้งถัดไป ใช้เมื่อไม่มีผู้ดูแลระบบคนใดเข้าสู่แผงผู้ดูแลระบบได้ (เช่น ผู้ดูแลระบบเพียงคนเดียวทำโทรศัพท์หาย) กรณีอื่นให้ใช้ **ผู้ใช้ > รีเซ็ตการยืนยันตัวตนแบบสองขั้นตอน** ในแผงผู้ดูแลระบบ
- อาร์กิวเมนต์/ตัวเลือก: `{user}` อีเมลผู้ใช้, `--reason=` (จำเป็น), `--actor=` (จำเป็น ผู้ดูแลระบบที่ตัดสินใจให้รีเซ็ต)
- บันทึกการตรวจสอบ: บันทึก (ทั้งในบันทึกการดำเนินงานและบันทึกความปลอดภัย พร้อมเหตุผล)
- ตัวอย่าง: `uv run manage.py security_reset_mfa admin@example.ac.kr --reason="Phone lost, identity verified by phone call" --actor=it-lead@example.ac.kr`

### `security_unlock_user`

- วัตถุประสงค์: ปลดล็อกบัญชีที่ถูกล็อกเพราะใส่รหัสผ่านผิดซ้ำ ๆ ก่อนครบระยะเวลาล็อก เหมือนกับ **ผู้ใช้ > ปลดล็อกการเข้าสู่ระบบ** ในแผงผู้ดูแลระบบ
- อาร์กิวเมนต์/ตัวเลือก: `{user}` อีเมลผู้ใช้, `--reason=` (จำเป็น)
- บันทึกการตรวจสอบ: บันทึก (ในบันทึกความปลอดภัยด้วย)
- การอ่านผลลัพธ์: `The account is not locked.` หมายความว่าไม่มีการเปลี่ยนแปลงใด
- หมายเหตุ: เกณฑ์การล็อก (จำนวนครั้งที่ล้มเหลว ระยะเวลาล็อก) ตั้งค่าที่ **การตั้งค่า > วิธีเข้าสู่ระบบ** ในแผงผู้ดูแลระบบ

### `people_find_duplicates`

- วัตถุประสงค์: แสดงรายการบุคคลที่น่าจะเป็นคนเดียวกัน เกณฑ์คือเลขประจำตัวประชาชนเหมือนกัน (แฮชการค้นหา) หรือชื่อแบบอักษรโรมันและวันเกิดเหมือนกัน ไม่รวมบุคคลที่ถูกรวมแล้ว

- รหัสสิ้นสุดการทำงาน: 2 เมื่อมีรายการที่อาจซ้ำ
- การดำเนินการต่อ: ตรวจสอบแต่ละกลุ่มที่ **บุคคล** ในแผงผู้ดูแลระบบ หากเป็นคนเดียวกัน ให้รัน **รวมข้อมูลซ้ำ** จากหน้าของบุคคลที่จะนำออก การรวมย้อนกลับไม่ได้ ([คู่มือผู้ดูแลระบบ บทที่ 14](../admin/14-merge-and-invitations.md))
- ตัวอย่าง: `uv run manage.py people_find_duplicates --limit=50`

## การรับสมัคร (ระยะที่ 3)

### `admission_matriculate`

- วัตถุประสงค์: สร้างระเบียนนักศึกษา (รหัสนักศึกษาใหม่) ให้ผู้สมัครที่ยืนยันสิทธิ์แล้วของรอบรับสมัคร เหมือนกับ **สร้างระเบียนนักศึกษา** แบบครั้งละหลายรายการที่ **การรับสมัคร > ใบสมัคร** ในแผงผู้ดูแลระบบ (`MatriculateApplicant`) ผู้สมัครแต่ละรายดำเนินการแยกกัน ความล้มเหลวหนึ่งรายจึงไม่หยุดรายอื่น
- อาร์กิวเมนต์/ตัวเลือก: `cycle` รหัสรอบรับสมัคร, `--term=` (จำเป็น รหัสภาคการศึกษาที่เข้าศึกษา เช่น `2027-SP` วันที่เข้าศึกษาคือวันแรกของภาคการศึกษา), `--actor=` (จำเป็น บัญชีที่มีสิทธิ์ `สร้างระเบียนนักศึกษาให้ผู้ได้รับคัดเลือก` จะดำเนินการเฉพาะผู้สมัครในขอบเขตของบัญชีนั้น), `--dry-run` (แสดงรายการเท่านั้น)
- บันทึกการตรวจสอบ: บันทึก (รอบรับสมัคร ภาคการศึกษา จำนวนผู้มีสิทธิ์ จำนวนที่สร้าง เลขที่ใบสมัครที่ล้มเหลว) ผู้สมัครแต่ละรายยังได้รับบันทึกการดำเนินงาน (`application.matriculated`)
- รหัสสิ้นสุดการทำงาน: 1 เมื่อไม่รู้จักรหัสรอบรับสมัครหรือภาคการศึกษา หรือไม่มี `--actor` 2 เมื่อมีผู้สมัครที่ล้มเหลว
- ตัวอย่าง: `uv run manage.py admission_matriculate DEMO-2027-REG --term=2027-SP --actor=admissions@example.ac.kr --dry-run`
- เมื่อล้มเหลว: `Only accepted offers without a student record ...` หมายความว่าผู้สมัครมีระเบียนแล้วหรือยังไม่ได้ยืนยันสิทธิ์ `The program is not in effect on the admission date.` หมายความว่าหลักสูตรไม่มีผลในวันที่เข้าศึกษา (ตรวจสอบช่วงเวลามีผลของหลักสูตรที่ ข้อมูลอ้างอิง > หลักสูตร) `not in your scope` หมายความว่าใบสมัครอยู่นอกขอบเขตของบัญชี `--actor`

### `admission_expire_drafts`

- วัตถุประสงค์: ทำเครื่องหมาย **หมดอายุ** ให้ใบสมัครฉบับร่างของรอบรับสมัครที่ปิดแล้ว และฉบับร่างที่ไม่มีการเปลี่ยนแปลงตามระยะเวลาที่ตั้งไว้ (**การตั้งค่า > การรับสมัคร > ฉบับร่างที่ไม่มีการแก้ไขหมดอายุหลัง (วัน)** ค่าเริ่มต้น 90) ใบสมัครที่หมดอายุจะไม่ขัดขวางการสมัครใหม่ในรอบเดียวกันอีก
- เมื่อใช้: ตามกำหนดเวลาทุกวันเวลา 03:10 (งาน Celery beat `admission.expire_drafts` รันคำสั่งนี้)
- ตัวเลือก: `--dry-run` (นับเท่านั้น)
- บันทึกการตรวจสอบ: บันทึก (จำนวนที่หมดอายุ)
- ตัวอย่าง: `uv run manage.py admission_expire_drafts --dry-run`

## กลุ่มเรียน (ระยะที่ 4)

### `section_copy`

- วัตถุประสงค์: เริ่มวางแผนภาคการศึกษาใหม่จากกลุ่มเรียนของภาคการศึกษาก่อนหน้า เหมือนกับ **กลุ่มเรียน > คัดลอกจากภาคการศึกษาอื่น** ในแผงผู้ดูแลระบบ (`CopySections`) คัดลอกกลุ่มเรียนที่ไม่ได้ถูกยกเลิกเป็นฉบับร่าง พร้อมอาจารย์ผู้สอน (หากยังปฏิบัติงานอยู่) เวลาเรียนและห้อง การจัดสรรที่นั่ง (เวลาเปิดให้ทุกคนเลื่อนตามผลต่างของวันเริ่มภาคการศึกษา) และประมวลรายวิชา (เป็นฉบับร่างที่ไม่เผยแพร่) ฉบับรายวิชาจะถูกแทนด้วยฉบับที่มีผล ณ วันเริ่มช่วงการเรียนใหม่
- อาร์กิวเมนต์/ตัวเลือก: `from-term`, `to-term` รหัสภาคการศึกษา (เช่น `2026-FA`), `--org-unit=` (เฉพาะกลุ่มเรียนของรหัสหน่วยงานนี้ ระบุซ้ำได้), `--dry-run` (คัดลอกในทรานแซกชันแล้วย้อนกลับ รายงานจึงตรงกับความจริง), `--actor=` (จำเป็น คัดลอกเฉพาะกลุ่มเรียนภายในขอบเขตสิทธิ์ `วางแผนกลุ่มเรียน` ของบัญชีนั้น)
- บันทึกการตรวจสอบ: บันทึก (ภาคการศึกษาต้นทางและปลายทาง จำนวนที่คัดลอก ข้าม และต้องตรวจสอบ การคัดลอกจริงยังบันทึกเหตุการณ์การดำเนินงาน `sections.copied`)
- การอ่านผลลัพธ์: `skipped` หมายความว่าภาคการศึกษาปลายทางมีรหัสกลุ่มเรียนเดียวกันอยู่แล้ว หรือไม่มีฉบับรายวิชาที่มีผล `note` หมายความว่ากลุ่มเรียนถูกคัดลอกแต่มีบางอย่างถูกละไว้ (คัดลอกโดยไม่มีห้องเพราะห้องไม่ว่าง อาจารย์ผู้สอนที่เกษียณแล้ว เป็นต้น) ช่วงการเรียนจับคู่ด้วยรหัส หากไม่มี กลุ่มเรียนจะเข้าไปอยู่ในช่วงการเรียนเต็มภาคการศึกษา
- รหัสสิ้นสุดการทำงาน: 1 สำหรับรหัสภาคการศึกษาที่ไม่รู้จักหรือไม่มี `--actor`
- ตัวอย่าง: `uv run manage.py section_copy 2026-FA 2027-FA --actor=academic@example.ac.kr --dry-run`

### `schedule_check_conflicts`

- วัตถุประสงค์: ตรวจสอบกลุ่มเรียนของภาคการศึกษาก่อนเผยแพร่ตารางเรียน การจองห้องและอาจารย์ผู้สอนซ้อนกันถูกป้องกันโดยฐานข้อมูลอยู่แล้ว คำสั่งนี้ค้นหาปัญหาที่ฐานข้อมูลยอมให้ผ่าน: จำนวนรับเกินความจุของห้อง ฉบับรายวิชาที่ไม่มีผล ณ วันเริ่มช่วงการเรียน อาจารย์ผู้สอนที่เกษียณแล้ว การจัดสรรที่นั่งเกินจำนวนรับ วันที่เรียนอยู่นอกช่วงการเรียน นอกจากนี้ยังตรวจสอบห้องชนกันในข้อมูลที่เข้ามาโดยไม่มีข้อจำกัด เช่น การกู้คืนข้อมูลสำรอง
- อาร์กิวเมนต์: `term` รหัสภาคการศึกษา
- บันทึกการตรวจสอบ: ไม่บันทึก (อ่านอย่างเดียว)
- รหัสสิ้นสุดการทำงาน: 2 เมื่อมีปัญหา 1 สำหรับรหัสภาคการศึกษาที่ไม่รู้จัก กลุ่มเรียนที่ยังไม่มีอาจารย์ผู้สอน ห้อง หรือเวลาเรียน จะแสดงเพื่อเป็นข้อมูลเท่านั้น (`Note`)
- ตัวอย่าง: `uv run manage.py schedule_check_conflicts 2027-SP`

## การลงทะเบียนเรียน (ระยะที่ 5)

### `registration_preflight`

- วัตถุประสงค์: ตรวจสอบภาคการศึกษาก่อนเปิดการลงทะเบียนเรียน แสดงช่วงลงทะเบียนเรียนและช่วงเพิ่ม/ลดรายวิชา ชุดกฎ จำนวนกลุ่มเรียนที่เผยแพร่แล้ว กลุ่มเรียนที่มีจำนวนรับ 0 การจัดสรรที่นั่งเกินจำนวนรับ ฉบับรายวิชาที่ไม่มีผล ณ วันเริ่มช่วงการเรียน จำนวนนักศึกษาที่กำลังศึกษาซึ่งไม่อยู่ในเกณฑ์หน่วยกิตใด และจำนวนนักศึกษาที่ถูกระงับการลงทะเบียน
- อาร์กิวเมนต์: `term` รหัสภาคการศึกษา (เช่น `2027-SP`)
- บันทึกการตรวจสอบ: ไม่บันทึก (อ่านอย่างเดียว)
- รหัสสิ้นสุดการทำงาน: 2 เมื่อมีปัญหา การไม่มีชุดกฎแสดงเป็นข้อมูล ไม่ถือเป็นปัญหา (ใช้ค่าเริ่มต้นของกฎ)
- ตัวอย่าง: `uv run manage.py registration_preflight 2027-SP`

### `registration_simulate`

- วัตถุประสงค์: แสดงทีละกฎว่าจะเกิดอะไรขึ้นหากนักศึกษาลงทะเบียนกลุ่มเรียนนั้นในขณะนี้ (หรือ ณ เวลาที่กำหนด) ไม่มีการบันทึกใด ๆ และไม่บันทึกการพยายาม ใช้สำหรับคำถาม "ทำไมจึงลงทะเบียนไม่ได้"
- อาร์กิวเมนต์: `student-number` รหัสนักศึกษา, `section` `course code-section code` (เช่น `CSE2010-01`)
- ตัวเลือก: `--term=` (รหัสภาคการศึกษา ค่าเริ่มต้นคือภาคการศึกษาล่าสุดที่มีกลุ่มเรียนนั้น), `--at=` (เวลาที่ประเมิน เช่น `"2027-02-10 10:00 Asia/Seoul"`)
- บันทึกการตรวจสอบ: ไม่บันทึก (อ่านอย่างเดียว)
- การอ่านผลลัพธ์: ผ่าน/ไม่ผ่าน ไม่อนุญาต/แจ้งเตือน และข้อความของแต่ละกฎ กฎที่มีการอนุญาตพิเศษจะแสดงว่าไม่ผ่านแต่ไม่ปิดกั้น จำนวนรับแสดงแยกไว้ใต้ตารางกฎ
- รหัสสิ้นสุดการทำงาน: 2 เมื่อการลงทะเบียนจะถูกปฏิเสธ
- ตัวอย่าง: `uv run manage.py registration_simulate 202612345 CSE2010-01 --at="2027-02-10 10:00 Asia/Seoul"`

### `waitlist_promote`

- วัตถุประสงค์: ลงทะเบียนนักศึกษาในรายชื่อสำรองตามลำดับสำหรับกลุ่มเรียนที่มีที่นั่งว่าง กฎทุกข้อจะถูกตรวจสอบอีกครั้งเมื่อเลื่อนขึ้น รายชื่อสำรองที่ไม่ผ่านกฎจะถูกนำออกจากรายชื่อสำรอง (พร้อมบันทึกเหตุผล) รายชื่อสำรองของกลุ่มเรียนที่ช่วงลงทะเบียนเรียนและช่วงเพิ่ม/ลดรายวิชาปิดแล้วทั้งคู่จะหมดอายุ นักศึกษาจะได้รับผลทางอีเมล
- อาร์กิวเมนต์/ตัวเลือก: `term?` รหัสภาคการศึกษา (ค่าเริ่มต้น: ทุกภาคการศึกษาที่มีรายชื่อสำรอง), `--actor=`
- บันทึกการตรวจสอบ: บันทึก (จำนวนกลุ่มเรียน ที่เลื่อนขึ้น ที่นำออก ที่หมดอายุ)
- เมื่อใช้: เมื่อมีการลดรายวิชา ถอนรายวิชา หรือปล่อยการจัดสรรที่นั่ง กลุ่มเรียนที่ได้รับผลกระทบจะถูกดำเนินการทันทีโดยงานในคิว คำสั่งนี้เป็นตาข่ายนิรภัยตามกำหนดเวลารายชั่วโมงที่จัดการสิ่งที่ตกหล่น
- ตัวอย่าง: `uv run manage.py waitlist_promote 2027-SP --actor=registrar@example.ac.kr`

### `registration_release_reserved_seats`

- วัตถุประสงค์: ทำเครื่องหมายการจัดสรรที่นั่งที่เลยเวลาเปิดให้ทุกคนแล้ว (เช่น ที่นั่งสำรองสำหรับนักศึกษาวิชาเอก) ว่าดำเนินการแล้ว และนำงานเลื่อนจากรายชื่อสำรองของกลุ่มเรียนเหล่านั้นเข้าคิว ที่นั่งสำรองกลายเป็นที่นั่งทั่วไปในการคำนวณทันทีที่เลยเวลาเปิด คำสั่งนี้จึงเพียงส่งต่อที่นั่งให้รายชื่อสำรอง
- บันทึกการตรวจสอบ: ไม่บันทึก (ทำงานทุก 5 นาที ผลการเลื่อนขึ้นอยู่ในประวัติการลงทะเบียน)
- เมื่อใช้: ตามกำหนดเวลา (ทุก 5 นาที งาน Celery beat `registration.release_reserved_seats`) งานเลื่อนขึ้นคือ `registration.promote_waitlist` ต่อกลุ่มเรียน (ครั้งละหนึ่งงานต่อกลุ่มเรียนผ่านล็อก Redis)
- ตัวอย่าง: `uv run manage.py registration_release_reserved_seats`

## ผลการเรียน (ระยะที่ 6)

### `term_close`

- วัตถุประสงค์: ปิดภาคการศึกษา เกรดทั้งหมดในภาคการศึกษาต้องยืนยันแล้ว สำหรับนักศึกษาแต่ละกลุ่ม (100 คน) จะคำนวณบันทึกผลรายภาคการศึกษา (หน่วยกิต เกรดเฉลี่ยรายภาคและสะสม) และกำหนดสถานภาพทางวิชาการ (ปกติ รอพินิจ พิจารณาพ้นสภาพ) และสิทธิ์ได้รับเกียรตินิยม (งาน `grading.close_term_records` ของ chord ใน Celery) จากนั้นงานปิดท้าย `grading.finish_term_close` จะจัดอันดับเกียรตินิยมต่อหลักสูตร ปิดบันทึกผลรายภาคการศึกษาเป็นบันทึกทางการ และตั้งภาคการศึกษาเป็น **ปิดผลการเรียน** ความคืบหน้าเก็บไว้ใน `job_batches` และแสดงเหนือรายการ **ผลการเรียน > บันทึกผลรายภาคการศึกษา** เมื่อเสร็จ เจ้าหน้าที่ผู้เริ่มจะได้รับอีเมล เหมือนกับ **ผลการเรียน > บันทึกผลรายภาคการศึกษา > ปิดภาคการศึกษา** ในแผงผู้ดูแลระบบ
- อาร์กิวเมนต์/ตัวเลือก: `term` รหัสภาคการศึกษา, `--dry-run` (ตรวจสอบเพียงว่าปิดภาคการศึกษาได้หรือไม่), `--reason=` (เหตุผลที่เก็บไว้ในบันทึก), `--actor=`
- บันทึกการตรวจสอบ: บันทึก (จำนวนนักศึกษา จำนวนกลุ่มเรียนที่มีเกรดยังไม่ยืนยัน id ของ batch) เมื่อการปิดเสร็จ บันทึกการตรวจสอบ `term.closed` จะเก็บจำนวนรอพินิจ พิจารณาพ้นสภาพ และเกียรตินิยม
- รหัสสิ้นสุดการทำงาน: 2 เมื่อบางกลุ่มเรียนมีเกรดที่ยังไม่ยืนยัน (แสดงจำนวนที่ยังไม่ยืนยันต่อกลุ่มเรียน) 1 เมื่อภาคการศึกษาไม่อยู่ในสถานะเผยแพร่
- เมื่อใช้: หลังการกรอกและยืนยันเกรดเสร็จสิ้น ติดตาม batch ใน Flower และในหน้าจอบันทึกผลรายภาคการศึกษา หากไม่มี worker ของ Celery สถานะภาคการศึกษาจะไม่เปลี่ยน กลุ่มที่ล้มเหลวด้วยข้อผิดพลาดของฐานข้อมูลจะลองใหม่ได้สูงสุด 3 ครั้ง หากยังล้มเหลว batch จะคงสถานะล้มเหลวและภาคการศึกษาจะไม่เปลี่ยน (แก้ไขสาเหตุแล้วรันอีกครั้ง การรันซ้ำให้ผลเหมือนเดิม)
- ตัวอย่าง: `uv run manage.py term_close 2026-FA --dry-run`, `uv run manage.py term_close 2026-FA --reason="Fall 2026 grades closed" --actor=registrar@example.ac.kr`

### `grades_recalculate`

- วัตถุประสงค์: คำนวณบันทึกผลรายภาคการศึกษา (หน่วยกิต เกรดเฉลี่ยรายภาคและสะสม) ใหม่จากเกรดที่ยืนยันแล้ว ใช้เพื่อนำนโยบายการวัดผลที่เปลี่ยนแปลง (จำนวนทศนิยมของเกรดเฉลี่ย การจัดการการเรียนซ้ำ) ไปใช้กับภาคการศึกษาที่ผ่านมา สถานภาพทางวิชาการและเกียรตินิยมคงค่าที่ตัดสินไว้ตอนปิดภาคการศึกษา การแก้ไขเกรดที่อนุมัติแล้วจะคำนวณนักศึกษาคนนั้นใหม่โดยอัตโนมัติ จึงไม่ต้องใช้คำสั่งนี้
- ตัวเลือก: `--term=` (นักศึกษาที่มีเกรดในภาคการศึกษานั้น ตั้งแต่ภาคการศึกษานั้นเป็นต้นไป), `--student-number=` (นักศึกษาหนึ่งคน), `--reason=` (จำเป็น), `--actor=`
- บันทึกการตรวจสอบ: บันทึก (จำนวนนักศึกษา เหตุผล)
- รหัสสิ้นสุดการทำงาน: 1 เมื่อไม่มีเหตุผล หรือรหัสภาคการศึกษาหรือรหัสนักศึกษาที่ไม่รู้จัก
- ตัวอย่าง: `uv run manage.py grades_recalculate --term=2026-SP --reason="GPA changed to three decimal places"`

### `grades_remind_missing`

- วัตถุประสงค์: ส่งอีเมลถึงอาจารย์ผู้สอนของกลุ่มเรียนที่ยังไม่ได้ส่งเกรด (ยังไม่กรอกหรือบันทึกเป็นฉบับร่าง) กลุ่มเรียนจะรวมเป็นข้อความเดียวต่ออาจารย์ผู้สอนหนึ่งคน
- อาร์กิวเมนต์/ตัวเลือก: `term` รหัสภาคการศึกษา, `--dry-run` (แสดงเป้าหมายโดยไม่ส่ง), `--actor=`
- บันทึกการตรวจสอบ: บันทึก (จำนวนกลุ่มเรียน อาจารย์ผู้สอน ข้อความที่ส่ง)
- เมื่อใช้: ไม่กี่วันก่อนช่วงกรอกเกรดจะปิด เพิ่มในกำหนดเวลาหากจำเป็น
- ตัวอย่าง: `uv run manage.py grades_remind_missing 2026-FA --dry-run`

## การประเมินรายวิชา (ระยะที่ 7)

### `evaluation_remind`

- วัตถุประสงค์: ส่งอีเมลถึงนักศึกษาที่ยังมีรายวิชาที่ยังไม่ได้ประเมินขณะที่ช่วงประเมินรายวิชาเปิดอยู่ รายวิชาที่เหลือจะรวมเป็นข้อความเดียวต่อนักศึกษาหนึ่งคน (ในภาษาของผู้รับ)
- อาร์กิวเมนต์/ตัวเลือก: `term` รหัสภาคการศึกษา, `--dry-run` (จำนวนนักศึกษาเป้าหมายเท่านั้น ไม่ส่ง), `--actor=`
- บันทึกการตรวจสอบ: บันทึก (จำนวนนักศึกษาเป้าหมาย ข้อความที่ส่ง)
- รหัสสิ้นสุดการทำงาน: 1 สำหรับรหัสภาคการศึกษาที่ไม่รู้จัก
- เมื่อใช้: หนึ่งหรือสองครั้งระหว่างช่วงประเมิน เพิ่มในกำหนดเวลาหากจำเป็น
- ตัวอย่าง: `uv run manage.py evaluation_remind 2026-FA --dry-run`

### `evaluation_publish_results`

- วัตถุประสงค์: ประกาศผลการประเมินรายวิชาของภาคการศึกษาให้อาจารย์ผู้สอน เหมือนกับ **การประเมินรายวิชา > การประเมินประจำภาคการศึกษา > ประกาศผล** ในแผงผู้ดูแลระบบ แม้หลังประกาศผลแล้ว ผลจะมองเห็นได้เฉพาะกลุ่มเรียนที่ถึงจำนวนผู้ตอบและอัตราการตอบขั้นต่ำ
- อาร์กิวเมนต์/ตัวเลือก: `term` รหัสภาคการศึกษา, `--actor=` (บัญชีที่มีสิทธิ์ `จัดการแบบประเมิน การประเมินประจำภาคการศึกษา และการประกาศผล` บันทึกเป็นผู้ประกาศ)
- บันทึกการตรวจสอบ: บันทึก (จำนวนผลตอบกลับ ประกาศผลแล้วหรือยัง) บันทึกการดำเนินงาน `evaluation.published`
- รหัสสิ้นสุดการทำงาน: 1 สำหรับรหัสภาคการศึกษาที่ไม่รู้จักหรือภาคการศึกษาที่ไม่มีการประเมินรายวิชา
- เมื่อใช้: หลังช่วงประเมินและการดำเนินการเรื่องเกรดเสร็จสิ้น ภาคการศึกษาที่ประกาศผลแล้วจะไม่ถูกเปลี่ยน
- ตัวอย่าง: `uv run manage.py evaluation_publish_results 2026-FA --actor=academic-affairs@example.ac.kr`

## หนังสือรับรอง (ระยะที่ 8)

### `certificate_verify`

- วัตถุประสงค์: ตรวจสอบรหัสตรวจสอบหนังสือรับรองด้วยเกณฑ์เดียวกับหน้าตรวจสอบสาธารณะ แสดงประเภท เลขที่เอกสาร วันที่ออก และผู้ถือแบบปิดบังบางส่วน
- อาร์กิวเมนต์/ตัวเลือก: `code` รหัสตรวจสอบ (ไม่แยกตัวพิมพ์ใหญ่เล็ก)
- บันทึกการตรวจสอบ: ไม่มี (อ่านอย่างเดียว)
- รหัสสิ้นสุดการทำงาน: 0 เมื่อใช้ได้ 2 สำหรับรหัสที่ไม่รู้จัก หนังสือรับรองที่ถูกเพิกถอน หรือเลยระยะเวลาที่ตรวจสอบได้
- ตัวอย่าง: `uv run manage.py certificate_verify 7Q2M9XK4TB0RWZ5C1HNA`

### `certificate_render`

- วัตถุประสงค์: สร้าง PDF ของหนังสือรับรองที่ออกแล้วใหม่ด้วยข้อมูลและแม่แบบปัจจุบัน และแทนที่ไฟล์ที่จัดเก็บไว้ เหมือนกับ **หนังสือรับรอง > หนังสือรับรองที่ออกแล้ว > สร้างใหม่** ในแผงผู้ดูแลระบบ เลขที่เอกสารและรหัสตรวจสอบคงเดิม ค่า checksum จะเปลี่ยน PDF สร้างโดย Gotenberg
- อาร์กิวเมนต์/ตัวเลือก: `issue` เลขที่เอกสาร, `--reason=` (จำเป็น), `--actor=` (บัญชีที่มีสิทธิ์ `ออก สร้างใหม่ และเพิกถอนหนังสือรับรอง`)
- บันทึกการตรวจสอบ: บันทึก (เลขที่เอกสาร checksum ใหม่) บันทึกการดำเนินงาน `certificate.rerendered`
- รหัสสิ้นสุดการทำงาน: 1 เมื่อไม่มีเหตุผล เลขที่เอกสารที่ไม่รู้จัก หรือสร้าง PDF ไม่ได้
- เมื่อใช้: เพื่อสร้างหนังสือรับรองบางฉบับใหม่หลังแก้ไขแม่แบบ การสะกดชื่อ หรือ `APP_URL`
- ตัวอย่าง: `uv run manage.py certificate_render ENR-2026-000001 --reason="Name spelling corrected"`

## การสอบ (ระยะที่ 9)

### `assessment_import_results`

- วัตถุประสงค์: กรอกผลสอบของรอบสอบจาก CSV ใช้กฎเดียวกับ **รอบสอบ > นำเข้าผลสอบ (CSV)** ในแผงผู้ดูแลระบบ (เฉพาะนักศึกษาที่สมัครสอบแล้ว ตัดสินผ่านจากคะแนน การกรอกอีกครั้งก่อนประกาศผลจะแทนที่ผลสอบ หลังประกาศผลแถวจะถูกรายงานเป็นข้อผิดพลาด)

### `lms_sync`

- วัตถุประสงค์: ส่งกลุ่มเรียนที่เผยแพร่แล้วไปยังแพลตฟอร์ม (การสร้างและเชื่อมโยงรายวิชา อาจารย์ผู้สอน นักศึกษาที่ลงทะเบียน) ทำสิ่งที่ **การเชื่อมโยงรายวิชา > ซิงค์อีกครั้ง** ทำในแผงผู้ดูแลระบบสำหรับทั้งภาคการศึกษา กลุ่มเรียนที่เชื่อมโยงแล้วจะเพียงถูกยืนยันซ้ำ (idempotent) ทุกขั้นตอนเก็บไว้ใน **บันทึกการซิงค์**
- อาร์กิวเมนต์/ตัวเลือก: `{platform}` รหัสแพลตฟอร์ม, `--term=` (รหัสภาคการศึกษา ค่าเริ่มต้นคือทุกภาคการศึกษาที่ยังไม่สิ้นสุด), `--section=` (course code-section code หนึ่งรายการ เช่น `CSE2010-01`), `--dry-run` (บันทึกสิ่งที่จะส่งเป็น "skipped" เท่านั้น), `--actor=`
- บันทึกการตรวจสอบ: บันทึก (แพลตฟอร์ม กลุ่มเรียน สมาชิก ความล้มเหลว)
- รหัสสิ้นสุดการทำงาน: 1 สำหรับรหัสแพลตฟอร์มหรือภาคการศึกษาที่ไม่รู้จัก 2 เมื่อมีกลุ่มเรียนใดล้มเหลว (แสดงข้อผิดพลาดต่อกลุ่มเรียน)
- เมื่อใช้: ก่อนเริ่มภาคการศึกษา หลังเปิดใช้งานแพลตฟอร์มใหม่

### `lms_reconcile`

### `media_prune_orphans`

- วัตถุประสงค์: ลบแถวสื่อที่ไม่มีเจ้าของแล้ว และไดเรกทอรี (`<media id>/`) ในที่จัดเก็บส่วนตัวที่ไม่มีแถวข้อมูล (รูปถ่ายบุคคล เอกสารใบสมัคร PDF หนังสือรับรอง หลักฐานการสอบ)
- ตัวเลือก: `--dry-run` (แสดงรายการเท่านั้น), `--actor=`
- บันทึกการตรวจสอบ: บันทึก (จำนวนแถว ไดเรกทอรี)
- เมื่อใช้: ทุกเดือนหรือหลังการลบข้อมูลจำนวนมาก

## คีย์การเข้ารหัสข้อมูลส่วนบุคคล (ระยะที่ 0)

### `pii_generate_key`

- วัตถุประสงค์: แสดงคีย์ใหม่ (32 ไบต์, `base64:...`) สำหรับ `PII_ENCRYPTION_KEY` และ `PII_HASH_KEY` ไม่บันทึกสิ่งใด
- บันทึกการตรวจสอบ: ไม่บันทึก
- ข้อควรระวัง: การเปลี่ยน `PII_HASH_KEY` ทำให้แฮชการค้นหาทั้งหมด (`*_hash`) ใช้ไม่ได้ ให้เปลี่ยนเฉพาะคีย์เข้ารหัส: ย้ายคีย์เดิมไปที่ `PII_PREVIOUS_KEYS` แล้วรัน `pii_reencrypt`
- ตัวอย่าง

  ```bash
  uv run manage.py pii_generate_key
  ```

### `pii_reencrypt`

- วัตถุประสงค์: หลังเปลี่ยนคีย์ จะเข้ารหัสข้อมูลส่วนบุคคลที่เข้ารหัสด้วยคีย์เดิมใหม่ด้วยคีย์ปัจจุบัน ทำงานเป็นกลุ่มงาน Celery ตามชุดของระเบียน ระเบียนที่ใช้คีย์ปัจจุบันแล้วจะไม่ถูกแตะต้อง
- อาร์กิวเมนต์: โมเดลที่มีฟิลด์ข้อมูลส่วนบุคคลแบบเข้ารหัส (`app_label.Model` เช่น `person.Person`)
- ตัวเลือก: `--chunk=500` (จำนวนระเบียนต่องาน), `--dry-run` (นับเฉพาะระเบียนที่ใช้คีย์เดิม), `--force` (ไม่ขอยืนยัน), `--actor=`
- บันทึกการตรวจสอบ: บันทึก (ID ของ batch จำนวนงาน / จำนวนที่แสดงตัวอย่าง)
- การตรวจสอบ: ติดตามงานใน Flower เมื่อเสร็จและ `--dry-run` รายงาน 0 ให้นำคีย์เดิมออกจาก `PII_PREVIOUS_KEYS`
- ตัวอย่าง

  ```bash
  uv run manage.py pii_reencrypt person.Person --dry-run
  uv run manage.py pii_reencrypt person.Person --force --actor=ops@example.edu
  ```

## การแปลภาษา (ระยะที่ 0)

### `i18n_missing`

- วัตถุประสงค์: ดึงข้อความที่แปลได้จากซอร์สโค้ดแบบเดียวกับ `makemessages` (โดยไม่เขียนไฟล์) เปรียบเทียบกับทุกแคตตาล็อก (`locale/` ส่วนกลางและ `locale/` ของแต่ละแอป) และแสดงรายการต่อภาษาของข้อความที่ขาดหาย (ไม่มีในแคตตาล็อก `msgstr` ว่าง fuzzy ตัวแทนข้อมูลไม่ตรงกัน) และรายการที่ล้าสมัย
- อาร์กิวเมนต์/ตัวเลือก: `[locale]` (ภาษาเดียว เช่น `ko`, `zh-hans`, `lo`), `--strict` (รหัสสิ้นสุดการทำงาน 2 เมื่อมีข้อความขาดหาย ใช้ใน CI), `--no-extract` (ตรวจสอบเฉพาะแคตตาล็อก ไม่สแกนซอร์สโค้ด)
- บันทึกการตรวจสอบ: ไม่บันทึก
- ต้องการ: GNU gettext (`xgettext`, `msguniq`)
- ตัวอย่าง

  ```bash
  uv run manage.py i18n_missing --strict
  uv run manage.py i18n_missing lo
  ```

### `i18n_export`

- วัตถุประสงค์: เขียนแผ่นงานสำหรับผู้แปล (`.xlsx` หรือ `.csv` เลือกตามนามสกุลไฟล์) คอลัมน์: `catalog` (ตำแหน่งแคตตาล็อก), `context`, `source` (msgid ภาษาอังกฤษ), `source_plural`, `translation`, `note` (คีย์ต้นฉบับ)
- อาร์กิวเมนต์/ตัวเลือก: `{locale} {path}`, `--missing` (เฉพาะข้อความที่ยังไม่มีคำแปล)
- บันทึกการตรวจสอบ: ไม่บันทึก
- ตัวอย่าง: `uv run manage.py i18n_export ko storage/ko.xlsx --missing`

### `i18n_import`

- วัตถุประสงค์: เขียนแผ่นงานที่ผู้แปลกรอกแล้วกลับเข้าแคตตาล็อก (`.po`) และคอมไพล์ (`.mo`) นำเข้าเฉพาะข้อความที่มีอยู่ในแคตตาล็อก (แคตตาล็อก context และข้อความภาษาอังกฤษเดียวกัน) คำแปลที่ว่างจะถูกข้าม
- อาร์กิวเมนต์/ตัวเลือก: `{locale} {path}`, `--dry-run` (แสดงรายการข้อความที่จะเขียน), `--actor=`
- บันทึกการตรวจสอบ: บันทึก (ภาษา จำนวนคำแปล)
- หมายเหตุ: แคตตาล็อกอยู่ในรีโพซิทอรี ให้ commit การเปลี่ยนแปลงของ `.po` หลังนำเข้า

### `i18n_makemessages`

- วัตถุประสงค์: รัน `makemessages` จากรากของรีโพซิทอรีเพื่อให้ทุกแคตตาล็อกตรงกับซอร์สโค้ด (ko, zh_Hans, lo) ข้อความจะไปอยู่ใน `locale/` ของแอปเมื่อแอปมี มิฉะนั้นไปอยู่ใน `locale/` ส่วนกลาง ไดเรกทอรี `.venv`, `tests`, `docs` และไดเรกทอรีลักษณะเดียวกันจะถูกข้าม
- ตัวเลือก: เหมือนกับ `makemessages` ของ Django (`-l`, `--no-obsolete`, ...)
- บันทึกการตรวจสอบ: ไม่บันทึก
- ตัวอย่าง: `uv run manage.py i18n_makemessages`

## การตรวจสอบ (ระยะที่ 0)

### `pdf_sample`

- วัตถุประสงค์: สร้าง PDF ของตารางที่ผสมอักษรฮันกึล CJK ลาว ไทย เทวนาครี ซีริลลิก และละติน เพื่อตรวจสอบฟอนต์และการเชื่อมต่อกับบริการ PDF (Gotenberg)
- อาร์กิวเมนต์: `[path]` (ค่าเริ่มต้น `pdf-sample.pdf` สัมพัทธ์กับที่จัดเก็บไฟล์ส่วนตัว `PRIVATE_MEDIA_ROOT`)
- บันทึกการตรวจสอบ: ไม่บันทึก
- เมื่อล้มเหลว: รหัสสิ้นสุดการทำงาน 1 หากเป็นข้อผิดพลาดการเชื่อมต่อ ให้ตรวจสอบ `GOTENBERG_URL`, `GOTENBERG_TIMEOUT` และคอนเทนเนอร์ Gotenberg
- ตัวอย่าง: `uv run manage.py pdf_sample`

### `naming_check`

- วัตถุประสงค์: ตรวจสอบสคีมาฐานข้อมูลและซอร์สโค้ดตาม [กฎการตั้งชื่อ](../../../development/naming.md) ตรวจสอบชื่อตารางและคอลัมน์ในแคตตาล็อกจริงของฐานข้อมูล (สคีมา `public`, `audit`, `reporting`) ชื่อไฟล์ไมเกรชันของแอป Ninefruits ชื่อคำสั่งจัดการ (`context_action`) และ msgid และ msgctxt ของแคตตาล็อกคำแปล (`.po`)
- กฎ: snake_case คำต่อท้ายที่ห้ามใช้ (`_old`, `_new`, `_backup`, `_tmp` วันที่ ตัวเลข) ชื่อที่มีรหัสภาษา คอลัมน์เวลาที่ไม่มีเขตเวลา (`timestamp without time zone`) ชื่อคอลัมน์บูลีน (`is_`, `has_`, `can_` หรือคำกริยา) ชื่อคอลัมน์วันที่ (`_date`) msgid ที่มีรูปแบบเหมือนคีย์เชิงความหมาย (`registration.errors.x`) ตารางที่ Django และแพ็กเกจกำหนด (`django_*`, allauth, Celery beat, `settings`, `cache`, `jobs`, `media` เป็นต้น) ไม่อยู่ในการตรวจสอบ
- ตัวเลือก: `--database=` (การเชื่อมต่อฐานข้อมูลที่จะตรวจสอบ ค่าเริ่มต้น `default`), `--skip-database` (ตรวจสอบไฟล์เท่านั้น ไม่ใช้ฐานข้อมูล)
- บันทึกการตรวจสอบ: ไม่บันทึก
- รหัสสิ้นสุดการทำงาน: 2 เมื่อพบปัญหา
- ตัวอย่าง

  ```bash
  uv run manage.py naming_check
  ```
