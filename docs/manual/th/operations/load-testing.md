# การทดสอบโหลด (ช่วงลงทะเบียนเรียนหนาแน่น)

- ผู้อ่าน: ผู้ดูแลระบบไอที
- เกี่ยวข้อง: [รายการตรวจสอบการนำขึ้นใช้งาน](deployment-checklist.md), [การติดตั้ง](installation.md), [คำสั่ง](commands.md)

Locust จำลองเช้าวันแรกของการลงทะเบียนเรียน ซึ่งนักศึกษาจำนวนมากแห่เข้าลงทะเบียนกลุ่มเรียนเดียวกันพร้อมกัน สคริปต์คือ `loadtest/registration.py` (`tests/load/registration.js` ของ k6 ในต้นฉบับ) ตัวช่วยรันคือ `loadtest/run.sh` และการตรวจสอบการรับเกินจำนวนคือ `loadtest/seat_check.sql`

[สารบัญคู่มือ](../README.md)

## การเตรียมการ

1. สร้างฐานข้อมูลสำหรับการทดสอบโหลดโดยเฉพาะ (ห้ามใช้ฐานข้อมูลระบบใช้งานจริง) สร้างบทบาทและฐานข้อมูลตามหัวข้อที่ 2 ของ [การติดตั้ง](installation.md) จากนั้นติดตั้งและโหลดข้อมูลสาธิตขนาดใหญ่ รายชื่อบัญชีนักศึกษาจะถูกเขียนลงใน `load-accounts.csv` ในที่จัดเก็บส่วนตัว (`PRIVATE_MEDIA_ROOT` ค่าเริ่มต้น `storage/private`)

   ```bash
   export DB_DATABASE=nf_load
   uv run manage.py setup_install --profile=korean-university --grade-scale=4.5 --force < /dev/null
   uv run manage.py setup_demo --size=large --seed=42 --student-accounts --force
   ```

2. ต้องมีช่วงลงทะเบียนเรียนที่เปิดอยู่ ข้อมูลสาธิตสร้างช่วงลงทะเบียนเรียนของภาคการศึกษาถัดไปตามชั้นปี (ชั้นปีที่ 4 เปิดแล้ว ชั้นปีที่ 3 ในอีกสองวัน ชั้นปีที่ 1 และ 2 ในอีกสามวัน) หากต้องการวัดกับทุกชั้นปี ให้เลื่อนเวลาเริ่มของช่วงลงทะเบียนเรียนอื่น ๆ ไปในอดีตที่ **ช่วงเวลาดำเนินการ** ในหน้า **แก้ไข** ของภาคการศึกษา ([คู่มือผู้ดูแลระบบ บทที่ 10](../admin/10-terms.md)) หรือรันคำสั่งต่อไปนี้ด้วย superuser ในฐานข้อมูลทดสอบ:

   ```sql
   UPDATE term_windows SET opens_at = now() - interval '1 hour'
    WHERE window_type = 'registration' AND opens_at > now() AND closes_at > now();
   ```

3. Redis และ worker ของ Celery ต้องทำงานอยู่ ที่นั่งตัดสินในฐานข้อมูลโดยตรง แต่การเลื่อนจากรายชื่อสำรอง การซิงค์ LMS และการแจ้งเตือนผ่านคิว หาก Redis ใช้ร่วมกับงานอื่น ให้ใช้หมายเลขฐานข้อมูลอื่น เช่น `REDIS_URL=redis://127.0.0.1:6379/7`

## การรัน

`loadtest/run.sh` จะเริ่ม gunicorn (`config/gunicorn.py`) และ worker ของ Celery รัน Locust แบบ headless รันการตรวจสอบที่นั่ง แล้วหยุดทุกอย่าง

```bash
export DB_DATABASE=nf_load DB_POOL=true DB_POOL_MIN=1 DB_POOL_MAX=2 DB_PREPARE_THRESHOLD=2
WORKERS=9 USERS=100 DURATION=1m loadtest/run.sh storage/loadtest/w9-u100
```

หากต้องการรันเอง ให้เริ่มเซิร์ฟเวอร์ด้วย `TRUSTED_PROXY_COUNT=1` แล้วรัน Locust:

```bash
TRUSTED_PROXY_COUNT=1 DJANGO_DEBUG=false GUNICORN_WORKERS=9 uv run gunicorn config.wsgi -c config/gunicorn.py
uv run --group loadtest locust -f loadtest/registration.py --headless -u 100 -r 20 -t 1m \
    --host http://127.0.0.1:8000 --csv storage/loadtest/run
psql -h 127.0.0.1 -U postgres -d nf_load -v term=<term id> -f loadtest/seat_check.sql
```

- สถานการณ์: เข้าสู่ระบบ (`/accounts/login/`) → หน้าลงทะเบียนเรียน → ค้นหารายวิชา (HTMX `?partial=results`) → ลงทะเบียนกลุ่มเรียนแรกที่มีที่นั่งว่าง → ลดรายวิชานั้น ทุกรอบจะล้างคุกกี้และเข้าสู่ระบบเป็นนักศึกษาคนถัดไป กลุ่มเรียนที่เต็มและการปฏิเสธตามกฎนับเป็นผลลัพธ์ปกติ (`registration outcomes`)
- ปุ่มลงทะเบียนและลดรายวิชาส่งคำขอแบบ HTMX (`HX-Request`) เซิร์ฟเวอร์ตอบ 302 ไปยังหน้าลงทะเบียนเรียน เวลาของ `enroll` และ `drop` รวมหน้านั้นด้วย (เบราว์เซอร์ต้องได้หน้านั้นก่อนจะสลับ `#registration`)
- นักศึกษาแต่ละคนส่งที่อยู่ `X-Forwarded-For` ของตนเอง เมื่อเซิร์ฟเวอร์อยู่หลังพร็อกซีหนึ่งชั้น (`TRUSTED_PROXY_COUNT=1`) ขีดจำกัดการเข้าสู่ระบบต่อที่อยู่ของ allauth จะใช้ต่อที่อยู่ของนักศึกษาแต่ละคน เหมือนในมหาวิทยาลัยจริง `ADDRESSES=1` จำลองนักศึกษาทุกคนอยู่หลังที่อยู่เดียว (NAT)
- ตัวแปรสภาพแวดล้อม: `ACCOUNTS` (CSV ของบัญชี) `SEARCH` (ข้อความค้นหา ค่าเริ่มต้น `GEN`) `ADDRESSES` `FIRST_ACCOUNT` (บัญชีแรก ค่าเริ่มต้นแบบสุ่ม) `run.sh` รับ `WORKERS`, `USERS`, `SPAWN_RATE`, `DURATION`, `TERM_ID`, `PORT`
- เพิ่ม `USERS` จาก 100 เป็น 200 และ 500 แล้วดู p95 ของแต่ละหน้าและอัตราความล้มเหลว เกณฑ์: หน้าลงทะเบียนเรียน p95 < 800 ms ลงทะเบียน p95 < 1.5 s ความล้มเหลว < 1 % Locust จะจบด้วยรหัส 1 เมื่อไม่ผ่านเกณฑ์
- บนเซิร์ฟเวอร์ ให้ดูจำนวนการเชื่อมต่อและการรอล็อกใน `pg_stat_activity` (`wait_event_type = 'Lock'`) งานค้างของ Celery และการใช้ CPU เต็ม Locust บนเซิร์ฟเวอร์เดียวกันก็ใช้ CPU ด้วย ตัวเลขจึงเป็นขอบล่าง

## สิ่งที่การออกแบบรับประกัน

- จำนวนรับได้รับการป้องกันด้วยการล็อกแถวของกลุ่มเรียน (`SeatAllocator.lock`, `SELECT ... FOR NO KEY UPDATE`) และข้อจำกัด CHECK คำขอที่เกิดพร้อมกันจึงไม่ทำให้กลุ่มเรียนรับเกินจำนวน (`tests/registration/test_concurrent_registration.py`: 16 โพรเซส 5 ที่นั่ง) ล็อกนี้ทำให้เฉพาะคำขอที่นั่งของกลุ่มเรียนเดียวกันรอกันเท่านั้น และไม่ปิดกั้นการตรวจสอบ foreign key ของแถวที่เพียงอ้างอิงกลุ่มเรียน (ประวัติการลงทะเบียน บันทึกการซิงค์ LMS)
- หลังการรัน คิวรีทั้งสี่ของ `loadtest/seat_check.sql` ต้องไม่คืนแถวใด (เกินจำนวนรับ ตัวนับที่นั่งไม่ตรง กลุ่มที่นั่งเกินจำนวนรับ การลงทะเบียนซ้ำในกลุ่มเรียน)
- จำนวนคิวรีของหน้าลงทะเบียนเรียนไม่เพิ่มขึ้นตามจำนวนการลงทะเบียน รายชื่อสำรอง หรือผลการค้นหา (`tests/registration/test_portal_query_count.py`)

## ขีดจำกัดการเข้าสู่ระบบต่อที่อยู่และพร็อกซี

นอกจากขีดจำกัดความล้มเหลวต่อบัญชี (5 ครั้งต่อนาที) allauth ยังใช้ **ขีดจำกัดการเข้าสู่ระบบต่อที่อยู่** (`LOGIN_RATE_LIMIT_PER_IP` ค่าเริ่มต้น `30/m/ip`) ซึ่งต้นฉบับไม่มี ที่อยู่ที่แอปพลิเคชันเห็นกำหนดโดย `TRUSTED_PROXY_COUNT` (`ninefruits.core.http.client_ip`)

- เมื่ออยู่หลัง Nginx โดยมี `TRUSTED_PROXY_COUNT=0` (ค่าเริ่มต้น) ทุกคำขอจะมีที่อยู่ของ Nginx มหาวิทยาลัยที่ออกอินเทอร์เน็ตผ่านที่อยู่ NAT เดียวก็เป็นกรณีเดียวกัน
- การรันที่จำลองกรณีนี้ (`ADDRESSES=1`, 100 VU, 1 นาที): จากการเข้าสู่ระบบ 4,876 ครั้ง **สำเร็จเพียง 30 ครั้ง** และ 4,846 ครั้งถูกปฏิเสธด้วย 429 (ความล้มเหลว 49 %) ในนาทีนั้นมีการลงทะเบียนสำเร็จเพียง 20 รายการ เมื่อให้นักศึกษาแต่ละคนมีที่อยู่ของตนเองภายใต้เงื่อนไขเดียวกัน ไม่มีการเข้าสู่ระบบใดถูกปฏิเสธ
- การตั้งค่าระบบใช้งานจริง: ตั้ง `TRUSTED_PROXY_COUNT` เป็นจำนวนพร็อกซี (`1` สำหรับ Nginx หนึ่งตัว) หากนักศึกษาส่วนใหญ่ใช้ที่อยู่ NAT เดียวกัน ให้เพิ่ม `LOGIN_RATE_LIMIT_PER_IP` ให้ถึงอัตราการเข้าสู่ระบบสูงสุด ตัวอย่าง: นักศึกษา 2,000 คนเข้าสู่ระบบภายใน 10 นาที คือ 200 ครั้งต่อนาทีจากที่อยู่เดียว จึงตั้ง `300/m/ip` ค่าว่างจะยกเลิกขีดจำกัดต่อที่อยู่ (เหมือนต้นฉบับ ขีดจำกัดความล้มเหลวต่อบัญชียังคงอยู่)

## การตัดสินใจเรื่องการตั้งค่าเซิร์ฟเวอร์

- **worker แบบ sync ของ gunicorn** (`config/gunicorn.py`) `GUNICORN_WORKERS` มีค่าเริ่มต้นเป็นจำนวนคอร์ CPU × 2 + 1 ปริมาณงานถูกจำกัดด้วย CPU: บน 4 คอร์ worker 4, 9 และ 16 ตัวให้ปริมาณงานเท่ากัน (23 ถึง 26 คำขอต่อวินาที) worker ที่มากขึ้นเพียงเพิ่มการเชื่อมต่อฐานข้อมูล (12 → 36) และการรอล็อก (สูงสุด 1 → 12) อย่าตั้งเกินคอร์ × 2 + 1 ให้ขยายระบบด้วยการเพิ่มเซิร์ฟเวอร์แอปพลิเคชัน
- **พูลการเชื่อมต่อและ prepared statement**: `DB_POOL=true`, `DB_POOL_MIN=1`, `DB_POOL_MAX=2`, `DB_PREPARE_THRESHOLD=2` เนื่องจากนโยบายความปลอดภัยระดับแถว (RLS) การวางแผนคิวรีจึงเป็นเวลาส่วนใหญ่ที่หน้าหนึ่งใช้ในฐานข้อมูล (31 คิวรีของหน้าลงทะเบียนเรียน: วางแผน 51 ms ทำงาน 19 ms) การใช้การเชื่อมต่อซ้ำและเตรียมคำสั่งด้วยการผูกค่าฝั่งเซิร์ฟเวอร์ทำให้แต่ละคิวรีถูกวางแผนเพียงครั้งเดียวต่อการเชื่อมต่อ บน 4 คอร์เดียวกัน ปริมาณงานเพิ่มจาก 16.8 เป็น 25.6 คำขอต่อวินาที และค่ามัธยฐานของหน้าลงทะเบียนเรียนสำหรับผู้ใช้หนึ่งคนลดจาก 160 ms เป็น 97 ms เซิร์ฟเวอร์ต้องใช้การเชื่อมต่อ worker × `DB_POOL_MAX` + จำนวน concurrency ของ Celery ซึ่งต้องต่ำกว่า `max_connections` ของ PostgreSQL เมื่ออยู่หลัง PgBouncer โหมด transaction จะใช้ prepared statement ไม่ได้ ให้คง `DB_PREPARE_THRESHOLD=0` ชุดการทดสอบทั้งหมด (1,066 การทดสอบ) ผ่านด้วยการตั้งค่าเหล่านี้
- **ASGI (การตัดสินใจเรื่อง Octane ในต้นฉบับ)**: ไม่นำมาใช้ ทุกหน้าเป็น view แบบ synchronous ซึ่ง ASGI จะรันในเธรดโดยไม่ได้ประโยชน์ และปริมาณงานเป็นไปตามจำนวนคอร์ CPU Django ไม่ต้องบูตแอปพลิเคชันใหม่ทุกคำขอ (ต่างจาก PHP-FPM) ประโยชน์ที่ Octane ให้จึงมีอยู่แล้ว ส่วนประโยชน์ของการเชื่อมต่อแบบคงอยู่มาจากพูลและ prepared statement ข้างต้น
- การเข้าสู่ระบบใช้ CPU ต่อคำขอสูงเพราะการตรวจสอบแฮช Argon2 (ประมาณ 140 ms เมื่อมีผู้ใช้หนึ่งคน) เมื่อการเข้าสู่ระบบหลั่งไหลเข้ามาในช่วงหนาแน่น ต้นทุนนี้จะกินปริมาณงานก่อน

วิธีอ่าน

- ไม่มีความล้มเหลวของ HTTP ในการรันใดเลย (ยกเว้นการรันแบบที่อยู่เดียว) และไม่มีการรับเกินจำนวน (`seat_check.sql` ไม่คืนแถวใด) การปฏิเสธคือกลุ่มเรียนเต็ม (`capacity`) และรายวิชาซ้ำ (`duplicate_course` การลงทะเบียนที่ค้างจากรอบที่ถูกตัดตอนท้ายของการรันก่อนหน้า) ซึ่งเป็นพฤติกรรมปกติ
- ความล่าช้าหลายวินาทีที่ 100 VU คือคิวของคำขอ เมื่อมีผู้ใช้หนึ่งคน เซิร์ฟเวอร์จัดการหน้าได้ในประมาณ 100 ms และการลงทะเบียน (POST รวมหน้าที่ส่งกลับ) ในประมาณ 290 ms เครื่องนี้ซึ่งแบ่ง 4 คอร์ให้ Locust, PostgreSQL และงานอื่นใช้ร่วมกัน ทำได้สูงสุด 25 ถึง 30 คำขอต่อวินาที บนเครื่องนี้ เกณฑ์ (หน้า p95 < 800 ms ลงทะเบียน p95 < 1.5 s) ไม่ผ่านที่ 100 VU
- การรอล็อกเกิดจากล็อกที่นั่งของกลุ่มเรียนเดียวกันเท่านั้นและเกิดขึ้นสั้น ๆ (สูงสุดชั่วขณะ 1 ถึง 12 มากขึ้นเมื่อมี worker มากขึ้น) การเชื่อมต่อฐานข้อมูลอยู่ที่หรือต่ำกว่า worker × 2
- หากถือว่าช่วงลงทะเบียนหนาแน่นคือ "นักศึกษา 2,000 คนส่งคำขอคนละ 6 ครั้งภายใน 10 นาที" จะได้ 20 คำขอต่อวินาที เครื่องนี้ (พูล + prepared statement) ทำได้ 25 ถึง 30 เซิร์ฟเวอร์แอปพลิเคชันเฉพาะแบบ 8 คอร์จึงมีส่วนเหลือ ก่อนเปิดใช้งานจริง: รันสคริปต์เดียวกันที่ 200 และ 500 VU บนสภาพแวดล้อม staging ที่ตั้งค่าเหมือนระบบใช้งานจริง (เซิร์ฟเวอร์แอปพลิเคชันเฉพาะ Nginx เซิร์ฟเวอร์ฐานข้อมูลแยก Locust บนเครื่องอื่น) และยืนยันว่าผ่านเกณฑ์
- ต้นฉบับ (Laravel, คอนเทนเนอร์พัฒนา Sail, เซิร์ฟเวอร์ในตัว) ทำได้ 24.7 req/s ด้วย 4 workers และ 34.5 req/s ด้วย 16 workers ที่ 100 VU เครื่องต่างกัน ตัวเลขจึงเปรียบเทียบกันโดยตรงไม่ได้
