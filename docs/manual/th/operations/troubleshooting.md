# การแก้ไขปัญหา

- ผู้อ่าน: ผู้ดูแลระบบไอที
- เกี่ยวข้อง: [รายการตรวจสอบการนำขึ้นใช้งาน](deployment-checklist.md), [งานตามกำหนดเวลา](scheduled-jobs.md), [คู่มือคำสั่ง](commands.md)

| อาการ | สิ่งที่ต้องตรวจสอบ |
|---|---|
| ถูกนำไปยังหน้าความปลอดภัยทันทีหลังเข้าสู่ระบบ | นโยบายการยืนยันตัวตนแบบสองขั้นตอนเป็น "บังคับ" และเลยระยะผ่อนผันแล้ว จะหายไปเมื่อผู้ใช้ลงทะเบียนการยืนยันตัวตน นโยบายอยู่ที่ **การตั้งค่า > ความปลอดภัย** |
| 403 ในแผงผู้ดูแลระบบ | ผู้ใช้ไม่มีการกำหนดบทบาทที่มีผลอยู่ซึ่งมีสิทธิ์ `admin_panel.access` (`เข้าใช้แผงผู้ดูแลระบบ`) เปิดผู้ใช้ที่ **ผู้ใช้และสิทธิ์การเข้าถึง > ผู้ใช้** แล้วตรวจสอบรายการ **การกำหนดบทบาท** (ระยะเวลา ขอบเขต) |
| เมนูบางรายการหายไป | บทบาทไม่มีสิทธิ์สำหรับหน้าจอนั้น (ตัวอย่างเช่น `roles.view`) |
| ไม่ได้รับรหัสทางอีเมล | การตั้งค่าอีเมล (`MAIL_*`, `DEFAULT_FROM_EMAIL`) รายการ `ส่งรหัสทางอีเมล` ใน **การตรวจสอบ > เหตุการณ์ด้านความปลอดภัย** ขีดจำกัดการส่ง (ต่อผู้ใช้หนึ่งครั้งต่อนาที ห้าครั้งต่อชั่วโมง) |
| หน้าเข้าสู่ระบบตอบ `429 Too Many Requests` | ที่อยู่หนึ่งพยายามเข้าสู่ระบบเกิน `LOGIN_RATE_LIMIT_PER_IP` (ค่าเริ่มต้น 30) ครั้งต่อนาที หากผู้ใช้จำนวนมากถูกปิดกั้นพร้อมกัน ให้ตรวจสอบว่า `TRUSTED_PROXY_COUNT` ตรงกับจำนวนพร็อกซีจริง (ทุกคนปรากฏเป็นที่อยู่ของ Nginx) หากอยู่หลัง NAT ของมหาวิทยาลัย ให้เพิ่มค่านี้ ([รายการตรวจสอบการนำขึ้นใช้งาน](deployment-checklist.md#พร็อกซีและที่อยู่ของไคลเอนต์)) |
| เข้าสู่ระบบไม่ได้แม้รหัสผ่านถูกต้อง | การเข้าสู่ระบบถูกล็อก (`ล็อกการเข้าสู่ระบบ` ใน **เหตุการณ์ด้านความปลอดภัย**) หรือบัญชีไม่ได้ใช้งาน ปลดล็อกด้วย `uv run manage.py security_unlock_user <email> --reason="..."` |
| หน้าจอแสดงข้อมูลของผู้อื่น 0 รายการ | อาจเป็นเรื่องปกติ (ความปลอดภัยระดับแถว) ยืนยันว่ามีการกำหนดผู้ดำเนินการของเซสชันฐานข้อมูลแล้วโดยดูคอลัมน์ผู้ใช้ใน **การตรวจสอบ > การเปลี่ยนแปลงข้อมูล** |
| `400 Bad Request` | ชื่อโฮสต์ที่ร้องขอไม่อยู่ใน `DJANGO_ALLOWED_HOSTS` |
| `403 CSRF verification failed` | `DJANGO_CSRF_TRUSTED_ORIGINS` ไม่มีที่อยู่ `https://` หรือ Nginx ไม่ส่ง `X-Forwarded-Proto` |
| เปลี่ยนเส้นทาง HTTPS ไม่สิ้นสุด | Nginx ไม่ส่ง `X-Forwarded-Proto $scheme` ทำให้ Django เห็นเป็นคำขอ HTTP (`SECURE_PROXY_SSL_HEADER`) |
| หน้าจอไม่มีสไตล์หรือสคริปต์ ข้อผิดพลาด `manifest.json` | `npm ci && npm run build` (`static/dist/`), `collectstatic`, location `/static/` ของ Nginx ระบบใช้งานจริงใช้ `VITE_DEV_MODE=false` |
| บางส่วนของหน้าจอแสดงเป็นภาษาอังกฤษ | ไม่ได้รัน `compilemessages --ignore=.venv` (ไม่มีไฟล์ `.mo`) สำหรับข้อความใหม่ ใช้ `uv run manage.py i18n_missing <locale>` |
| `permission denied for schema public` | แอปพลิเคชันพยายามรัน DDL ด้วย `app_runtime` ให้รันไมเกรชันด้วย `uv run manage.py migrate` หรือ `setup_install` เท่านั้น (ทั้งสองใช้ `app_migrator` โดยอัตโนมัติ) |
| `Audit records are append-only` | มีความพยายามแก้ไขหรือลบตารางบันทึกการตรวจสอบ การปิดกั้นนี้เป็นไปตามที่ออกแบบไว้ |
| การสร้าง PDF ล้มเหลว | `uv run manage.py pdf_sample` สถานะของ Gotenberg, `GOTENBERG_URL`, `GOTENBERG_TIMEOUT` |
| งานในคิวค้าง | ตรวจสอบการเชื่อมต่อของ worker และงานที่ล้มเหลวใน Flower, `uv run celery -A config inspect active` การเชื่อมต่อ Redis (`REDIS_URL`) |
| งานตามกำหนดเวลาไม่ทำงาน `/api/v1/health/` ตอบ `degraded` | beat หยุดทำงาน (ไม่มีสัญญาณชีพของตัวจัดกำหนดเวลานานกว่า 5 นาที) ตรวจสอบโพรเซส beat และล็อกของมัน beat ต้องมีเพียงตัวเดียว |
| `Received unregistered task` ในล็อกของ worker | worker ยังรันโค้ดเวอร์ชันก่อนหน้า ให้รีสตาร์ต worker หลังนำขึ้นใช้งาน |
| การปิดภาคการศึกษาไม่เสร็จสิ้น | งาน `grading.close_term_records` ที่ล้มเหลวใน Flower แก้ไขสาเหตุ แล้วเริ่มการปิดภาคการศึกษาอีกครั้ง (การคำนวณรายนักศึกษาให้ผลเหมือนเดิมเมื่อรันซ้ำ) |

การติดตามรายคำขอ: ด้วยค่าของส่วนหัวการตอบกลับ `X-Request-Id` ท่านสามารถค้นหาล็อก (`request_id` ใน JSON) บันทึกการดำเนินงาน การเปลี่ยนแปลงข้อมูล และเหตุการณ์ด้านความปลอดภัยได้พร้อมกัน เมื่อ Nginx ส่ง `X-Request-Id $request_id` ล็อกการเข้าถึงของ Nginx ก็ใช้ร่วมได้ด้วย การรันคำสั่งใช้รหัสการรันที่ขึ้นต้นด้วย `cmd-`
