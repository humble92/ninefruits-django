# การจัดการคีย์

- ผู้อ่าน: ผู้ดูแลระบบไอที
- เกี่ยวข้อง: [การติดตั้ง](installation.md), [คู่มือคำสั่ง](commands.md), [รายการตรวจสอบการนำขึ้นใช้งาน](deployment-checklist.md)

| คีย์ | วัตถุประสงค์ | หากสูญหาย | การเปลี่ยนคีย์ |
|---|---|---|---|
| `DJANGO_SECRET_KEY` | เซสชัน CSRF การลงนาม (ลิงก์ตั้งรหัสผ่านใหม่ ลิงก์ยืนยันอีเมล คุกกี้ของอุปกรณ์ที่จดจำไว้) แฮชของรหัสยืนยันตัวตนทางอีเมล การเข้ารหัสข้อมูลลับของการยืนยันตัวตนแบบสองขั้นตอน (ข้อมูลลับ TOTP ของแอปยืนยันตัวตน รหัสกู้คืน) และข้อมูลลับไคลเอนต์ของ SSO | ผู้ใช้ทุกคนจะออกจากระบบ ลิงก์ที่ส่งไปแล้วจะใช้ไม่ได้ แอปยืนยันตัวตนและรหัสกู้คืนที่ลงทะเบียนไว้จะใช้งานไม่ได้ (ต้องรีเซ็ตการยืนยันตัวตนแบบสองขั้นตอนรายผู้ใช้) ต้องกรอกข้อมูลลับไคลเอนต์ของ SSO ใหม่ | เปลี่ยนโดยใส่คีย์เดิมใน `DJANGO_SECRET_KEY_FALLBACKS` (ขั้นตอนด้านล่าง) |
| `PII_ENCRYPTION_KEY` | การเข้ารหัสข้อมูลส่วนบุคคล เช่น เลขประจำตัวประชาชน (AES-256-GCM) | **ไม่สามารถกู้คืนข้อมูลส่วนบุคคลที่เข้ารหัสไว้ได้** | เปลี่ยนโดยใส่คีย์เดิมใน `PII_PREVIOUS_KEYS` (ขั้นตอนด้านล่าง) |
| `PII_HASH_KEY` | แฮชสำหรับการค้นหาข้อมูลส่วนบุคคลแบบตรงทุกตัวอักษร (HMAC-SHA256) | การค้นหาจะใช้งานไม่ได้ (ข้อมูลยังอยู่) | โดยหลักแล้วไม่เปลี่ยน |

สร้าง `DJANGO_SECRET_KEY` ด้วย `uv run python -c "import secrets; print(secrets.token_urlsafe(50))"` และคีย์ข้อมูลส่วนบุคคลทั้งสองด้วย `uv run manage.py pii_generate_key`

หลักการจัดเก็บ

- เก็บคีย์ทั้งสามชุดอย่างน้อยสองสำเนาไว้นอกการตั้งค่าของเซิร์ฟเวอร์ ในที่จัดเก็บข้อมูลลับ (Vault ตัวจัดการข้อมูลลับบนคลาวด์ ฯลฯ) หรือในที่เก็บแบบออฟไลน์ที่ปิดผนึก
- ห้ามเก็บคีย์ไว้ร่วมกับไฟล์สำรองข้อมูล ข้อมูลสำรองของฐานข้อมูลที่รั่วไหลต้องอ่านไม่ได้หากไม่มีคีย์
- ห้ามใช้คีย์จาก `.env` สำหรับการพัฒนาหรือจากการตั้งค่าการทดสอบในระบบใช้งานจริง
- โพรเซสเว็บ (gunicorn) worker ของ Celery และ Celery beat ต้องอ่านค่าคีย์เดียวกันทั้งหมด หลังเปลี่ยนคีย์ ให้รีสตาร์ตทั้งสามพร้อมกัน

## การเปลี่ยน `DJANGO_SECRET_KEY`

ใช้สำหรับการเปลี่ยนตามกำหนดหรือเมื่อผู้ที่รู้คีย์เปลี่ยนไป อาศัย `SECRET_KEY_FALLBACKS` ของ Django จึงไม่มีผู้ใดถูกออกจากระบบตราบที่ยังเก็บคีย์เดิมไว้ เป็นแนวทางเดียวกับ `APP_PREVIOUS_KEYS` ในต้นฉบับ (Laravel)

1. สร้างคีย์ใหม่: `uv run python -c "import secrets; print(secrets.token_urlsafe(50))"`
2. ใส่คีย์ปัจจุบันไว้เป็นลำดับแรกใน `DJANGO_SECRET_KEY_FALLBACKS` (คั่นด้วยจุลภาคหากมีหลายคีย์) และใส่คีย์ใหม่ใน `DJANGO_SECRET_KEY`
   ```
   DJANGO_SECRET_KEY=<new key>
   DJANGO_SECRET_KEY_FALLBACKS=<previous key>
   ```
3. รีสตาร์ต gunicorn, worker ของ Celery และ beat (Docker: `docker compose restart app worker beat`)
4. เข้ารหัสข้อมูลลับของการยืนยันตัวตนแบบสองขั้นตอนและข้อมูลลับไคลเอนต์ของ SSO ใหม่ด้วยคีย์ใหม่ ตรวจสอบจำนวนด้วย `uv run manage.py security_reencrypt_secrets --dry-run` รันโดยไม่มี `--dry-run` แล้วยืนยันว่า `--dry-run` รายงาน 0 หากนำคีย์เดิมออกก่อนขั้นตอนนี้ แอปยืนยันตัวตนและรหัสกู้คืนจะใช้งานไม่ได้
5. กำหนดระยะเวลาที่จะเก็บคีย์เดิมไว้ รายการต่อไปนี้ใช้ได้เฉพาะขณะที่ยังเก็บคีย์เดิมไว้:

   | รายการ | ขณะที่ยังเก็บคีย์เดิมไว้ | หลังนำคีย์เดิมออก |
   |---|---|---|
   | เซสชันการเข้าสู่ระบบ | ย้ายไปใช้คีย์ใหม่เมื่อมีคำขอครั้งแรกหลังการเปลี่ยน | เฉพาะเซสชันที่ไม่ได้ใช้ในระหว่างนั้นจะถูกออกจากระบบ |
   | ลิงก์ตั้งรหัสผ่านใหม่ ลิงก์ยืนยันอีเมล | ใช้ได้ (3 วัน) | ต้องขอใหม่ |
   | คุกกี้ของอุปกรณ์ที่จดจำไว้ | ใช้ได้ (ตามระยะเวลาจดจำในการตั้งค่าความปลอดภัย ค่าเริ่มต้น 30 วัน) | จะถูกขอการยืนยันตัวตนแบบสองขั้นตอนอีกครั้งในการเข้าสู่ระบบครั้งถัดไป |
   | รหัสยืนยันตัวตนทางอีเมล | รหัสที่ส่งก่อนการเปลี่ยนไม่นานจะไม่ตรงกัน (ใช้ได้ 10 นาที) | เหมือนกัน |

   เก็บไว้อย่างน้อย 3 วัน หรือตามระยะเวลาจดจำหากต้องการคงอุปกรณ์ที่จดจำไว้
6. เมื่อครบระยะเวลา ให้นำคีย์เดิมออกจาก `DJANGO_SECRET_KEY_FALLBACKS` และรีสตาร์ตเช่นเดียวกับขั้นตอนที่ 3
7. เก็บคีย์เดิมแบบปิดผนึกไว้ตลอดระยะเวลาเก็บรักษาข้อมูลสำรอง ข้อมูลลับของการยืนยันตัวตนแบบสองขั้นตอนในข้อมูลสำรองที่เก่ากว่าเข้ารหัสด้วยคีย์นั้น เมื่อกู้คืนข้อมูลสำรองที่เก่ากว่า ให้ใส่คีย์นั้นใน `DJANGO_SECRET_KEY_FALLBACKS` แล้วดำเนินการขั้นตอนที่ 4

### หากคีย์รั่วไหล

1. ดำเนินการขั้นตอนที่ 1 ถึง 4 ทันที (คีย์เดิมจำเป็นเฉพาะสำหรับการเข้ารหัสใหม่ในขั้นตอนที่ 4)
2. ทันทีที่ขั้นตอนที่ 4 เสร็จ ให้นำคีย์เดิมออกและรีสตาร์ต ทุกเซสชันจะสิ้นสุด ลิงก์ที่ส่งไปแล้วและอุปกรณ์ที่จดจำไว้จะใช้ไม่ได้ (เป็นผลที่ตั้งใจ)
3. ทบทวนการเข้าสู่ระบบและงานบริหารจัดการในช่วงที่คีย์รั่วไหลจากบันทึกความปลอดภัย ([การตรวจสอบและการบำรุงรักษา](audit-and-maintenance.md))

## การเปลี่ยนคีย์ข้อมูลส่วนบุคคล

1. สร้างคีย์ใหม่ด้วย `uv run manage.py pii_generate_key` (ใช้เฉพาะ `PII_ENCRYPTION_KEY` จากผลลัพธ์)
2. ใส่คีย์ปัจจุบันใน `PII_PREVIOUS_KEYS` (คั่นด้วยจุลภาคหากมีหลายคีย์) และใส่คีย์ใหม่ใน `PII_ENCRYPTION_KEY`
3. ให้โพรเซสอ่านการตั้งค่าใหม่: รีสตาร์ต gunicorn และ worker ของ Celery (Docker: `docker compose restart app worker beat`)
4. สำหรับแต่ละโมเดลที่มีข้อมูลส่วนบุคคล ให้ตรวจสอบจำนวนระเบียนด้วย `uv run manage.py pii_reencrypt {app.Model} --dry-run` (เช่น `person.Person`) แล้วรันโดยไม่มี `--force` (ตอบการยืนยัน)
5. เมื่อ Flower แสดงว่างานเสร็จสิ้นและ `--dry-run` รายงาน 0 ให้นำคีย์เดิมออกจาก `PII_PREVIOUS_KEYS`
6. เก็บคีย์เดิมแบบปิดผนึกไว้ตลอดระยะเวลาเก็บรักษาข้อมูลสำรอง (จำเป็นสำหรับการกู้คืนข้อมูลสำรองที่เก่ากว่า)

การเปลี่ยน `PII_HASH_KEY` จะทำให้แฮชการค้นหาที่จัดเก็บไว้ทั้งหมดผิด การค้นหาแบบตรงทุกตัวอักษรด้วยเลขประจำตัวประชาชนหรือเลขที่หนังสือเดินทางจึงจะล้มเหลว โดยหลักแล้วจึงไม่เปลี่ยน
