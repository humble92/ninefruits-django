# 負荷テスト(履修登録のピーク)

- 対象読者: IT 運用担当者
- 関連: [デプロイチェックリスト](deployment-checklist.md)、[インストール](installation.md)、[コマンド](commands.md)

履修登録初日の朝のように、多数の学生が同じ開講科目に同時に殺到する状況を Locust で再現します。スクリプトは `loadtest/registration.py`(オリジナルの k6 `tests/load/registration.js`)、実行用のヘルパーは `loadtest/run.sh`、定員超過のチェックは `loadtest/seat_check.sql` です。

[マニュアル目次](../README.md)

## 準備

1. 負荷テスト専用のデータベースを作成します(本番のデータベースは決して使わないでください)。ロールとデータベースは [インストール](installation.md) の 2 節と同様に作成し、インストールしてから大規模なデモを読み込みます。学生アカウントの一覧は非公開ストレージ(`PRIVATE_MEDIA_ROOT`、既定 `storage/private`)の `load-accounts.csv` に書き出されます。

   ```bash
   export DB_DATABASE=nf_load
   uv run manage.py setup_install --profile=korean-university --grade-scale=4.5 --force < /dev/null
   uv run manage.py setup_demo --size=large --seed=42 --student-accounts --force
   ```

2. 履修登録の業務期間が開いている必要があります。デモは次学期の履修登録の業務期間を学年別に作成します(4 年生はすでに開いており、3 年生は 2 日後、1・2 年生は 3 日後)。全学年で測定するには、学期の **編集** ページの **業務期間** で他の履修登録の業務期間の開始を過去に移すか([管理者マニュアル 第 10 章](../admin/10-terms.md))、テスト用データベースでスーパーユーザーとして次を実行します。

   ```sql
   UPDATE term_windows SET opens_at = now() - interval '1 hour'
    WHERE window_type = 'registration' AND opens_at > now() AND closes_at > now();
   ```

3. Redis と Celery ワーカーが動作している必要があります。席はデータベースで直接決まりますが、キャンセル待ちの繰り上げ、LMS の同期、通知はキューを通じて処理されます。Redis を他の作業と共有している場合は、別のデータベース番号を使用します。例: `REDIS_URL=redis://127.0.0.1:6379/7`。

## 実行

`loadtest/run.sh` は gunicorn(`config/gunicorn.py`)と Celery ワーカーを起動し、Locust をヘッドレスで実行し、席のチェックを実行してから、すべてを停止します。

```bash
export DB_DATABASE=nf_load DB_POOL=true DB_POOL_MIN=1 DB_POOL_MAX=2 DB_PREPARE_THRESHOLD=2
WORKERS=9 USERS=100 DURATION=1m loadtest/run.sh storage/loadtest/w9-u100
```

手動で実行するには、`TRUSTED_PROXY_COUNT=1` でサーバーを起動し、Locust を実行します。

```bash
TRUSTED_PROXY_COUNT=1 DJANGO_DEBUG=false GUNICORN_WORKERS=9 uv run gunicorn config.wsgi -c config/gunicorn.py
uv run --group loadtest locust -f loadtest/registration.py --headless -u 100 -r 20 -t 1m \
    --host http://127.0.0.1:8000 --csv storage/loadtest/run
psql -h 127.0.0.1 -U postgres -d nf_load -v term=<term id> -f loadtest/seat_check.sql
```

- シナリオ: ログイン(`/accounts/login/`) → 履修登録ページ → 科目検索(HTMX `?partial=results`) → 空席のある最初の開講科目に履修登録 → 削除。反復のたびに Cookie を消去し、次の学生としてログインします。満席の開講科目やルールによる拒否は正常な結果として数えます(`registration outcomes`)。
- 履修登録と削除のボタンは HTMX と同様に POST します(`HX-Request`)。サーバーは履修登録ページへの 302 を返します。`enroll` と `drop` の時間にはそのページが含まれます(ブラウザーは `#registration` を差し替える前にそのページを必要とするため)。
- 各学生は自分専用の `X-Forwarded-For` アドレスを送ります。サーバーがプロキシ 1 段の背後にある場合(`TRUSTED_PROXY_COUNT=1`)、allauth のアドレスごとのログイン制限は、実際のキャンパスと同様に学生のアドレスごとに適用されます。`ADDRESSES=1` は、全学生が 1 つのアドレス(NAT)の背後にいる状況を再現します。
- 環境変数: `ACCOUNTS`(アカウントの CSV)、`SEARCH`(検索文字列、既定 `GEN`)、`ADDRESSES`、`FIRST_ACCOUNT`(最初のアカウント、既定はランダム)。`run.sh` は `WORKERS`、`USERS`、`SPAWN_RATE`、`DURATION`、`TERM_ID`、`PORT` を受け取ります。
- `USERS` を 100 から 200、500 へと上げながら、各ページの p95 と失敗率を観察します。目標: 履修登録ページの p95 < 800 ms、履修登録の p95 < 1.5 s、失敗率 < 1 %。目標を満たさない場合、Locust は終了コード 1 で終了します。
- サーバー側では、`pg_stat_activity` の接続数とロック待ち(`wait_event_type = 'Lock'`)、Celery の滞留、CPU の飽和を観察します。同じサーバー上の Locust も CPU を使うため、数値は下限値です。

## 設計上の保証

- 定員は開講科目の行ロック(`SeatAllocator.lock`、`SELECT ... FOR NO KEY UPDATE`)と CHECK 制約で保護されているため、同時リクエストで開講科目が定員を超えて履修されることはありません(`tests/registration/test_concurrent_registration.py`: 16 プロセス、5 席)。このロックで互いに待つのは同じ開講科目の席を求めるリクエストだけで、開講科目を参照するだけの行(履修登録の試行、LMS の同期ログ)の外部キーチェックはブロックしません。
- 実行後、`loadtest/seat_check.sql` の 4 つのクエリはいずれも行を返してはなりません(定員超過、席カウンターの不一致、席グループの定員超過、開講科目の重複履修)。
- 履修登録ページのクエリ数は、履修登録、キャンセル待ち、検索結果の件数に応じて増えません(`tests/registration/test_portal_query_count.py`)。

## アドレスごとのログイン制限とプロキシ

アカウントごとの失敗回数の制限(1 分に 5 回)に加えて、allauth は **アドレスごとのログイン制限**(`LOGIN_RATE_LIMIT_PER_IP`、既定 `30/m/ip`)を適用します。これはオリジナルにはなかったものです。アプリケーションから見えるアドレスは `TRUSTED_PROXY_COUNT` で決まります(`ninefruits.core.http.client_ip`)。

- Nginx の背後で `TRUSTED_PROXY_COUNT=0`(既定)の場合、すべてのリクエストが Nginx のアドレスになります。キャンパスが 1 つの NAT アドレスから外に出る場合も同じです。
- これを再現した実行(`ADDRESSES=1`、100 VU、1 分間)では、4,876 回のログインのうち **成功したのは 30 回だけ** で、4,846 回が 429 で拒否されました(失敗率 49 %)。その 1 分間に成立した履修登録は 20 件だけでした。同じ条件で学生ごとに 1 つのアドレスを使った場合、拒否されたログインはありませんでした。
- 本番の設定: `TRUSTED_PROXY_COUNT` をプロキシの数に設定します(Nginx 1 台なら `1`)。大半の学生が 1 つの NAT アドレスを共有する場合は、`LOGIN_RATE_LIMIT_PER_IP` をピーク時のログイン頻度まで引き上げます。例: 2,000 人の学生が 10 分以内にログインすると 1 つのアドレスから 1 分あたり 200 回になるため、`300/m/ip`。空の値にするとアドレスごとの制限はなくなります(オリジナルと同じ。アカウントごとの失敗回数の制限は残ります)。

## サーバー構成の決定

- **gunicorn の sync ワーカー**(`config/gunicorn.py`)。`GUNICORN_WORKERS` の既定値は CPU コア数 × 2 + 1 です。スループットは CPU に制約されていました。4 コアでは、ワーカー 4、9、16 のいずれも同じスループット(毎秒 23〜26 リクエスト)でした。ワーカーを増やしても、データベースの接続数(12 → 36)とロック待ち(ピーク 1 → 12)が増えただけでした。コア数 × 2 + 1 を超えないようにし、アプリケーションサーバーを増やしてスケールアウトしてください。
- **コネクションプールとプリペアドステートメント**: `DB_POOL=true`、`DB_POOL_MIN=1`、`DB_POOL_MAX=2`、`DB_PREPARE_THRESHOLD=2`。行レベルセキュリティ(RLS)のポリシーのため、ページのデータベース時間の大半はクエリ計画でした(履修登録ページの 31 クエリ: 計画 51 ms、実行 19 ms)。接続を再利用し、サーバー側バインディングでステートメントを準備すると、各クエリの計画は接続ごとに 1 回で済みます。同じ 4 コアで、スループットは毎秒 16.8 リクエストから 25.6 リクエストに、ユーザー 1 人での履修登録ページの中央値は 160 ms から 97 ms になりました。サーバーにはワーカー数 × `DB_POOL_MAX` + Celery の並行数の接続が必要で、PostgreSQL の `max_connections` を下回る必要があります。トランザクションモードの PgBouncer の背後ではプリペアドステートメントを使えないため、`DB_PREPARE_THRESHOLD=0` のままにしてください。この設定でテストスイート全体(1,066 件)が成功します。
- **ASGI(オリジナルの Octane の判断)**: 採用しません。すべてのページは同期ビューで、ASGI ではスレッドで実行されるだけで利点がなく、スループットは CPU コア数に従います。Django は(PHP-FPM と違って)リクエストごとにアプリケーションをブートストラップしないため、Octane が与える利得はすでに得られています。永続的な接続の利得は、上記のプールとプリペアドステートメントから得られます。
- ログインは Argon2 のハッシュ検証のため、リクエストあたりの CPU コストが大きくなります(ユーザー 1 人で約 140 ms)。ピーク時にログインが集中すると、まずこのコストがスループットを圧迫します。

読み方

- どの実行でも(アドレス 1 つの実行を除き)HTTP の失敗はなく、定員超過もありませんでした(`seat_check.sql` は行を返しませんでした)。拒否は満席の開講科目(`capacity`)と重複科目(`duplicate_course`、以前の実行の終了時に打ち切られた反復が残した履修登録)で、正常な動作です。
- 100 VU での数秒の遅延はリクエストの待ち行列によるものです。ユーザー 1 人では、サーバーはページを約 100 ms、履修登録(POST と返されるページ)を約 290 ms で処理します。4 コアを Locust、PostgreSQL、他の作業で共有するこのマシンでは、毎秒 25〜30 リクエストが上限です。このマシンでは、100 VU で目標(ページ p95 < 800 ms、履修登録 p95 < 1.5 s)を満たしません。
- ロック待ちは同じ開講科目の席のロックからのみ発生し、短時間でした(瞬間的なピーク 1〜12、ワーカーが多いほど多い)。データベースの接続数はワーカー数 × 2 以下にとどまりました。
- 履修登録のピークを「2,000 人の学生が 10 分以内にそれぞれ 6 リクエスト」とすると、毎秒 20 リクエストになります。このマシン(プール + プリペアドステートメント)は 25〜30 を処理したので、専用の 8 コアのアプリケーションサーバーなら余裕があります。本稼働の前に、本番と同じ構成のステージング環境(専用のアプリケーションサーバー、Nginx、別のデータベースサーバー、別マシンの Locust)で同じスクリプトを 200 VU と 500 VU で実行し、目標を満たすことを確認してください。
- オリジナル(Laravel、Sail 開発コンテナ、組み込みサーバー)は 100 VU でワーカー 4 で 24.7 req/s、ワーカー 16 で 34.5 req/s でした。マシンが異なるため、数値は直接比較できません。
