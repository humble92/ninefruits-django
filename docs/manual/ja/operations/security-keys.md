# キー管理

- 対象読者: IT 運用担当者
- 関連: [インストール](installation.md)、[コマンドリファレンス](commands.md)、[デプロイチェックリスト](deployment-checklist.md)

| キー | 用途 | 紛失した場合 | ローテーション |
|---|---|---|---|
| `DJANGO_SECRET_KEY` | セッション、CSRF、署名(パスワードリセットのリンク、メールアドレス確認のリンク、記憶されたデバイスの Cookie)、二要素認証のメールのコードのハッシュ、二要素認証のシークレット(認証アプリの TOTP シークレット、リカバリーコード)と SSO のクライアントシークレットの暗号化 | すべてのユーザーがログアウトされ、送信済みのリンクが機能しなくなり、登録済みの認証アプリとリカバリーコードが機能しなくなります(ユーザーごとに二要素認証のリセットが必要)。SSO のクライアントシークレットは再入力が必要です | 以前のキーを `DJANGO_SECRET_KEY_FALLBACKS` に設定してローテーションします(下記の手順) |
| `PII_ENCRYPTION_KEY` | 国民識別番号などの個人情報の暗号化(AES-256-GCM) | **暗号化された個人情報は復元できません** | 以前のキーを `PII_PREVIOUS_KEYS` に設定してローテーションします(下記の手順) |
| `PII_HASH_KEY` | 個人情報の完全一致検索用のハッシュ(HMAC-SHA256) | 検索が機能しなくなります(データは残ります) | 原則としてローテーションしません |

`DJANGO_SECRET_KEY` は `uv run python -c "import secrets; print(secrets.token_urlsafe(50))"` で、2 つの個人情報キーは `uv run manage.py pii_generate_key` で生成します。

保管の原則

- 3 つのキーは、サーバーの環境設定とは別に、シークレットストア(Vault、クラウドのシークレットマネージャーなど)または封印したオフラインの保管場所に少なくとも 2 部保管します。
- バックアップファイルと一緒には保管しないでください。DB のバックアップが流出しても、キーがなければ読めない状態を保つ必要があります。
- 開発用の `.env` やテスト設定のキーを本番で使用しないでください。
- Web プロセス(gunicorn)、Celery ワーカー、Celery beat はすべて同じキーの値を読み込む必要があります。キーを変更したら、3 つを同時に再起動してください。

## `DJANGO_SECRET_KEY` のローテーション

定期的なローテーションや、キーを知る担当者が変わったときに使用します。Django の `SECRET_KEY_FALLBACKS` を利用するため、以前のキーを保持している間は誰もログアウトされません。これはオリジナル(Laravel)の `APP_PREVIOUS_KEYS` と同じ方式です。

1. 新しいキーを生成します: `uv run python -c "import secrets; print(secrets.token_urlsafe(50))"`。
2. 現在のキーを `DJANGO_SECRET_KEY_FALLBACKS` の先頭に(複数ある場合はカンマ区切り)、新しいキーを `DJANGO_SECRET_KEY` に設定します。
   ```
   DJANGO_SECRET_KEY=<new key>
   DJANGO_SECRET_KEY_FALLBACKS=<previous key>
   ```
3. gunicorn、Celery ワーカー、beat を再起動します(Docker: `docker compose restart app worker beat`)。
4. 二要素認証のシークレットと SSO のクライアントシークレットを新しいキーで再暗号化します。`uv run manage.py security_reencrypt_secrets --dry-run` で件数を確認し、`--dry-run` なしで実行してから、`--dry-run` が 0 を報告することを確認します。この手順の前に以前のキーを削除すると、認証アプリとリカバリーコードが機能しなくなります。
5. 以前のキーを保持する期間を決めます。次のものは、以前のキーを保持している間だけ有効です。

   | 項目 | 以前のキーを保持している間 | 削除した後 |
   |---|---|---|
   | ログインセッション | ローテーション後の最初のリクエストで新しいキーに移行します | その間に使われなかったセッションだけがログアウトされます |
   | パスワードリセットのリンク、メールアドレス確認のリンク | 有効(3 日) | 再度リクエストが必要です |
   | 記憶されたデバイスの Cookie | 有効(セキュリティ設定の記憶期間、既定 30 日) | 次回のログイン時に二要素認証が再度求められます |
   | 二要素認証のメールのコード | ローテーション直前に送信されたコードは一致しません(有効期間 10 分) | 同じ |

   少なくとも 3 日、記憶されたデバイスを維持するなら記憶期間の間は保持してください。
6. 期間が終わったら、`DJANGO_SECRET_KEY_FALLBACKS` から以前のキーを削除し、手順 3 と同様に再起動します。
7. 以前のキーは、バックアップの保存期間中は封印して保管します。古いバックアップの二要素認証のシークレットはそのキーで暗号化されています。古いバックアップを復元するときは、そのキーを `DJANGO_SECRET_KEY_FALLBACKS` に設定して手順 4 を実行します。

### キーが漏洩した場合

1. 手順 1 から 4 をただちに実行します(以前のキーは手順 4 の再暗号化にのみ必要です)。
2. 手順 4 が終わりしだい、以前のキーを削除して再起動します。すべてのセッションが終了し、送信済みのリンクと記憶されたデバイスは無効になります(意図した結果です)。
3. 漏洩期間中のログインと管理作業をセキュリティログで確認します([監査とメンテナンス](audit-and-maintenance.md))。

## 個人情報キーのローテーション

1. `uv run manage.py pii_generate_key` で新しいキーを生成します(出力のうち `PII_ENCRYPTION_KEY` のみを使用します)。
2. 現在のキーを `PII_PREVIOUS_KEYS`(複数ある場合はカンマ区切り)に、新しいキーを `PII_ENCRYPTION_KEY` に設定します。
3. プロセスに設定を再読み込みさせます: gunicorn と Celery ワーカーを再起動します(Docker: `docker compose restart app worker beat`)。
4. 個人情報を持つモデルごとに、`uv run manage.py pii_reencrypt {app.Model} --dry-run`(例: `person.Person`)で対象レコードの件数を確認してから、`--force` なしで実行します(確認に答えます)。
5. Flower でタスクの完了が表示され、`--dry-run` が 0 を報告したら、`PII_PREVIOUS_KEYS` から以前のキーを削除します。
6. 以前のキーは、バックアップの保存期間中は封印して保管します(古いバックアップを復元するのに必要です)。

`PII_HASH_KEY` を変更すると、保存済みの検索ハッシュがすべて合わなくなり、国民識別番号やパスポート番号による完全一致検索ができなくなります。原則としてローテーションしません。
