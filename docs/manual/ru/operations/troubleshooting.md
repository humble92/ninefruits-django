# Устранение неполадок

- Для кого: ИТ-специалисты по эксплуатации
- Связанные документы: [контрольный список развёртывания](deployment-checklist.md), [задания по расписанию](scheduled-jobs.md), [справочник команд](commands.md)

| Признак | Что проверить |
|---|---|
| Сразу после входа происходит переход на страницу безопасности | Политика двухфакторной аутентификации — «обязательно», и льготный период истёк. Проблема решается, когда пользователь подключит двухфакторную аутентификацию. Политика находится в разделе **Настройки > Безопасность** |
| 403 в панели администрирования | У пользователя нет действующего назначения роли с разрешением `admin_panel.access` (`Открывать панель администрирования`). Откройте пользователя в разделе **Пользователи и доступ > Пользователи** и проверьте список **Назначения ролей** (период, область действия) |
| Отсутствует пункт меню | У роли нет разрешения на этот экран (например, `roles.view`) |
| Не приходят коды по эл. почте | Настройки почты (`MAIL_*`, `DEFAULT_FROM_EMAIL`), записи `Код по эл. почте отправлен` в разделе **Аудит > События безопасности**, ограничения отправки (для каждого пользователя раз в минуту, пять раз в час) |
| Страница входа отвечает `429 Too Many Requests` | С одного адреса превышено `LOGIN_RATE_LIMIT_PER_IP` (по умолчанию 30) попыток в минуту. Если заблокировано сразу много пользователей, проверьте, что `TRUSTED_PROXY_COUNT` соответствует реальному числу прокси (все выглядят как адрес Nginx); за NAT кампуса увеличьте значение ([контрольный список развёртывания](deployment-checklist.md#прокси-и-адрес-клиента)) |
| Вход не удаётся с правильным паролем | Вход заблокирован (`Вход заблокирован` среди **событий безопасности**) или учётная запись неактивна. Снимите блокировку командой `uv run manage.py security_unlock_user <email> --reason="..."` |
| Экран показывает 0 строк чужих данных | Это может быть нормой (защита на уровне строк). Убедитесь, что исполнитель сессии БД задан, посмотрев столбец пользователя в разделе **Аудит > Изменения данных** |
| `400 Bad Request` | Запрошенного имени хоста нет в `DJANGO_ALLOWED_HOSTS` |
| `403 CSRF verification failed` | В `DJANGO_CSRF_TRUSTED_ORIGINS` нет адреса `https://`, или Nginx не передаёт `X-Forwarded-Proto` |
| Бесконечные перенаправления на HTTPS | Nginx не передаёт `X-Forwarded-Proto $scheme`, поэтому Django видит HTTP-запрос (`SECURE_PROXY_SSL_HEADER`) |
| Экраны без стилей или скриптов, ошибка `manifest.json` | `npm ci && npm run build` (`static/dist/`), `collectstatic`, location `/static/` в Nginx. В рабочей среде используется `VITE_DEV_MODE=false` |
| Части экранов отображаются на английском | Не выполнена `compilemessages --ignore=.venv` (нет файлов `.mo`). Для новых строк — `uv run manage.py i18n_missing <locale>` |
| `permission denied for schema public` | Приложение попыталось выполнить DDL под `app_runtime`. Выполняйте миграции только через `uv run manage.py migrate` или `setup_install` (обе автоматически используют `app_migrator`) |
| `Audit records are append-only` | Попытка изменить или удалить таблицу аудита. Эта блокировка предусмотрена |
| Не формируется PDF | `uv run manage.py pdf_sample`, состояние Gotenberg, `GOTENBERG_URL`, `GOTENBERG_TIMEOUT` |
| Задачи очереди зависли | Проверьте подключение воркера и неудавшиеся задачи во Flower, `uv run celery -A config inspect active`, подключение к Redis (`REDIS_URL`) |
| Задания по расписанию не выполняются, `/api/v1/health/` отвечает `degraded` | Beat остановлен (нет сигнала активности планировщика более 5 минут). Проверьте процесс beat и его журнал. Только один beat |
| `Received unregistered task` в журнале воркера | Воркер всё ещё выполняет предыдущий код. Перезапустите воркер после развёртывания |
| Закрытие семестра не завершается | Неудавшиеся задачи `grading.close_term_records` во Flower. Устраните причину и снова запустите закрытие семестра (расчёты по каждому студенту при повторном запуске дают тот же результат) |

Трассировка отдельного запроса: по значению заголовка ответа `X-Request-Id` можно одновременно искать в журналах (`request_id` в JSON), журнале действий, изменениях данных и событиях безопасности. Если Nginx передаёт `X-Request-Id $request_id`, к ним добавляется и журнал доступа Nginx. Запуски команд используют ID запуска, начинающийся с `cmd-`.
