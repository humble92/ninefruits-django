# Нагрузочное тестирование (пик записи на дисциплины)

- Для кого: ИТ-специалисты по эксплуатации
- Связанные документы: [контрольный список развёртывания](deployment-checklist.md), [установка](installation.md), [команды](commands.md)

Locust воспроизводит первое утро записи на дисциплины, когда множество студентов одновременно бросаются в одни и те же группы. Сценарий — `loadtest/registration.py` (k6-сценарий `tests/load/registration.js` исходной системы), вспомогательный скрипт запуска — `loadtest/run.sh`, проверка превышения числа мест — `loadtest/seat_check.sql`.

[Содержание руководства](../README.md)

## Подготовка

1. Создайте базу данных только для нагрузочного тестирования (никогда не используйте рабочую базу данных). Роли и база данных создаются, как в разделе 2 документа [установка](installation.md); затем выполните установку и загрузите большие демонстрационные данные. Список учётных записей студентов записывается в `load-accounts.csv` в закрытом хранилище (`PRIVATE_MEDIA_ROOT`, по умолчанию `storage/private`).

   ```bash
   export DB_DATABASE=nf_load
   uv run manage.py setup_install --profile=korean-university --grade-scale=4.5 --force < /dev/null
   uv run manage.py setup_demo --size=large --seed=42 --student-accounts --force
   ```

2. Период записи на дисциплины должен быть открыт. Демонстрационные данные создают периоды записи следующего семестра по курсам (4-й курс уже открыт, 3-й — через два дня, 1-й и 2-й — через три дня). Чтобы измерять со всеми курсами, перенесите начало остальных периодов записи в прошлое в разделе **Периоды семестра** на странице **Редактировать** семестра ([руководство администратора, глава 10](../admin/10-terms.md)) или выполните в тестовой базе данных от имени суперпользователя:

   ```sql
   UPDATE term_windows SET opens_at = now() - interval '1 hour'
    WHERE window_type = 'registration' AND opens_at > now() AND closes_at > now();
   ```

3. Должны работать Redis и воркер Celery. Места определяются непосредственно в базе данных, но перевод из листа ожидания, синхронизация с LMS и уведомления проходят через очередь. Если Redis используется другими задачами, возьмите другой номер базы данных, например `REDIS_URL=redis://127.0.0.1:6379/7`.

## Запуск

`loadtest/run.sh` запускает gunicorn (`config/gunicorn.py`) и воркер Celery, выполняет Locust в режиме без интерфейса, выполняет проверку мест и всё останавливает.

```bash
export DB_DATABASE=nf_load DB_POOL=true DB_POOL_MIN=1 DB_POOL_MAX=2 DB_PREPARE_THRESHOLD=2
WORKERS=9 USERS=100 DURATION=1m loadtest/run.sh storage/loadtest/w9-u100
```

Чтобы запустить вручную, запустите сервер с `TRUSTED_PROXY_COUNT=1` и выполните Locust:

```bash
TRUSTED_PROXY_COUNT=1 DJANGO_DEBUG=false GUNICORN_WORKERS=9 uv run gunicorn config.wsgi -c config/gunicorn.py
uv run --group loadtest locust -f loadtest/registration.py --headless -u 100 -r 20 -t 1m \
    --host http://127.0.0.1:8000 --csv storage/loadtest/run
psql -h 127.0.0.1 -U postgres -d nf_load -v term=<term id> -f loadtest/seat_check.sql
```

- Сценарий: вход (`/accounts/login/`) → страница записи на дисциплины → поиск дисциплин (HTMX `?partial=results`) → запись в первую группу со свободными местами → отмена записи. Каждая итерация очищает cookie и входит как следующий студент. Заполненные группы и отказы по правилам считаются нормальными исходами (`registration outcomes`).
- Кнопки записи и отмены записи отправляют запросы как HTMX (`HX-Request`); сервер отвечает 302 на страницу записи. Замеры `enroll` и `drop` включают эту страницу (браузеру она нужна, прежде чем он заменит `#registration`).
- Каждый студент отправляет собственный адрес `X-Forwarded-For`. Когда сервер находится за одним прокси (`TRUSTED_PROXY_COUNT=1`), ограничение входа allauth по адресу применяется к адресу каждого студента, как в реальном кампусе. `ADDRESSES=1` воспроизводит ситуацию, когда все студенты находятся за одним адресом (NAT).
- Окружение: `ACCOUNTS` (CSV учётных записей), `SEARCH` (текст поиска, по умолчанию `GEN`), `ADDRESSES`, `FIRST_ACCOUNT` (первая учётная запись, по умолчанию случайная). `run.sh` принимает `WORKERS`, `USERS`, `SPAWN_RATE`, `DURATION`, `TERM_ID`, `PORT`.
- Увеличивайте `USERS` со 100 до 200 и до 500 и следите за p95 каждой страницы и долей сбоев. Пороги: p95 страницы записи < 800 мс, p95 записи < 1,5 с, сбои < 1 %. Locust завершается с кодом 1, если порог не выполнен.
- На сервере следите за числом подключений и ожиданиями блокировок в `pg_stat_activity` (`wait_event_type = 'Lock'`), очередью Celery и загрузкой CPU. Locust на том же сервере тоже использует CPU, поэтому цифры — нижняя граница.

## Что гарантирует архитектура

- Число мест защищено блокировкой строки группы (`SeatAllocator.lock`, `SELECT ... FOR NO KEY UPDATE`) и ограничениями CHECK, поэтому одновременные запросы никогда не превышают число мест группы (`tests/registration/test_concurrent_registration.py`: 16 процессов, 5 мест). Блокировка заставляет ждать друг друга только запросы на места одной и той же группы; она не блокирует проверки внешних ключей строк, которые лишь ссылаются на группу (попытки записи, журналы синхронизации с LMS).
- После запуска четыре запроса `loadtest/seat_check.sql` не должны возвращать строк (превышение числа мест, несоответствие счётчика мест, превышение числа мест в группе распределения, повторная запись в группу).
- Число запросов страницы записи на дисциплины не растёт с числом записей, записей в листе ожидания или результатов поиска (`tests/registration/test_portal_query_count.py`).

## Ограничение входа по адресу и прокси

Помимо ограничения неудачных попыток на учётную запись (5 в минуту), allauth применяет **ограничение входа по адресу** (`LOGIN_RATE_LIMIT_PER_IP`, по умолчанию `30/m/ip`), которого не было в исходной системе. Адрес, который видит приложение, задаётся `TRUSTED_PROXY_COUNT` (`ninefruits.core.http.client_ip`).

- За Nginx с `TRUSTED_PROXY_COUNT=0` (по умолчанию) у каждого запроса адрес Nginx. Кампус, выходящий через один адрес NAT, — тот же случай.
- Запуск, воспроизводящий это (`ADDRESSES=1`, 100 VU, 1 минута): из 4 876 входов **успешны только 30**, а 4 846 отклонены с 429 (49 % сбоев). За эту минуту прошло только 20 записей. С отдельным адресом для каждого студента при тех же условиях ни один вход не был отклонён.
- Настройки рабочей среды: задайте `TRUSTED_PROXY_COUNT` равным числу прокси (`1` для одного Nginx). Если большинство студентов использует один адрес NAT, увеличьте `LOGIN_RATE_LIMIT_PER_IP` до пиковой частоты входов. Пример: 2 000 студентов, входящих в течение 10 минут, — это 200 в минуту с одного адреса, значит `300/m/ip`. Пустое значение снимает ограничение по адресу (как в исходной системе; ограничение неудачных попыток на учётную запись остаётся).

## Решения по конфигурации сервера

- **Синхронные воркеры gunicorn** (`config/gunicorn.py`). `GUNICORN_WORKERS` по умолчанию — ядра CPU × 2 + 1. Пропускная способность упиралась в CPU: на 4 ядрах 4, 9 и 16 воркеров дали одинаковую пропускную способность (от 23 до 26 запросов в секунду). Больше воркеров лишь добавляло подключений к базе данных (12 → 36) и ожиданий блокировок (пик 1 → 12). Не превышайте ядра × 2 + 1; масштабируйтесь добавлением серверов приложений.
- **Пул подключений и подготовленные выражения**: `DB_POOL=true`, `DB_POOL_MIN=1`, `DB_POOL_MAX=2`, `DB_PREPARE_THRESHOLD=2`. Из-за политик защиты на уровне строк (RLS) планирование запросов занимало большую часть времени страницы в базе данных (31 запрос страницы записи: 51 мс на планирование, 19 мс на выполнение). Повторное использование подключений и подготовка выражений с привязкой на стороне сервера планируют каждый запрос один раз на подключение. На тех же 4 ядрах пропускная способность выросла с 16,8 до 25,6 запроса в секунду, а медиана страницы записи для одного пользователя снизилась со 160 мс до 97 мс. Серверу нужно воркеры × `DB_POOL_MAX` + параллелизм Celery подключений, меньше `max_connections` PostgreSQL. За PgBouncer в режиме транзакций подготовленные выражения использовать нельзя: оставьте `DB_PREPARE_THRESHOLD=0`. Полный набор тестов (1 066 тестов) проходит с этими настройками.
- **ASGI (решение исходной системы об Octane)**: не принято. Каждая страница — синхронное представление, которое ASGI выполнял бы в потоке без выгоды, а пропускная способность следует за ядрами CPU. Django не загружает приложение заново для каждого запроса (в отличие от PHP-FPM), поэтому выигрыш, который даёт Octane, уже есть; выигрыш от постоянных подключений дают пул и подготовленные выражения, описанные выше.
- Вход требует много CPU на запрос из-за проверки хеша Argon2 (около 140 мс при одном пользователе). Когда на пике скапливаются входы, эти затраты первыми съедают пропускную способность.

Как читать

- Ни в одном запуске (кроме запуска с одним адресом) не было сбоев HTTP и превышения числа мест (`seat_check.sql` не вернул строк). Отказы — это заполненные группы (`capacity`) и повторные дисциплины (`duplicate_course`, записи, оставшиеся от итераций, прерванных в конце предыдущего запуска): нормальное поведение.
- Задержки в несколько секунд при 100 VU — это очередь запросов. При одном пользователе сервер обрабатывает страницу примерно за 100 мс, а запись (POST плюс возвращаемая страница) — примерно за 290 мс; эта машина, делящая 4 ядра между Locust, PostgreSQL и другими задачами, достигает предела в 25–30 запросов в секунду. На этой машине пороги (p95 страницы < 800 мс, p95 записи < 1,5 с) при 100 VU не выполняются.
- Ожидания блокировок возникали только из-за блокировок мест одной и той же группы и были короткими (мгновенный пик от 1 до 12, больше при большем числе воркеров). Подключения к базе данных оставались на уровне воркеры × 2 или ниже.
- Если принять пик записи за «2 000 студентов делают по 6 запросов в течение 10 минут», получается 20 запросов в секунду. Эта машина (пул + подготовленные выражения) выдала 25–30, поэтому у выделенного 8-ядерного сервера приложений есть запас. Перед вводом в эксплуатацию: выполните тот же сценарий при 200 и 500 VU в промежуточной среде, настроенной как рабочая (выделенный сервер приложений, Nginx, отдельный сервер базы данных, Locust на другой машине), и подтвердите пороги.
- Исходная система (Laravel, контейнер разработки Sail, встроенный сервер) выдала при 100 VU 24,7 запр./с с 4 воркерами и 34,5 запр./с с 16. Машины разные, поэтому цифры напрямую не сравниваются.
