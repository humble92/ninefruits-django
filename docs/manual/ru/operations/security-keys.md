# Управление ключами

- Для кого: ИТ-специалисты по эксплуатации
- Связанные документы: [установка](installation.md), [справочник команд](commands.md), [контрольный список развёртывания](deployment-checklist.md)

| Ключ | Назначение | При утере | Ротация |
|---|---|---|---|
| `DJANGO_SECRET_KEY` | Сессии, CSRF, подписи (ссылки сброса пароля, ссылки подтверждения эл. почты, cookie запомненных устройств), хеши кодов двухфакторной аутентификации по эл. почте, шифрование секретов двухфакторной аутентификации (секреты TOTP аутентификаторов, коды восстановления) и секретов клиентов SSO | Все пользователи выходят из системы, отправленные ссылки перестают работать, подключённые приложения-аутентификаторы и коды восстановления перестают работать (нужен сброс двухфакторной аутентификации каждому пользователю), секреты клиентов SSO нужно ввести заново | Ротация с предыдущим ключом в `DJANGO_SECRET_KEY_FALLBACKS` (порядок ниже) |
| `PII_ENCRYPTION_KEY` | Шифрование персональных данных, например номеров удостоверений личности (AES-256-GCM) | **Зашифрованные персональные данные восстановить невозможно** | Ротация с предыдущим ключом в `PII_PREVIOUS_KEYS` (порядок ниже) |
| `PII_HASH_KEY` | Хеши для поиска по точному совпадению в персональных данных (HMAC-SHA256) | Поиск перестаёт работать (данные остаются) | Как правило, не меняется |

Создайте `DJANGO_SECRET_KEY` командой `uv run python -c "import secrets; print(secrets.token_urlsafe(50))"`, а два ключа персональных данных — командой `uv run manage.py pii_generate_key`.

Правила хранения

- Храните не менее двух копий трёх ключей вне конфигурации сервера — в хранилище секретов (Vault, облачный менеджер секретов и т. п.) или в опечатанном автономном хранилище.
- Не храните их рядом с файлами резервных копий. Утёкшая резервная копия базы данных не должна читаться без ключей.
- Никогда не используйте в рабочей среде ключи из `.env` для разработки или из тестовых настроек.
- Веб-процессы (gunicorn), воркеры Celery и Celery beat должны читать одни и те же значения ключей. После смены ключа перезапускайте все три одновременно.

## Ротация `DJANGO_SECRET_KEY`

Используйте для плановой ротации или при смене людей, знающих ключ. Порядок опирается на `SECRET_KEY_FALLBACKS` Django, поэтому, пока предыдущий ключ сохраняется, никто не выходит из системы. Это тот же подход, что и `APP_PREVIOUS_KEYS` в исходной системе (Laravel).

1. Создайте новый ключ: `uv run python -c "import secrets; print(secrets.token_urlsafe(50))"`.
2. Поставьте текущий ключ первым в `DJANGO_SECRET_KEY_FALLBACKS` (несколько — через запятую), а новый ключ — в `DJANGO_SECRET_KEY`.
   ```
   DJANGO_SECRET_KEY=<new key>
   DJANGO_SECRET_KEY_FALLBACKS=<previous key>
   ```
3. Перезапустите gunicorn, воркеры Celery и beat (Docker: `docker compose restart app worker beat`).
4. Заново зашифруйте новым ключом секреты двухфакторной аутентификации и секреты клиентов SSO. Проверьте количество командой `uv run manage.py security_reencrypt_secrets --dry-run`, выполните её без `--dry-run`, затем убедитесь, что `--dry-run` сообщает 0. Если удалить предыдущий ключ до этого шага, приложения-аутентификаторы и коды восстановления перестанут работать.
5. Решите, как долго хранить предыдущий ключ. Следующее остаётся действительным только пока он хранится:

   | Элемент | Пока предыдущий ключ хранится | После его удаления |
   |---|---|---|
   | Сеансы входа | Переводятся на новый ключ при первом запросе после ротации | Выходят из системы только сеансы, не использовавшиеся за это время |
   | Ссылки сброса пароля, ссылки подтверждения эл. почты | Действительны (3 дня) | Нужно запросить заново |
   | Cookie запомненных устройств | Действительны (срок запоминания из настроек безопасности, по умолчанию 30 дней) | При следующем входе снова запрашивается двухфакторная аутентификация |
   | Коды двухфакторной аутентификации по эл. почте | Коды, отправленные непосредственно перед ротацией, не совпадают (действительны 10 минут) | То же |

   Храните его не менее 3 дней или в течение срока запоминания, чтобы сохранить запомненные устройства.
6. По окончании срока удалите предыдущий ключ из `DJANGO_SECRET_KEY_FALLBACKS` и перезапустите процессы, как в шаге 3.
7. Храните предыдущий ключ опечатанным в течение срока хранения резервных копий. Секреты двухфакторной аутентификации в старых резервных копиях зашифрованы им. При восстановлении старой резервной копии поместите этот ключ в `DJANGO_SECRET_KEY_FALLBACKS` и выполните шаг 4.

### Если ключ утёк

1. Выполните шаги 1–4 сразу (предыдущий ключ нужен только для повторного шифрования в шаге 4).
2. Сразу после шага 4 удалите предыдущий ключ и перезапустите процессы. Все сеансы завершатся, а отправленные ссылки и запомненные устройства станут недействительными (так и задумано).
3. Проверьте входы и административные действия за время утечки в журнале безопасности ([аудит и обслуживание](audit-and-maintenance.md)).

## Ротация ключа персональных данных

1. Создайте новый ключ командой `uv run manage.py pii_generate_key` (используйте из вывода только `PII_ENCRYPTION_KEY`).
2. Перенесите текущий ключ в `PII_PREVIOUS_KEYS` (несколько — через запятую), а новый ключ — в `PII_ENCRYPTION_KEY`.
3. Заставьте процессы заново прочитать конфигурацию: перезапустите gunicorn и воркеры Celery (Docker: `docker compose restart app worker beat`).
4. Для каждой модели с персональными данными проверьте число записей командой `uv run manage.py pii_reencrypt {app.Model} --dry-run` (например, `person.Person`), затем выполните её без `--force` (ответьте на запрос подтверждения).
5. Когда Flower покажет, что задачи завершены, а `--dry-run` сообщит 0, удалите предыдущий ключ из `PII_PREVIOUS_KEYS`.
6. Храните предыдущий ключ опечатанным в течение срока хранения резервных копий (нужен для восстановления старых резервных копий).

Смена `PII_HASH_KEY` делает все сохранённые поисковые хеши неверными, поэтому поиск по точному совпадению номера удостоверения личности или паспорта перестаёт работать. Как правило, этот ключ не меняется.
