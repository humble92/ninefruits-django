# Задания по расписанию и очереди

- Для кого: ИТ-специалисты по эксплуатации
- Связанные документы: [контрольный список развёртывания](deployment-checklist.md), [целостность аудита](audit-and-maintenance.md), [справочник команд](commands.md)

## Постоянно работающие процессы

| Процесс | Команда | Проверка |
|---|---|---|
| Веб | `uv run gunicorn config.wsgi -c config/gunicorn.py` | `GET /api/v1/health/` |
| Воркер очереди | `uv run celery -A config worker --loglevel=INFO` | **Workers** во Flower, `uv run celery -A config inspect ping` |
| Планировщик | `uv run celery -A config beat --loglevel=INFO` (**ровно один процесс на всю систему**) | `scheduler` в `/api/v1/health/`, журнал beat |
| Монитор очереди (необязательно) | `uv run celery -A config flower --port=5555` | Только во внутренней сети или за ограничением доступа Nginx |

Все три используют один и тот же код и переменные окружения. Пример systemd:

```ini
# /etc/systemd/system/ninefruits-celery.service
[Service]
User=ninefruits
WorkingDirectory=/srv/ninefruits
EnvironmentFile=/etc/ninefruits/env
ExecStart=/usr/local/bin/uv run --no-sync celery -A config worker --loglevel=INFO
KillSignal=SIGTERM
TimeoutStopSec=300
Restart=always
```

Создайте ещё одну службу такого же вида для beat с `ExecStart=... celery -A config beat --loglevel=INFO`. Даже при нескольких серверах включайте службу beat только на одном из них.

## Задания по расписанию

Регистрации задаются в `beat_schedule` файла `config/celery.py`; beat при запуске согласует с ним планировщик django-celery-beat в базе данных (таблицы `django_celery_beat_*`). Время указано в часовом поясе сервера (`APP_TIMEZONE`, по умолчанию UTC). Каждое задание по расписанию удерживает блокировку Redis (`single_instance`), поэтому одно и то же задание никогда не выполняется дважды одновременно.

| Задание (имя Celery) | Периодичность | Команда, делающая то же самое | Обнаружение сбоев |
|---|---|---|---|
| `admission.expire_drafts` | Ежедневно в 03:10 | `admission_expire_drafts` | Выполняет саму команду, поэтому каждый запуск записывается в журнал действий (журнал `command`). Если записи нет больше суток, проверьте beat и воркер |
| `registration.release_reserved_seats` | Каждые 5 минут | `registration_release_reserved_seats` | Записи аудита нет. Если у распределений мест, время открытия которых прошло, `release_processed_at` всё ещё пусто, проверьте beat |
| `registration.promote_waitlists` | Ежечасно, в начале часа | `waitlist_promote` | Записи в журнале действий нет (переведённые записи на дисциплины видны в изменениях данных как `system:task:registration.promote_waitlists`). Результат задачи во Flower (группы, переводы) |
| `lms.reconcile` | Ежедневно в 02:30 | `lms_reconcile` | Записи синхронизации по каждой связи (панель администрирования **Интеграция с LMS**), результат задачи во Flower |
| `audit.seal` | Ежедневно в 03:30 | `audit_seal` | Запечатывает цепочку хешей аудита ([целостность аудита](audit-and-maintenance.md)). Проверьте, если `audit_verify_chain` показывает больше незапечатанных строк, чем за один день |
| `core.heartbeat` | Каждую минуту | Нет | Записывает время последнего запуска в ключ кеша `system:heartbeat`. `/api/v1/health/` отвечает `degraded`, если оно старше 5 минут |

## Задачи очереди

| Задача (имя Celery) | Чем запускается | Примечания |
|---|---|---|
| `pii.reencrypt_records` | `pii_reencrypt` | Одна задача на порцию записей (group). Если порция завершилась ошибкой, запустите команду снова (записи, уже зашифрованные текущим ключом, пропускаются) |
| `registration.promote_waitlist` | Отмена записи или выход из дисциплины, открытие распределённых мест | Для каждой группы выполняется только одна (блокировка Redis, дубликаты предотвращаются). Перевод из листа ожидания заново проверяет все правила записи. Ставится в очередь после фиксации транзакции |
| `grading.close_term_records`, `grading.finish_term_close` | `term_close`, закрытие семестра в панели администрирования | Chord: задачи по 100 студентов, затем завершающая задача (ранжирование отличий, смена состояния семестра, уведомление сотрудника, запустившего закрытие). Ход выполнения — строка `job_batches` `term-close:{term code}`, показывается в панели администрирования. Задача пакета повторяется до 3 раз при ошибках базы данных; если ошибка остаётся, весь пакет помечается неудавшимся и завершающая задача не выполняется. Устраните причину и снова запустите закрытие семестра (расчёты по каждому студенту при повторном запуске дают тот же результат) |
| `importing.import_chunk` | Импорт CSV в панели администрирования, `reference_import` | Одна задача на порцию. Результаты — в `imports`, строки с ошибками — в `failed_import_rows` (результаты импорта в панели администрирования) |
| `lms.sync_section`, `lms.sync_enrollment` | События изменения групп и записей на дисциплины | При сбое повторяются до 3 раз с интервалом в минуту. Оставшееся исправляет ночное `lms.reconcile` |

Во время выполнения задачи исполнитель БД записывается как `system:task:{task name}` (например, `system:task:grading.close_term_records`) вместе с ID запроса и пользователем запроса, поставившего её в очередь.

Flower показывает неудавшиеся задачи (**Tasks**, состояние `FAILURE`) и их исключения. Задачи Celery используют `acks_late`, поэтому задача, прерванная из-за падения воркера, выполняется снова. Каждая задача построена так, чтобы при повторном выполнении давать тот же результат (идемпотентна).
