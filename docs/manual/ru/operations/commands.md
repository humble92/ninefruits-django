# Справочник команд управления

- Для кого: ИТ-специалисты по эксплуатации
- Охват: все команды, зарегистрированные приложениями Ninefruits в этом репозитории (`ninefruits/*/management/commands/`), и встроенные команды Django, используемые при эксплуатации. Добавленную команду необходимо описать в этом документе записью `### \`command\`` (на всех 16 языках), иначе CI завершится ошибкой (`tests/tooling/test_command_documentation.py`).

## Общие соглашения

Каждая команда запускается как `uv run manage.py {command}`. В среде разработки Docker — `docker compose exec app uv run manage.py {command}`.

| Пункт | Правило |
|---|---|
| Имя | Исходное `{context}:{action}` становится `{context}_{action}` (имена команд Django не могут содержать `:`). Пример: `term:close` → `term_close` |
| Запись аудита | Команды, изменяющие данные (ниже — «Аудит: записывается»), при каждом запуске заносят в журнал действий (журнал `command`) команду, аргументы, параметры, пользователя ОС, код завершения и результат. Просматривайте их в разделе **Аудит > Журнал действий** панели администрирования |
| ID запуска | Каждый запуск получает ID, начинающийся с `cmd-`, вместо ID запроса. Журнал действий, изменения данных, сделанные этим запуском, и поставленные им задачи Celery несут один и тот же ID, поэтому на вопрос «какая команда внесла это изменение» отвечает этот ID. `--actor` — значение, которое указывает оператор, поэтому оно не заносится в столбец пользователя изменений данных (фактический исполнитель — пользователь ОС) |
| `--actor=<email>` | Общий для всех аудируемых команд. Записывает учётную запись ответственного администратора. Неизвестный адрес эл. почты прерывает запуск |
| `--dry-run` | Выводит результат, ничего не изменяя. Доступен для операций, которые трудно отменить |
| `--force` | Выполнение без запросов подтверждения (для расписаний и сценариев развёртывания) |
| `--reason=` | Доступен в командах, требующих указать причину |
| Коды завершения | 0 — успех, 1 — сбой или отмена, 2 — команда проверки обнаружила проблему |
| Контекст БД | Во время выполнения команды исполнитель сессии БД задаётся как `system:command:{command}` и отображается в изменениях данных (триггер) |

## Встроенные команды Django

### `migrate`

- Назначение: применяет миграции базы данных. Обёртка Ninefruits над командой Django: без `--database` используется подключение владельца схемы (`migrator`, роль `app_migrator`). У подключения приложения (`app_runtime`) нет прав на DDL. `showmigrations` и `sqlmigrate` по умолчанию также используют подключение `migrator`.
- Когда: при первой установке и при каждом развёртывании (`setup_install` тоже её выполняет).
- Параметры: те же, что у Django `migrate` (`app_label`, `migration_name`, `--plan`, `--check`, `--database`).
- Аудит: не записывается (изменения схемы хранятся в истории миграций `django_migrations`)
- Примеры

  ```bash
  uv run manage.py migrate
  uv run manage.py migrate --plan
  ```

- При сбое: при ошибках прав проверьте подготовку ролей базы данных (`db/sql/roles/`) в [руководстве по установке](installation.md).

### `collectstatic`

- Назначение: собирает результат сборки Vite (`static/dist/`) и статические файлы Django и unfold в `STATIC_ROOT` (`staticfiles/`). Этот каталог раздаёт веб-сервер (Nginx).
- Когда: при каждом развёртывании, после `npm ci && npm run build`.
- Параметры: `--noinput` (без вопросов), `--clear` (удалить существующие файлы перед сбором).
- Аудит: не записывается
- Примеры

  ```bash
  npm ci && npm run build
  uv run manage.py collectstatic --noinput
  ```

### `compilemessages`

- Назначение: компилирует файлы переводов (`.po`) в используемые во время работы файлы `.mo`. Файлы `.mo` не хранятся в репозитории, поэтому выполняйте команду при каждой установке и развёртывании. В системе должен быть установлен `gettext`.
- Когда: при каждом развёртывании и после правки файлов переводов.
- Параметры: `--locale=` (например, `ko`, `zh_Hans`, `lo`), `--ignore=.venv`.
- Аудит: не записывается
- Примеры

  ```bash
  uv run manage.py compilemessages --ignore=.venv
  ```

### `createsuperuser`

- Назначение: **не используется.** Суперпользователь Django обходит каталог ролей и разрешений и журнал аудита, поэтому команда завершается ошибкой (код завершения 1) и указывает на `security_create_administrator`.
- Вместо неё: создайте первого администратора командой `security_create_administrator` (включает назначение роли системного администратора и запись аудита).
- Аудит: неприменимо

## Установка и демонстрационные данные (этап 1)

### `setup_install`

- Назначение: новые установки и обновления. По очереди выполняет миграции, обязательные данные (шаблоны ролей и синхронизация разрешений, страны, языки, виды справочников, виды подразделений), параметры учебного заведения, шкалу оценок, профили установки и создание первого администратора. Повторный запуск безопасен (существующие данные и значения, изменённые администраторами, сохраняются).
- Когда: при первой установке и при каждом развёртывании.
- Параметры: `--institution-name=`, `--locale=` (язык по умолчанию), `--timezone=` (например, `Asia/Seoul`), `--profile=` (ключ профиля установки, можно повторять: `korean-university`, `yust-legacy`), `--grade-scale=` (шкала оценок `4.5` или `4.3`; после задания фиксируется; если пусто — шкала первого профиля), `--admin-email=`, `--admin-name=`, `--force` (без вопросов; пароль администратора читается из стандартного ввода).
- Аудит: записывается (применённые профили, создан ли администратор)
- Примеры

  ```bash
  uv run manage.py setup_install
  echo "$ADMIN_PASSWORD" | uv run manage.py setup_install --force --locale=ko --timezone=Asia/Seoul \
      --institution-name="Demo University" --profile=korean-university \
      --admin-email=admin@example.ac.kr --admin-name="Administrator"
  ```

- Как читать вывод: `DONE` для каждого шага. `Administrator exists` означает, что назначение системного администратора уже существует, поэтому создание пропущено.
- При сбое: ошибка об отсутствии ключа означает, что в окружении должны быть заданы `DJANGO_SECRET_KEY` и значения из `pii_generate_key`. Сбой миграции: проверьте роли базы данных ([установка](installation.md)). `The grade scale is fixed` означает, что `--grade-scale` отличается от уже зафиксированной шкалы.

### `setup_demo`

- Назначение: создаёт вымышленный университет (подразделения, программы, здания и аудитории, прошлый, текущий и следующий семестры вокруг сегодняшней даты с их периодами, профиль корейского университета). Выводит фиксированные демонстрационные учётные записи по ролям (`registrar@demo.test` и т. д., пароль `demo-password`). Объёмы создаются массовыми вставками.
- Когда: среды разработки, обучения и демонстрации. **Никогда не выполняется в рабочей среде (`DJANGO_ENV=production`), даже с `--force`.**
- Параметры: `--size=tiny|small|medium|large` (около 20/100/2 000/20 000 студентов; `tiny` — для тестов и быстрых проверок), `--seed=` (то же значение — те же данные), `--force` (без подтверждения).
- `--student-accounts`: создаёт учётную запись для каждого обучающегося студента и записывает `load-accounts.csv` (эл. почта, пароль) в закрытое хранилище для нагрузочных тестов ([нагрузочное тестирование](load-testing.md)).
- Аудит: записывается (размер, seed, длительность)
- Пример: `uv run manage.py setup_demo --size=small --seed=42 --force`
- При сбое: без обязательных данных демонстрационные учётные записи пропускаются (нет их ролей); сначала выполните `setup_install`. При повторном запуске на той же базе данных существующие демонстрационные данные пропускаются.

## Справочные данные и семестры (этап 1)

### `reference_import`

- Назначение: импортирует справочные данные из CSV по тем же правилам, что и **Импорт CSV** в панели администрирования (строки находятся по коду и обновляются, пустые ячейки переводов сохраняют существующие значения, строки с ошибками сохраняются отдельно).
- Аргументы: `type` `org_units`, `programs`, `buildings`, `rooms`, `lookup_values`, `students` (личные дела студентов), `instructors`, `courses` (версии дисциплин), `registration_holds` (ограничения на запись) / `file` CSV в UTF-8 со строкой заголовков.
- Параметры: `--actor=` (обязателен; импорт записывается на эту учётную запись, а его результат появляется на экране **Импорты CSV** этой учётной записи), `--chunk=100` (строк на задачу Celery), `--dry-run` (только проверка заголовков и подсчёт строк).
- Аудит: записывается (вид, имя файла, строки, номер импорта, строки с ошибками)
- Формат столбцов: [руководство администратора, глава 9](../admin/09-csv-import.md).
- Коды завершения: если задачи выполняются сразу (eager-воркеры), результат выводится, а строки с ошибками дают 2. Если импорт только поставлен в очередь — 0. Результат и CSV строк с ошибками находятся в разделе **Справочные данные > Импорты CSV** панели администрирования.
- Пример: `uv run manage.py reference_import org_units /srv/import/org-units.csv --actor=admin@example.ac.kr --dry-run`

### `term_inspect`

- Назначение: показывает текущие семестры и открытые рабочие периоды (вид, семестр, учебный период, название, критерии охвата, время закрытия) на заданный момент. Используется для проверки настроек семестров и периодов или вопросов вроде «почему запись не открыта?».
- Параметры: `--at=` (по умолчанию — сейчас; например, `"2027-02-15 09:00"`; без часового пояса применяется часовой пояс сервера (UTC); `"2027-02-15 09:00 Asia/Seoul"` или `2027-02-15T09:00+09:00` задают его явно).
- Аудит: не записывается (только чтение)
- Как читать вывод: даты оцениваются в часовом поясе учебного заведения. Периоды запланированных или архивных семестров никогда не открываются. Время закрытия показывается в часовом поясе учебного заведения.

## Безопасность (этапы 0, 2)

### `security_create_administrator`

- Назначение: создаёт учётную запись с ролью системного администратора. Обычно вызывается из `setup_install`.
- Параметры: `--email=`, `--name=`, `--password-stdin` (пароль из стандартного ввода. Обязателен при неинтерактивном запуске).
- Аудит: записывается (ID созданного пользователя)
- Пример: `uv run manage.py security_create_administrator --email=admin@example.ac.kr --name="Administrator"`
- Пример (неинтерактивно): `printf '%s\n' "$ADMIN_PASSWORD" | uv run manage.py security_create_administrator --email=admin@example.ac.kr --name="Administrator" --password-stdin`
- При сбое: `system_administrator role is missing` означает, что сначала нужно выполнить `setup_install`. Пароль должен содержать не менее 12 символов.

### `security_sync_permissions`

- Назначение: приводит список разрешений в БД в соответствие с каталогом разрешений в коде. Новые разрешения создаются; разрешения, отсутствующие в каталоге, удаляются (и снимаются со всех ролей). Системные роли всегда получают все разрешения.
- Когда: после развёртывания (`setup_install` делает это в шаге обязательных данных).
- Параметры: `--dry-run` (выводит только список создаваемых/удаляемых), `--force` (пропускает подтверждение удаления).
- Аудит: записывается (созданные/удалённые разрешения)
- Как читать вывод: строки `create` и `delete`. При наличии удалений появляется запрос подтверждения.
- При сбое: ответ «нет» на запрос подтверждения завершает работу с кодом 1 без изменений.

### `security_reencrypt_secrets`

- Назначение: после ротации `DJANGO_SECRET_KEY` заново шифрует новым ключом секреты, защищённые производным от него ключом (секреты TOTP приложений-аутентификаторов, исходные данные кодов восстановления, секреты клиентов SSO). До этого они читаются предыдущим ключом из `DJANGO_SECRET_KEY_FALLBACKS`. Выполните её перед удалением предыдущего ключа ([управление ключами](security-keys.md)).
- Аргументы/параметры: `--dry-run` (только подсчитывает секреты, всё ещё зашифрованные предыдущим ключом).
- Аудит: записывается (количества)
- Как читать вывод: `Dry run: 0 authenticator(s) and 0 SSO client secret(s) use a previous key.` означает, что предыдущий ключ можно удалить. `cannot be decrypted` означает, что значение не читается ни одним из настроенных ключей: добавьте предыдущий ключ в `DJANGO_SECRET_KEY_FALLBACKS` и запустите снова.
- Пример: `uv run manage.py security_reencrypt_secrets --dry-run`

### `security_reset_mfa`

- Назначение: сбрасывает двухфакторную аутентификацию пользователя (приложение-аутентификатор, коды по эл. почте, коды восстановления, запомненные устройства). Пользователь подключает её заново при следующем входе. Используйте, когда ни один администратор не может войти в панель администрирования (например, единственный администратор потерял телефон). В остальных случаях используйте **Пользователи > Сбросить двухфакторную аутентификацию** в панели администрирования.
- Аргументы/параметры: `{user}` эл. почта пользователя, `--reason=` (обязателен), `--actor=` (обязателен. Администратор, принявший решение о сбросе).
- Аудит: записывается (в журнал действий и журнал безопасности, с причиной)
- Пример: `uv run manage.py security_reset_mfa admin@example.ac.kr --reason="Phone lost, identity verified by phone call" --actor=it-lead@example.ac.kr`

### `security_unlock_user`

- Назначение: снимает блокировку учётной записи, заблокированной из-за повторного ввода неверного пароля, до окончания срока блокировки. То же, что **Пользователи > Разблокировать вход** в панели администрирования.
- Аргументы/параметры: `{user}` эл. почта пользователя, `--reason=` (обязателен).
- Аудит: записывается (также в журнал безопасности)
- Как читать вывод: `The account is not locked.` означает, что ничего не изменено.
- Примечание: пороги блокировки (неудачные попытки, длительность блокировки) задаются в разделе **Настройки > Способы входа** панели администрирования.

## Лица и личные дела студентов (этап 2)

### `people_find_duplicates`

- Назначение: выводит лица, которые, по-видимому, являются одним человеком. Критерии — одинаковый номер удостоверения личности (поисковый хеш) или одинаковые имя латиницей и дата рождения. Объединённые лица исключаются.
- Параметры: `--limit=100` (число выводимых групп).
- Аудит: не записывается (только чтение)
- Коды завершения: 2, если есть кандидаты в дубликаты.
- Дальнейшие действия: проверьте каждую группу в разделе **Лица** панели администрирования и, если это один человек, выполните **Объединить дубликат** со страницы лица, которое нужно оставить. Объединение нельзя отменить ([руководство администратора, глава 14](../admin/14-merge-and-invitations.md)).
- Пример: `uv run manage.py people_find_duplicates --limit=50`

## Приём (этап 3)

### `admission_matriculate`

- Назначение: создаёт личные дела студентов (новые студенческие номера) для подтвердивших зачисление абитуриентов приёмной кампании. То же, что массовое **Создать личное дело** в разделе **Приём > Заявления** панели администрирования (`MatriculateApplicant`). Каждый абитуриент обрабатывается отдельно, поэтому сбой одного не останавливает остальных.
- Аргументы/параметры: `cycle` код приёмной кампании, `--term=` (обязателен; код семестра поступления, например `2027-SP`; дата зачисления — первый день семестра), `--actor=` (обязателен; учётная запись с разрешением `Создавать личные дела для принятых абитуриентов`; обрабатываются только абитуриенты в области действия этой учётной записи), `--dry-run` (только список).
- Аудит: записывается (кампания, семестр, кандидаты, созданные, номера заявлений с ошибками). Для каждого абитуриента также создаётся бизнес-запись аудита (`application.matriculated`).
- Коды завершения: 1, если код кампании или семестра неизвестен или нет `--actor`; 2, если обработка абитуриента не удалась.
- Пример: `uv run manage.py admission_matriculate DEMO-2027-REG --term=2027-SP --actor=admissions@example.ac.kr --dry-run`
- При сбое: `Only accepted offers without a student record ...` означает, что у абитуриента уже есть личное дело или он не подтвердил зачисление; `The program is not in effect on the admission date.` означает, что программа не действует на дату зачисления (проверьте срок действия программы в разделе «Справочные данные > Программы»); `not in your scope` означает, что заявление вне области действия учётной записи `--actor`.

### `admission_expire_drafts`

- Назначение: помечает как **Истёк срок** черновики заявлений закрытых кампаний и черновики, не изменявшиеся в течение заданного срока (**Настройки > Приём > Аннулировать неизменяемые черновики через (дней)**, по умолчанию 90). Заявления с истёкшим сроком больше не мешают подать новое заявление в ту же кампанию.
- Когда: по расписанию ежедневно в 03:10 (задача Celery beat `admission.expire_drafts` выполняет эту команду).
- Параметры: `--dry-run` (только подсчёт).
- Аудит: записывается (число заявлений с истёкшим сроком)
- Пример: `uv run manage.py admission_expire_drafts --dry-run`

## Группы (этап 4)

### `section_copy`

- Назначение: начинает планирование нового семестра с групп предыдущего семестра. То же, что **Группы > Копировать из другого семестра** в панели администрирования (`CopySections`). Копирует неотменённые группы как черновики вместе с преподавателями (если они ещё работают), временем занятий и аудиториями, распределением мест (время открытия сдвигается на разницу дат начала семестров) и программой дисциплины (как закрытый черновик). Версия дисциплины заменяется версией, действующей на начало нового учебного периода.
- Аргументы/параметры: `from-term`, `to-term` коды семестров (например, `2026-FA`), `--org-unit=` (только группы этого кода подразделения; можно повторять), `--dry-run` (выполняет копирование в транзакции и откатывает его, поэтому отчёт точен), `--actor=` (обязателен. Копируются только группы в пределах области действия разрешения `Планировать группы` этой учётной записи).
- Аудит: записывается (исходный и целевой семестры, число скопированных, пропущенных и требующих проверки; при реальном копировании также записывается бизнес-событие аудита `sections.copied`)
- Как читать вывод: `skipped` означает, что в целевом семестре уже есть группа с тем же кодом или нет действующей версии дисциплины; `note` означает, что группа скопирована, но что-то не перенесено (скопирована без аудитории, потому что она уже занята, уволившийся преподаватель и т. п.). Учебные периоды сопоставляются по коду; если такого нет, группа попадает в учебный период на весь семестр.
- Коды завершения: 1 при неизвестном коде семестра или отсутствии `--actor`.
- Пример: `uv run manage.py section_copy 2026-FA 2027-FA --actor=academic@example.ac.kr --dry-run`

### `schedule_check_conflicts`

- Назначение: проверяет группы семестра перед публикацией расписания. Двойное бронирование аудиторий и преподавателей уже предотвращает БД; команда находит проблемы, которые БД допускает: число мест больше вместимости аудитории, версия дисциплины, не действующая на дату начала учебного периода, уволившийся преподаватель, распределение мест сверх числа мест, даты занятий вне учебного периода. Она также проверяет конфликты аудиторий в данных, поступивших без ограничений, например при восстановлении из резервной копии.
- Аргументы: `term` код семестра.
- Аудит: не записывается (только чтение)
- Коды завершения: 2 при наличии проблем, 1 при неизвестном коде семестра. Группы, у которых ещё нет преподавателя, аудитории или времени занятий, показываются только для сведения (`Note`).
- Пример: `uv run manage.py schedule_check_conflicts 2027-SP`

## Запись на дисциплины (этап 5)

### `registration_preflight`

- Назначение: проверяет семестр перед открытием записи. Показывает периоды записи и добавления/отказа, набор правил, число опубликованных групп, группы с числом мест 0, распределение мест сверх числа мест, версии дисциплин, не действующие на дату начала учебного периода, число активных студентов, не охваченных лимитом кредитов, и число студентов с ограничением на запись.
- Аргументы: `term` код семестра (например, `2027-SP`).
- Аудит: не записывается (только чтение)
- Коды завершения: 2 при наличии проблем. Отсутствие набора правил показывается для сведения, а не как проблема (применяются значения правил по умолчанию).
- Пример: `uv run manage.py registration_preflight 2027-SP`

### `registration_simulate`

- Назначение: показывает по каждому правилу, что произойдёт, если студент запишется в группу сейчас (или в заданный момент). Ничего не сохраняется, и попытка не записывается. Используйте для вопросов «почему я не могу записаться?».
- Аргументы: `student-number` студенческий номер, `section` `код дисциплины-код группы` (например, `CSE2010-01`).
- Параметры: `--term=` (код семестра. По умолчанию — последний семестр, в котором есть эта группа), `--at=` (момент оценки. Например, `"2027-02-10 10:00 Asia/Seoul"`).
- Аудит: не записывается (только чтение)
- Как читать вывод: по каждому правилу — пройдено/не пройдено, запрет/предупреждение и сообщение. Правило, на которое действует исключение, показывается как не пройденное, но не запрещает запись. Число мест показывается отдельно под таблицей правил.
- Коды завершения: 2, если в записи было бы отказано.
- Пример: `uv run manage.py registration_simulate 202612345 CSE2010-01 --at="2027-02-10 10:00 Asia/Seoul"`

### `waitlist_promote`

- Назначение: по очереди записывает студентов из листа ожидания в группы, где есть свободные места. При переводе все правила проверяются снова; записи листа ожидания, не прошедшие правило, удаляются из листа ожидания (с записью причины). Листы ожидания групп, у которых закрыты и период записи, и период добавления/отказа, истекают. Студенты получают результат по эл. почте.
- Аргументы/параметры: `term?` код семестра (по умолчанию — все семестры с записями в листах ожидания), `--actor=`.
- Аудит: записывается (число групп, переведённых, удалённых, истёкших)
- Когда: при отмене записи, выходе из дисциплины или открытии распределённых мест затронутая группа обрабатывается сразу заданием очереди. Эта команда — ежечасная страховка по расписанию, обрабатывающая всё пропущенное.
- Пример: `uv run manage.py waitlist_promote 2027-SP --actor=registrar@example.ac.kr`

### `registration_release_reserved_seats`

- Назначение: помечает как обработанные распределения мест, время открытия которых прошло (например, места, зарезервированные для студентов специальности), и ставит в очередь задание перевода из листа ожидания для этих групп. Зарезервированные места становятся общими в расчёте сразу по наступлении времени открытия, поэтому команда лишь передаёт места листу ожидания.
- Аудит: не записывается (выполняется каждые 5 минут. Результаты перевода — в записях о записи на дисциплины)
- Когда: по расписанию (каждые 5 минут, задача Celery beat `registration.release_reserved_seats`). Задача перевода — `registration.promote_waitlist` для каждой группы (в каждой группе по одной за раз благодаря блокировке Redis).
- Пример: `uv run manage.py registration_release_reserved_seats`

## Оценки (этап 6)

### `term_close`

- Назначение: закрывает семестр. Все оценки семестра должны быть утверждены. Для каждой порции студентов (100) рассчитываются итоги семестра (кредиты, средний балл за семестр и накопленный) и определяются академический статус (нормальная успеваемость, академическое предупреждение, рассмотрение отчисления) и право на отличие (задачи `grading.close_term_records` в chord Celery); завершающая задача `grading.finish_term_close` затем ранжирует отличия по программам, закрывает итоги семестра как официальные записи и переводит семестр в состояние **Оценки закрыты**. Ход выполнения хранится в `job_batches` и показывается над списком **Оценки > Итоги семестров**. По завершении сотрудник, запустивший закрытие, получает письмо. То же, что **Оценки > Итоги семестров > Закрыть семестр** в панели администрирования.
- Аргументы/параметры: `term` код семестра, `--dry-run` (только проверяет, можно ли закрыть семестр), `--reason=` (причина, сохраняемая в записи), `--actor=`.
- Аудит: записывается (число студентов, число групп с неутверждёнными оценками, ID пакета). По завершении закрытия запись аудита `term.closed` содержит число академических предупреждений, рассмотрений отчисления и отличий.
- Коды завершения: 2, если в некоторых группах есть неутверждённые оценки (выводится число неутверждённых по каждой группе). 1, если семестр не в состоянии «опубликован».
- Когда: после завершения ввода и утверждения оценок. Следите за пакетом во Flower и на экране итогов семестров. Без воркера Celery состояние семестра не меняется. Порция, завершившаяся ошибкой базы данных, повторяется до 3 раз; если ошибка остаётся, пакет остаётся неудавшимся и семестр не меняется (устраните причину и запустите снова; повторный запуск даёт тот же результат).
- Примеры: `uv run manage.py term_close 2026-FA --dry-run`, `uv run manage.py term_close 2026-FA --reason="Fall 2026 grades closed" --actor=registrar@example.ac.kr`

### `grades_recalculate`

- Назначение: пересчитывает итоги семестров (кредиты, средний балл за семестр и накопленный) по утверждённым оценкам. Используйте, чтобы применить изменённые правила оценивания (число знаков среднего балла, обработка повторного изучения) к прошлым семестрам. Академический статус и отличия сохраняют значения, определённые при закрытии семестра. Одобренное изменение оценки автоматически пересчитывает данные этого студента, поэтому для него команда не нужна.
- Параметры: `--term=` (студенты с оценками в этом семестре, начиная с этого семестра), `--student-number=` (один студент), `--reason=` (обязателен), `--actor=`.
- Аудит: записывается (число студентов, причина)
- Коды завершения: 1 без причины или при неизвестном коде семестра или студенческом номере.
- Пример: `uv run manage.py grades_recalculate --term=2026-SP --reason="GPA changed to three decimal places"`

### `grades_remind_missing`

- Назначение: отправляет письма преподавателям групп, оценки которых ещё не отправлены (не введены или сохранены как черновик). Группы объединяются по преподавателю в одно письмо.
- Аргументы/параметры: `term` код семестра, `--dry-run` (выводит адресатов без отправки), `--actor=`.
- Аудит: записывается (группы, преподаватели, отправленные письма)
- Когда: за несколько дней до закрытия периода ввода оценок. При необходимости добавьте в расписание.
- Пример: `uv run manage.py grades_remind_missing 2026-FA --dry-run`

## Анкетирование по дисциплинам (этап 7)

### `evaluation_remind`

- Назначение: отправляет письма студентам, у которых остались неоценённые дисциплины, пока открыт период анкетирования. Оставшиеся дисциплины объединяются по студенту в одно письмо (на языке получателя).
- Аргументы/параметры: `term` код семестра, `--dry-run` (только число адресатов, ничего не отправляется), `--actor=`.
- Аудит: записывается (студенты-адресаты, отправленные письма)
- Коды завершения: 1 при неизвестном коде семестра.
- Когда: один-два раза за период анкетирования. При необходимости добавьте в расписание.
- Пример: `uv run manage.py evaluation_remind 2026-FA --dry-run`

### `evaluation_publish_results`

- Назначение: публикует результаты анкетирования семестра для преподавателей. То же, что **Анкетирование по дисциплине > Анкетирование по семестрам > Опубликовать результаты** в панели администрирования. Даже после публикации результаты видны только для групп, достигших минимального числа ответов и доли ответивших.
- Аргументы/параметры: `term` код семестра, `--actor=` (учётная запись с разрешением `Управлять анкетами, анкетированием по семестрам и публикацией`; записывается как опубликовавший).
- Аудит: записывается (число ответов, были ли уже опубликованы). Бизнес-аудит `evaluation.published`.
- Коды завершения: 1 при неизвестном коде семестра или семестре без анкетирования.
- Когда: после завершения периода анкетирования и обработки оценок. Уже опубликованный семестр не меняется.
- Пример: `uv run manage.py evaluation_publish_results 2026-FA --actor=academic-affairs@example.ac.kr`

## Справки (этап 8)

### `certificate_verify`

- Назначение: проверяет код проверки справки по тем же критериям, что и общедоступная страница проверки. Выводит вид, регистрационный номер, дату выдачи и замаскированные данные владельца.
- Аргументы/параметры: `code` код проверки (регистр не важен).
- Аудит: нет (только чтение)
- Коды завершения: 0, если справка действительна; 2 при неизвестном коде, аннулированной справке или истёкшем сроке проверки.
- Пример: `uv run manage.py certificate_verify 7Q2M9XK4TB0RWZ5C1HNA`

### `certificate_render`

- Назначение: заново формирует PDF выданной справки по текущим данным и шаблону, заменяя сохранённый файл. То же, что **Справки > Выданные справки > Сформировать заново** в панели администрирования. Регистрационный номер и код проверки остаются прежними; контрольная сумма меняется. PDF формирует Gotenberg.
- Аргументы/параметры: `issue` регистрационный номер, `--reason=` (обязателен), `--actor=` (учётная запись с разрешением `Выдавать, формировать заново и аннулировать справки`).
- Аудит: записывается (регистрационный номер, новая контрольная сумма); бизнес-аудит `certificate.rerendered`.
- Коды завершения: 1 без причины, при неизвестном регистрационном номере или если PDF не удаётся сформировать.
- Когда: чтобы заново сформировать конкретную справку после исправления шаблона, написания имени или `APP_URL`.
- Пример: `uv run manage.py certificate_render ENR-2026-000001 --reason="Name spelling corrected"`

## Экзамены (этап 9)

### `assessment_import_results`

- Назначение: вводит результаты экзаменационной сессии из CSV. Те же правила, что и у **Экзаменационные сессии > Импорт результатов (CSV)** в панели администрирования (только зарегистрированные студенты, сдача определяется по баллам, повторный ввод до публикации заменяет результат, после публикации строки сообщаются как ошибки).
- Аргументы/параметры: `type` код вида экзамена / `held_date` дата экзамена `YYYY-MM-DD` / `file` CSV в UTF-8 со строкой заголовков, `--actor=` (обязателен, записывается как лицо, внёсшее результаты), `--dry-run` (только проверка строк, ничего не записывается).
- Формат столбцов: [руководство администратора, глава 24](../admin/24-assessments.md).
- Аудит: записывается (сессия, имя файла, число строк, число введённых/неявок/ошибок). Каждый результат также получает бизнес-запись аудита `assessment.result_recorded`.
- Коды завершения: 1, если сессия не найдена, файл не читается или нет `--actor`; 2 при наличии строк с ошибками (остальные строки записываются).
- Пример: `uv run manage.py assessment_import_results ENG_COMP 2026-05-15 storage/eng.csv --actor=registrar@example.ac.kr --dry-run`

### `assessment_publish_results`

- Назначение: публикует результаты сессии для студентов. То же, что **Экзаменационные сессии > Опубликовать результаты** в панели администрирования. После публикации результаты меняются только через запросы на исправление.
- Аргументы/параметры: `type` код вида экзамена / `held_date` дата экзамена, `--actor=` (обязателен, с разрешением регистрировать студентов, вводить и публиковать результаты).
- Аудит: записывается (сессия, число результатов) и бизнес-запись аудита `assessment.results_published`
- Коды завершения: 1, если сессия не найдена, уже опубликована, нет `--actor` или у него нет разрешения.
- Когда: после завершения ввода результатов.
- Пример: `uv run manage.py assessment_publish_results ENG_COMP 2026-05-15 --actor=registrar@example.ac.kr`

## Посещаемость (этап 10)

### `attendance_generate_sessions`

- Назначение: создаёт занятия для каждой группы семестра по её времени занятий (день недели, время, пара). То же, что **Создать по расписанию** на портале преподавателя и **Создать занятия** на вкладке **Занятия** панели администрирования. Существующие занятия и их посещаемость сохраняются (повторный запуск безопасен). Отменённые группы пропускаются.
- Аргументы/параметры: `term` код семестра, `--section=` (код дисциплины-код группы, например `CSE2010-01`, только одна), `--dry-run` (только число групп), `--actor=`.
- Аудит: записывается (семестр, группы, созданные занятия)
- Когда: до начала семестра, после утверждения времени занятий. Запустите снова при изменении времени занятий.
- Пример: `uv run manage.py attendance_generate_sessions 2026-FA --dry-run`

## Выпуск (этап 11)

### `degree_audit_run`

- Назначение: сохраняет проверку требований к выпуску для каждого обучающегося студента. То же, что **Проверки требований к выпуску > Выполнить проверки** в панели администрирования. Основой для обработки выпуска служит последняя сохранённая проверка. Каждый запуск добавляет новые снимки.
- Параметры: `--term=` (код семестра, к которому относится проверка), `--student-number=` (один студент), `--min-year-level=` (только этот курс и старше), `--actor=`.
- Аудит: записывается (число студентов, число выполнивших требования). С `--actor` также записывается бизнес-аудит `graduation.audits_run`.
- Коды завершения: 1 при неизвестном коде семестра.
- Когда: перед рассмотрением выпуска (конец семестра) и после изменения наборов требований или эквивалентных дисциплин.
- Пример: `uv run manage.py degree_audit_run --term=2026-FA --min-year-level=4 --actor=registrar@example.edu`

## Интеграция с LMS (этап 12)

### `lms_sync`

- Назначение: передаёт опубликованные группы на платформу (создание и связывание курса, преподаватели, записанные студенты). Делает для всего семестра то же, что **Связи с курсами > Синхронизировать снова** в панели администрирования. Для уже связанных групп только повторно обеспечивается состояние (идемпотентно). Каждый шаг сохраняется в **Журналы синхронизации**.
- Аргументы/параметры: `{platform}` код платформы, `--term=` (код семестра, по умолчанию — все незавершённые семестры), `--section=` (один код дисциплины-код группы, например `CSE2010-01`), `--dry-run` (только записывает то, что было бы отправлено, как «skipped»), `--actor=`.
- Аудит: записывается (платформа, группы, участники, сбои)
- Коды завершения: 1 при неизвестном коде платформы или семестра, 2 при сбое хотя бы одной группы (выводится ошибка по каждой группе).
- Когда: до начала семестра, после активации новой платформы.
- Пример: `uv run manage.py lms_sync DEMO --term=2026-FA --dry-run`

### `lms_reconcile`

- Назначение: сравнивает списки курсов платформы со списками записанных в информационной системе студентов, добавляет недостающих участников и удаляет лишних. Ещё не связанные группы синхронизируются целиком. Расхождения сохраняются в журнале синхронизации (`reconcile`, `missing` и `extra` в `payload`).
- Аргументы/параметры: `{platform?}` (если не указано — все активные платформы), `--term=` (по умолчанию — незавершённые семестры), `--dry-run` (только записывает расхождения), `--actor=`.
- Аудит: записывается (группы по платформам, число добавленных/удалённых/сбоев)
- Коды завершения: 1 при неизвестном коде платформы или семестра или если нет активной платформы, 2 при сбое хотя бы одной группы.
- Когда: по расписанию ежедневно в 02:30 как задача `lms.reconcile` (Celery beat). Запускайте вручную после сбоя платформы.

### `api_issue_token`

- Назначение: выпускает токен интеграции API для учётной записи ([ADR 0004-django](../../../../porting/decisions/0004-django-api-tokens.md)), обычно служебной учётной записи только с нужными разрешениями (LMS: `lms.manage`, BI: `reports.view`). Токен выводится **один раз**, в первой строке стандартного вывода; база данных хранит только его хеш. Запросы передают его в заголовке `Authorization: Token <token>`.
- Аргументы/параметры: `{email}` эл. почта учётной записи, `--days=` (срок действия от 1 до 365 дней, по умолчанию `API_TOKEN_TTL_DAYS` = 90), `--reason=` (назначение, записывается в аудит), `--actor=`.
- Аудит: записывается (`api.token_issued`: префикс ключа и срок действия; сам токен — никогда)
- Коды завершения: 1 при неизвестной или неактивной учётной записи или сроке действия вне диапазона.
- Пример: `uv run manage.py api_issue_token moodle-sync@example.ac.kr --days=365 --reason="Moodle callbacks" --actor=admin@example.ac.kr`

### `api_revoke_tokens`

- Назначение: отзывает токены API учётной записи (все или один с `--key=`). `--list` только выводит токены (префикс ключа, время выпуска и окончания срока).
- Аргументы/параметры: `{email}`, `--key=` (префикс ключа), `--list`, `--reason=`, `--actor=`.
- Аудит: записывается (`api.token_revoked`: префиксы отозванных ключей)
- Коды завершения: 1 при неизвестной учётной записи или отсутствии токена с указанным `--key`.
- Когда: при прекращении интеграции, возможной утечке токена или смене ответственного.

## Эксплуатационные проверки и очистка (этап 13)

### `system_health_check`

- Назначение: проверяет конфигурацию и ключи (`DJANGO_SECRET_KEY`, ключи персональных данных, `DEBUG`), подключение к БД и роли (runtime, migrator, reporting), RLS в таблицах персональных данных, неприменённые миграции, синхронизацию каталога разрешений, Redis, воркеры Celery, Gotenberg, запись в закрытое хранилище и сигнал активности beat (`core.heartbeat`, в пределах 5 минут).
- Параметры: `--json` (вывод для мониторинга).
- Аудит: нет (только чтение)
- Коды завершения: 2 при неудаче любой проверки.
- Когда: сразу после развёртывания, при подозрении на сбой, периодически из системы мониторинга. Балансировщики нагрузки используют `/api/v1/health/`.
- Примеры

  ```bash
  uv run manage.py system_health_check
  uv run manage.py system_health_check --json
  ```

### `audit_seal`

- Назначение: связывает новые строки таблиц аудита (`audit.record_changes`, `audit.activity_log`, `audit.security_events`) в цепочку хешей ([целостность аудита](audit-and-maintenance.md)). Выполняется через подключение владельца схемы (`migrator`).
- Параметры: `--table=` (одна из record_changes, activity_log, security_events; можно повторять), `--actor=`.
- Аудит: записывается (число запечатанных строк по таблицам)
- Когда: по расписанию ежедневно в 03:30.
- Примеры

  ```bash
  uv run manage.py audit_seal
  uv run manage.py audit_seal --table=activity_log
  ```

### `audit_verify_chain`

- Назначение: заново вычисляет хеши содержимого и цепочку строк аудита, чтобы обнаружить подделку, удаление и изменение порядка. Выводит по каждой таблице проверенные строки, запечатанные строки, несоответствия и первый несоответствующий id.
- Параметры: `--table=`.
- Аудит: нет (только чтение)
- Коды завершения: 2 при наличии несоответствия.
- Когда: перед резервным копированием, при проверках безопасности, после очистки.

### `audit_prune`

- Назначение: удаляет **запечатанные** строки аудита с истёкшим сроком хранения. Выполняется через подключение владельца схемы в транзакции с `app.audit_maintenance = on`. Незапечатанные строки сохраняются (сначала выполните `audit_seal`). Каждое удаление записывает событие безопасности `audit.pruned` (таблица, граничная дата, число удалённых строк, диапазон id, `chain_hash` граничной строки).
- Параметры: `--before=YYYY-MM-DD` (обязателен; строки до полуночи этого дня), `--table=`, `--dry-run` (только подсчёт), `--actor=`.
- Аудит: записывается (граничная дата, число удалённых строк и диапазон id по таблицам)
- Когда: согласно политике хранения, после резервного копирования.
- Примеры

  ```bash
  uv run manage.py audit_prune --before=2023-03-01 --dry-run
  uv run manage.py audit_prune --before=2023-03-01 --table=record_changes --actor=ops@example.edu
  ```

### `media_prune_orphans`

- Назначение: удаляет строки медиафайлов, владелец которых больше не существует, и каталоги (`<media id>/`) в закрытом хранилище без строки (фотографии лиц, документы заявлений, PDF справок, подтверждающие документы экзаменов).
- Параметры: `--dry-run` (только список), `--actor=`.
- Аудит: записывается (строки, каталоги)
- Когда: ежемесячно или после массового удаления.

## Ключи шифрования персональных данных (этап 0)

### `pii_generate_key`

- Назначение: выводит новые ключи (32 байта, `base64:...`) для `PII_ENCRYPTION_KEY` и `PII_HASH_KEY`. Ничего не сохраняет.
- Аудит: не записывается
- Внимание: смена `PII_HASH_KEY` делает недействительными все поисковые хеши (`*_hash`). Выполняйте ротацию только ключа шифрования: перенесите старый ключ в `PII_PREVIOUS_KEYS`, затем выполните `pii_reencrypt`.
- Пример

  ```bash
  uv run manage.py pii_generate_key
  ```

### `pii_reencrypt`

- Назначение: после ротации ключа заново шифрует текущим ключом персональные данные, зашифрованные предыдущим ключом. Выполняется как группа задач Celery по порциям записей. Записи, уже зашифрованные текущим ключом, не затрагиваются.
- Аргументы: модель с зашифрованными полями персональных данных (`app_label.Model`, например `person.Person`).
- Параметры: `--chunk=500` (записей на задачу), `--dry-run` (только подсчитывает записи с предыдущим ключом), `--force` (без подтверждения), `--actor=`.
- Аудит: записывается (ID пакета, число задач / число при предпросмотре)
- Проверка: следите за задачами во Flower. Когда они завершатся и `--dry-run` сообщит 0, удалите предыдущий ключ из `PII_PREVIOUS_KEYS`.
- Примеры

  ```bash
  uv run manage.py pii_reencrypt person.Person --dry-run
  uv run manage.py pii_reencrypt person.Person --force --actor=ops@example.edu
  ```

## Локализация (этап 0)

### `i18n_missing`

- Назначение: извлекает переводимые строки из исходного кода так же, как `makemessages` (без записи файлов), сравнивает их со всеми каталогами (глобальный `locale/` и `locale/` каждого приложения) и выводит по каждому языку отсутствующие строки (нет в каталоге, пустой `msgstr`, fuzzy, отличающиеся подстановки) и устаревшие записи.
- Аргументы/параметры: `[locale]` (только один язык, например `ko`, `zh-hans`, `lo`), `--strict` (код завершения 2 при отсутствующих строках; используется в CI), `--no-extract` (проверять только каталоги, без сканирования исходного кода).
- Аудит: не записывается
- Требуется: GNU gettext (`xgettext`, `msguniq`).
- Примеры

  ```bash
  uv run manage.py i18n_missing --strict
  uv run manage.py i18n_missing lo
  ```

### `i18n_export`

- Назначение: записывает таблицу для переводчиков (`.xlsx` или `.csv`, выбирается по расширению). Столбцы: `catalog` (расположение каталога), `context`, `source` (английский msgid), `source_plural`, `translation`, `note` (исходный ключ).
- Аргументы/параметры: `{locale} {path}`, `--missing` (только строки без перевода).
- Аудит: не записывается
- Пример: `uv run manage.py i18n_export ko storage/ko.xlsx --missing`

### `i18n_import`

- Назначение: записывает заполненную переводчиками таблицу обратно в каталоги (`.po`) и компилирует их (`.mo`). Импортируются только строки, существующие в каталогах (тот же каталог, контекст и английский текст); пустые переводы пропускаются.
- Аргументы/параметры: `{locale} {path}`, `--dry-run` (вывести строки, которые были бы записаны), `--actor=`.
- Аудит: записывается (язык, число переводов)
- Примечание: каталоги хранятся в репозитории. После импорта зафиксируйте изменения `.po` (commit).

### `i18n_makemessages`

- Назначение: запускает `makemessages` из корня репозитория, чтобы все каталоги соответствовали исходному коду (ko, zh_Hans, lo). Строки попадают в `locale/` приложения, если он есть, иначе — в глобальный `locale/`. `.venv`, `tests`, `docs` и подобные каталоги пропускаются.
- Параметры: как у Django `makemessages` (`-l`, `--no-obsolete`, ...).
- Аудит: не записывается
- Пример: `uv run manage.py i18n_makemessages`

## Проверки (этап 0)

### `pdf_sample`

- Назначение: формирует PDF с таблицей, в которой смешаны хангыль, иероглифы CJK, лаосское и тайское письмо, деванагари, кириллица и латиница, чтобы проверить шрифты и подключение к службе PDF (Gotenberg).
- Аргумент: `[path]` (по умолчанию `pdf-sample.pdf`, относительно закрытого файлового хранилища `PRIVATE_MEDIA_ROOT`).
- Аудит: не записывается
- При сбое: код завершения 1. При ошибках подключения проверьте `GOTENBERG_URL`, `GOTENBERG_TIMEOUT` и контейнер Gotenberg.
- Пример: `uv run manage.py pdf_sample`

### `naming_check`

- Назначение: проверяет схему базы данных и исходный код на соответствие [соглашениям об именовании](../../../development/naming.md). Проверяются имена таблиц и столбцов в фактическом каталоге базы данных (схемы `public`, `audit`, `reporting`), имена файлов миграций приложений Ninefruits, имена команд управления (`context_action`), а также msgid и msgctxt каталогов переводов (`.po`).
- Правила: snake_case, запрещённые суффиксы (`_old`, `_new`, `_backup`, `_tmp`, даты, числа), имена с кодом языка, столбцы времени без часового пояса (`timestamp without time zone`), имена логических столбцов (`is_`, `has_`, `can_` или глагол), имена столбцов дат (`_date`), msgid в виде семантических ключей (`registration.errors.x`). Таблицы, определённые Django и пакетами (`django_*`, allauth, Celery beat, `settings`, `cache`, `jobs`, `media` и т. д.), исключаются.
- Параметры: `--database=` (проверяемое подключение к базе данных, по умолчанию `default`), `--skip-database` (только проверка файлов, без базы данных).
- Аудит: не записывается
- Код завершения: 2 при обнаружении проблем.
- Пример

  ```bash
  uv run manage.py naming_check
  ```
