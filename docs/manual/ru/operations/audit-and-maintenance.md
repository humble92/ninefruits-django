# Целостность аудита и регулярное обслуживание

- Для кого: ИТ-специалисты по эксплуатации, специалисты по безопасности
- Связанные документы: [руководство администратора, глава 4, аудит](../admin/04-audit.md), [справочник команд](commands.md), [резервное копирование и восстановление](backup-restore.md)

## Цепочка хешей аудита

Таблицы аудита (`audit.record_changes` для изменений данных, `audit.activity_log` для бизнес-действий, `audit.security_events` для событий безопасности) допускают только добавление (это обеспечивают триггеры). Поверх этого есть механизм, который **выявляет** подделку.

- При вставке каждая строка получает SHA-256 своего содержимого (`row_hash`).
- `audit_seal` (задание по расписанию `audit.seal`, ежедневно в 03:30) связывает новые строки в цепочку в порядке ID: `chain_hash = SHA-256(previous chain_hash || row_hash)`. Она вызывает функцию БД `audit.seal()` через подключение владельца схемы (`migrator`).
- `audit_verify_chain` заново вычисляет хеш содержимого и цепочку каждой строки. По каждой таблице она выводит проверенные строки, запечатанные строки, несоответствия и первый несоответствующий id; строка с изменённым содержимым сообщается как «несоответствие строки», отсутствующая или переставленная строка — как «несоответствие цепочки», и команда возвращает код завершения 2.

```bash
uv run manage.py audit_seal
uv run manage.py audit_verify_chain
uv run manage.py audit_verify_chain --table=security_events
```

Что нужно помнить

- Строку, изменённую до запечатывания (в течение того же дня), цепочка обнаружить не может. Поэтому запечатывание выполняется ежедневно, а проверка — перед резервным копированием и при проверках безопасности.
- Когда очистка (`audit_prune`) удаляет самые старые строки, связь первой оставшейся строки не проверяется (удалённый диапазон сохраняется в записи аудита команды очистки).
- Задать `app.audit_maintenance = on` может только администратор БД (владелец схемы `app_migrator`). У роли приложения (`app_runtime`) нет прав UPDATE и DELETE на таблицы аудита.

## Хранение и очистка

1. Определите сроки хранения (например, изменения данных — 3 года, бизнес-действия — 5 лет, события безопасности — 1 год).
2. Перед очисткой сделайте резервную копию ([резервное копирование и восстановление](backup-restore.md)) и убедитесь в целостности цепочки командой `audit_verify_chain`.
3. Проверьте количество командой `uv run manage.py audit_prune --before=YYYY-MM-DD --table=record_changes --dry-run`, затем выполните её без `--dry-run` (запишите учётную запись оператора через `--actor=`). Незапечатанные строки никогда не удаляются, поэтому сначала выполните `audit_seal`.
4. После очистки снова выполните `audit_verify_chain`.

Сама очистка записывается: каждый запуск заносит в журнал действий (журнал `command`) граничную дату, параметры, исполнителя и пользователя ОС, а также по каждой таблице **число удалённых строк, диапазон удалённых ID и chain_hash на границе**; фактическое удаление также записывается как событие безопасности `audit.pruned` (**Аудит > События безопасности**). Эта запись сама связывается в цепочку при следующем запечатывании. Именно из-за этой границы `audit_verify_chain` не проверяет связь первой оставшейся строки; сравнение граничного хеша с записью об очистке позволяет убедиться, что удалённый диапазон соответствует записанной очистке.

## Очистка файлов

`uv run manage.py media_prune_orphans --dry-run` выводит строки медиафайлов, владелец которых больше не существует, и каталоги без строки (`PRIVATE_MEDIA_ROOT/<media id>/`); без `--dry-run` удаляет их. Охватывает фотографии лиц, документы заявлений, PDF справок и подтверждающие документы экзаменов. Выполняйте ежемесячно или после массового удаления.

## Проверки работоспособности

| Проверка | Как | При сбое |
|---|---|---|
| Состояние службы | `GET /api/v1/health/` (без входа, для балансировщиков нагрузки и мониторинга) | `unavailable` (503), если не отвечают БД или кеш, `degraded` (200), если сигнал активности планировщика старше 5 минут, иначе `ok`. После входа с разрешением `Открывать панель администрирования` также показывает каждую проверку (`database`, `cache`, `scheduler`) |
| Полная проверка | `uv run manage.py system_health_check [--json]` | 12 проверок: ключи, роли БД, RLS, миграции, каталог разрешений, Redis, воркеры Celery, Gotenberg, хранилище, сигнал активности beat. Код завершения 2 при неудаче любой |
| Настройки рабочей среды | `uv run manage.py check --deploy` | Предупреждения о `DEBUG`, перенаправлениях на HTTPS, HSTS, защищённых cookie, секретном ключе |
| Миграции | `uv run manage.py migrate --check` | Код завершения 1 при неприменённых миграциях |
| Каталог разрешений | `uv run manage.py security_sync_permissions` | Переносит список разрешений из кода в БД (повторный запуск безопасен) |
| Служба PDF | `uv run manage.py pdf_sample` | Подключение к Gotenberg, шрифты |
| Переводы | `uv run manage.py i18n_missing --strict` | Код завершения 2 при отсутствующих переводах |
| Цепочка аудита | `uv run manage.py audit_verify_chain` | Код завершения 2 при несоответствии |
| Очередь | Flower, `uv run celery -A config inspect ping` | Воркер не отвечает |

Подключите мониторинг к HTTP-статусу и значению `status` в `/api/v1/health/`; остальное выполняйте при развёртывании и в рамках [регулярных проверок](deployment-checklist.md#регулярные-проверки).
