# ການຄຸ້ມຄອງກະແຈ

- ກຸ່ມເປົ້າໝາຍ: ຜູ້ປະຕິບັດງານ IT
- ກ່ຽວຂ້ອງ: [ການຕິດຕັ້ງ](installation.md), [ເອກະສານອ້າງອີງຄຳສັ່ງ](commands.md), [ລາຍການກວດສອບການນຳໃຊ້ລະບົບ](deployment-checklist.md)

| ກະແຈ | ຈຸດປະສົງ | ຖ້າເຮັດເສຍ | ການປ່ຽນ |
|---|---|---|---|
| `DJANGO_SECRET_KEY` | ເຊສຊັນ, CSRF, ການລົງລາຍເຊັນ (ລິ້ງຕັ້ງລະຫັດຜ່ານໃໝ່, ລິ້ງຢືນຢັນອີເມວ, ຄຸກກີຈື່ອຸປະກອນ), ແຮດຊ໌ຂອງລະຫັດຢືນຢັນສອງຂັ້ນຕອນທາງອີເມວ, ການເຂົ້າລະຫັດຄວາມລັບການຢືນຢັນສອງຂັ້ນຕອນ (ຄວາມລັບ TOTP ຂອງແອັບຢືນຢັນ, ລະຫັດກູ້ຄືນ) ແລະ ຄວາມລັບ client ຂອງ SSO | ຜູ້ໃຊ້ທຸກຄົນຖືກອອກຈາກລະບົບ, ລິ້ງທີ່ສົ່ງໄປແລ້ວໃຊ້ບໍ່ໄດ້, ແອັບຢືນຢັນ ແລະ ລະຫັດກູ້ຄືນທີ່ລົງທະບຽນແລ້ວໃຊ້ບໍ່ໄດ້ (ຕ້ອງຣີເຊັດການຢືນຢັນສອງຂັ້ນຕອນເປັນລາຍຜູ້ໃຊ້), ຕ້ອງປ້ອນຄວາມລັບ client ຂອງ SSO ໃໝ່ | ປ່ຽນໂດຍໃສ່ກະແຈເກົ່າໄວ້ໃນ `DJANGO_SECRET_KEY_FALLBACKS` (ຕາມຂັ້ນຕອນຂ້າງລຸ່ມ) |
| `PII_ENCRYPTION_KEY` | ການເຂົ້າລະຫັດຂໍ້ມູນສ່ວນບຸກຄົນ ເຊັ່ນ ເລກບັດປະຈຳຕົວ (AES-256-GCM) | **ກູ້ຄືນຂໍ້ມູນສ່ວນບຸກຄົນທີ່ເຂົ້າລະຫັດແລ້ວບໍ່ໄດ້** | ປ່ຽນໂດຍໃສ່ກະແຈເກົ່າໄວ້ໃນ `PII_PREVIOUS_KEYS` (ຕາມຂັ້ນຕອນຂ້າງລຸ່ມ) |
| `PII_HASH_KEY` | ແຮດຊ໌ສຳລັບຄົ້ນຫາຂໍ້ມູນສ່ວນບຸກຄົນແບບກົງກັນທຸກຕົວ (HMAC-SHA256) | ຄົ້ນຫາບໍ່ໄດ້ (ຂໍ້ມູນຍັງຢູ່) | ຕາມຫຼັກການບໍ່ປ່ຽນ |

ສ້າງ `DJANGO_SECRET_KEY` ດ້ວຍ `uv run python -c "import secrets; print(secrets.token_urlsafe(50))"` ແລະ ສ້າງກະແຈຂໍ້ມູນສ່ວນບຸກຄົນທັງສອງດ້ວຍ `uv run manage.py pii_generate_key`.

ຫຼັກການເກັບຮັກສາ

- ເກັບກະແຈທັງສາມໄວ້ຢ່າງໜ້ອຍສອງຊຸດ ແຍກຈາກການຕັ້ງຄ່າຂອງເຊີບເວີ ໃນບ່ອນເກັບຄວາມລັບ (Vault, ບໍລິການຈັດການຄວາມລັບຂອງຄລາວ ແລະ ອື່ນໆ) ຫຼື ການເກັບແບບອອບລາຍທີ່ປະທັບຕາ.
- ບໍ່ເກັບໄວ້ບ່ອນດຽວກັນກັບໄຟລ໌ສຳຮອງ. ເຖິງແມ່ນໄຟລ໌ສຳຮອງ DB ຮົ່ວໄຫຼ ກໍຕ້ອງອ່ານຂໍ້ມູນສ່ວນບຸກຄົນບໍ່ໄດ້ຖ້າບໍ່ມີກະແຈ.
- ຢ່າໃຊ້ກະແຈຂອງ `.env` ສຳລັບພັດທະນາ ຫຼື ການຕັ້ງຄ່າທົດສອບໃນການນຳໃຊ້ຈິງ.
- ໂປຣເຊສເວັບ (gunicorn), Celery worker ແລະ Celery beat ຕ້ອງອ່ານຄ່າກະແຈດຽວກັນ. ຫຼັງຈາກປ່ຽນກະແຈ ໃຫ້ເລີ່ມທັງສາມໂປຣເຊສໃໝ່ພ້ອມກັນ.

## ຂັ້ນຕອນການປ່ຽນ `DJANGO_SECRET_KEY`

ໃຊ້ສຳລັບການປ່ຽນຕາມກຳນົດ ຫຼື ເມື່ອຜູ້ທີ່ຮູ້ກະແຈປ່ຽນແປງ. ໃຊ້ `SECRET_KEY_FALLBACKS` ຂອງ Django ດັ່ງນັ້ນໃນລະຫວ່າງທີ່ຍັງເກັບກະແຈເກົ່າໄວ້ ຜູ້ໃຊ້ຈະບໍ່ຖືກອອກຈາກລະບົບ. ເປັນວິທີດຽວກັນກັບ `APP_PREVIOUS_KEYS` ຂອງລະບົບເດີມ (Laravel).

1. ສ້າງກະແຈໃໝ່: `uv run python -c "import secrets; print(secrets.token_urlsafe(50))"`.
2. ໃສ່ກະແຈປັດຈຸບັນໄວ້ທຳອິດຂອງ `DJANGO_SECRET_KEY_FALLBACKS` (ຫຼາຍອັນໃຫ້ຂັ້ນດ້ວຍຈຸດ) ແລະ ໃສ່ກະແຈໃໝ່ໄວ້ໃນ `DJANGO_SECRET_KEY`.
   ```
   DJANGO_SECRET_KEY=<ກະແຈໃໝ່>
   DJANGO_SECRET_KEY_FALLBACKS=<ກະແຈເກົ່າ>
   ```
3. ເລີ່ມ gunicorn, Celery worker ແລະ beat ໃໝ່ (Docker: `docker compose restart app worker beat`).
4. ເຂົ້າລະຫັດຄວາມລັບການຢືນຢັນສອງຂັ້ນຕອນ ແລະ ຄວາມລັບ client ຂອງ SSO ຄືນໃໝ່ດ້ວຍກະແຈໃໝ່. ກວດຈຳນວນດ້ວຍ `uv run manage.py security_reencrypt_secrets --dry-run`, ແລ່ນໂດຍບໍ່ມີ `--dry-run`, ແລ້ວກວດວ່າ `--dry-run` ລາຍງານ 0. ຖ້າລຶບກະແຈເກົ່າກ່ອນຂັ້ນຕອນນີ້ ແອັບຢືນຢັນ ແລະ ລະຫັດກູ້ຄືນຈະໃຊ້ບໍ່ໄດ້.
5. ກຳນົດໄລຍະເວລາເກັບກະແຈເກົ່າໄວ້. ລາຍການຕໍ່ໄປນີ້ໃຊ້ໄດ້ສະເພາະໃນລະຫວ່າງທີ່ຍັງເກັບກະແຈເກົ່າໄວ້:

   | ລາຍການ | ໃນລະຫວ່າງທີ່ຍັງເກັບກະແຈເກົ່າ | ຫຼັງຈາກລຶບກະແຈເກົ່າ |
   |---|---|---|
   | ເຊສຊັນການເຂົ້າສູ່ລະບົບ | ຖືກຍ້າຍໄປໃຊ້ກະແຈໃໝ່ໃນຄຳຮ້ອງຂໍທຳອິດຫຼັງການປ່ຽນ | ສະເພາະເຊສຊັນທີ່ບໍ່ໄດ້ໃຊ້ໃນໄລຍະນັ້ນຈະຖືກອອກຈາກລະບົບ |
   | ລິ້ງຕັ້ງລະຫັດຜ່ານໃໝ່, ລິ້ງຢືນຢັນອີເມວ | ໃຊ້ໄດ້ (3 ມື້) | ຕ້ອງຂໍໃໝ່ |
   | ຄຸກກີຈື່ອຸປະກອນ | ໃຊ້ໄດ້ (ຈຳນວນມື້ຈື່ໃນການຕັ້ງຄ່າຄວາມປອດໄພ, ຄ່າເລີ່ມຕົ້ນ 30 ມື້) | ຈະຖາມການຢືນຢັນສອງຂັ້ນຕອນອີກເມື່ອເຂົ້າສູ່ລະບົບຄັ້ງຕໍ່ໄປ |
   | ລະຫັດຢືນຢັນສອງຂັ້ນຕອນທາງອີເມວ | ລະຫັດທີ່ສົ່ງກ່ອນການປ່ຽນບໍ່ກົງກັນ (ໃຊ້ໄດ້ 10 ນາທີ) | ຄືກັນ |

   ໂດຍທົ່ວໄປໃຫ້ເກັບໄວ້ຢ່າງໜ້ອຍ 3 ມື້, ຖ້າຢາກຮັກສາອຸປະກອນທີ່ຈື່ໄວ້ ໃຫ້ເກັບໄວ້ຕາມຈຳນວນມື້ຈື່.
6. ເມື່ອໝົດໄລຍະເວລາ ໃຫ້ລຶບກະແຈເກົ່າອອກຈາກ `DJANGO_SECRET_KEY_FALLBACKS` ແລ້ວເລີ່ມໃໝ່ຄືຂັ້ນຕອນທີ 3.
7. ເກັບກະແຈເກົ່າແບບປະທັບຕາໄວ້ຕະຫຼອດໄລຍະເກັບຮັກສາໄຟລ໌ສຳຮອງ. ຄວາມລັບການຢືນຢັນສອງຂັ້ນຕອນໃນໄຟລ໌ສຳຮອງເກົ່າເຂົ້າລະຫັດດ້ວຍກະແຈນັ້ນ. ເມື່ອກູ້ຄືນໄຟລ໌ສຳຮອງເກົ່າ ໃຫ້ໃສ່ກະແຈນັ້ນໃນ `DJANGO_SECRET_KEY_FALLBACKS` ແລ້ວແລ່ນຂັ້ນຕອນທີ 4.

### ເມື່ອກະແຈຮົ່ວໄຫຼ

1. ແລ່ນຂັ້ນຕອນທີ 1 ຫາ 4 ຂ້າງເທິງທັນທີ (ກະແຈເກົ່າຈຳເປັນສະເພາະສຳລັບການເຂົ້າລະຫັດຄືນໃໝ່ໃນຂັ້ນຕອນທີ 4).
2. ເມື່ອຂັ້ນຕອນທີ 4 ສຳເລັດ ໃຫ້ລຶບກະແຈເກົ່າແລ້ວເລີ່ມໃໝ່ທັນທີ. ເຊສຊັນທັງໝົດຈະສິ້ນສຸດ ແລະ ລິ້ງທີ່ສົ່ງໄປແລ້ວ ແລະ ອຸປະກອນທີ່ຈື່ໄວ້ຈະໃຊ້ບໍ່ໄດ້ (ເປັນຜົນທີ່ຕັ້ງໃຈ).
3. ກວດການເຂົ້າສູ່ລະບົບ ແລະ ວຽກບໍລິຫານໃນໄລຍະທີ່ຮົ່ວໄຫຼໃນ log ຄວາມປອດໄພ ([ຄວາມຖືກຕ້ອງຄົບຖ້ວນຂອງບັນທຶກການກວດສອບ](audit-and-maintenance.md)).

## ຂັ້ນຕອນການປ່ຽນກະແຈຂໍ້ມູນສ່ວນບຸກຄົນ

1. ສ້າງກະແຈໃໝ່ດ້ວຍ `uv run manage.py pii_generate_key` (ໃຊ້ສະເພາະ `PII_ENCRYPTION_KEY` ຈາກຜົນລັບ).
2. ໃສ່ກະແຈປັດຈຸບັນໄວ້ໃນ `PII_PREVIOUS_KEYS` (ຫຼາຍອັນໃຫ້ຂັ້ນດ້ວຍຈຸດ) ແລະ ໃສ່ກະແຈໃໝ່ໄວ້ໃນ `PII_ENCRYPTION_KEY`.
3. ໃຫ້ໂປຣເຊສອ່ານການຕັ້ງຄ່າໃໝ່: ເລີ່ມ gunicorn ແລະ Celery worker ໃໝ່ (Docker: `docker compose restart app worker beat`).
4. ສຳລັບແຕ່ລະໂມເດລທີ່ມີຂໍ້ມູນສ່ວນບຸກຄົນ ກວດຈຳນວນດ້ວຍ `uv run manage.py pii_reencrypt {ແອັບ.ໂມເດລ} --dry-run` (ຕົວຢ່າງ `person.Person`) ແລ້ວແລ່ນໂດຍບໍ່ມີ `--force` (ຕອບຄຳຖາມຢືນຢັນ).
5. ຫຼັງຈາກ Flower ສະແດງວ່າວຽກສຳເລັດ ແລະ ຜົນ `--dry-run` ເປັນ 0 ແລ້ວ ໃຫ້ລຶບກະແຈເກົ່າອອກຈາກ `PII_PREVIOUS_KEYS`.
6. ເກັບກະແຈເກົ່າແບບປະທັບຕາໄວ້ຕະຫຼອດໄລຍະເກັບຮັກສາໄຟລ໌ສຳຮອງ (ຕ້ອງໃຊ້ເມື່ອກູ້ຄືນໄຟລ໌ສຳຮອງເກົ່າ).
