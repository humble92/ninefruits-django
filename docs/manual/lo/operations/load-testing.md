# ການທົດສອບພາລະ (ຊ່ວງສູງສຸດຂອງການລົງທະບຽນຮຽນ)

- ກຸ່ມເປົ້າໝາຍ: ຜູ້ປະຕິບັດງານ IT
- ກ່ຽວຂ້ອງ: [ລາຍການກວດສອບການນຳໃຊ້ລະບົບ](deployment-checklist.md), [ການຕິດຕັ້ງ](installation.md), [ເອກະສານອ້າງອີງຄຳສັ່ງ](commands.md)

ໃຊ້ Locust ຈຳລອງສະພາບຕອນເຊົ້າມື້ທຳອິດຂອງການລົງທະບຽນຮຽນ ທີ່ນັກສຶກສາຈຳນວນຫຼາຍແຫ່ເຂົ້າກຸ່ມຮຽນດຽວກັນພ້ອມກັນ. ສະຄຣິບແມ່ນ `loadtest/registration.py` (ສະຄຣິບ k6 ຂອງຕົ້ນສະບັບ `tests/load/registration.js`), ຕົວຊ່ວຍແລ່ນແມ່ນ `loadtest/run.sh`, ການກວດການລົງທະບຽນເກີນບ່ອນນັ່ງແມ່ນ `loadtest/seat_check.sql`.

[ສາລະບານຄູ່ມື](../README.md)

## ການກະກຽມ

1. ສ້າງຖານຂໍ້ມູນສະເພາະສຳລັບການທົດສອບພາລະ (ຢ່າເຮັດໃນຖານຂໍ້ມູນນຳໃຊ້ຈິງ). ການສ້າງ role ແລະ ຖານຂໍ້ມູນຄືກັບພາກທີ 2 ຂອງ [ການຕິດຕັ້ງ](installation.md), ຈາກນັ້ນຕິດຕັ້ງ ແລະ ໃສ່ຂໍ້ມູນເດໂມຂະໜາດໃຫຍ່. ລາຍການບັນຊີນັກສຶກສາ CSV ຈະຖືກຂຽນໄວ້ທີ່ `load-accounts.csv` ໃນບ່ອນເກັບສ່ວນຕົວ (`PRIVATE_MEDIA_ROOT`, ຄ່າເລີ່ມຕົ້ນ `storage/private`).

   ```bash
   export DB_DATABASE=nf_load
   uv run manage.py setup_install --profile=korean-university --grade-scale=4.5 --force < /dev/null
   uv run manage.py setup_demo --size=large --seed=42 --student-accounts --force
   ```

2. ໄລຍະລົງທະບຽນຮຽນຕ້ອງເປີດຢູ່. ເດໂມສ້າງໄລຍະລົງທະບຽນຮຽນຂອງພາກຮຽນໜ້າຕາມຊັ້ນປີ (ປີ 4 ເປີດແລ້ວ, ປີ 3 ອີກ 2 ມື້, ປີ 1 ແລະ 2 ອີກ 3 ມື້). ຖ້າຕ້ອງການວັດແທກກັບທຸກຊັ້ນປີ, ໃຫ້ປ່ຽນເວລາເລີ່ມຂອງໄລຍະລົງທະບຽນທີ່ເຫຼືອເປັນກ່ອນເວລາປັດຈຸບັນທີ່ **ໄລຍະເວລາດຳເນີນງານ** ຂອງໜ້າ **ແກ້ໄຂ** ພາກຮຽນ ([ຄູ່ມືຜູ້ບໍລິຫານ ບົດທີ 10](../admin/10-terms.md)), ຫຼື ແລ່ນຄຳສັ່ງນີ້ດ້ວຍ superuser ໃນຖານຂໍ້ມູນທົດສອບ:

   ```sql
   UPDATE term_windows SET opens_at = now() - interval '1 hour'
    WHERE window_type = 'registration' AND opens_at > now() AND closes_at > now();
   ```

3. Redis ແລະ Celery worker ຕ້ອງເຮັດວຽກຢູ່. ບ່ອນນັ່ງຖືກຕັດສິນໃນຖານຂໍ້ມູນໂດຍກົງ, ແຕ່ການເລື່ອນຂັ້ນລາຍຊື່ລໍຖ້າ, ການຊິງຄ໌ LMS ແລະ ການແຈ້ງເຕືອນແມ່ນຜ່ານຄິວ. ຖ້າໃຊ້ Redis ຮ່ວມກັບວຽກອື່ນ ໃຫ້ໃຊ້ເລກຖານຂໍ້ມູນອື່ນ ເຊັ່ນ `REDIS_URL=redis://127.0.0.1:6379/7`.

## ການແລ່ນ

`loadtest/run.sh` ເປີດ gunicorn (`config/gunicorn.py`) ແລະ Celery worker, ແລ່ນ Locust ແບບ headless, ກວດບ່ອນນັ່ງ ແລ້ວປິດທັງໝົດ.

```bash
export DB_DATABASE=nf_load DB_POOL=true DB_POOL_MIN=1 DB_POOL_MAX=2 DB_PREPARE_THRESHOLD=2
WORKERS=9 USERS=100 DURATION=1m loadtest/run.sh storage/loadtest/w9-u100
```

ເມື່ອແລ່ນເອງ ໃຫ້ເປີດເຊີບເວີດ້ວຍ `TRUSTED_PROXY_COUNT=1` ແລ້ວແລ່ນ Locust:

```bash
TRUSTED_PROXY_COUNT=1 DJANGO_DEBUG=false GUNICORN_WORKERS=9 uv run gunicorn config.wsgi -c config/gunicorn.py
uv run --group loadtest locust -f loadtest/registration.py --headless -u 100 -r 20 -t 1m \
    --host http://127.0.0.1:8000 --csv storage/loadtest/run
psql -h 127.0.0.1 -U postgres -d nf_load -v term=<id ພາກຮຽນ> -f loadtest/seat_check.sql
```

- ສະຖານະການ: ເຂົ້າສູ່ລະບົບ (`/accounts/login/`) → ໜ້າລົງທະບຽນຮຽນ → ຄົ້ນຫາວິຊາ (HTMX `?partial=results`) → ລົງທະບຽນກຸ່ມຮຽນທຳອິດທີ່ມີບ່ອນຫວ່າງ → ຖອນ. ແຕ່ລະຮອບຈະລຶບ cookie ແລະ ເຂົ້າສູ່ລະບົບເປັນນັກສຶກສາຄົນຖັດໄປ. ກຸ່ມເຕັມ ແລະ ການປະຕິເສດຕາມກົດຖືກນັບເປັນຜົນປົກກະຕິ (`registration outcomes`).
- ປຸ່ມລົງທະບຽນ ແລະ ຖອນ POST ດ້ວຍ `HX-Request` ຄືກັບ HTMX, ເຊີບເວີຕອບ 302 ກັບໄປໜ້າລົງທະບຽນຮຽນ. ເວລາຂອງ `enroll` ແລະ `drop` ລວມໜ້ານັ້ນນຳ (ບຣາວເຊີກໍຕ້ອງໄດ້ໜ້ານັ້ນກ່ອນຈຶ່ງປ່ຽນ `#registration`).
- ນັກສຶກສາແຕ່ລະຄົນສົ່ງທີ່ຢູ່ `X-Forwarded-For` ຂອງຕົນເອງ. ເມື່ອເຊີບເວີຢູ່ຫຼັງ proxy 1 ຊັ້ນ (`TRUSTED_PROXY_COUNT=1`), ການຈຳກັດການເຂົ້າສູ່ລະບົບຕໍ່ທີ່ຢູ່ຂອງ allauth ຈະນຳໃຊ້ຕາມທີ່ຢູ່ຂອງນັກສຶກສາແຕ່ລະຄົນຄືກັບວິທະຍາເຂດຈິງ. `ADDRESSES=1` ຈຳລອງນັກສຶກສາທຸກຄົນຢູ່ຫຼັງທີ່ຢູ່ດຽວ (NAT).
- ຕົວແປສະພາບແວດລ້ອມ: `ACCOUNTS` (CSV ບັນຊີ), `SEARCH` (ຄຳຄົ້ນຫາ, ຄ່າເລີ່ມຕົ້ນ `GEN`), `ADDRESSES`, `FIRST_ACCOUNT` (ບັນຊີເລີ່ມຕົ້ນ, ຄ່າເລີ່ມຕົ້ນແບບສຸ່ມ). `run.sh` ຮັບ `WORKERS`, `USERS`, `SPAWN_RATE`, `DURATION`, `TERM_ID`, `PORT`.
- ເພີ່ມ `USERS` ຈາກ 100 → 200 → 500 ແລ້ວເບິ່ງ p95 ຂອງແຕ່ລະໜ້າ ແລະ ອັດຕາຄວາມລົ້ມເຫຼວ. ເກນ: ໜ້າລົງທະບຽນຮຽນ p95 < 800ms, ການລົງທະບຽນ p95 < 1.5s, ອັດຕາລົ້ມເຫຼວ < 1%. ຖ້າເກີນເກນ Locust ຈະຈົບດ້ວຍລະຫັດອອກ 1.
- ຢູ່ຝັ່ງເຊີບເວີ ໃຫ້ເບິ່ງຈຳນວນການເຊື່ອມຕໍ່ ແລະ ການລໍຖ້າ lock ໃນ `pg_stat_activity` (`wait_event_type = 'Lock'`), ຄວາມຊັກຊ້າຂອງ Celery ແລະ ການໃຊ້ CPU ເຕັມ. ຖ້າແລ່ນ Locust ໃນເຄື່ອງດຽວກັບເຊີບເວີ Locust ກໍໃຊ້ CPU ນຳ ສະນັ້ນຕົວເລກແມ່ນຂັ້ນຕ່ຳ.

## ສິ່ງທີ່ການອອກແບບຮັບປະກັນ

- ຈຳນວນບ່ອນນັ່ງຖືກປົກປ້ອງດ້ວຍ lock ແຖວຂອງກຸ່ມຮຽນ (`SeatAllocator.lock`, `SELECT ... FOR NO KEY UPDATE`) ແລະ CHECK constraint, ສະນັ້ນເຖິງຄຳຮ້ອງຂໍພ້ອມກັນຈະຫຼາຍກໍບໍ່ເກີດການລົງທະບຽນເກີນ (`tests/registration/test_concurrent_registration.py`: 16 process, 5 ບ່ອນ). lock ນີ້ເຮັດໃຫ້ພຽງແຕ່ຄຳຮ້ອງຂໍທີ່ຈັບບ່ອນນັ່ງຂອງກຸ່ມຮຽນດຽວກັນລໍຖ້າກັນ, ບໍ່ກີດຂວາງການກວດ foreign key ຂອງແຖວທີ່ພຽງແຕ່ອ້າງອີງກຸ່ມຮຽນ (ບັນທຶກການພະຍາຍາມລົງທະບຽນ, ບັນທຶກການຊິງຄ໌ LMS).
- ຫຼັງການວັດແທກ ທັງສີ່ query ຂອງ `loadtest/seat_check.sql` ຕ້ອງໄດ້ 0 ແຖວ (ເກີນຈຳນວນ, ຕົວນັບບ່ອນນັ່ງບໍ່ກົງ, ກຸ່ມບ່ອນນັ່ງເກີນ, ລົງທະບຽນຊ້ຳໃນກຸ່ມດຽວກັນ).
- ຈຳນວນ query ຂອງໜ້າລົງທະບຽນຮຽນບໍ່ຂຶ້ນກັບຈຳນວນການລົງທະບຽນ, ລາຍຊື່ລໍຖ້າ ຫຼື ຜົນການຄົ້ນຫາ (`tests/registration/test_portal_query_count.py`).

## ການຈຳກັດການເຂົ້າສູ່ລະບົບຕໍ່ທີ່ຢູ່ ແລະ proxy

ນອກຈາກການຈຳກັດຄວາມລົ້ມເຫຼວຕໍ່ບັນຊີ (5 ຄັ້ງຕໍ່ນາທີ), allauth ຍັງມີ **ການຈຳກັດການເຂົ້າສູ່ລະບົບຕໍ່ທີ່ຢູ່** (`LOGIN_RATE_LIMIT_PER_IP`, ຄ່າເລີ່ມຕົ້ນ `30/m/ip`) ທີ່ຕົ້ນສະບັບບໍ່ມີ. ທີ່ຢູ່ທີ່ແອັບເຫັນຖືກກຳນົດດ້ວຍ `TRUSTED_PROXY_COUNT` (`ninefruits.core.http.client_ip`).

- ຖ້າຢູ່ຫຼັງ Nginx ແລະ ປະ `TRUSTED_PROXY_COUNT=0` (ຄ່າເລີ່ມຕົ້ນ), ທຸກຄຳຮ້ອງຂໍຈະມີທີ່ຢູ່ດຽວຄືທີ່ຢູ່ຂອງ Nginx. ວິທະຍາເຂດທີ່ອອກອິນເຕີເນັດຜ່ານທີ່ຢູ່ NAT ດຽວກໍຄືກັນ.
- ໃນການວັດແທກທີ່ຈຳລອງສະພາບນີ້ (`ADDRESSES=1`, 100 VU, 1 ນາທີ), ການເຂົ້າສູ່ລະບົບ 4,876 ຄັ້ງ **ສຳເລັດພຽງ 30 ຄັ້ງ** ແລະ 4,846 ຄັ້ງຖືກປະຕິເສດດ້ວຍ 429 (ອັດຕາລົ້ມເຫຼວ 49%). ໃນນາທີນັ້ນມີການລົງທະບຽນພຽງ 20 ລາຍການ. ໃນເງື່ອນໄຂດຽວກັນທີ່ນັກສຶກສາແຕ່ລະຄົນມີທີ່ຢູ່ຕ່າງກັນ ບໍ່ມີການເຂົ້າສູ່ລະບົບຖືກປະຕິເສດເລີຍ.
- ການຕັ້ງຄ່ານຳໃຊ້ຈິງ: ຕັ້ງ `TRUSTED_PROXY_COUNT` ຕາມຈຳນວນຊັ້ນ proxy (Nginx 1 ຊັ້ນແມ່ນ `1`). ຖ້ານັກສຶກສາສ່ວນໃຫຍ່ຢູ່ຫຼັງທີ່ຢູ່ NAT ດຽວ ໃຫ້ເພີ່ມ `LOGIN_RATE_LIMIT_PER_IP` ຕາມຈຳນວນການເຂົ້າສູ່ລະບົບໃນຊ່ວງສູງສຸດ. ຕົວຢ່າງ: ນັກສຶກສາ 2,000 ຄົນເຂົ້າສູ່ລະບົບພາຍໃນ 10 ນາທີ ແມ່ນ 200 ຄັ້ງຕໍ່ນາທີຈາກທີ່ຢູ່ດຽວ ສະນັ້ນ `300/m/ip`. ຄ່າຫວ່າງຈະຍົກເລີກການຈຳກັດຕໍ່ທີ່ຢູ່ (ຄືກັບຕົ້ນສະບັບ, ການຈຳກັດຄວາມລົ້ມເຫຼວຕໍ່ບັນຊີຍັງຄົງຢູ່).

## ການຕັດສິນໃຈການຕັ້ງຄ່າເຊີບເວີ

- **gunicorn sync worker** (`config/gunicorn.py`). ຄ່າເລີ່ມຕົ້ນຂອງ `GUNICORN_WORKERS` ແມ່ນຈຳນວນ core ຂອງ CPU × 2 + 1. ໃນການວັດແທກ ປະລິມານການປະມວນຜົນຖືກຈຳກັດດ້ວຍ CPU: ໃນ 4 core, worker 4, 9 ແລະ 16 ໄດ້ປະລິມານເທົ່າກັນ (23~26 ຄຳຮ້ອງຂໍຕໍ່ວິນາທີ). ການເພີ່ມ worker ພຽງແຕ່ເພີ່ມການເຊື່ອມຕໍ່ຖານຂໍ້ມູນ (12 → 36) ແລະ ການລໍຖ້າ lock (ສູງສຸດ 1 → 12). ຢ່າເພີ່ມເກີນ core × 2 + 1, ໃຫ້ຂະຫຍາຍເຊີບເວີແອັບອອກທາງລວງນອນແທນ.
- **connection pool ແລະ prepared statement**: `DB_POOL=true`, `DB_POOL_MIN=1`, `DB_POOL_MAX=2`, `DB_PREPARE_THRESHOLD=2`. ຍ້ອນນະໂຍບາຍ row level security (RLS), ການວາງແຜນ query ກິນເວລາຖານຂໍ້ມູນສ່ວນໃຫຍ່ຂອງໜ້າ (31 query ຂອງໜ້າລົງທະບຽນຮຽນ: ວາງແຜນ 51ms, ປະຕິບັດ 19ms). ການໃຊ້ການເຊື່ອມຕໍ່ຄືນ ແລະ prepared statement ດ້ວຍ server-side binding ເຮັດໃຫ້ແຕ່ລະ query ຖືກວາງແຜນພຽງເທື່ອດຽວຕໍ່ການເຊື່ອມຕໍ່. ໃນ 4 core ດຽວກັນ ປະລິມານເພີ່ມຈາກ 16.8 ເປັນ 25.6 ຄຳຮ້ອງຂໍຕໍ່ວິນາທີ, ແລະ ຄ່າກາງຂອງໜ້າລົງທະບຽນຮຽນເມື່ອມີຜູ້ໃຊ້ 1 ຄົນຫຼຸດຈາກ 160ms ເປັນ 97ms. ຈຳນວນການເຊື່ອມຕໍ່ທີ່ຕ້ອງການແມ່ນ worker ຕໍ່ເຊີບເວີ × `DB_POOL_MAX` + ຈຳນວນ Celery concurrency ແລະ ຕ້ອງນ້ອຍກວ່າ `max_connections` ຂອງ PostgreSQL. ຖ້າມີ PgBouncer ແບບ transaction ຢູ່ດ້ານໜ້າ ຈະໃຊ້ prepared statement ບໍ່ໄດ້ ໃຫ້ປະ `DB_PREPARE_THRESHOLD=0`. ການທົດສອບທັງໝົດ (1,066 ລາຍການ) ຜ່ານກັບການຕັ້ງຄ່ານີ້.
- **ASGI (ທຽບເທົ່າການຕັດສິນໃຈ Octane ຂອງຕົ້ນສະບັບ)**: ບໍ່ນຳໃຊ້. ທຸກໜ້າແມ່ນ view ແບບ synchronous ເຊິ່ງ ASGI ຈະສົ່ງໄປແລ່ນໃນ thread ໂດຍບໍ່ມີປະໂຫຍດ, ແລະ ປະລິມານແມ່ນຕາມຈຳນວນ core ຂອງ CPU. Django ບໍ່ໄດ້ bootstrap ແອັບໃໝ່ທຸກຄຳຮ້ອງຂໍ (ຕ່າງຈາກ PHP-FPM) ສະນັ້ນປະໂຫຍດທີ່ Octane ໃຫ້ມີຢູ່ແລ້ວ, ສ່ວນປະໂຫຍດຂອງການໃຊ້ການເຊື່ອມຕໍ່ຄືນແມ່ນໄດ້ຈາກ pool ແລະ prepared statement ຂ້າງເທິງ.
- ການເຂົ້າສູ່ລະບົບໃຊ້ CPU ຕໍ່ຄຳຮ້ອງຂໍຫຼາຍ ຍ້ອນການກວດ hash Argon2 (ປະມານ 140ms ເມື່ອມີຜູ້ໃຊ້ 1 ຄົນ). ເມື່ອການເຂົ້າສູ່ລະບົບຫຼັ່ງໄຫຼເຂົ້າໃນຊ່ວງສູງສຸດ ຄ່າໃຊ້ຈ່າຍນີ້ຈະຫຼຸດປະລິມານກ່ອນ.
