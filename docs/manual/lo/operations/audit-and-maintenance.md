# ຄວາມຖືກຕ້ອງຄົບຖ້ວນຂອງບັນທຶກການກວດສອບ ແລະ ການລ້າງຂໍ້ມູນຕາມກຳນົດ

- ກຸ່ມເປົ້າໝາຍ: ຜູ້ປະຕິບັດງານ IT, ຜູ້ຮັບຜິດຊອບຄວາມປອດໄພ
- ກ່ຽວຂ້ອງ: [ຄູ່ມືຜູ້ບໍລິຫານບົດທີ 4 ການເບິ່ງບັນທຶກການກວດສອບ](../admin/04-audit.md), [ເອກະສານອ້າງອີງຄຳສັ່ງ](commands.md), [ການສຳຮອງ ແລະ ກູ້ຄືນຂໍ້ມູນ](backup-restore.md)

## ລະບົບຕ່ອງໂສ້ແຮດຊ໌ຂອງບັນທຶກການກວດສອບ

ຕາຕະລາງບັນທຶກການກວດສອບ (`audit.record_changes` ບັນທຶກການປ່ຽນແປງຂໍ້ມູນ, `audit.activity_log` ບັນທຶກການກວດສອບທາງທຸລະກິດ, `audit.security_events` ເຫດການຄວາມປອດໄພ) ສາມາດເພີ່ມແຖວໄດ້ເທົ່ານັ້ນ (ບັງຄັບດ້ວຍ trigger). ນອກຈາກນັ້ນຍັງມີກົນໄກທີ່ **ເປີດເຜີຍ** ການປອມແປງອີກ.

- ທຸກແຖວຈະຖືກຕິດຄ່າ SHA-256 ຂອງເນື້ອຫາ (`row_hash`) ໃນເວລາແຊກເຂົ້າ.
- `audit_seal` (ວຽກຕາມກຳນົດເວລາ `audit.seal`, ທຸກວັນ 03:30) ເຊື່ອມແຖວໃໝ່ເຂົ້າຕ່ອງໂສ້ຕາມລຳດັບ ID: `chain_hash = SHA-256(chain_hash ກ່ອນໜ້າ || row_hash)`. ມັນເອີ້ນຟັງຊັນ DB `audit.seal()` ຜ່ານການເຊື່ອມຕໍ່ຂອງເຈົ້າຂອງ schema (`migrator`).
- `audit_verify_chain` ຄຳນວນແຮດຊ໌ເນື້ອຫາ ແລະ ຕ່ອງໂສ້ຂອງທຸກແຖວຄືນໃໝ່. ສຳລັບແຕ່ລະຕາຕະລາງ ຈະສະແດງຈຳນວນທີ່ກວດ, ຈຳນວນທີ່ປະທັບຕາ, ຈຳນວນທີ່ບໍ່ກົງກັນ ແລະ id ທຳອິດທີ່ບໍ່ກົງກັນ; ແຖວທີ່ເນື້ອຫາຖືກປ່ຽນຈະສະແດງເປັນ "row mismatch", ແຖວທີ່ຫາຍໄປ ຫຼື ຖືກສະຫຼັບລຳດັບຈະສະແດງເປັນ "chain mismatch" ແລະ ສົ່ງລະຫັດອອກ 2 ກັບຄືນ.

```bash
uv run manage.py audit_seal
uv run manage.py audit_verify_chain
uv run manage.py audit_verify_chain --table=security_events
```

ຂໍ້ຄວນລະວັງ

- ແຖວທີ່ຖືກປ່ຽນກ່ອນການປະທັບຕາ (ພາຍໃນມື້ດຽວກັນ) ຈະບໍ່ຖືກຈັບດ້ວຍຕ່ອງໂສ້. ດັ່ງນັ້ນຈຶ່ງປະທັບຕາທຸກວັນ ແລະ ກວດສອບກ່ອນການສຳຮອງຂໍ້ມູນ ແລະ ໃນເວລາກວດກາຄວາມປອດໄພ.
- ຖ້າລຶບສ່ວນຕົ້ນດ້ວຍການລ້າງຂໍ້ມູນ (`audit_prune`), ການເຊື່ອມຕໍ່ຂອງແຖວທຳອິດທີ່ເຫຼືອຢູ່ຈະບໍ່ຖືກກວດ (ຂອບເຂດທີ່ລຶບຈະຖືກບັນທຶກໄວ້ໃນບັນທຶກການກວດສອບຂອງຄຳສັ່ງລ້າງຂໍ້ມູນ).
- ມີພຽງຜູ້ບໍລິຫານ DB (ເຈົ້າຂອງ schema `app_migrator`) ເທົ່ານັ້ນທີ່ສາມາດຕັ້ງ `app.audit_maintenance = on` ໄດ້. ບົດບາດຂອງແອັບພລິເຄຊັນ (`app_runtime`) ບໍ່ມີສິດ UPDATE ຫຼື DELETE ໃນຕາຕະລາງບັນທຶກການກວດສອບ.

## ການເກັບຮັກສາ ແລະ ການລ້າງຂໍ້ມູນ

1. ກຳນົດໄລຍະເວລາເກັບຮັກສາ (ຕົວຢ່າງ: ບັນທຶກການປ່ຽນແປງຂໍ້ມູນ 3 ປີ, ບັນທຶກການກວດສອບທາງທຸລະກິດ 5 ປີ, ເຫດການຄວາມປອດໄພ 1 ປີ).
2. ກ່ອນລ້າງຂໍ້ມູນ ໃຫ້ສຳຮອງຂໍ້ມູນ ([ການສຳຮອງ ແລະ ກູ້ຄືນຂໍ້ມູນ](backup-restore.md)) ແລະ ຢືນຢັນວ່າຕ່ອງໂສ້ຍັງຄົບຖ້ວນດ້ວຍ `audit_verify_chain`.
3. ເບິ່ງຈຳນວນແຖວດ້ວຍ `uv run manage.py audit_prune --before=YYYY-MM-DD --table=record_changes --dry-run` ແລ້ວຈຶ່ງແລ່ນໂດຍບໍ່ມີ `--dry-run` (ບັນທຶກບັນຊີຜູ້ແລ່ນດ້ວຍ `--actor=`). ແຖວທີ່ຍັງບໍ່ໄດ້ປະທັບຕາຈະບໍ່ຖືກລຶບ ດັ່ງນັ້ນໃຫ້ແລ່ນ `audit_seal` ກ່ອນ.
4. ຫຼັງຈາກລ້າງຂໍ້ມູນແລ້ວ ໃຫ້ແລ່ນ `audit_verify_chain` ອີກຄັ້ງ.

ບັນທຶກຂອງການລ້າງຂໍ້ມູນເອງ: ທຸກຄັ້ງທີ່ແລ່ນ ບັນທຶກການກວດສອບທາງທຸລະກິດ (log `command`) ຈະເກັບວັນທີອ້າງອີງ, ຕົວເລືອກ, ຜູ້ແລ່ນ, ຜູ້ໃຊ້ OS ແລະ ສຳລັບແຕ່ລະຕາຕະລາງ **ຈຳນວນແຖວທີ່ລຶບ, ຂອບເຂດ ID ທີ່ລຶບ ແລະ chain_hash ທີ່ຂອບເຂດ** ສ່ວນການລຶບຕົວຈິງຍັງຖືກບັນທຶກເປັນເຫດການຄວາມປອດໄພ `audit.pruned` ອີກດ້ວຍ (**ການກວດສອບ > ເຫດການຄວາມປອດໄພ**). ແຖວບັນທຶກນີ້ຈະເຂົ້າຕ່ອງໂສ້ໃນການປະທັບຕາຄັ້ງຕໍ່ໄປ. ຂອບເຂດນີ້ຄືເຫດຜົນທີ່ `audit_verify_chain` ບໍ່ກວດການເຊື່ອມຕໍ່ຂອງແຖວທຳອິດທີ່ເຫຼືອຢູ່ ແລະ ເມື່ອປຽບທຽບແຮດຊ໌ຂອບເຂດກັບບັນທຶກການລ້າງຂໍ້ມູນ ກໍສາມາດຢືນຢັນໄດ້ວ່າຂອບເຂດທີ່ຖືກລຶບກົງກັບການລ້າງຂໍ້ມູນທີ່ໄດ້ບັນທຶກໄວ້.

## ການລ້າງໄຟລ໌

`uv run manage.py media_prune_orphans --dry-run` ສະແດງແຖວສື່ (media) ທີ່ເຈົ້າຂອງຫາຍໄປແລ້ວ ແລະ ໄດເຣັກທໍຣີທີ່ບໍ່ມີແຖວ (`PRIVATE_MEDIA_ROOT/<media id>/`) ແລະ ຖ້າແລ່ນໂດຍບໍ່ມີ `--dry-run` ຈະລຶບອອກ. ເປົ້າໝາຍຄືຮູບຖ່າຍບຸກຄົນ, ເອກະສານສະໝັກ, PDF ໃບຢັ້ງຢືນ ແລະ ຫຼັກຖານການສອບເສັງ. ແລ່ນເດືອນລະຄັ້ງ ຫຼື ຫຼັງຈາກການລຶບຈຳນວນຫຼາຍ.
