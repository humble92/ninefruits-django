# ເອກະສານອ້າງອີງຄຳສັ່ງບໍລິຫານ

- ກຸ່ມເປົ້າໝາຍ: ຜູ້ປະຕິບັດງານ IT
- ຂອບເຂດ: ຄຳສັ່ງທັງໝົດທີ່ແອັບ Ninefruits ໃນ repository ນີ້ລົງທະບຽນ (`ninefruits/*/management/commands/`) ແລະ ຄຳສັ່ງໃນຕົວຂອງ Django ທີ່ໃຊ້ໃນການດຳເນີນງານ. ເມື່ອເພີ່ມຄຳສັ່ງ ຕ້ອງເພີ່ມລາຍການ `### \`ຄຳສັ່ງ\`` ໃສ່ເອກະສານນີ້ (ທັງ 4 ພາສາ) ດ້ວຍ CI ຈຶ່ງຜ່ານ (`tests/tooling/test_command_documentation.py`).

## ຂໍ້ມູນທົ່ວໄປ

ທຸກຄຳສັ່ງແລ່ນດ້ວຍ `uv run manage.py {ຄຳສັ່ງ}`. ໃນສະພາບແວດລ້ອມພັດທະນາ Docker ໃຊ້ `docker compose exec app uv run manage.py {ຄຳສັ່ງ}`.

| ລາຍການ | ກົດລະບຽບ |
|---|---|
| ຊື່ | ປ່ຽນ `{context}:{action}` ຂອງຕົ້ນສະບັບເປັນ `{context}_{action}` (ຊື່ຄຳສັ່ງ Django ໃຊ້ `:` ບໍ່ໄດ້). ຕົວຢ່າງ: `term:close` → `term_close` |
| ບັນທຶກການກວດສອບ | ຄຳສັ່ງທີ່ປ່ຽນຂໍ້ມູນ ("ການກວດສອບ: ບັນທຶກ" ຂ້າງລຸ່ມ) ຈະບັນທຶກຄຳສັ່ງ, ອາກິວເມັນ, ຕົວເລືອກ, ຜູ້ໃຊ້ OS, ລະຫັດອອກ ແລະ ຜົນລົງບັນທຶກການກວດສອບທາງທຸລະກິດ (log `command`) ທຸກຄັ້ງທີ່ແລ່ນ. ກວດທີ່ **ການກວດສອບ > ບັນທຶກການກວດສອບທາງທຸລະກິດ** ໃນໜ້າບໍລິຫານ |
| ID ການແລ່ນ | ທຸກຄັ້ງທີ່ແລ່ນ ID ທີ່ຂຶ້ນຕົ້ນດ້ວຍ `cmd-` ຈະຖືກໃສ່ແທນທີ່ ID ຄຳຮ້ອງຂໍ. ບັນທຶກການກວດສອບທາງທຸລະກິດ, ບັນທຶກການປ່ຽນແປງຂໍ້ມູນທີ່ການແລ່ນນັ້ນປ່ຽນ ແລະ ວຽກ Celery ທີ່ການແລ່ນນັ້ນໃສ່ເຂົ້າ ມີ ID ດຽວກັນ ດັ່ງນັ້ນຈຶ່ງຄົ້ນຫາ "ການປ່ຽນແປງນີ້ມາຈາກຄຳສັ່ງໃດ" ດ້ວຍ ID ໄດ້. `--actor` ເປັນຄ່າທີ່ຜູ້ແລ່ນຂຽນເອງ ຈຶ່ງບໍ່ໃສ່ໃນຊ່ອງຜູ້ໃຊ້ຂອງບັນທຶກການປ່ຽນແປງຂໍ້ມູນ (ຜູ້ແລ່ນຕົວຈິງຄືຜູ້ໃຊ້ OS) |
| `--actor=<ອີເມວ>` | ມີຢູ່ທົ່ວໄປໃນຄຳສັ່ງທີ່ບັນທຶກການກວດສອບ. ບັນທຶກບັນຊີຜູ້ບໍລິຫານທີ່ຮັບຜິດຊອບ. ຖ້າເປັນອີເມວທີ່ບໍ່ມີຢູ່ ຈະບໍ່ແລ່ນ |
| `--dry-run` | ສະແດງສະເພາະຜົນໂດຍບໍ່ປ່ຽນແປງຫຍັງ. ມີຢູ່ໃນວຽກທີ່ຍ້ອນກັບຍາກ |
| `--force` | ແລ່ນໂດຍບໍ່ຖາມຢືນຢັນ (ສຳລັບວຽກຕາມກຳນົດເວລາ ແລະ ສະຄຣິບນຳໃຊ້ລະບົບ) |
| `--reason=` | ມີຢູ່ໃນຄຳສັ່ງທີ່ຕ້ອງການເຫດຜົນ |
| ລະຫັດອອກ | 0 ສຳເລັດ, 1 ລົ້ມເຫຼວ ຫຼື ຍົກເລີກ, 2 ຄຳສັ່ງກວດກາພົບບັນຫາ |
| ບໍລິບົດ DB | ໃນຂະນະແລ່ນ ຜູ້ປະຕິບັດຂອງເຊສຊັນ DB ຖືກຕັ້ງເປັນ `system:command:{ຄຳສັ່ງ}` ແລະ ຖືກບັນທຶກໃນບັນທຶກການປ່ຽນແປງຂໍ້ມູນ (trigger) |

## ຄຳສັ່ງໃນຕົວຂອງ Django

### `migrate`

- ຈຸດປະສົງ: ນຳໃຊ້ migration ຂອງຖານຂໍ້ມູນ. ເປັນຄຳສັ່ງ Ninefruits ທີ່ຫໍ່ຄຳສັ່ງພື້ນຖານຂອງ Django: ຖ້າບໍ່ລະບຸ `--database` ຈະໃຊ້ການເຊື່ອມຕໍ່ຂອງເຈົ້າຂອງ schema (`migrator`, ບົດບາດ `app_migrator`). ການເຊື່ອມຕໍ່ຂອງແອັບພລິເຄຊັນ (`app_runtime`) ບໍ່ມີສິດ DDL. `showmigrations` ແລະ `sqlmigrate` ກໍໃຊ້ການເຊື່ອມຕໍ່ `migrator` ເປັນຄ່າເລີ່ມຕົ້ນຄືກັນ.
- ເວລາແລ່ນ: ການຕິດຕັ້ງຄັ້ງທຳອິດ ແລະ ທຸກຄັ້ງທີ່ນຳໃຊ້ລະບົບ (`setup_install` ກໍແລ່ນນຳ).
- ຕົວເລືອກ: ຄືກັບ `migrate` ຂອງ Django (`app_label`, `migration_name`, `--plan`, `--check`, `--database`).
- ການກວດສອບ: ບໍ່ບັນທຶກ (ການປ່ຽນແປງ schema ຖືກເກັບໄວ້ໃນປະຫວັດ migration `django_migrations`)
- ຕົວຢ່າງ

  ```bash
  uv run manage.py migrate
  uv run manage.py migrate --plan
  ```

- ເມື່ອລົ້ມເຫຼວ: ຖ້າເປັນຂໍ້ຜິດພາດສິດ ໃຫ້ກວດການກະກຽມບົດບາດ DB (`db/sql/roles/`) ໃນ [ຄູ່ມືການຕິດຕັ້ງ](installation.md).

### `collectstatic`

- ຈຸດປະສົງ: ລວບລວມຜົນການ build ຂອງ Vite (`static/dist/`) ແລະ ໄຟລ໌ static ຂອງ Django ແລະ unfold ໄປໄວ້ທີ່ `STATIC_ROOT` (`staticfiles/`). Web server (Nginx) ໃຫ້ບໍລິການໄດເຣັກທໍຣີນີ້.
- ເວລາແລ່ນ: ທຸກຄັ້ງທີ່ນຳໃຊ້ລະບົບ ຫຼັງຈາກ `npm ci && npm run build`.
- ຕົວເລືອກ: `--noinput` (ບໍ່ຖາມ), `--clear` (ລຶບໄຟລ໌ເກົ່າກ່ອນລວບລວມ).
- ການກວດສອບ: ບໍ່ບັນທຶກ
- ຕົວຢ່າງ

  ```bash
  npm ci && npm run build
  uv run manage.py collectstatic --noinput
  ```

### `compilemessages`

- ຈຸດປະສົງ: ຄອມໄພລ໌ໄຟລ໌ແປ (`.po`) ເປັນ `.mo` ສຳລັບການແລ່ນ. `.mo` ບໍ່ຖືກເກັບໄວ້ໃນ repository ຈຶ່ງຕ້ອງແລ່ນທຸກຄັ້ງທີ່ຕິດຕັ້ງ ແລະ ນຳໃຊ້ລະບົບ. ລະບົບຕ້ອງມີ `gettext`.
- ເວລາແລ່ນ: ທຸກຄັ້ງທີ່ນຳໃຊ້ລະບົບ ແລະ ຫຼັງຈາກແກ້ໄຂໄຟລ໌ແປ.
- ຕົວເລືອກ: `--locale=` (ຕົວຢ່າງ `ko`, `zh_Hans`, `lo`), `--ignore=.venv`.
- ການກວດສອບ: ບໍ່ບັນທຶກ
- ຕົວຢ່າງ

  ```bash
  uv run manage.py compilemessages --ignore=.venv
  ```

### `createsuperuser`

- ຈຸດປະສົງ: **ບໍ່ໃຊ້.** Superuser ພື້ນຖານຂອງ Django ຂ້າມລາຍການບົດບາດ ແລະ ສິດ ແລະ ການກວດສອບ ດັ່ງນັ້ນຄຳສັ່ງນີ້ຈະຈົບດ້ວຍຂໍ້ຜິດພາດ (ລະຫັດອອກ 1) ແລະ ແນະນຳ `security_create_administrator`.
- ແທນທີ່: ສ້າງຜູ້ບໍລິຫານຄົນທຳອິດດ້ວຍ `security_create_administrator` (ລວມທັງການມອບບົດບາດຜູ້ບໍລິຫານລະບົບ ແລະ ບັນທຶກການກວດສອບ).
- ການກວດສອບ: ບໍ່ກ່ຽວຂ້ອງ

## ການຕິດຕັ້ງ ແລະ ເດໂມ (Phase 1)

### `setup_install`

- ຈຸດປະສົງ: ການຕິດຕັ້ງໃໝ່ ແລະ ການອັບເດດ. ດຳເນີນຕາມລຳດັບ: ການເຄື່ອນຍ້າຍຖານຂໍ້ມູນ, ຂໍ້ມູນທີ່ຈຳເປັນ (ແມ່ແບບບົດບາດ ແລະ ການຊິງຄ໌ສິດ, ປະເທດ, ພາສາ, ປະເພດລາຍການລະຫັດ, ປະເພດຫົວໜ່ວຍອົງການ), ການຕັ້ງຄ່າພື້ນຖານຂອງສະຖາບັນ, ການກຳນົດລະບົບຄະແນນ, ໂປຣໄຟລ໌ການຕິດຕັ້ງ ແລະ ຜູ້ບໍລິຫານຄົນທຳອິດ. ດຳເນີນຊ້ຳໄດ້ຢ່າງປອດໄພ (ຂໍ້ມູນທີ່ມີຢູ່ ແລະ ຄ່າທີ່ຜູ້ບໍລິຫານປ່ຽນແປງຈະຖືກຮັກສາໄວ້).
- ເວລາດຳເນີນ: ການຕິດຕັ້ງຄັ້ງທຳອິດ ແລະ ທຸກຄັ້ງທີ່ເຜີຍແຜ່.
- ຕົວເລືອກ: `--institution-name=`, `--locale=` (ພາສາເລີ່ມຕົ້ນ), `--timezone=` (ຕົວຢ່າງ `Asia/Seoul`), `--profile=` (ກະແຈໂປຣໄຟລ໌ການຕິດຕັ້ງ, ລະບຸໄດ້ຫຼາຍຄັ້ງ: `korean-university`, `yust-legacy`), `--grade-scale=` (ລະບົບຄະແນນ `4.5` ຫຼື `4.3`; ເມື່ອກຳນົດແລ້ວປ່ຽນບໍ່ໄດ້; ຖ້າວ່າງຈະໃຊ້ລະບົບຂອງໂປຣໄຟລ໌ທຳອິດ), `--admin-email=`, `--admin-name=`, `--force` (ດຳເນີນໂດຍບໍ່ຖາມ; ລະຫັດຜ່ານຜູ້ບໍລິຫານອ່ານຈາກ standard input).
- ການກວດສອບ: ບັນທຶກ (ໂປຣໄຟລ໌ທີ່ນຳໃຊ້, ການສ້າງຜູ້ບໍລິຫານຫຼືບໍ່)
- ຕົວຢ່າງ

  ```bash
  uv run manage.py setup_install
  echo "$ADMIN_PASSWORD" | uv run manage.py setup_install --force --locale=ko --timezone=Asia/Seoul \
      --institution-name="Demo University" --profile=korean-university \
      --admin-email=admin@example.ac.kr --admin-name="Administrator"
  ```

- ການອ່ານຜົນ: `DONE` ແຕ່ລະຂັ້ນຕອນ. `Administrator exists` ໝາຍຄວາມວ່າມີການມອບໝາຍຜູ້ບໍລິຫານລະບົບແລ້ວ ຈຶ່ງຂ້າມການສ້າງ.
- ເມື່ອລົ້ມເຫຼວ: ຖ້າແຈ້ງວ່າຂາດກະແຈ ໃຫ້ໃສ່ `DJANGO_SECRET_KEY` ແລະ ຄ່າທີ່ສ້າງດ້ວຍ `pii_generate_key` ໃນການຕັ້ງຄ່າສະພາບແວດລ້ອມ. ຖ້າການເຄື່ອນຍ້າຍລົ້ມເຫຼວ ໃຫ້ກວດການກະກຽມບົດບາດຖານຂໍ້ມູນ ([ການຕິດຕັ້ງ](installation.md)). `The grade scale is fixed` ໝາຍຄວາມວ່າ `--grade-scale` ຕ່າງຈາກລະບົບທີ່ກຳນົດໄວ້ແລ້ວ.

### `setup_demo`

- ຈຸດປະສົງ: ສ້າງຂໍ້ມູນມະຫາວິທະຍາໄລສົມມຸດ (ອົງການ, ຫຼັກສູດ, ອາຄານ ແລະ ຫ້ອງຮຽນ, ພາກຮຽນທີ່ຜ່ານມາ ປັດຈຸບັນ ແລະ ຕໍ່ໄປອີງຕາມມື້ນີ້ພ້ອມໄລຍະເວລາວຽກ, ໂປຣໄຟລ໌ມະຫາວິທະຍາໄລເກົາຫຼີ). ສະແດງບັນຊີເດໂມຄົງທີ່ຕາມບົດບາດ (`registrar@demo.test` ເປັນຕົ້ນ, ລະຫັດຜ່ານ `demo-password`). ຂໍ້ມູນຈຳນວນຫຼາຍສ້າງດ້ວຍການເພີ່ມເປັນຊຸດ.
- ເວລາດຳເນີນ: ສະພາບແວດລ້ອມການພັດທະນາ, ການຝຶກອົບຮົມ ແລະ ການສາທິດ. **ບໍ່ດຳເນີນໃນສະພາບແວດລ້ອມການຜະລິດ (`DJANGO_ENV=production`) ເຖິງແມ່ນຈະໃສ່ `--force`.**
- ຕົວເລືອກ: `--size=tiny|small|medium|large` (ນັກສຶກສາປະມານ 20/100/2,000/20,000 ຄົນ; `tiny` ສຳລັບການທົດສອບ ແລະ ກວດໄວ), `--seed=` (ຄ່າດຽວກັນໃຫ້ຂໍ້ມູນດຽວກັນ), `--force` (ຂ້າມການຢືນຢັນ).
- `--student-accounts`: ສ້າງບັນຊີໃຫ້ນັກສຶກສາທີ່ກຳລັງຮຽນທຸກຄົນ ແລະ ຂຽນລົງ `load-accounts.csv` (ອີເມວ, ລະຫັດຜ່ານ) ໃນບ່ອນເກັບແບບສ່ວນຕົວ ສຳລັບການທົດສອບການຮັບນ້ຳໜັກ ([ການທົດສອບການຮັບນ້ຳໜັກ](load-testing.md)).
- ການກວດສອບ: ບັນທຶກ (ຂະໜາດ, seed, ເວລາທີ່ໃຊ້)
- ຕົວຢ່າງ: `uv run manage.py setup_demo --size=small --seed=42 --force`
- ເມື່ອລົ້ມເຫຼວ: ຖ້າບໍ່ມີຂໍ້ມູນທີ່ຈຳເປັນ ບັນຊີເດໂມຈະຖືກຂ້າມເພາະບໍ່ມີບົດບາດ. ໃຫ້ດຳເນີນ `setup_install` ກ່ອນ. ການດຳເນີນຊ້ຳໃນຖານຂໍ້ມູນດຽວກັນຈະຂ້າມຂໍ້ມູນເດໂມທີ່ມີແລ້ວ.

## ຂໍ້ມູນອ້າງອີງ ແລະ ພາກຮຽນ (Phase 1)

### `reference_import`

- ຈຸດປະສົງ: ນຳເຂົ້າຂໍ້ມູນອ້າງອີງຈາກ CSV ດ້ວຍກົດດຽວກັນກັບ **ນຳເຂົ້າ CSV** ໃນໜ້າຈໍບໍລິຫານ (ຊອກແຖວທີ່ມີຢູ່ດ້ວຍລະຫັດແລ້ວອັບເດດ, ຫ້ອງແປພາສາທີ່ວ່າງຈະຮັກສາຄ່າເດີມ, ແຖວທີ່ລົ້ມເຫຼວຖືກບັນທຶກແຍກ).
- ອາກິວເມັນ: `type` `org_units`, `programs`, `buildings`, `rooms`, `lookup_values`, `students` (ບັນທຶກນັກສຶກສາ), `instructors` (ອາຈານ), `courses` (ເວີຊັນລາຍວິຊາ), `registration_holds` (ການລະງັບການລົງທະບຽນ) / `file` CSV UTF-8 ທີ່ມີແຖວຫົວ.
- ຕົວເລືອກ: `--actor=` (ຈຳເປັນ; ການນຳເຂົ້າຖືກບັນທຶກພາຍໃຕ້ບັນຊີນີ້ ແລະ ຜົນຈະສະແດງໃນໜ້າ **ການນຳເຂົ້າ CSV** ຂອງບັນຊີນັ້ນ), `--chunk=100` (ຈຳນວນແຖວຕໍ່ວຽກ Celery), `--dry-run` (ກວດແຖວຫົວ ແລະ ນັບແຖວເທົ່ານັ້ນ).
- ການກວດສອບ: ບັນທຶກ (ປະເພດ, ຊື່ໄຟລ໌, ຈຳນວນແຖວ, ເລກການນຳເຂົ້າ, ຈຳນວນແຖວທີ່ລົ້ມເຫຼວ)
- ຮູບແບບຖັນ: [ຄູ່ມືຜູ້ບໍລິຫານ ບົດທີ 9](../admin/09-csv-import.md).
- ລະຫັດອອກ: ເມື່ອວຽກດຳເນີນທັນທີ (worker ແບບ synchronous) ຈະສະແດງຜົນ ແລະ ຖ້າມີແຖວລົ້ມເຫຼວແມ່ນ 2. ຖ້າພຽງແຕ່ເຂົ້າຄິວແມ່ນ 0. ຜົນ ແລະ CSV ແຖວທີ່ລົ້ມເຫຼວເບິ່ງໄດ້ທີ່ **ຂໍ້ມູນອ້າງອີງ > ການນຳເຂົ້າ CSV** ໃນໜ້າຈໍບໍລິຫານ.
- ຕົວຢ່າງ: `uv run manage.py reference_import org_units /srv/import/org-units.csv --actor=admin@example.ac.kr --dry-run`

### `term_inspect`

- ຈຸດປະສົງ: ສະແດງພາກຮຽນທີ່ກຳລັງຮຽນ ແລະ ໄລຍະເວລາວຽກທີ່ເປີດຢູ່ (ປະເພດ, ພາກຮຽນ, ຊ່ວງ, ຊື່, ເງື່ອນໄຂເປົ້າໝາຍ, ເວລາປິດ) ໃນເວລາທີ່ກຳນົດ. ໃຊ້ກວດການຕັ້ງຄ່າພາກຮຽນ ແລະ ໄລຍະເວລາວຽກ ຫຼື ຕອບຄຳຖາມເຊັ່ນ "ເປັນຫຍັງການລົງທະບຽນຍັງບໍ່ເປີດ?".
- ຕົວເລືອກ: `--at=` (ເລີ່ມຕົ້ນແມ່ນປັດຈຸບັນ; ຕົວຢ່າງ `"2027-02-15 09:00"`; ຖ້າບໍ່ໃສ່ເຂດເວລາຈະໃຊ້ເຂດເວລາເຊີບເວີ (UTC); ລະບຸໄດ້ເຊັ່ນ `"2027-02-15 09:00 Asia/Seoul"` ຫຼື `2027-02-15T09:00+09:00`).
- ການກວດສອບ: ບໍ່ບັນທຶກ (ອ່ານເທົ່ານັ້ນ)
- ການອ່ານຜົນ: ວັນທີຕັດສິນຕາມເຂດເວລາຂອງສະຖາບັນ. ໄລຍະເວລາວຽກຂອງພາກຮຽນທີ່ຢູ່ໃນສະຖານະວາງແຜນ (planned) ຫຼື ເກັບຮັກສາ (archived) ຈະບໍ່ເປີດ. ເວລາປິດສະແດງຕາມເຂດເວລາຂອງສະຖາບັນ.

## ຄວາມປອດໄພ (Phase 0, 2)

### `security_create_administrator`

- ການນຳໃຊ້: ສ້າງບັນຊີທີ່ມີບົດບາດຜູ້ບໍລິຫານລະບົບ. ໂດຍປົກກະຕິ `setup_install` ເປັນຜູ້ເອີ້ນ.
- ຕົວເລືອກ: `--email=`, `--name=`, `--password-stdin` (ລະຫັດຜ່ານຈາກ standard input. ຈຳເປັນເມື່ອແລ່ນແບບບໍ່ໂຕ້ຕອບ).
- ການກວດສອບ: ບັນທຶກ (ID ຜູ້ໃຊ້ທີ່ສ້າງ)
- ຕົວຢ່າງ: `uv run manage.py security_create_administrator --email=admin@example.ac.kr --name="ຜູ້ບໍລິຫານ"`
- ຕົວຢ່າງ (ບໍ່ໂຕ້ຕອບ): `printf '%s\n' "$ADMIN_PASSWORD" | uv run manage.py security_create_administrator --email=admin@example.ac.kr --name="ຜູ້ບໍລິຫານ" --password-stdin`
- ເມື່ອລົ້ມເຫຼວ: ຖ້າເປັນ `system_administrator role is missing` ໃຫ້ແລ່ນ `setup_install` ກ່ອນ. ລະຫັດຜ່ານຕ້ອງມີຢ່າງໜ້ອຍ 12 ຕົວອັກສອນ.

### `security_sync_permissions`

- ການນຳໃຊ້: ເຮັດໃຫ້ລາຍການສິດໃນໂຄດ ແລະ ລາຍການສິດໃນ DB ກົງກັນ. ສິດໃໝ່ຈະຖືກສ້າງ ແລະ ສິດທີ່ຫາຍໄປຈາກລາຍການຈະຖືກລຶບ (ຖືກເອົາອອກຈາກທຸກບົດບາດ). ບົດບາດຂອງລະບົບຈະໄດ້ຮັບທຸກສິດສະເໝີ.
- ເວລາແລ່ນ: ຫຼັງການນຳໃຊ້ລະບົບ (`setup_install` ຈັດການໃຫ້ພ້ອມໃນຂັ້ນຕອນຂໍ້ມູນຈຳເປັນ).
- ຕົວເລືອກ: `--dry-run` (ສະແດງສະເພາະລາຍການສ້າງ/ລຶບ), `--force` (ຂ້າມການຢືນຢັນການລຶບ).
- ການກວດສອບ: ບັນທຶກ (ສິດທີ່ສ້າງ/ລຶບ)
- ການອ່ານຜົນອອກ: ແຖວ `create`, `delete`. ຖ້າມີການລຶບ ຈະມີຄຳຖາມຢືນຢັນ.
- ເມື່ອລົ້ມເຫຼວ: ຖ້າຕອບ "ບໍ່" ຕໍ່ຄຳຖາມຢືນຢັນ ຈະອອກດ້ວຍລະຫັດ 1 ໂດຍບໍ່ປ່ຽນແປງຫຍັງ.

### `security_reencrypt_secrets`

- ການນຳໃຊ້: ຫຼັງຈາກປ່ຽນ `DJANGO_SECRET_KEY` ແລ້ວ, ເຂົ້າລະຫັດຄ່າລັບທີ່ເຂົ້າລະຫັດດ້ວຍກະແຈທີ່ສ້າງຈາກມັນ (ຄ່າລັບ TOTP ຂອງແອັບຢືນຢັນ, seed ຂອງລະຫັດກູ້ຄືນ, ຄ່າລັບ client ຂອງ SSO) ຄືນໃໝ່ດ້ວຍກະແຈໃໝ່. ກ່ອນໜ້ານັ້ນ ລະບົບອ່ານຄ່າເຫຼົ່ານີ້ດ້ວຍກະແຈເກົ່າໃນ `DJANGO_SECRET_KEY_FALLBACKS`. ໃຫ້ແລ່ນກ່ອນລຶບກະແຈເກົ່າ ([ການຄຸ້ມຄອງກະແຈ](security-keys.md)).
- ອາກິວເມັນ/ຕົວເລືອກ: `--dry-run` (ນັບສະເພາະຈຳນວນທີ່ຍັງເຂົ້າລະຫັດດ້ວຍກະແຈເກົ່າ).
- ການກວດສອບ: ບັນທຶກ (ຈຳນວນ)
- ການອ່ານຜົນອອກ: `Dry run: 0 authenticator(s) and 0 SSO client secret(s) use a previous key.` ໝາຍວ່າລຶບກະແຈເກົ່າໄດ້. `cannot be decrypted` ໝາຍວ່າມີຄ່າທີ່ອ່ານບໍ່ໄດ້ດ້ວຍກະແຈໃດເລີຍ: ໃສ່ກະແຈເກົ່າໃນ `DJANGO_SECRET_KEY_FALLBACKS` ແລ້ວແລ່ນໃໝ່.
- ຕົວຢ່າງ: `uv run manage.py security_reencrypt_secrets --dry-run`

### `security_reset_mfa`

- ການນຳໃຊ້: ຕັ້ງຄ່າໃໝ່ການຢືນຢັນສອງຂັ້ນຕອນຂອງຜູ້ໃຊ້ (ແອັບຢືນຢັນ, ລະຫັດອີເມວ, ລະຫັດກູ້ຄືນ, ອຸປະກອນທີ່ຈື່ໄວ້). ຜູ້ໃຊ້ຈະລົງທະບຽນໃໝ່ເມື່ອເຂົ້າສູ່ລະບົບຄັ້ງຕໍ່ໄປ. ໃຊ້ເມື່ອບໍ່ມີຜູ້ບໍລິຫານຄົນໃດເຂົ້າໜ້າບໍລິຫານໄດ້ (ຕົວຢ່າງ: ຜູ້ບໍລິຫານຄົນດຽວເຮັດໂທລະສັບເສຍ). ກໍລະນີອື່ນໃຫ້ໃຊ້ **ຜູ້ໃຊ້ > ຕັ້ງຄ່າໃໝ່ການຢືນຢັນສອງຂັ້ນຕອນ** ໃນໜ້າບໍລິຫານ.
- ອາກິວເມັນ/ຕົວເລືອກ: `{user}` ອີເມວຜູ້ໃຊ້, `--reason=` (ຈຳເປັນ), `--actor=` (ຈຳເປັນ. ຜູ້ບໍລິຫານທີ່ຕັດສິນໃຈຕັ້ງຄ່າໃໝ່).
- ການກວດສອບ: ບັນທຶກ (ທັງບັນທຶກການກວດສອບທາງທຸລະກິດ ແລະ log ຄວາມປອດໄພ ພ້ອມເຫດຜົນ)
- ຕົວຢ່າງ: `uv run manage.py security_reset_mfa admin@example.ac.kr --reason="휴대폰 분실, 본인 확인 완료(전화)" --actor=it-lead@example.ac.kr`

### `security_unlock_user`

- ການນຳໃຊ້: ປົດລັອກບັນຊີທີ່ຖືກລັອກຍ້ອນໃສ່ລະຫັດຜ່ານຜິດຕິດຕໍ່ກັນ ກ່ອນເວລາລັອກຈະໝົດ. ຄືກັນກັບ **ຜູ້ໃຊ້ > ປົດລັອກການເຂົ້າສູ່ລະບົບ** ໃນໜ້າບໍລິຫານ.
- ອາກິວເມັນ/ຕົວເລືອກ: `{user}` ອີເມວຜູ້ໃຊ້, `--reason=` (ຈຳເປັນ).
- ການກວດສອບ: ບັນທຶກ (ບັນທຶກໃນ log ຄວາມປອດໄພດ້ວຍ)
- ການອ່ານຜົນອອກ: ຖ້າເປັນ `The account is not locked.` ໝາຍວ່າບໍ່ໄດ້ປ່ຽນແປງຫຍັງ.
- ໝາຍເຫດ: ເກນການລັອກ (ຈຳນວນຄັ້ງທີ່ລົ້ມເຫຼວ, ເວລາລັອກ) ກຳນົດທີ່ **ການຕັ້ງຄ່າ > ວິທີເຂົ້າສູ່ລະບົບ** ໃນໜ້າບໍລິຫານ.

## ບຸກຄົນ ແລະ ບັນທຶກນັກສຶກສາ (Phase 2)

### `people_find_duplicates`

- ການນຳໃຊ້: ສະແດງລາຍຊື່ບຸກຄົນທີ່ເບິ່ງຄືວ່າເປັນຄົນດຽວກັນ. ເກນຄືເລກບັດປະຈຳຕົວ (ແຮດຊ໌ຄົ້ນຫາ) ກົງກັນ ຫຼື ຊື່ເປັນຕົວອັກສອນລາຕິນ ແລະ ວັນເດືອນປີເກີດກົງກັນ. ບໍ່ລວມບຸກຄົນທີ່ຖືກລວມແລ້ວ.
- ຕົວເລືອກ: `--limit=100` (ຈຳນວນກຸ່ມທີ່ສະແດງ).
- ການກວດສອບ: ບໍ່ບັນທຶກ (ອ່ານເທົ່ານັ້ນ)
- ລະຫັດອອກ: 2 ຖ້າມີຜູ້ສົງໄສວ່າຊ້ຳກັນ.
- ການດຳເນີນການຕໍ່: ກວດແຕ່ລະກຸ່ມທີ່ **ບຸກຄົນ** ໃນໜ້າບໍລິຫານ ແລະ ຖ້າເປັນຄົນດຽວກັນ ໃຫ້ແລ່ນ **ລວມບຸກຄົນທີ່ຊ້ຳກັນ** ຈາກໜ້າຂອງບຸກຄົນທີ່ຈະເກັບໄວ້. ການລວມຍ້ອນກັບບໍ່ໄດ້ ([ຄູ່ມືຜູ້ບໍລິຫານ ບົດທີ 14](../admin/14-merge-and-invitations.md)).

## ການຮັບເຂົ້າຮຽນ (Phase 3)

### `admission_matriculate`

- ຈຸດປະສົງ: ສ້າງບັນທຶກນັກສຶກສາ (ລະຫັດນັກສຶກສາໃໝ່) ໃຫ້ຜູ້ສະໝັກທີ່ຢືນຢັນການເຂົ້າຮຽນແລ້ວຂອງຮອບການຮັບສະໝັກ. ຄືກັນກັບ **ສ້າງບັນທຶກນັກສຶກສາ** ແບບເປັນຊຸດໃນ **ການຮັບເຂົ້າຮຽນ > ໃບສະໝັກ** ຂອງໜ້າຈໍຜູ້ບໍລິຫານ (`MatriculateApplicant`). ຜູ້ສະໝັກແຕ່ລະຄົນຖືກດຳເນີນການແຍກກັນ, ດັ່ງນັ້ນຖ້າຄົນໜຶ່ງລົ້ມເຫຼວ ຄົນອື່ນກໍ່ຍັງດຳເນີນຕໍ່.
- ອາກິວເມັນ/ຕົວເລືອກ: `cycle` ລະຫັດຮອບການຮັບສະໝັກ, `--term=` (ຈຳເປັນ. ລະຫັດພາກຮຽນເຂົ້າຮຽນ, ເຊັ່ນ `2027-SP`. ວັນເຂົ້າຮຽນແມ່ນມື້ທຳອິດຂອງພາກຮຽນ), `--actor=` (ຈຳເປັນ. ບັນຊີທີ່ມີສິດ "ສ້າງບັນທຶກນັກສຶກສາໃຫ້ຜູ້ສະໝັກທີ່ຜ່ານການຄັດເລືອກ". ດຳເນີນການສະເພາະຜູ້ສະໝັກໃນຂອບເຂດສິດຂອງບັນຊີນັ້ນ), `--dry-run` (ສະແດງລາຍຊື່ເທົ່ານັ້ນ).
- ການກວດສອບ: ບັນທຶກ (ຮອບ, ພາກຮຽນ, ຈຳນວນເປົ້າໝາຍ, ຈຳນວນທີ່ສ້າງ, ເລກໃບສະໝັກທີ່ລົ້ມເຫຼວ). ຜູ້ສະໝັກແຕ່ລະຄົນຍັງມີບັນທຶກການກວດສອບທຸລະກິດ (`application.matriculated`).
- ລະຫັດອອກ: 1 ເມື່ອບໍ່ມີລະຫັດຮອບ ຫຼື ພາກຮຽນ ຫຼື ບໍ່ມີ `--actor`, 2 ເມື່ອມີຜູ້ສະໝັກທີ່ລົ້ມເຫຼວ.
- ຕົວຢ່າງ: `uv run manage.py admission_matriculate DEMO-2027-REG --term=2027-SP --actor=admissions@example.ac.kr --dry-run`
- ເມື່ອລົ້ມເຫຼວ: `Only accepted offers without a student record ...` ໝາຍຄວາມວ່າມີບັນທຶກນັກສຶກສາແລ້ວ ຫຼື ຍັງບໍ່ໄດ້ຢືນຢັນ; `The program is not in effect on the admission date.` ໝາຍຄວາມວ່າຫຼັກສູດບໍ່ມີຜົນໃນວັນເຂົ້າຮຽນ (ກວດສອບໄລຍະມີຜົນຂອງຫຼັກສູດໃນ ຂໍ້ມູນພື້ນຖານ > ຫຼັກສູດ); `not in your scope` ໝາຍຄວາມວ່າໃບສະໝັກຢູ່ນອກຂອບເຂດສິດຂອງບັນຊີ `--actor`.

### `admission_expire_drafts`

- ຈຸດປະສົງ: ປ່ຽນໃບສະໝັກສະບັບຮ່າງຂອງຮອບທີ່ປິດແລ້ວ ແລະ ສະບັບຮ່າງທີ່ບໍ່ໄດ້ແກ້ໄຂໃນໄລຍະທີ່ກຳນົດ (**ການຕັ້ງຄ່າ > ການຮັບເຂົ້າຮຽນ > ສະບັບຮ່າງໝົດອາຍຸຫຼັງຈາກ (ມື້)**, ຄ່າເລີ່ມຕົ້ນ 90 ມື້) ເປັນ **ໝົດອາຍຸ**. ໃບສະໝັກທີ່ໝົດອາຍຸບໍ່ກີດຂວາງການສະໝັກໃໝ່ໃນຮອບດຽວກັນ.
- ເວລາດຳເນີນການ: ຕາມກຳນົດເວລາ (ທຸກມື້ເວລາ 03:10, ວຽກ Celery beat `admission.expire_drafts` ດຳເນີນຄຳສັ່ງນີ້).
- ຕົວເລືອກ: `--dry-run` (ນັບຈຳນວນເທົ່ານັ້ນ).
- ການກວດສອບ: ບັນທຶກ (ຈຳນວນທີ່ໝົດອາຍຸ)
- ຕົວຢ່າງ: `uv run manage.py admission_expire_drafts --dry-run`

## ກຸ່ມຮຽນ (Phase 4)

### `section_copy`

- ການນຳໃຊ້: ເລີ່ມການຈັດກຸ່ມຮຽນຂອງພາກຮຽນໃໝ່ຈາກກຸ່ມຮຽນຂອງພາກຮຽນກ່ອນ. ຄືກັນກັບ **ກຸ່ມຮຽນ > ສຳເນົາຈາກພາກຮຽນອື່ນ** ໃນໜ້າບໍລິຫານ (`CopySections`). ສຳເນົາກຸ່ມຮຽນທີ່ບໍ່ຖືກຍົກເລີກໃນສະຖານະຮ່າງ ພ້ອມກັບອາຈານຜູ້ສອນ (ຖ້າຍັງເຮັດວຽກຢູ່), ເວລາສອນ ແລະ ຫ້ອງຮຽນ, ການຈັດສັນບ່ອນນັ່ງ (ເວລາປ່ຽນເລື່ອນຕາມຄວາມຕ່າງຂອງວັນເລີ່ມພາກຮຽນ) ແລະ ແຜນການສອນ (ຮ່າງທີ່ບໍ່ເປີດເຜີຍ). ເວີຊັນວິຊາຈະປ່ຽນເປັນເວີຊັນທີ່ມີຜົນໃນວັນເລີ່ມເຊສຊັນໃໝ່.
- ອາກິວເມັນ/ຕົວເລືອກ: `from-term`, `to-term` ລະຫັດພາກຮຽນ (ຕົວຢ່າງ: `2026-FA`), `--org-unit=` (ສະເພາະກຸ່ມຮຽນຂອງລະຫັດໜ່ວຍງານນີ້, ລະບຸໄດ້ຫຼາຍຄັ້ງ), `--dry-run` (ທົດລອງສຳເນົາໃນທຣານແຊັກຊັນແລ້ວຍົກເລີກ ຜົນຈຶ່ງຄືກັບຕົວຈິງ), `--actor=` (ຈຳເປັນ. ສຳເນົາສະເພາະກຸ່ມຮຽນໃນຂອບເຂດສິດ `ຈັດກຸ່ມຮຽນ` ຂອງບັນຊີນັ້ນ).
- ການກວດສອບ: ບັນທຶກ (ພາກຮຽນຕົ້ນທາງ ແລະ ເປົ້າໝາຍ, ຈຳນວນທີ່ສຳເນົາ, ຂ້າມ ແລະ ຕ້ອງກວດ. ການສຳເນົາຕົວຈິງຍັງບັນທຶກເຫດການ `sections.copied` ນຳ)
- ການອ່ານຜົນອອກ: `skipped` ຄືກຸ່ມຮຽນທີ່ມີກຸ່ມດຽວກັນຢູ່ແລ້ວໃນພາກຮຽນເປົ້າໝາຍ ຫຼື ບໍ່ມີເວີຊັນວິຊາທີ່ມີຜົນ ສ່ວນ `note` ຄືສຳເນົາແລ້ວແຕ່ມີສິ່ງທີ່ຂາດ (ຫ້ອງຮຽນຖືກໃຊ້ຢູ່ແລ້ວຈຶ່ງສຳເນົາໂດຍບໍ່ມີຫ້ອງຮຽນ, ອາຈານທີ່ລາອອກແລ້ວ ແລະ ອື່ນໆ). ເຊສຊັນຈັບຄູ່ດ້ວຍລະຫັດ ຖ້າບໍ່ມີ ຈະໃສ່ໃນເຊສຊັນເຕັມພາກຮຽນ.
- ລະຫັດອອກ: 1 ຖ້າບໍ່ມີລະຫັດພາກຮຽນ ຫຼື ບໍ່ມີ `--actor`.
- ຕົວຢ່າງ: `uv run manage.py section_copy 2026-FA 2027-FA --actor=academic@example.ac.kr --dry-run`

### `schedule_check_conflicts`

- ການນຳໃຊ້: ກວດກຸ່ມຮຽນຂອງພາກຮຽນກ່ອນເປີດເຜີຍຕາຕະລາງຮຽນ. ການຈັດຫ້ອງຮຽນ ຫຼື ອາຈານຊ້ຳກັນຖືກ DB ຂັດຂວາງຢູ່ແລ້ວ ແຕ່ຄຳສັ່ງນີ້ຊອກຫາບັນຫາທີ່ DB ອະນຸຍາດ ເຊັ່ນ: ຈຳນວນຮັບໃຫຍ່ກວ່າຄວາມຈຸຂອງຫ້ອງຮຽນ, ເວີຊັນວິຊາທີ່ບໍ່ມີຜົນໃນວັນເລີ່ມເຊສຊັນ, ອາຈານຜູ້ສອນທີ່ລາອອກແລ້ວ, ການຈັດສັນບ່ອນນັ່ງເກີນຈຳນວນຮັບ, ວັນສອນນອກເຊສຊັນ. ກວດການຊ້ຳກັນຂອງຫ້ອງຮຽນໃນຂໍ້ມູນທີ່ເຂົ້າມາໂດຍບໍ່ມີຂໍ້ຈຳກັດ ເຊັ່ນ ການກູ້ຄືນຈາກການສຳຮອງຂໍ້ມູນ ອີກດ້ວຍ.
- ອາກິວເມັນ: `term` ລະຫັດພາກຮຽນ.
- ການກວດສອບ: ບໍ່ບັນທຶກ (ອ່ານເທົ່ານັ້ນ)
- ລະຫັດອອກ: 2 ຖ້າມີບັນຫາ, 1 ຖ້າບໍ່ມີລະຫັດພາກຮຽນ. ກຸ່ມຮຽນທີ່ຍັງບໍ່ມີອາຈານຜູ້ສອນ, ຫ້ອງຮຽນ ຫຼື ເວລາສອນ ຈະສະແດງເປັນຂໍ້ມູນອ້າງອີງ (`Note`) ເທົ່ານັ້ນ.
- ຕົວຢ່າງ: `uv run manage.py schedule_check_conflicts 2027-SP`

## ການລົງທະບຽນຮຽນ (Phase 5)

### `registration_preflight`

- ການນຳໃຊ້: ກວດພາກຮຽນກ່ອນເປີດການລົງທະບຽນຮຽນ. ສະແດງໄລຍະລົງທະບຽນຮຽນ ແລະ ໄລຍະເພີ່ມ-ຖອນ, ຊຸດກົດລະບຽບ, ຈຳນວນກຸ່ມຮຽນທີ່ເປີດເຜີຍ, ກຸ່ມຮຽນທີ່ຈຳນວນຮັບເປັນ 0, ການຈັດສັນບ່ອນນັ່ງເກີນຈຳນວນຮັບ, ເວີຊັນວິຊາທີ່ບໍ່ມີຜົນໃນວັນເລີ່ມເຊສຊັນ, ຈຳນວນນັກສຶກສາປັດຈຸບັນທີ່ບໍ່ມີເພດານໜ່ວຍກິດ ແລະ ຈຳນວນນັກສຶກສາທີ່ຖືກຈຳກັດການລົງທະບຽນຮຽນ.
- ອາກິວເມັນ: `term` ລະຫັດພາກຮຽນ (ຕົວຢ່າງ: `2027-SP`).
- ການກວດສອບ: ບໍ່ບັນທຶກ (ອ່ານເທົ່ານັ້ນ)
- ລະຫັດອອກ: 2 ຖ້າມີບັນຫາ. ຖ້າບໍ່ມີຊຸດກົດລະບຽບ ຈະສະແດງເປັນຂໍ້ມູນອ້າງອີງ ບໍ່ແມ່ນບັນຫາ (ນຳໃຊ້ຄ່າເລີ່ມຕົ້ນຂອງກົດລະບຽບ).
- ຕົວຢ່າງ: `uv run manage.py registration_preflight 2027-SP`

### `registration_simulate`

- ການນຳໃຊ້: ສະແດງຜົນຕໍ່ກົດລະບຽບວ່າຈະເກີດຫຍັງຂຶ້ນຖ້ານັກສຶກສາລົງທະບຽນກຸ່ມຮຽນຕອນນີ້ (ຫຼື ໃນເວລາທີ່ລະບຸ). ບໍ່ບັນທຶກ ແລະ ບໍ່ທິ້ງບັນທຶກການພະຍາຍາມ. ໃຊ້ຕອບຄຳຖາມ "ເປັນຫຍັງລົງທະບຽນບໍ່ໄດ້".
- ອາກິວເມັນ: `student-number` ລະຫັດນັກສຶກສາ, `section` `ລະຫັດວິຊາ-ກຸ່ມ` (ຕົວຢ່າງ: `CSE2010-01`).
- ຕົວເລືອກ: `--term=` (ລະຫັດພາກຮຽນ. ຄ່າເລີ່ມຕົ້ນຄືພາກຮຽນຫຼ້າສຸດທີ່ມີກຸ່ມນັ້ນ), `--at=` (ເວລາຕັດສິນ. ຕົວຢ່າງ: `"2027-02-10 10:00 Asia/Seoul"`).
- ການກວດສອບ: ບໍ່ບັນທຶກ (ອ່ານເທົ່ານັ້ນ)
- ການອ່ານຜົນອອກ: ຕໍ່ກົດລະບຽບ ຜ່ານ/ບໍ່ຜ່ານ, ຂັດຂວາງ/ເຕືອນ ແລະ ຂໍ້ຄວາມ. ກົດລະບຽບທີ່ມີຂໍ້ຍົກເວັ້ນ (override) ນຳໃຊ້ຈະສະແດງເປັນບໍ່ຜ່ານ ແຕ່ບໍ່ຂັດຂວາງ. ຈຳນວນຮັບສະແດງແຍກຕ່າງຫາກລຸ່ມຕາຕະລາງກົດລະບຽບ.
- ລະຫັດອອກ: 2 ຖ້າການລົງທະບຽນຈະຖືກປະຕິເສດ.
- ຕົວຢ່າງ: `uv run manage.py registration_simulate 202612345 CSE2010-01 --at="2027-02-10 10:00 Asia/Seoul"`

### `waitlist_promote`

- ການນຳໃຊ້: ລົງທະບຽນຜູ້ລໍຖ້າຂອງກຸ່ມຮຽນທີ່ມີບ່ອນວ່າງຕາມລຳດັບ. ເມື່ອເລື່ອນຂຶ້ນ ຈະກວດທຸກກົດລະບຽບຄືນໃໝ່ ແລະ ຜູ້ລໍຖ້າທີ່ບໍ່ຜ່ານກົດລະບຽບຈະຖືກເອົາອອກຈາກລາຍຊື່ລໍຖ້າ (ບັນທຶກເຫດຜົນ). ລາຍຊື່ລໍຖ້າຂອງກຸ່ມຮຽນທີ່ໄລຍະລົງທະບຽນຮຽນ ແລະ ໄລຍະເພີ່ມ-ຖອນປິດແລ້ວທັງສອງຈະໝົດອາຍຸ. ສົ່ງເມວຜົນໃຫ້ນັກສຶກສາ.
- ອາກິວເມັນ/ຕົວເລືອກ: `term?` ລະຫັດພາກຮຽນ (ຄ່າເລີ່ມຕົ້ນ: ທຸກພາກຮຽນທີ່ມີຜູ້ລໍຖ້າ), `--actor=`.
- ການກວດສອບ: ບັນທຶກ (ຈຳນວນກຸ່ມຮຽນ, ເລື່ອນຂຶ້ນ, ເອົາອອກ ແລະ ໝົດອາຍຸ)
- ເວລາແລ່ນ: ເມື່ອມີການຍົກເລີກ/ຖອນ ແລະ ການປ່ອຍການຈັດສັນບ່ອນນັ່ງ ກຸ່ມຮຽນນັ້ນຈະຖືກປະມວນຜົນທັນທີດ້ວຍວຽກໃນຄິວ. ຄຳສັ່ງນີ້ເປັນຕາໜ່າງນິລະໄພທີ່ແລ່ນທຸກຊົ່ວໂມງຕາມກຳນົດເວລາເພື່ອຈັດການສິ່ງທີ່ຕົກຄ້າງ.
- ຕົວຢ່າງ: `uv run manage.py waitlist_promote 2027-SP --actor=registrar@example.ac.kr`

### `registration_release_reserved_seats`

- ການນຳໃຊ້: ໝາຍການຈັດສັນບ່ອນນັ່ງທີ່ເລີຍເວລາປ່ຽນແລ້ວ (ຕົວຢ່າງ: ບ່ອນນັ່ງສະຫງວນສຳລັບນັກສຶກສາສາຂາວິຊາເອກ) ວ່າປະມວນຜົນແລ້ວ ແລະ ໃສ່ວຽກເລື່ອນຂຶ້ນຈາກລາຍຊື່ລໍຖ້າຂອງກຸ່ມຮຽນນັ້ນເຂົ້າຄິວ. ບ່ອນນັ່ງສະຫງວນຈະກາຍເປັນບ່ອນນັ່ງທົ່ວໄປທັນທີໃນການຄຳນວນເມື່ອເລີຍເວລາປ່ຽນ ດັ່ງນັ້ນຄຳສັ່ງນີ້ມີໜ້າທີ່ສົ່ງຕໍ່ບ່ອນນັ່ງໃຫ້ຜູ້ລໍຖ້າເທົ່ານັ້ນ.
- ການກວດສອບ: ບໍ່ບັນທຶກ (ແລ່ນທຸກ 5 ນາທີ. ຜົນການເລື່ອນຂຶ້ນຢູ່ໃນບັນທຶກການລົງທະບຽນຮຽນ)
- ເວລາແລ່ນ: ຕາມກຳນົດເວລາ (ທຸກ 5 ນາທີ, ວຽກ Celery beat `registration.release_reserved_seats`). ວຽກເລື່ອນຂຶ້ນແມ່ນ `registration.promote_waitlist` ຕໍ່ກຸ່ມຮຽນ (ດ້ວຍການລັອກ Redis ເທື່ອລະອັນຕໍ່ກຸ່ມຮຽນ).
- ຕົວຢ່າງ: `uv run manage.py registration_release_reserved_seats`

## ເກຣດ (Phase 6)

### `term_close`

- ການນຳໃຊ້: ປິດພາກຮຽນ. ເກຣດທັງໝົດຂອງພາກຮຽນຕ້ອງຖືກຢືນຢັນແລ້ວ. ຄຳນວນບັນທຶກພາກຮຽນ (ໜ່ວຍກິດ, GPA ຂອງພາກຮຽນ ແລະ ສະສົມ) ຕໍ່ກຸ່ມນັກສຶກສາ (100 ຄົນ) ແລະ ຕັດສິນສະຖານະການຮຽນ (ປົກກະຕິ, ເຕືອນທາງວິຊາການ, ພິຈາລະນາໃຫ້ອອກ) ແລະ ການເປັນນັກສຶກສາດີເດັ່ນ (ວຽກ `grading.close_term_records` ຂອງ Celery chord) ຈາກນັ້ນວຽກສຸດທ້າຍ `grading.finish_term_close` ຈັດອັນດັບນັກສຶກສາດີເດັ່ນຕໍ່ຫຼັກສູດ ປິດບັນທຶກພາກຮຽນເປັນບັນທຶກທາງການ ແລະ ປ່ຽນພາກຮຽນເປັນສະຖານະ **ປິດເກຣດ**. ຄວາມຄືບໜ້າເກັບໄວ້ໃນ `job_batches` ແລະ ສະແດງຢູ່ເທິງລາຍການ **ເກຣດ > ບັນທຶກພາກຮຽນ**. ເມື່ອສຳເລັດ ຈະສົ່ງເມວໃຫ້ພະນັກງານທີ່ເລີ່ມ. ຄືກັນກັບ **ເກຣດ > ບັນທຶກພາກຮຽນ > ປິດພາກຮຽນ** ໃນໜ້າບໍລິຫານ.
- ອາກິວເມັນ/ຕົວເລືອກ: `term` ລະຫັດພາກຮຽນ, `--dry-run` (ກວດສະເພາະວ່າປິດໄດ້ຫຼືບໍ່), `--reason=` (ເຫດຜົນທີ່ຈະບັນທຶກ), `--actor=`.
- ການກວດສອບ: ບັນທຶກ (ຈຳນວນນັກສຶກສາ, ຈຳນວນກຸ່ມຮຽນທີ່ຍັງບໍ່ຢືນຢັນ, ID ຂອງ batch). ເມື່ອປິດສຳເລັດ ບັນທຶກການກວດສອບ `term.closed` ຈະເກັບຈຳນວນຜູ້ຖືກເຕືອນທາງວິຊາການ, ພິຈາລະນາໃຫ້ອອກ ແລະ ນັກສຶກສາດີເດັ່ນ.
- ລະຫັດອອກ: 2 ຖ້າມີກຸ່ມຮຽນທີ່ເກຣດຍັງບໍ່ຖືກຢືນຢັນ (ສະແດງຈຳນວນທີ່ຍັງບໍ່ຢືນຢັນຕໍ່ກຸ່ມຮຽນ). ພາກຮຽນທີ່ບໍ່ຢູ່ໃນສະຖານະເປີດເຜີຍ (published) ເປັນ 1.
- ເວລາແລ່ນ: ຫຼັງການປ້ອນ ແລະ ຢືນຢັນເກຣດສຳເລັດ. ເບິ່ງຄວາມຄືບໜ້າໃນ Flower ແລະ ໜ້າບັນທຶກພາກຮຽນ. ຖ້າບໍ່ມີ Celery worker ສະຖານະພາກຮຽນຈະບໍ່ປ່ຽນ. ກຸ່ມທີ່ລົ້ມເຫຼວຍ້ອນຂໍ້ຜິດພາດຖານຂໍ້ມູນຈະລອງໃໝ່ສູງສຸດ 3 ຄັ້ງ; ຖ້າຍັງລົ້ມເຫຼວ batch ຈະຢູ່ໃນສະຖານະລົ້ມເຫຼວ ແລະ ພາກຮຽນບໍ່ປ່ຽນ (ແກ້ໄຂສາເຫດແລ້ວແລ່ນໃໝ່; ແລ່ນໃໝ່ໄດ້ຜົນຄືເກົ່າ).
- ຕົວຢ່າງ: `uv run manage.py term_close 2026-FA --dry-run`, `uv run manage.py term_close 2026-FA --reason="2026-2 성적 마감" --actor=registrar@example.ac.kr`

### `grades_recalculate`

- ການນຳໃຊ້: ຄຳນວນບັນທຶກພາກຮຽນ (ໜ່ວຍກິດ, GPA ຂອງພາກຮຽນ ແລະ ສະສົມ) ຄືນໃໝ່ຈາກເກຣດທີ່ຢືນຢັນແລ້ວ. ໃຊ້ເມື່ອປ່ຽນນະໂຍບາຍການປະມວນຜົນເກຣດ (ຈຳນວນຕຳແໜ່ງທົດສະນິຍົມຂອງ GPA, ການນັບການຮຽນຊ້ຳ) ແລ້ວນຳໃຊ້ກັບພາກຮຽນທີ່ຜ່ານມາ. ສະຖານະການຮຽນ ແລະ ນັກສຶກສາດີເດັ່ນຍັງຄົງຄ່າທີ່ກຳນົດຕອນປິດພາກຮຽນ. ການອະນຸມັດການແກ້ໄຂເກຣດຈະຄຳນວນນັກສຶກສາຄົນນັ້ນຄືນໃໝ່ອັດຕະໂນມັດ ຈຶ່ງບໍ່ຈຳເປັນຕ້ອງໃຊ້ຄຳສັ່ງນີ້.
- ຕົວເລືອກ: `--term=` (ນັກສຶກສາທີ່ມີເກຣດໃນພາກຮຽນນັ້ນ ເລີ່ມແຕ່ພາກຮຽນນັ້ນ), `--student-number=` (ນັກສຶກສາຄົນດຽວ), `--reason=` (ຈຳເປັນ), `--actor=`.
- ການກວດສອບ: ບັນທຶກ (ຈຳນວນນັກສຶກສາ, ເຫດຜົນ)
- ລະຫັດອອກ: 1 ຖ້າບໍ່ມີເຫດຜົນ ຫຼື ບໍ່ພົບລະຫັດພາກຮຽນ ຫຼື ລະຫັດນັກສຶກສາ.
- ຕົວຢ່າງ: `uv run manage.py grades_recalculate --term=2026-SP --reason="평점 소수 셋째 자리로 변경"`

### `grades_remind_missing`

- ການນຳໃຊ້: ສົ່ງເມວແຈ້ງເຕືອນໃຫ້ອາຈານຜູ້ສອນຂອງກຸ່ມຮຽນທີ່ຍັງບໍ່ສົ່ງເກຣດ (ຍັງບໍ່ປ້ອນ ຫຼື ບັນທຶກຊົ່ວຄາວ). ລວມກຸ່ມຮຽນຕໍ່ອາຈານແລ້ວສົ່ງຄົນລະສະບັບ.
- ອາກິວເມັນ/ຕົວເລືອກ: `term` ລະຫັດພາກຮຽນ, `--dry-run` (ສະແດງເປົ້າໝາຍໂດຍບໍ່ສົ່ງ), `--actor=`.
- ການກວດສອບ: ບັນທຶກ (ຈຳນວນກຸ່ມຮຽນ, ອາຈານ ແລະ ທີ່ສົ່ງ)
- ເວລາແລ່ນ: ສອງສາມມື້ກ່ອນສິ້ນສຸດໄລຍະປ້ອນເກຣດ. ລົງທະບຽນໃນຕົວກຳນົດເວລາຖ້າຈຳເປັນ.
- ຕົວຢ່າງ: `uv run manage.py grades_remind_missing 2026-FA --dry-run`

## ການປະເມີນການສອນ (Phase 7)

### `evaluation_remind`

- ການນຳໃຊ້: ສົ່ງເມວແຈ້ງເຕືອນໃຫ້ນັກສຶກສາທີ່ຍັງມີວິຊາທີ່ບໍ່ໄດ້ປະເມີນໃນຂະນະທີ່ໄລຍະການປະເມີນການສອນເປີດຢູ່. ລວມວິຊາທີ່ເຫຼືອຕໍ່ນັກສຶກສາແລ້ວສົ່ງຄົນລະສະບັບ (ເປັນພາສາຂອງຜູ້ຮັບ).
- ອາກິວເມັນ/ຕົວເລືອກ: `term` ລະຫັດພາກຮຽນ, `--dry-run` (ສະເພາະຈຳນວນນັກສຶກສາເປົ້າໝາຍ ໂດຍບໍ່ສົ່ງ), `--actor=`.
- ການກວດສອບ: ບັນທຶກ (ຈຳນວນນັກສຶກສາເປົ້າໝາຍ, ຈຳນວນທີ່ສົ່ງ)
- ລະຫັດອອກ: 1 ຖ້າບໍ່ພົບລະຫັດພາກຮຽນ.
- ເວລາແລ່ນ: ໜຶ່ງຫຼືສອງຄັ້ງໃນລະຫວ່າງໄລຍະການປະເມີນ. ລົງທະບຽນໃນຕົວກຳນົດເວລາຖ້າຈຳເປັນ.
- ຕົວຢ່າງ: `uv run manage.py evaluation_remind 2026-FA --dry-run`

### `evaluation_publish_results`

- ການນຳໃຊ້: ເປີດເຜີຍຜົນການປະເມີນການສອນຂອງພາກຮຽນໃຫ້ອາຈານ. ຄືກັນກັບ **ການປະເມີນການສອນ > ການປະເມີນການສອນຕາມພາກຮຽນ > ເຜີຍແຜ່ຜົນ** ໃນໜ້າບໍລິຫານ. ຫຼັງເປີດເຜີຍແລ້ວ ກໍຍັງເຫັນຜົນສະເພາະກຸ່ມຮຽນທີ່ບັນລຸຈຳນວນຄຳຕອບຂັ້ນຕ່ຳ ແລະ ອັດຕາການຕອບ.
- ອາກິວເມັນ/ຕົວເລືອກ: `term` ລະຫັດພາກຮຽນ, `--actor=` (ບັນຊີທີ່ມີສິດ `ຄຸ້ມຄອງແບບຟອມການປະເມີນ, ການປະເມີນຕາມພາກຮຽນ ແລະ ການເຜີຍແຜ່`; ບັນທຶກເປັນຜູ້ເຜີຍແຜ່).
- ການກວດສອບ: ບັນທຶກ (ຈຳນວນຄຳຕອບ, ເປີດເຜີຍແລ້ວຫຼືບໍ່). ການກວດສອບທຸລະກິດ `evaluation.published`.
- ລະຫັດອອກ: 1 ຖ້າບໍ່ພົບລະຫັດພາກຮຽນ ຫຼື ພາກຮຽນບໍ່ມີການປະເມີນການສອນ.
- ເວລາແລ່ນ: ຫຼັງໄລຍະການປະເມີນ ແລະ ການປະມວນຜົນເກຣດສິ້ນສຸດ. ພາກຮຽນທີ່ເປີດເຜີຍແລ້ວຈະບໍ່ຖືກປ່ຽນ.
- ຕົວຢ່າງ: `uv run manage.py evaluation_publish_results 2026-FA --actor=academic-affairs@example.ac.kr`

## ໃບຢັ້ງຢືນ (Phase 8)

### `certificate_verify`

- ການນຳໃຊ້: ກວດລະຫັດຢືນຢັນຂອງໃບຢັ້ງຢືນດ້ວຍເກນດຽວກັນກັບໜ້າກວດຄວາມແທ້ສາທາລະນະ. ສະແດງປະເພດ, ເລກທີ, ວັນທີອອກ ແລະ ຊື່ເຈົ້າຂອງທີ່ຖືກປິດບັງບາງສ່ວນ.
- ອາກິວເມັນ/ຕົວເລືອກ: `code` ລະຫັດຢືນຢັນ (ບໍ່ແຍກຕົວພິມ).
- ການກວດສອບ: ບໍ່ມີ (ອ່ານ)
- ລະຫັດອອກ: 0 ຖ້າຖືກຕ້ອງ, 2 ຖ້າເປັນລະຫັດທີ່ບໍ່ມີຢູ່, ຖືກຖອນ ຫຼື ໝົດອາຍຸ.
- ຕົວຢ່າງ: `uv run manage.py certificate_verify 7Q2M9XK4TB0RWZ5C1HNA`

### `certificate_render`

- ການນຳໃຊ້: ສ້າງ PDF ຂອງໃບຢັ້ງຢືນທີ່ອອກແລ້ວຄືນໃໝ່ດ້ວຍຂໍ້ມູນ ແລະ ແມ່ແບບປັດຈຸບັນ ແລະ ປ່ຽນໄຟລ໌ທີ່ເກັບໄວ້. ຄືກັນກັບ **ໃບຢັ້ງຢືນ > ໃບຢັ້ງຢືນທີ່ອອກແລ້ວ > ສ້າງໃໝ່** ໃນໜ້າບໍລິຫານ. ເລກທີ ແລະ ລະຫັດຢືນຢັນຄົງເດີມ ແຕ່ checksum ປ່ຽນ. PDF ສ້າງໂດຍ Gotenberg.
- ອາກິວເມັນ/ຕົວເລືອກ: `issue` ເລກທີ, `--reason=` (ຈຳເປັນ), `--actor=` (ບັນຊີທີ່ມີສິດ `ອອກ, ສ້າງໃໝ່ ແລະ ຖອນໃບຢັ້ງຢືນ`).
- ການກວດສອບ: ບັນທຶກ (ເລກທີ, checksum ໃໝ່); ບັນທຶກການກວດສອບທຸລະກິດ `certificate.rerendered`.
- ລະຫັດອອກ: 1 ຖ້າບໍ່ມີເຫດຜົນ, ບໍ່ພົບເລກທີ ຫຼື ສ້າງ PDF ບໍ່ໄດ້.
- ເວລາແລ່ນ: ເມື່ອຕ້ອງການສ້າງໃບຢັ້ງຢືນສະເພາະໃບຄືນໃໝ່ຫຼັງແກ້ໄຂແມ່ແບບ, ການສະກົດຊື່ ຫຼື `APP_URL`.
- ຕົວຢ່າງ: `uv run manage.py certificate_render ENR-2026-000001 --reason="ແກ້ໄຂການສະກົດຊື່"`

## ການສອບເສັງພາສາ/ການສອບເສັງລວມ (Phase 9)

### `assessment_import_results`

- ການນຳໃຊ້: ປ້ອນຜົນຂອງຮອບການສອບເສັງຈາກ CSV. ກົດລະບຽບດຽວກັນກັບ **ຮອບການສອບເສັງ > ນຳເຂົ້າຜົນ (CSV)** ໃນໜ້າບໍລິຫານ (ສະເພາະນັກສຶກສາທີ່ລົງທະບຽນສອບ, ຕັດສິນຜ່ານດ້ວຍຄະແນນ, ຖ້າປ້ອນຊ້ຳກ່ອນເປີດເຜີຍຈະແທນທີ່, ຫຼັງເປີດເຜີຍແຖວເຫຼົ່ານັ້ນຖືກລາຍງານເປັນຜິດພາດ).
- ອາກິວເມັນ/ຕົວເລືອກ: `type` ລະຫັດປະເພດການສອບເສັງ / `held_date` ວັນສອບ `YYYY-MM-DD` / `file` CSV ແບບ UTF-8 ທີ່ມີແຖວຫົວ, `--actor=` (ຈຳເປັນ, ບັນທຶກເປັນຜູ້ປ້ອນຜົນ), `--dry-run` (ກວດແຖວໂດຍບໍ່ບັນທຶກ).
- ຮູບແບບຖັນ: [ຄູ່ມືຜູ້ບໍລິຫານ ບົດທີ 24](../admin/24-assessments.md).
- ການກວດສອບ: ບັນທຶກ (ຮອບ, ຊື່ໄຟລ໌, ຈຳນວນແຖວ, ຈຳນວນທີ່ປ້ອນ, ຂາດສອບ ແລະ ຜິດພາດ). ແຕ່ລະຜົນມີບັນທຶກການກວດສອບ `assessment.result_recorded` ນຳ.
- ລະຫັດອອກ: 1 ຖ້າບໍ່ພົບຮອບ, ອ່ານໄຟລ໌ບໍ່ໄດ້ ຫຼື ບໍ່ມີ `--actor`; 2 ຖ້າມີແຖວຜິດພາດ (ແຖວທີ່ເຫຼືອຖືກບັນທຶກ).
- ຕົວຢ່າງ: `uv run manage.py assessment_import_results ENG_COMP 2026-05-15 storage/eng.csv --actor=registrar@example.ac.kr --dry-run`

### `assessment_publish_results`

- ການນຳໃຊ້: ເປີດເຜີຍຜົນຂອງຮອບໃຫ້ນັກສຶກສາ. ຄືກັນກັບ **ຮອບການສອບເສັງ > ເປີດເຜີຍຜົນ** ໃນໜ້າບໍລິຫານ. ຫຼັງເປີດເຜີຍ ຜົນປ່ຽນໄດ້ສະເພາະຜ່ານຄຳຮ້ອງແກ້ໄຂ.
- ອາກິວເມັນ/ຕົວເລືອກ: `type` ລະຫັດປະເພດການສອບເສັງ / `held_date` ວັນສອບ, `--actor=` (ຈຳເປັນ, ມີສິດລົງທະບຽນ, ປ້ອນ ແລະ ເປີດເຜີຍຜົນ).
- ການກວດສອບ: ບັນທຶກ (ຮອບ, ຈຳນວນຜົນ) ແລະ ບັນທຶກການກວດສອບ `assessment.results_published`
- ລະຫັດອອກ: 1 ຖ້າບໍ່ພົບຮອບ, ເປີດເຜີຍແລ້ວ, ບໍ່ມີ `--actor` ຫຼື ບໍ່ມີສິດ.
- ເວລາແລ່ນ: ຫຼັງການປ້ອນຜົນສຳເລັດ.
- ຕົວຢ່າງ: `uv run manage.py assessment_publish_results ENG_COMP 2026-05-15 --actor=registrar@example.ac.kr`

## ການເຂົ້າຮຽນ (Phase 10)

### `attendance_generate_sessions`

- ການນຳໃຊ້: ສ້າງຄາບຮຽນຈາກເວລາສອນ (ວັນ, ເວລາ, ໄລຍະ) ສຳລັບແຕ່ລະກຸ່ມຮຽນຂອງພາກຮຽນ. ຄືກັນກັບ **ສ້າງຈາກເວລາຮຽນ** ໃນພອດທໍອາຈານ ແລະ **ສ້າງຄາບຮຽນ** ໃນແຖບ **ຄາບຮຽນ** ຂອງໜ້າບໍລິຫານ. ຄາບຮຽນ ແລະ ການເຂົ້າຮຽນທີ່ມີຢູ່ແລ້ວຄົງເດີມ (ແລ່ນຊ້ຳໄດ້ຢ່າງປອດໄພ). ກຸ່ມຮຽນທີ່ຖືກຍົກເລີກຈະຖືກຂ້າມ.
- ອາກິວເມັນ/ຕົວເລືອກ: `term` ລະຫັດພາກຮຽນ, `--section=` (ລະຫັດວິຊາ-ກຸ່ມ ຕົວຢ່າງ: `CSE2010-01` ພຽງອັນດຽວ), `--dry-run` (ສະເພາະຈຳນວນກຸ່ມຮຽນເປົ້າໝາຍ), `--actor=`.
- ການກວດສອບ: ບັນທຶກ (ພາກຮຽນ, ຈຳນວນກຸ່ມຮຽນ, ຈຳນວນຄາບຮຽນທີ່ສ້າງ)
- ເວລາແລ່ນ: ກ່ອນເລີ່ມພາກຮຽນ ຫຼັງຢືນຢັນເວລາສອນແລ້ວ. ແລ່ນຊ້ຳເມື່ອເວລາສອນປ່ຽນ.
- ຕົວຢ່າງ: `uv run manage.py attendance_generate_sessions 2026-FA --dry-run`

## ການຈົບການສຶກສາ (Phase 11)

### `degree_audit_run`

- ການນຳໃຊ້: ບັນທຶກການກວດເງື່ອນໄຂການຈົບການສຶກສາຂອງນັກສຶກສາທີ່ກຳລັງຮຽນແຕ່ລະຄົນ. ຄືກັນກັບ **ການກວດເງື່ອນໄຂການຈົບການສຶກສາ > ແລ່ນການກວດ** ໃນໜ້າບໍລິຫານ. ການກວດຫຼ້າສຸດທີ່ບັນທຶກໄວ້ເປັນພື້ນຖານຂອງການດຳເນີນການຈົບການສຶກສາ. ການແລ່ນແຕ່ລະຄັ້ງເພີ່ມພາບບັນທຶກໃໝ່.
- ຕົວເລືອກ: `--term=` (ລະຫັດພາກຮຽນທີ່ການກວດສັງກັດ), `--student-number=` (ຄົນດຽວ), `--min-year-level=` (ສະເພາະຊັ້ນປີນີ້ຂຶ້ນໄປ), `--actor=`.
- ການກວດສອບ: ບັນທຶກ (ຈຳນວນນັກສຶກສາ, ຈຳນວນທີ່ຄົບເງື່ອນໄຂ). ເມື່ອມີ `--actor` ຈະບັນທຶກ `graduation.audits_run` ນຳ.
- ລະຫັດອອກ: 1 ເມື່ອບໍ່ຮູ້ຈັກລະຫັດພາກຮຽນ.
- ເວລາແລ່ນ: ກ່ອນການພິຈາລະນາຈົບການສຶກສາ (ທ້າຍພາກຮຽນ) ແລະ ຫຼັງແກ້ໄຂຊຸດເງື່ອນໄຂ ຫຼື ວິຊາທົດແທນ.
- ຕົວຢ່າງ: `uv run manage.py degree_audit_run --term=2026-FA --min-year-level=4 --actor=registrar@example.edu`

## ການເຊື່ອມຕໍ່ LMS (Phase 12)

### `lms_sync`

- ການນຳໃຊ້: ສົ່ງກຸ່ມຮຽນທີ່ເປີດເຜີຍແລ້ວເຂົ້າແພລັດຟອມ (ສ້າງ ແລະ ເຊື່ອມຕໍ່ຫ້ອງຮຽນ, ອາຈານຜູ້ສອນ, ນັກສຶກສາທີ່ກຳລັງລົງທະບຽນຮຽນ). ດຳເນີນການຄືກັນກັບ **ການເຊື່ອມຕໍ່ວິຊາ > ຊິງຄ໌ອີກຄັ້ງ** ໃນໜ້າບໍລິຫານ ແຕ່ເປັນລະດັບພາກຮຽນ. ກຸ່ມຮຽນທີ່ເຊື່ອມຕໍ່ແລ້ວຈະຖືກຮັບປະກັນຄືນເທົ່ານັ້ນ (idempotent). ທຸກຂັ້ນຕອນຖືກເກັບໃນ **ບັນທຶກການຊິງຄ໌**.
- ອາກິວເມັນ/ຕົວເລືອກ: `{platform}` ລະຫັດແພລັດຟອມ, `--term=` (ລະຫັດພາກຮຽນ ຄ່າເລີ່ມຕົ້ນຄືທຸກພາກຮຽນທີ່ຍັງບໍ່ສິ້ນສຸດ), `--section=` (ລະຫັດວິຊາ-ກຸ່ມ ອັນດຽວ ເຊັ່ນ `CSE2010-01`), `--dry-run` (ບັນທຶກສິ່ງທີ່ຈະສົ່ງເປັນ "ຂ້າມ" ເທົ່ານັ້ນ), `--actor=`.
- ການກວດສອບ: ບັນທຶກ (ແພລັດຟອມ, ຈຳນວນກຸ່ມຮຽນ, ຈຳນວນສະມາຊິກ, ຈຳນວນທີ່ລົ້ມເຫຼວ)
- ລະຫັດອອກ: 1 ເມື່ອບໍ່ຮູ້ຈັກລະຫັດແພລັດຟອມ ຫຼື ພາກຮຽນ, 2 ຖ້າມີກຸ່ມຮຽນທີ່ລົ້ມເຫຼວ (ຂໍ້ຜິດພາດຂອງແຕ່ລະກຸ່ມຮຽນຈະຖືກສະແດງ).
- ເວລາແລ່ນ: ກ່ອນເລີ່ມພາກຮຽນ, ຫຼັງຈາກເປີດໃຊ້ແພລັດຟອມໃໝ່.
- ຕົວຢ່າງ: `uv run manage.py lms_sync DEMO --term=2026-FA --dry-run`

### `lms_reconcile`

- ການນຳໃຊ້: ປຽບທຽບລາຍຊື່ຫ້ອງຮຽນຂອງແພລັດຟອມກັບລາຍຊື່ຜູ້ລົງທະບຽນຮຽນຂອງລະບົບບໍລິຫານການສຶກສາ ແລ້ວເພີ່ມສະມາຊິກທີ່ຂາດ ແລະ ເອົາສະມາຊິກທີ່ເກີນອອກ. ກຸ່ມຮຽນທີ່ຍັງບໍ່ເຊື່ອມຕໍ່ຈະຖືກຊິງທັງໝົດ. ຄວາມແຕກຕ່າງຖືກບັນທຶກໃນບັນທຶກການຊິງ (`reconcile`, `missing` ແລະ `extra` ໃນ `payload`).
- ອາກິວເມັນ/ຕົວເລືອກ: `{platform?}` (ຖ້າບໍ່ມີ ທຸກແພລັດຟອມທີ່ໃຊ້ງານຢູ່), `--term=` (ຄ່າເລີ່ມຕົ້ນຄືພາກຮຽນທີ່ຍັງບໍ່ສິ້ນສຸດ), `--dry-run` (ບັນທຶກສະເພາະຄວາມແຕກຕ່າງ), `--actor=`.
- ການກວດສອບ: ບັນທຶກ (ຈຳນວນກຸ່ມຮຽນຕໍ່ແພລັດຟອມ, ຈຳນວນທີ່ເພີ່ມ, ເອົາອອກ ແລະ ລົ້ມເຫຼວ)
- ລະຫັດອອກ: 1 ເມື່ອບໍ່ຮູ້ຈັກລະຫັດແພລັດຟອມ ຫຼື ພາກຮຽນ ຫຼື ບໍ່ມີແພລັດຟອມທີ່ໃຊ້ງານ, 2 ຖ້າມີກຸ່ມຮຽນທີ່ລົ້ມເຫຼວ.
- ເວລາແລ່ນ: ທຸກວັນ 02:30 ໂດຍວຽກຕາມກຳນົດເວລາ `lms.reconcile` (Celery beat). ແລ່ນດ້ວຍມືຫຼັງແພລັດຟອມຂັດຂ້ອງ.

### `api_issue_token`

- ການນຳໃຊ້: ອອກ token ສຳລັບການເຊື່ອມຕໍ່ API ໃຫ້ບັນຊີ ([ADR 0004-django](../../../../porting/decisions/0004-django-api-tokens.md)). ໂດຍທົ່ວໄປອອກໃຫ້ບັນຊີບໍລິການທີ່ມີສະເພາະສິດທີ່ຈຳເປັນ (LMS: `lms.manage`, BI: `reports.view`). Token ສະແດງ **ເທື່ອດຽວ** ໃນແຖວທຳອິດຂອງຜົນອອກ; ຖານຂໍ້ມູນເກັບພຽງ digest. ສົ່ງໃນ header `Authorization: Token <token>`.
- ອາກິວເມັນ/ຕົວເລືອກ: `{email}` ອີເມວບັນຊີ, `--days=` (ອາຍຸ 1 ຫາ 365 ມື້, ຄ່າເລີ່ມຕົ້ນ `API_TOKEN_TTL_DAYS` = 90), `--reason=` (ຈຸດປະສົງ, ບັນທຶກໃນການກວດສອບ), `--actor=`.
- ການກວດສອບ: ບັນທຶກ (`api.token_issued`: ຄຳນຳໜ້າຂອງ key ແລະ ເວລາໝົດອາຍຸ; ບໍ່ເກັບ token ຕົວຈິງ)
- ລະຫັດອອກ: 1 ເມື່ອບໍ່ຮູ້ຈັກບັນຊີ, ບັນຊີບໍ່ໄດ້ໃຊ້ງານ ຫຼື ອາຍຸເກີນຂອບເຂດ.
- ຕົວຢ່າງ: `uv run manage.py api_issue_token moodle-sync@example.ac.kr --days=365 --reason="Moodle callback" --actor=admin@example.ac.kr`

### `api_revoke_tokens`

- ການນຳໃຊ້: ຍົກເລີກ token API ຂອງບັນຊີ (ທັງໝົດ ຫຼື ອັນດຽວດ້ວຍ `--key=`). `--list` ສະແດງສະເພາະລາຍການ token (ຄຳນຳໜ້າ key, ເວລາອອກ ແລະ ໝົດອາຍຸ).
- ອາກິວເມັນ/ຕົວເລືອກ: `{email}`, `--key=` (ຄຳນຳໜ້າ key), `--list`, `--reason=`, `--actor=`.
- ການກວດສອບ: ບັນທຶກ (`api.token_revoked`: ຄຳນຳໜ້າ key ທີ່ຖືກຍົກເລີກ)
- ລະຫັດອອກ: 1 ເມື່ອບໍ່ຮູ້ຈັກບັນຊີ ຫຼື ບໍ່ມີ token ຂອງ `--key`.
- ເວລາແລ່ນ: ເມື່ອສິ້ນສຸດການເຊື່ອມຕໍ່, ສົງໄສວ່າ token ຮົ່ວໄຫຼ ຫຼື ປ່ຽນຜູ້ຮັບຜິດຊອບ.

### `audit_verify_chain`

- ການນຳໃຊ້: ຄຳນວນແຮດຊ໌ເນື້ອຫາ ແລະ ຕ່ອງໂສ້ຂອງແຖວບັນທຶກການກວດສອບຄືນໃໝ່ເພື່ອຊອກຫາການປອມແປງ, ການລຶບ ແລະ ການປ່ຽນລຳດັບ. ສະແດງຈຳນວນທີ່ກວດ, ຈຳນວນທີ່ປະທັບຕາ, ຈຳນວນທີ່ບໍ່ກົງກັນ ແລະ id ທຳອິດທີ່ບໍ່ກົງກັນຕໍ່ຕາຕະລາງ.
- ຕົວເລືອກ: `--table=`.
- ການກວດສອບ: ບໍ່ມີ (ອ່ານ)
- ລະຫັດອອກ: 2 ຖ້າມີຄວາມບໍ່ກົງກັນ.

### `audit_prune`

- ການນຳໃຊ້: ລຶບແຖວບັນທຶກການກວດສອບທີ່ **ປະທັບຕາແລ້ວ** ແລະ ເກີນໄລຍະເກັບຮັກສາ. ແລ່ນດ້ວຍການເຊື່ອມຕໍ່ຂອງເຈົ້າຂອງ schema ໃນທຸລະກຳທີ່ເປີດ `app.audit_maintenance = on`. ແຖວທີ່ຍັງບໍ່ປະທັບຕາຈະຖືກເກັບໄວ້ (ແລ່ນ `audit_seal` ກ່ອນ). ທຸກຄັ້ງທີ່ລຶບຈະບັນທຶກເຫດການຄວາມປອດໄພ `audit.pruned` (ຕາຕະລາງ, ວັນທີອ້າງອີງ, ຈຳນວນທີ່ລຶບ, ຂອບເຂດ id, `chain_hash` ຂອງແຖວຂອບ).
- ຕົວເລືອກ: `--before=YYYY-MM-DD` (ຈຳເປັນ, ກ່ອນ 0 ໂມງຂອງວັນນັ້ນ), `--table=`, `--dry-run` (ສະເພາະຈຳນວນ), `--actor=`.
- ການກວດສອບ: ບັນທຶກ (ວັນທີອ້າງອີງ, ຈຳນວນທີ່ລຶບ ແລະ ຂອບເຂດ id ຕໍ່ຕາຕະລາງ)
- ເວລາແລ່ນ: ຕາມນະໂຍບາຍເກັບຮັກສາ ຫຼັງສຳຮອງຂໍ້ມູນ.
- ຕົວຢ່າງ

  ```bash
  uv run manage.py audit_prune --before=2023-03-01 --dry-run
  uv run manage.py audit_prune --before=2023-03-01 --table=record_changes --actor=ops@example.edu.la
  ```

- ການກວດສອບ: ບັນທຶກ (ຈຳນວນແຖວ, ຈຳນວນໄດເຣັກທໍຣີ)

## ກະແຈເຂົ້າລະຫັດຂໍ້ມູນສ່ວນບຸກຄົນ (Phase 0)

### `pii_generate_key`

- ການນຳໃຊ້: ສະແດງກະແຈໃໝ່ (32 ໄບຕ໌, `base64:...`) ສຳລັບໃສ່ໃນ `PII_ENCRYPTION_KEY`, `PII_HASH_KEY`. ບໍ່ບັນທຶກຫຍັງ.
- ການກວດສອບ: ບໍ່ບັນທຶກ
- ຂໍ້ຄວນລະວັງ: ຖ້າປ່ຽນ `PII_HASH_KEY` ແຮດຊ໌ຄົ້ນຫາທັງໝົດ (`*_hash`) ຈະໃຊ້ບໍ່ໄດ້. ປ່ຽນສະເພາະກະແຈເຂົ້າລະຫັດ: ຍ້າຍກະແຈເກົ່າໄປ `PII_PREVIOUS_KEYS` ແລ້ວແລ່ນ `pii_reencrypt`.
- ຕົວຢ່າງ

  ```bash
  uv run manage.py pii_generate_key
  ```

### `pii_reencrypt`

- ການນຳໃຊ້: ຫຼັງປ່ຽນກະແຈ ເຂົ້າລະຫັດຂໍ້ມູນສ່ວນບຸກຄົນທີ່ເຂົ້າລະຫັດດ້ວຍກະແຈເກົ່າຄືນໃໝ່ດ້ວຍກະແຈປັດຈຸບັນ. ແບ່ງບັນທຶກເປັນສ່ວນ ແລະ ແລ່ນເປັນກຸ່ມວຽກ Celery. ບັນທຶກທີ່ໃຊ້ກະແຈປັດຈຸບັນແລ້ວຈະບໍ່ຖືກແຕະຕ້ອງ.
- ອາກິວເມັນ: ໂມເດລທີ່ມີຊ່ອງຂໍ້ມູນສ່ວນບຸກຄົນທີ່ເຂົ້າລະຫັດ (`app_label.Model`, ເຊັ່ນ `person.Person`).
- ຕົວເລືອກ: `--chunk=500` (ຈຳນວນບັນທຶກຕໍ່ວຽກ), `--dry-run` (ນັບສະເພາະຈຳນວນບັນທຶກທີ່ໃຊ້ກະແຈເກົ່າ), `--force` (ບໍ່ຖາມຢືນຢັນ), `--actor=`.
- ການກວດສອບ: ບັນທຶກ (ID batch, ຈຳນວນວຽກ / ຈຳນວນຂອງການເບິ່ງລ່ວງໜ້າ)
- ການກວດ: ເບິ່ງຄວາມຄືບໜ້າຂອງວຽກໃນ Flower. ຫຼັງສຳເລັດ ຖ້າຜົນ `--dry-run` ເປັນ 0 ໃຫ້ເອົາກະແຈເກົ່າອອກຈາກ `PII_PREVIOUS_KEYS`.
- ຕົວຢ່າງ

  ```bash
  uv run manage.py pii_reencrypt person.Person --dry-run
  uv run manage.py pii_reencrypt person.Person --force --actor=ops@example.edu.la
  ```

## ຫຼາຍພາສາ (Phase 0)

### `i18n_missing`

- ຈຸດປະສົງ: ດຶງຂໍ້ຄວາມທີ່ຕ້ອງແປອອກຈາກຊອດໂຄດແບບດຽວກັບ `makemessages` (ບໍ່ຂຽນໄຟລ໌), ປຽບທຽບກັບທຸກແຄັດຕາລັອກ (`locale/` ສ່ວນກາງ ແລະ `locale/` ຂອງແຕ່ລະແອັບ) ແລະ ສະແດງລາຍການທີ່ຂາດ (ບໍ່ມີໃນແຄັດຕາລັອກ, `msgstr` ຫວ່າງ, fuzzy, ຕົວແທນບໍ່ກົງກັນ) ແລະ ລາຍການທີ່ບໍ່ໃຊ້ແລ້ວ (obsolete) ຕາມແຕ່ລະພາສາ.
- ອາກິວເມັນ/ຕົວເລືອກ: `[locale]` (ສະເພາະພາສາດຽວ, ເຊັ່ນ `ko`, `zh-hans`, `lo`), `--strict` (ຖ້າມີລາຍການຂາດ ລະຫັດອອກແມ່ນ 2; ໃຊ້ໃນ CI), `--no-extract` (ກວດສະເພາະແຄັດຕາລັອກ, ບໍ່ສະແກນຊອດໂຄດ).
- ການກວດສອບ (audit): ບໍ່ບັນທຶກ
- ຕ້ອງການ: GNU gettext (`xgettext`, `msguniq`).
- ຕົວຢ່າງ

  ```bash
  uv run manage.py i18n_missing --strict
  uv run manage.py i18n_missing lo
  ```

### `i18n_export`

- ຈຸດປະສົງ: ສ້າງຕາຕະລາງໃຫ້ນັກແປ (`.xlsx` ຫຼື `.csv`, ເລືອກຕາມນາມສະກຸນໄຟລ໌). ຖັນ: `catalog` (ບ່ອນຢູ່ຂອງແຄັດຕາລັອກ), `context`, `source` (msgid ພາສາອັງກິດ), `source_plural`, `translation`, `note` (ຄີເດີມ).
- ອາກິວເມັນ/ຕົວເລືອກ: `{locale} {path}`, `--missing` (ສະເພາະຂໍ້ຄວາມທີ່ຍັງບໍ່ໄດ້ແປ).
- ການກວດສອບ (audit): ບໍ່ບັນທຶກ
- ຕົວຢ່າງ: `uv run manage.py i18n_export ko storage/ko.xlsx --missing`

### `i18n_import`

- ຈຸດປະສົງ: ນຳຕາຕະລາງທີ່ນັກແປຕື່ມແລ້ວກັບເຂົ້າແຄັດຕາລັອກ (`.po`) ແລະ ຄອມໄພລ໌ (`.mo`). ນຳເຂົ້າສະເພາະຂໍ້ຄວາມທີ່ມີໃນແຄັດຕາລັອກ (ແຄັດຕາລັອກ, ບໍລິບົດ ແລະ ຂໍ້ຄວາມອັງກິດກົງກັນ) ແລະ ຂ້າມຄຳແປທີ່ຫວ່າງ.
- ອາກິວເມັນ/ຕົວເລືອກ: `{locale} {path}`, `--dry-run` (ສະແດງສະເພາະລາຍການທີ່ຈະຂຽນ), `--actor=`.
- ການກວດສອບ (audit): ບັນທຶກ (ພາສາ, ຈຳນວນຄຳແປ)
- ໝາຍເຫດ: ແຄັດຕາລັອກຖືກຈັດການໃນ repository. ຫຼັງຈາກນຳເຂົ້າແລ້ວໃຫ້ commit ການປ່ຽນແປງຂອງ `.po`.

### `i18n_makemessages`

- ຈຸດປະສົງ: ແລ່ນ `makemessages` ຈາກຮາກຂອງ repository ເພື່ອໃຫ້ທຸກແຄັດຕາລັອກກົງກັບຊອດໂຄດ (ko, zh_Hans, lo). ຂໍ້ຄວາມຈະໄປທີ່ `locale/` ຂອງແອັບ ຖ້າແອັບມີ, ຖ້າບໍ່ມີຈະໄປທີ່ `locale/` ສ່ວນກາງ. ຂ້າມ `.venv`, `tests`, `docs` ແລະ ອື່ນໆ.
- ຕົວເລືອກ: ຄືກັບ Django `makemessages` (`-l`, `--no-obsolete` ...).
- ການກວດສອບ (audit): ບໍ່ບັນທຶກ
- ຕົວຢ່າງ: `uv run manage.py i18n_makemessages`

### `naming_check`

- ຈຸດປະສົງ: ກວດ schema ຂອງຖານຂໍ້ມູນ ແລະ source ຕາມ [ກົດການຕັ້ງຊື່](../../../development/naming.md). ສິ່ງທີ່ກວດຄື ຊື່ຕາຕະລາງ ແລະ ຖັນໃນ catalog ຂອງຖານຂໍ້ມູນຕົວຈິງ (schema `public`, `audit`, `reporting`), ຊື່ໄຟລ໌ migration ຂອງແອັບ Ninefruits, ຊື່ຄຳສັ່ງບໍລິຫານ (`context_action`) ແລະ msgid ແລະ msgctxt ຂອງ catalog ການແປ (`.po`).
- ກົດ: snake_case, ຄຳຕໍ່ທ້າຍທີ່ຫ້າມ (`_old`, `_new`, `_backup`, `_tmp`, ວັນທີ, ຕົວເລກ), ຊື່ທີ່ມີລະຫັດພາສາ, ຖັນເວລາທີ່ບໍ່ມີເຂດເວລາ (`timestamp without time zone`), ຊື່ຖັນ boolean (`is_`, `has_`, `can_` ຫຼື ຮູບຄຳກິລິຍາ), ຊື່ຖັນວັນທີ (`_date`), msgid ທີ່ມີຮູບແບບເປັນກະແຈຄວາມໝາຍ (`registration.errors.x`). ຍົກເວັ້ນຕາຕະລາງທີ່ Django ແລະ package ກຳນົດ (`django_*`, allauth, Celery beat, `settings`, `cache`, `jobs`, `media` ແລະ ອື່ນໆ).
- ຕົວເລືອກ: `--database=` (ການເຊື່ອມຕໍ່ຖານຂໍ້ມູນທີ່ຈະກວດ, ຄ່າເລີ່ມຕົ້ນ `default`), `--skip-database` (ກວດສະເພາະໄຟລ໌ ໂດຍບໍ່ໃຊ້ຖານຂໍ້ມູນ).
- ການກວດສອບ: ບໍ່ບັນທຶກ
- ລະຫັດອອກ: 2 ເມື່ອພົບບັນຫາ.
- ຕົວຢ່າງ

  ```bash
  uv run manage.py naming_check
  ```
