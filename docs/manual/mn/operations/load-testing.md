# Ачааллын тест (хичээл сонголтын оргил үе)

- Зориулалт: МТ-ийн ашиглалтын ажилтнууд
- Холбогдох: [байршуулалтын хяналтын хуудас](deployment-checklist.md), [суулгалт](installation.md), [командууд](commands.md)

Locust нь олон оюутан нэг бүлгүүд рүү нэгэн зэрэг шавдаг хичээл сонголтын эхний өглөөг дуурайна. Скрипт нь `loadtest/registration.py` (анхны системийн k6 `tests/load/registration.js`), ажиллуулах туслах нь `loadtest/run.sh`, хэт бүртгэлийн шалгалт нь `loadtest/seat_check.sql`.

[Гарын авлагын агуулга](../README.md)

## Бэлтгэл

1. Зөвхөн ачааллын тестэд зориулсан өгөгдлийн сан үүсгэнэ (production-ий өгөгдлийн санг хэзээ ч биш). Роль болон өгөгдлийн санг [суулгалт](installation.md)-ын 2-р хэсгийн адил үүсгэнэ; дараа нь суулгаж, том демог ачаална. Оюутны бүртгэлийн жагсаалтыг хувийн хадгалалт дахь `load-accounts.csv`-д (`PRIVATE_MEDIA_ROOT`, анхдагч `storage/private`) бичнэ.

   ```bash
   export DB_DATABASE=nf_load
   uv run manage.py setup_install --profile=korean-university --grade-scale=4.5 --force < /dev/null
   uv run manage.py setup_demo --size=large --seed=42 --student-accounts --force
   ```

2. Хичээл сонголтын хугацаа нээлттэй байх ёстой. Демо дараагийн улирлын хичээл сонголтын хугацааг курсээр үүсгэнэ (4-р курс аль хэдийн нээлттэй, 3-р курс хоёр хоногийн дараа, 1, 2-р курс гурван хоногийн дараа). Бүх курсээр хэмжихийн тулд улирлын **Засах** хуудасны **Үйл ажиллагааны хугацаа** хэсэгт бусад хичээл сонголтын хугацааны эхлэлийг өнгөрсөн рүү шилжүүлнэ ([админы гарын авлага, 10-р бүлэг](../admin/10-terms.md)), эсвэл тестийн өгөгдлийн санд superuser-ээр дараахыг ажиллуулна:

   ```sql
   UPDATE term_windows SET opens_at = now() - interval '1 hour'
    WHERE window_type = 'registration' AND opens_at > now() AND closes_at > now();
   ```

3. Redis болон Celery worker ажиллаж байх ёстой. Суудлыг өгөгдлийн санд шууд шийддэг ч хүлээлгийн жагсаалтын дэвшүүлэлт, LMS синхрончлол болон мэдэгдэл дарааллаар дамжина. Redis-ийг өөр ажилтай хуваалцдаг бол өөр өгөгдлийн сангийн дугаар ашиглана, жишээ нь `REDIS_URL=redis://127.0.0.1:6379/7`.

## Ажиллуулах

`loadtest/run.sh` нь gunicorn (`config/gunicorn.py`) болон Celery worker-ийг эхлүүлж, Locust-ийг headless горимд ажиллуулаад суудлын шалгалтыг хийж, бүгдийг зогсооно.

```bash
export DB_DATABASE=nf_load DB_POOL=true DB_POOL_MIN=1 DB_POOL_MAX=2 DB_PREPARE_THRESHOLD=2
WORKERS=9 USERS=100 DURATION=1m loadtest/run.sh storage/loadtest/w9-u100
```

Гараар ажиллуулахдаа серверийг `TRUSTED_PROXY_COUNT=1`-тэйгээр эхлүүлж Locust-ийг ажиллуулна:

```bash
TRUSTED_PROXY_COUNT=1 DJANGO_DEBUG=false GUNICORN_WORKERS=9 uv run gunicorn config.wsgi -c config/gunicorn.py
uv run --group loadtest locust -f loadtest/registration.py --headless -u 100 -r 20 -t 1m \
    --host http://127.0.0.1:8000 --csv storage/loadtest/run
psql -h 127.0.0.1 -U postgres -d nf_load -v term=<term id> -f loadtest/seat_check.sql
```

- Хувилбар: нэвтрэх (`/accounts/login/`) → хичээл сонголтын хуудас → хичээл хайх (HTMX `?partial=results`) → сул суудалтай эхний бүлэгт бүртгүүлэх → хасах. Давталт бүр cookie-г цэвэрлэж дараагийн оюутнаар нэвтэрнэ. Дүүрсэн бүлэг болон дүрмийн татгалзлыг хэвийн үр дүн гэж тоолно (`registration outcomes`).
- Бүртгүүлэх, хасах товчнууд HTMX шиг (`HX-Request`) илгээнэ; сервер хичээл сонголтын хуудас руу 302-оор хариулна. `enroll` болон `drop`-ийн хугацаа тэр хуудсыг багтаана (хөтөч `#registration`-ийг солихоос өмнө түүнийг хэрэгтэй).
- Оюутан бүр өөрийн `X-Forwarded-For` хаягийг илгээнэ. Сервер нэг проксины ард (`TRUSTED_PROXY_COUNT=1`) байх үед allauth-ийн хаяг тус бүрийн нэвтрэлтийн хязгаар бодит кампусын адил оюутны хаяг тус бүрээр үйлчилнэ. `ADDRESSES=1` нь бүх оюутныг нэг хаягийн (NAT) ард байгаагаар дуурайна.
- Орчин: `ACCOUNTS` (бүртгэлийн CSV), `SEARCH` (хайх текст, анхдагч `GEN`), `ADDRESSES`, `FIRST_ACCOUNT` (эхний бүртгэл, анхдагчаар санамсаргүй). `run.sh` нь `WORKERS`, `USERS`, `SPAWN_RATE`, `DURATION`, `TERM_ID`, `PORT`-ийг авна.
- `USERS`-ийг 100-аас 200, 500 хүртэл нэмэгдүүлж хуудас тус бүрийн p95 болон алдааны хувийг ажиглана. Босго: хичээл сонголтын хуудас p95 < 800 ms, бүртгүүлэх p95 < 1.5 s, алдаа < 1 %. Босго хангагдахгүй бол Locust exit code 1-ээр дуусна.
- Сервер дээр `pg_stat_activity` дахь холболтын тоо болон түгжээний хүлээлт (`wait_event_type = 'Lock'`), Celery-ийн хуримтлал болон CPU-ийн ачааллыг ажиглана. Ижил сервер дээрх Locust ч CPU ашигладаг тул тоонууд доод хязгаар болно.

## Загварын баталгаа

- Суудлын тоог бүлгийн мөрийн түгжээ (`SeatAllocator.lock`, `SELECT ... FOR NO KEY UPDATE`) болон CHECK хязгаарлалтаар хамгаалдаг тул зэрэг хүсэлтүүд бүлгийг хэзээ ч хэт бүртгэхгүй (`tests/registration/test_concurrent_registration.py`: 16 процесс, 5 суудал). Түгжээ нь зөвхөн ижил бүлгийн суудлын хүсэлтүүдийг бие биенээ хүлээлгэнэ; бүлгийг зөвхөн лавладаг мөрүүдийн (хичээл сонголтын оролдлого, LMS синхрончлолын бүртгэл) гадаад түлхүүрийн шалгалтыг хаахгүй.
- Ажиллуулсны дараа `loadtest/seat_check.sql`-ийн дөрвөн асуулга мөр буцаах ёсгүй (суудлын тооноос хэтэрсэн, суудлын тоолуурын зөрүү, суудлын бүлэг хэтэрсэн, бүлэгт давхар бүртгэл).
- Хичээл сонголтын хуудасны асуулгын тоо бүртгэл, хүлээлгийн жагсаалтын бичлэг эсвэл хайлтын үр дүнгээр өсөхгүй (`tests/registration/test_portal_query_count.py`).

## Хаяг тус бүрийн нэвтрэлтийн хязгаар ба прокси

Бүртгэл тус бүрийн амжилтгүй оролдлогын хязгаараас (минутад 5) гадна allauth анхны системд байгаагүй **хаяг тус бүрийн нэвтрэлтийн хязгаар**-ыг (`LOGIN_RATE_LIMIT_PER_IP`, анхдагч `30/m/ip`) хэрэглэнэ. Аппликейшны харах хаягийг `TRUSTED_PROXY_COUNT` (`ninefruits.core.http.client_ip`) тогтооно.

- Nginx-ийн ард `TRUSTED_PROXY_COUNT=0` (анхдагч) бол хүсэлт бүр Nginx-ийн хаягтай байна. Нэг NAT хаягаар гардаг кампус ч мөн адил тохиолдол.
- Үүнийг дуурайсан ажиллуулалт (`ADDRESSES=1`, 100 VU, 1 минут): 4,876 нэвтрэлтээс **зөвхөн 30 нь амжилттай** болж, 4,846 нь 429-өөр татгалзагдсан (49 % алдаа). Тэр минутад зөвхөн 20 бүртгэл хийгдсэн. Ижил нөхцөлд оюутан тус бүр нэг хаягтай үед ямар ч нэвтрэлт татгалзагдаагүй.
- Production-ий тохиргоо: `TRUSTED_PROXY_COUNT`-ийг проксины тоогоор тохируулна (нэг Nginx бол `1`). Ихэнх оюутан нэг NAT хаягийг хуваалцдаг бол `LOGIN_RATE_LIMIT_PER_IP`-ийг оргил үеийн нэвтрэлтийн хурд хүртэл нэмэгдүүлнэ. Жишээ: 10 минутад нэвтрэх 2,000 оюутан нь нэг хаягаас минутад 200 тул `300/m/ip`. Хоосон утга хаяг тус бүрийн хязгаарыг арилгана (анхны системтэй адил; бүртгэл тус бүрийн амжилтгүй оролдлогын хязгаар хэвээр).

## Серверийн тохиргооны шийдвэрүүд

- **gunicorn sync worker** (`config/gunicorn.py`). `GUNICORN_WORKERS` анхдагчаар CPU цөм × 2 + 1. Дамжуулах чадвар CPU-гаар хязгаарлагдсан: 4 цөм дээр 4, 9, 16 worker ижил дамжуулах чадвар өгсөн (секундэд 23-аас 26 хүсэлт). Илүү олон worker зөвхөн өгөгдлийн сангийн холболт (12 → 36) болон түгжээний хүлээлтийг (оргил 1 → 12) нэмсэн. Цөм × 2 + 1-ээс дээш гаргахгүй; илүү олон аппликейшн сервер нэмж өргөжүүлнэ.
- **Холболтын сан ба prepared statement**: `DB_POOL=true`, `DB_POOL_MIN=1`, `DB_POOL_MAX=2`, `DB_PREPARE_THRESHOLD=2`. Мөрийн түвшний хамгаалалтын (RLS) бодлогуудаас болж асуулгын төлөвлөлт хуудасны өгөгдлийн сангийн хугацааны ихэнхийг эзэлж байв (хичээл сонголтын хуудасны 31 асуулга: төлөвлөлт 51 ms, гүйцэтгэл 19 ms). Холболтыг дахин ашиглаж, серверийн талын binding-тэй statement бэлтгэснээр асуулга бүрийг холболт тус бүрт нэг удаа төлөвлөнө. Ижил 4 цөм дээр дамжуулах чадвар секундэд 16.8-аас 25.6 хүсэлт болж, нэг хэрэглэгчийн хичээл сонголтын хуудасны медиан 160 ms-ээс 97 ms болсон. Сервер worker × `DB_POOL_MAX` + Celery concurrency холболт шаардах бөгөөд энэ нь PostgreSQL-ийн `max_connections`-аас бага байх ёстой. Transaction горимтой PgBouncer-ийн ард prepared statement ашиглах боломжгүй: `DB_PREPARE_THRESHOLD=0` хэвээр үлдээнэ. Бүх тестийн багц (1,066 тест) эдгээр тохиргоотой амжилттай өнгөрнө.
- **ASGI (анхны системийн Octane-ийн шийдвэр)**: хэрэглээгүй. Хуудас бүр синхрон view бөгөөд ASGI түүнийг ашиггүйгээр thread-д ажиллуулах байсан, дамжуулах чадвар CPU цөмийг дагана. Django хүсэлт бүрт аппликейшныг дахин ачаалдаггүй (PHP-FPM-ээс ялгаатай) тул Octane-ийн өгдөг ашиг аль хэдийн бий; байнгын холболтын ашиг дээрх сан болон prepared statement-ээс гарна.
- Нэвтрэлт Argon2 хэшийн шалгалтаас болж хүсэлт тутамд их CPU зарцуулна (нэг хэрэглэгчтэй үед ойролцоогоор 140 ms). Оргил үед нэвтрэлт хуримтлагдахад энэ зардал дамжуулах чадварыг хамгийн түрүүнд идэнэ.

Хэрхэн унших

- Ямар ч ажиллуулалтад (нэг хаягийнхаас бусад) HTTP алдаа гараагүй, хэт бүртгэл гараагүй (`seat_check.sql` мөр буцаагаагүй). Татгалзлууд нь дүүрсэн бүлэг (`capacity`) болон давхар хичээл (`duplicate_course`, өмнөх ажиллуулалтын төгсгөлд тасарсан давталтуудын үлдээсэн бүртгэл): хэвийн үйлдэл.
- 100 VU дээрх хэдэн секундын саатал нь хүсэлтийн дараалал. Нэг хэрэглэгчтэй үед сервер хуудсыг ойролцоогоор 100 ms-д, бүртгэлийг (POST ба буцаасан хуудас) ойролцоогоор 290 ms-д боловсруулна; 4 цөмөө Locust, PostgreSQL болон бусад ажилтай хуваалцсан энэ машин секундэд 25-аас 30 хүсэлтэд хүрч зогсоно. Энэ машин дээр 100 VU-д босго (хуудас p95 < 800 ms, бүртгүүлэх p95 < 1.5 s) хангагдахгүй.
- Түгжээний хүлээлт зөвхөн ижил бүлгийн суудлын түгжээнээс гарсан бөгөөд богино байсан (агшин зуурын оргил 1-ээс 12, worker олон байх тусам их). Өгөгдлийн сангийн холболт worker × 2 буюу түүнээс доош байсан.
- Хичээл сонголтын оргилыг "10 минутад 2,000 оюутан тус бүр 6 хүсэлт" гэж үзвэл секундэд 20 хүсэлт болно. Энэ машин (сан + prepared statement) 25-аас 30-д хүрсэн тул тусгай 8 цөмт аппликейшн серверт нөөц бий. Ашиглалтад оруулахаас өмнө: production-тэй ижил тохируулсан staging орчинд (тусгай аппликейшн сервер, Nginx, тусдаа өгөгдлийн сангийн сервер, өөр машин дээрх Locust) ижил скриптийг 200 ба 500 VU-д ажиллуулж босгыг баталгаажуулна.
- Анхны систем (Laravel, Sail хөгжүүлэлтийн контейнер, суурин сервер) 100 VU-д 4 worker-тэй 24.7 req/s, 16-тай 34.5 req/s гаргасан. Машинууд өөр тул тоонуудыг шууд харьцуулах боломжгүй.
