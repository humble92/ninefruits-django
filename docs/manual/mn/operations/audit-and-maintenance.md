# Аудитын бүрэн бүтэн байдал ба тогтмол засвар үйлчилгээ

- Зориулалт: МТ-ийн ашиглалтын ажилтнууд, мэдээллийн аюулгүй байдал хариуцсан ажилтнууд
- Холбогдох: [админы гарын авлагын 4-р бүлэг, аудит](../admin/04-audit.md), [командын лавлах](commands.md), [нөөцлөлт ба сэргээлт](backup-restore.md)

## Аудитын хэш гинж

Аудитын хүснэгтүүд (өгөгдлийн өөрчлөлтийн `audit.record_changes`, бизнесийн үйлдлийн `audit.activity_log`, аюулгүй байдлын үйл явдлын `audit.security_events`) зөвхөн нэмэх боломжтой (trigger-ээр хангагдана). Үүн дээр нэмж хуурамчаар өөрчилсөн байдлыг **ил гаргах** механизм бий.

- Мөр бүрийг оруулах үед түүний агуулгын SHA-256 (`row_hash`) тооцогдоно.
- `audit_seal` (төлөвлөгдсөн ажил `audit.seal`, өдөр бүр 03:30-д) шинэ мөрүүдийг ID-ийн дарааллаар гинжинд холбоно: `chain_hash = SHA-256(previous chain_hash || row_hash)`. Энэ нь DB-ийн `audit.seal()` функцийг схемийн эзэмшигчийн холболтоор (`migrator`) дуудна.
- `audit_verify_chain` мөр бүрийн агуулгын хэш болон гинжийг дахин тооцоолно. Хүснэгт тус бүрээр шалгасан мөр, битүүмжилсэн мөр, зөрүү болон эхний зөрүүтэй id-г хэвлэнэ; агуулга нь өөрчлөгдсөн мөрийг "row mismatch", алга болсон эсвэл дараалал нь өөрчлөгдсөн мөрийг "chain mismatch" гэж мэдээлж, команд exit code 2 буцаана.

```bash
uv run manage.py audit_seal
uv run manage.py audit_verify_chain
uv run manage.py audit_verify_chain --table=security_events
```

Анхаарах зүйлс

- Битүүмжлэгдэхээс өмнө (тухайн өдөртөө) өөрчлөгдсөн мөрийг гинж илрүүлж чадахгүй. Тиймээс битүүмжлэлийг өдөр бүр, шалгалтыг нөөцлөхийн өмнө болон аюулгүй байдлын хяналтын үеэр хийнэ.
- Цэвэрлэлт (`audit_prune`) хамгийн хуучин мөрүүдийг устгахад үлдсэн эхний мөрийн холбоосыг шалгахгүй (цэвэрлэсэн хүрээ нь цэвэрлэх командын аудитын бичлэгт хадгалагдана).
- Зөвхөн DB-ийн админ (схемийн эзэмшигч `app_migrator`) `app.audit_maintenance = on` тохируулж чадна. Аппликейшны роль (`app_runtime`) аудитын хүснэгтүүдэд UPDATE эсвэл DELETE эрхгүй.

## Хадгалах хугацаа ба цэвэрлэлт

1. Хадгалах хугацааг тогтооно (жишээ нь өгөгдлийн өөрчлөлт 3 жил, бизнесийн үйлдэл 5 жил, аюулгүй байдлын үйл явдал 1 жил).
2. Цэвэрлэхийн өмнө нөөцөлж ([нөөцлөлт ба сэргээлт](backup-restore.md)), `audit_verify_chain`-ээр гинж бүрэн бүтэн эсэхийг шалгана.
3. `uv run manage.py audit_prune --before=YYYY-MM-DD --table=record_changes --dry-run`-аар тоог шалгаад `--dry-run`-гүйгээр ажиллуулна (`--actor=`-ээр операторын бүртгэлийг тэмдэглэнэ). Битүүмжлэгдээгүй мөрүүд хэзээ ч устахгүй тул эхлээд `audit_seal` ажиллуулна.
4. Цэвэрлэсний дараа `audit_verify_chain`-ийг дахин ажиллуулна.

Цэвэрлэлт өөрөө бүртгэгддэг: ажиллах бүрд үйлдлийн бүртгэлд (log `command`) хязгаар огноо, сонголтууд, гүйцэтгэгч болон үйлдлийн системийн хэрэглэгч, мөн хүснэгт тус бүрээр **устгасан мөрийн тоо, устгасан ID-ийн хүрээ, хил дээрх chain_hash** бичигдэнэ; бодит устгалт мөн аюулгүй байдлын үйл явдал `audit.pruned` болж бүртгэгдэнэ (**Аудит > Аюулгүй байдлын үйл явдлууд**). Энэ бичлэгийн мөр өөрөө дараагийн битүүмжлэлээр гинжинд холбогдоно. Энэ хил нь яг `audit_verify_chain` үлдсэн эхний мөрийн холбоосыг шалгадаггүй шалтгаан юм; хилийн хэшийг цэвэрлэлтийн бичлэгтэй харьцуулснаар устгагдсан хүрээ нь бүртгэгдсэн цэвэрлэлттэй таарч байгааг баталж болно.

## Файл цэвэрлэх

`uv run manage.py media_prune_orphans --dry-run` нь эзэмшигч нь байхаа больсон медиа мөрүүд болон мөргүй директоруудыг (`PRIVATE_MEDIA_ROOT/<media id>/`) жагсаана; `--dry-run`-гүйгээр тэдгээрийг устгана. Хувь хүний зураг, өргөдлийн баримт, тодорхойлолтын PDF, шалгалтын нотлох баримтыг хамарна. Сар бүр эсвэл их хэмжээний устгалтын дараа ажиллуулна.

## Эрүүл мэндийн шалгалт

| Шалгалт | Арга | Амжилтгүй үед |
|---|---|---|
| Үйлчилгээний төлөв | `GET /api/v1/health/` (нэвтрэлтгүй, ачаалал тэнцвэржүүлэгч болон мониторингт) | DB эсвэл кэш хариу өгөхгүй бол `unavailable` (503), төлөвлөгчийн heartbeat 5 минутаас хуучин бол `degraded` (200), бусад үед `ok`. `Удирдлагын самбарыг нээх` эрхтэйгээр нэвтэрсэн бол шалгалт тус бүрийг (`database`, `cache`, `scheduler`) мөн харуулна |
| Бүрэн шалгалт | `uv run manage.py system_health_check [--json]` | 12 шалгалт: түлхүүр, DB-ийн роль, RLS, миграц, эрхийн каталог, Redis, Celery worker, Gotenberg, хадгалалт, beat heartbeat. Аль нэг нь амжилтгүй бол exit code 2 |
| Production тохиргоо | `uv run manage.py check --deploy` | `DEBUG`, HTTPS чиглүүлэлт, HSTS, хамгаалалттай cookie, нууц түлхүүрийн тухай анхааруулга |
| Миграц | `uv run manage.py migrate --check` | Хэрэгжээгүй миграц байвал exit code 1 |
| Эрхийн каталог | `uv run manage.py security_sync_permissions` | Кодын эрхийн жагсаалтыг DB-д тусгана (дахин ажиллуулахад аюулгүй) |
| PDF үйлчилгээ | `uv run manage.py pdf_sample` | Gotenberg-ийн холболт, фонт |
| Орчуулга | `uv run manage.py i18n_missing --strict` | Орчуулга дутуу бол exit code 2 |
| Аудитын гинж | `uv run manage.py audit_verify_chain` | Зөрүү байвал exit code 2 |
| Дараалал | Flower, `uv run celery -A config inspect ping` | Worker хариу өгөхгүй |

Мониторингийг `/api/v1/health/`-ийн HTTP төлөв болон `status` утгатай холбоно; бусдыг байршуулах үед болон [тогтмол шалгалт](deployment-checklist.md#тогтмол-шалгалт)-д ажиллуулна.
