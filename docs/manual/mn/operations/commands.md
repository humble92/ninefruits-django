# Удирдлагын командын лавлах

- Зориулалт: МТ-ийн ашиглалтын ажилтнууд
- Хамрах хүрээ: энэ репозиторийн Ninefruits аппуудын бүртгэсэн бүх команд (`ninefruits/*/management/commands/`) болон ашиглалтад хэрэглэгддэг Django-гийн суурин командууд. Команд нэмэхэд энэ баримтад (бүх хэлээр) `### \`command\`` бичлэг мөн нэмэх ёстой, эс бөгөөс CI амжилтгүй болно (`tests/tooling/test_command_documentation.py`).

## Нийтлэг дүрэм

Бүх команд `uv run manage.py {command}` хэлбэрээр ажиллана. Docker хөгжүүлэлтийн орчинд `docker compose exec app uv run manage.py {command}`.

| Зүйл | Дүрэм |
|---|---|
| Нэр | Анхны `{context}:{action}` нь `{context}_{action}` болно (Django-гийн командын нэрэнд `:` орж болохгүй). Жишээ: `term:close` → `term_close` |
| Аудитын бичлэг | Өгөгдөл өөрчилдөг командууд (доор "Аудит: бүртгэнэ") ажиллах бүрдээ команд, аргумент, сонголт, үйлдлийн системийн хэрэглэгч, exit code болон үр дүнг үйлдлийн бүртгэлд (log `command`) бичнэ. Удирдлагын самбарын **Аудит > Үйлдлийн бүртгэл** хэсэгт шалгана |
| Ажиллуулалтын ID | Ажиллуулалт бүр хүсэлтийн ID-ийн оронд `cmd-`-ээр эхэлсэн ID авна. Үйлдлийн бүртгэл, тухайн ажиллуулалтын хийсэн өгөгдлийн өөрчлөлтүүд болон түүний илгээсэн Celery ажлууд бүгд ижил ID-тай тул "энэ өөрчлөлтийг аль команд хийсэн бэ" гэдэгт ID-аар хариулна. `--actor` нь ашиглалтын ажилтны оруулсан утга тул өгөгдлийн өөрчлөлтийн хэрэглэгчийн баганад оруулахгүй (бодит гүйцэтгэгч нь үйлдлийн системийн хэрэглэгч) |
| `--actor=<email>` | Аудиттай бүх командад нийтлэг. Хариуцсан админы бүртгэлийг тэмдэглэнэ. Үл мэдэгдэх и-мэйл бол ажиллуулалт зогсоно |
| `--dry-run` | Юуг ч өөрчлөхгүйгээр үр дүнг хэвлэнэ. Буцаахад хэцүү үйлдлүүдэд байдаг |
| `--force` | Баталгаажуулах асуултгүйгээр ажиллана (төлөвлөгдсөн ажил болон байршуулалтын скриптэд) |
| `--reason=` | Шалтгаан шаарддаг командуудад байдаг |
| Exit code | 0 амжилттай, 1 амжилтгүй эсвэл цуцлагдсан, 2 шалгах команд асуудал илрүүлсэн |
| DB контекст | Команд ажиллах үед DB сессийн гүйцэтгэгч `system:command:{command}` гэж тохируулагдаж, өгөгдлийн өөрчлөлтөд (trigger) харагдана |

## Django-гийн суурин командууд

### `migrate`

- Зориулалт: өгөгдлийн сангийн миграцыг хэрэгжүүлнэ. Django-гийн командын Ninefruits бүрхүүл: `--database`-гүй бол схемийн эзэмшигчийн холболтыг (`migrator`, роль `app_migrator`) ашиглана. Аппликейшны холболт (`app_runtime`) DDL эрхгүй. `showmigrations` болон `sqlmigrate` мөн анхдагчаар `migrator` холболтыг ашиглана.
- Хэзээ: анхны суулгалт болон байршуулалт бүрд (`setup_install` ч мөн ажиллуулна).
- Сонголтууд: Django-гийн `migrate`-тэй ижил (`app_label`, `migration_name`, `--plan`, `--check`, `--database`).
- Аудит: бүртгэхгүй (схемийн өөрчлөлт миграцын түүх `django_migrations`-д хадгалагдана)
- Жишээ

  ```bash
  uv run manage.py migrate
  uv run manage.py migrate --plan
  ```

- Алдаа гарвал: эрхийн алдаа бол [суулгалтын гарын авлага](installation.md) дахь өгөгдлийн сангийн роль бэлтгэлийг (`db/sql/roles/`) шалгана.

### `collectstatic`

- Зориулалт: Vite-ийн бүтээлтийн гаралт (`static/dist/`) болон Django, unfold-ийн статик файлуудыг `STATIC_ROOT` (`staticfiles/`)-д цуглуулна. Веб сервер (Nginx) энэ директорыг түгээнэ.
- Хэзээ: байршуулалт бүрд, `npm ci && npm run build`-ийн дараа.
- Сонголтууд: `--noinput` (асуултгүй), `--clear` (цуглуулахаас өмнө байгаа файлуудыг устгана).
- Аудит: бүртгэхгүй
- Жишээ

  ```bash
  npm ci && npm run build
  uv run manage.py collectstatic --noinput
  ```

### `compilemessages`

- Зориулалт: орчуулгын файлуудыг (`.po`) ажиллах үеийн `.mo` файл болгон хөрвүүлнэ. `.mo` файлуудыг репозиторид хадгалдаггүй тул суулгалт болон байршуулалт бүрд ажиллуулна. Системд `gettext` суусан байх ёстой.
- Хэзээ: байршуулалт бүрд болон орчуулгын файл зассаны дараа.
- Сонголтууд: `--locale=` (жишээ нь `ko`, `zh_Hans`, `lo`), `--ignore=.venv`.
- Аудит: бүртгэхгүй
- Жишээ

  ```bash
  uv run manage.py compilemessages --ignore=.venv
  ```

### `createsuperuser`

- Зориулалт: **ашиглахгүй.** Django-гийн superuser үүрэг, эрхийн каталог болон аудитын мөрийг тойрдог тул энэ команд алдаагаар (exit code 1) дуусч, `security_create_administrator` руу чиглүүлнэ.
- Оронд нь: анхны админыг `security_create_administrator`-оор үүсгэнэ (системийн админы үүргийн оноолт болон аудитын бичлэгийг багтаана).
- Аудит: хамаарахгүй

## Суулгалт ба демо (1-р үе шат)

### `setup_install`

- Зориулалт: шинэ суулгалт ба шинэчлэл. Дараах дарааллаар ажиллана: миграц, зайлшгүй өгөгдөл (үүргийн загвар ба эрхийн синхрончлол, улс, хэл, кодын жагсаалтын төрөл, бүтцийн нэгжийн төрөл), байгууллагын тохиргоо, дүнгийн шкал, суулгалтын профайл болон анхны админ. Дахин ажиллуулахад аюулгүй (байгаа өгөгдөл болон админуудын өөрчилсөн утгууд хадгалагдана).
- Хэзээ: анхны суулгалт болон байршуулалт бүрд.
- Сонголтууд: `--institution-name=`, `--locale=` (анхдагч хэл), `--timezone=` (жишээ нь `Asia/Seoul`), `--profile=` (суулгалтын профайлын түлхүүр, давтаж болно: `korean-university`, `yust-legacy`), `--grade-scale=` (дүнгийн шкал `4.5` эсвэл `4.3`; нэг тохируулсны дараа тогтмол; хоосон бол эхний профайлын шкал), `--admin-email=`, `--admin-name=`, `--force` (асуултгүй; админы нууц үгийг стандарт оролтоос уншина).
- Аудит: бүртгэнэ (хэрэглэсэн профайл, админ үүсгэсэн эсэх)
- Жишээ

  ```bash
  uv run manage.py setup_install
  echo "$ADMIN_PASSWORD" | uv run manage.py setup_install --force --locale=ko --timezone=Asia/Seoul \
      --institution-name="Demo University" --profile=korean-university \
      --admin-email=admin@example.ac.kr --admin-name="Administrator"
  ```

- Гаралтыг унших: алхам бүрд `DONE`. `Administrator exists` нь системийн админы оноолт аль хэдийн байгаа тул үүсгэхийг алгассан гэсэн үг.
- Алдаа гарвал: түлхүүр дутуу гэсэн алдаа бол `DJANGO_SECRET_KEY` болон `pii_generate_key`-ийн утгуудыг орчинд тохируулах ёстой. Миграцын алдаа: өгөгдлийн сангийн ролийг шалгана ([суулгалт](installation.md)). `The grade scale is fixed` нь `--grade-scale` аль хэдийн тогтоосон шкалаас өөр гэсэн үг.

### `setup_demo`

- Зориулалт: зохиомол их сургууль үүсгэнэ (бүтцийн нэгж, хөтөлбөр, байр ба танхим, өнөөдрийн орчим өмнөх, одоогийн, дараагийн улирал ба тэдгээрийн хугацаа, Солонгосын их сургуулийн профайл). Үүрэг тус бүрийн тогтмол демо бүртгэлүүдийг (`registrar@demo.test` гэх мэт, нууц үг `demo-password`) хэвлэнэ. Их хэмжээний өгөгдлийг бөөн оруулгаар үүсгэнэ.
- Хэзээ: хөгжүүлэлт, сургалт, танилцуулгын орчин. **Production-д (`DJANGO_ENV=production`) `--force`-тэй ч ажиллахгүй.**
- Сонголтууд: `--size=tiny|small|medium|large` (ойролцоогоор 20/100/2,000/20,000 оюутан; `tiny` нь тест болон хурдан шалгалтад), `--seed=` (ижил утга, ижил өгөгдөл), `--force` (баталгаажуулалтгүй).
- `--student-accounts`: суралцаж буй оюутан бүрд бүртгэл үүсгэж, хувийн хадгалалтад `load-accounts.csv` (и-мэйл, нууц үг) бичнэ; ачааллын тестэд ([ачааллын тест](load-testing.md)).
- Аудит: бүртгэнэ (хэмжээ, seed, хугацаа)
- Жишээ: `uv run manage.py setup_demo --size=small --seed=42 --force`
- Алдаа гарвал: зайлшгүй өгөгдөлгүй бол демо бүртгэлүүдийг алгасна (тэдгээрийн үүрэг байхгүй); эхлээд `setup_install` ажиллуулна. Ижил өгөгдлийн сан дээр дахин ажиллуулбал байгаа демо өгөгдлийг алгасна.

## Лавлах мэдээлэл ба улирал (1-р үе шат)

### `reference_import`

- Зориулалт: лавлах мэдээллийг CSV-ээс оруулна; удирдлагын самбар дахь **CSV оруулах**-тай ижил дүрэмтэй (мөрийг кодоор нь олж шинэчилнэ, хоосон орчуулгын нүд байгаа утгыг хадгална, амжилтгүй мөрүүдийг тусад нь хадгална).
- Аргументууд: `type` нь `org_units`, `programs`, `buildings`, `rooms`, `lookup_values`, `students` (оюутны бүртгэл), `instructors`, `courses` (хичээлийн хувилбар), `registration_holds` (хичээл сонголтын хориг) / `file` толгой мөртэй UTF-8 CSV.
- Сонголтууд: `--actor=` (заавал; оруулгыг энэ бүртгэлээр тэмдэглэх бөгөөд үр дүн нь тэр бүртгэлийн **CSV оруулгууд** дэлгэцэд харагдана), `--chunk=100` (Celery-ийн нэг ажил дахь мөрийн тоо), `--dry-run` (зөвхөн толгой шалгах ба мөр тоолох).
- Аудит: бүртгэнэ (төрөл, файлын нэр, мөр, оруулгын дугаар, амжилтгүй мөр)
- Баганын формат: [админы гарын авлагын 9-р бүлэг](../admin/09-csv-import.md).
- Exit code: ажлууд шууд ажиллавал (eager worker) үр дүн хэвлэгдэж, амжилтгүй мөр байвал 2. Оруулгыг зөвхөн дараалалд оруулсан бол 0. Үр дүн болон амжилтгүй мөрийн CSV удирдлагын самбарын **Лавлах мэдээлэл > CSV оруулгууд** хэсэгт байна.
- Жишээ: `uv run manage.py reference_import org_units /srv/import/org-units.csv --actor=admin@example.ac.kr --dry-run`

### `term_inspect`

- Зориулалт: тухайн цэгт хичээллэж буй улирлууд болон нээлттэй үйл ажиллагааны хугацаануудыг (төрөл, улирал, хичээллэх хугацаа, нэр, хамрах оюутан, хаагдах цаг) харуулна. Улирал, хугацааны тохиргоог шалгах, эсвэл "хичээл сонголт яагаад нээгдэхгүй байна?" гэх мэт асуултад ашиглана.
- Сонголтууд: `--at=` (анхдагч одоо; жишээ нь `"2027-02-15 09:00"`; цагийн бүсгүй бол серверийн цагийн бүс (UTC) үйлчилнэ; `"2027-02-15 09:00 Asia/Seoul"` эсвэл `2027-02-15T09:00+09:00` нь цагийн бүсийг заана).
- Аудит: бүртгэхгүй (зөвхөн унших)
- Гаралтыг унших: огноог байгууллагын цагийн бүсээр шийднэ. Төлөвлөсөн эсвэл архивласан улирлын хугацаа хэзээ ч нээгдэхгүй. Хаагдах цагийг байгууллагын цагийн бүсээр харуулна.

## Аюулгүй байдал (0, 2-р үе шат)

### `security_create_administrator`

- Зориулалт: системийн админы үүрэгтэй бүртгэл үүсгэнэ. Ихэвчлэн `setup_install` дуудна.
- Сонголтууд: `--email=`, `--name=`, `--password-stdin` (нууц үгийг стандарт оролтоос; интерактив бус ажиллуулахад заавал).
- Аудит: бүртгэнэ (үүсгэсэн хэрэглэгчийн ID)
- Жишээ: `uv run manage.py security_create_administrator --email=admin@example.ac.kr --name="Administrator"`
- Жишээ (интерактив бус): `printf '%s\n' "$ADMIN_PASSWORD" | uv run manage.py security_create_administrator --email=admin@example.ac.kr --name="Administrator" --password-stdin`
- Алдаа гарвал: `system_administrator role is missing` нь эхлээд `setup_install` ажиллуулах ёстой гэсэн үг. Нууц үг дор хаяж 12 тэмдэгт байх ёстой.

### `security_sync_permissions`

- Зориулалт: DB-ийн эрхийн жагсаалтыг код дахь эрхийн каталогтой тааруулна. Шинэ эрхүүдийг үүсгэнэ; каталогт байхгүй эрхүүдийг устгана (бүх үүргээс хасна). Системийн үүргүүд үргэлж бүх эрхийг авна.
- Хэзээ: байршуулсны дараа (`setup_install` зайлшгүй өгөгдлийн алхамдаа үүнийг хийнэ).
- Сонголтууд: `--dry-run` (зөвхөн үүсгэх/устгах жагсаалтыг хэвлэнэ), `--force` (устгалтын баталгаажуулалтыг алгасна).
- Аудит: бүртгэнэ (үүсгэсэн/устгасан эрхүүд)
- Гаралтыг унших: `create` болон `delete` мөрүүд. Устгал байвал баталгаажуулах асуулт гарна.
- Алдаа гарвал: баталгаажуулалтад "үгүй" гэж хариулбал exit code 1-ээр дуусч юу ч өөрчлөхгүй.

### `security_reencrypt_secrets`

- Зориулалт: `DJANGO_SECRET_KEY`-г сольсны дараа түүнээс гаргасан түлхүүрээр хамгаалагдсан нууцуудыг (баталгаажуулах аппын TOTP нууц, сэргээх кодын seed, SSO client secret) шинэ түлхүүрээр дахин шифрлэнэ. Түүнээс өмнө тэдгээрийг `DJANGO_SECRET_KEY_FALLBACKS` дахь өмнөх түлхүүрээр уншина. Өмнөх түлхүүрийг хасахаас өмнө ажиллуулна ([түлхүүрийн удирдлага](security-keys.md)).
- Аргумент/сонголт: `--dry-run` (зөвхөн өмнөх түлхүүрээр шифрлэгдсэн хэвээр байгаа нууцуудыг тоолно).
- Аудит: бүртгэнэ (тоо)
- Гаралтыг унших: `Dry run: 0 authenticator(s) and 0 SSO client secret(s) use a previous key.` нь өмнөх түлхүүрийг хасаж болно гэсэн үг. `cannot be decrypted` нь утгыг тохируулсан ямар ч түлхүүрээр уншиж чадахгүй гэсэн үг: өмнөх түлхүүрийг `DJANGO_SECRET_KEY_FALLBACKS`-д хийж дахин ажиллуулна.
- Жишээ: `uv run manage.py security_reencrypt_secrets --dry-run`

### `security_reset_mfa`

- Зориулалт: хэрэглэгчийн хоёр шатлалт баталгаажуулалтыг (баталгаажуулах апп, и-мэйлийн код, сэргээх код, санасан төхөөрөмж) шинэчилнэ. Хэрэглэгч дараагийн нэвтрэлтэд дахин бүртгүүлнэ. Ямар ч админ удирдлагын самбарт нэвтэрч чадахгүй үед (жишээ нь цорын ганц админ утсаа алдсан) ашиглана. Бусад үед удирдлагын самбарын **Хэрэглэгчид > Хоёр шатлалт баталгаажуулалтыг шинэчлэх**-ийг ашиглана.
- Аргумент/сонголт: `{user}` хэрэглэгчийн и-мэйл, `--reason=` (заавал), `--actor=` (заавал; шинэчлэхийг шийдсэн админ).
- Аудит: бүртгэнэ (үйлдлийн бүртгэл болон аюулгүй байдлын бүртгэлийн аль алинд, шалтгааны хамт)
- Жишээ: `uv run manage.py security_reset_mfa admin@example.ac.kr --reason="Phone lost, identity verified by phone call" --actor=it-lead@example.ac.kr`

### `security_unlock_user`

- Зориулалт: удаа дараа буруу нууц үг оруулснаас түгжигдсэн бүртгэлийг түгжээний хугацаа дуусахаас өмнө тайлна. Удирдлагын самбарын **Хэрэглэгчид > Нэвтрэлтийн түгжээг тайлах**-тай ижил.
- Аргумент/сонголт: `{user}` хэрэглэгчийн и-мэйл, `--reason=` (заавал).
- Аудит: бүртгэнэ (аюулгүй байдлын бүртгэлд ч мөн)
- Гаралтыг унших: `The account is not locked.` нь юу ч өөрчлөөгүй гэсэн үг.
- Тэмдэглэл: түгжээний босгыг (амжилтгүй оролдлого, түгжээний хугацаа) удирдлагын самбарын **Тохиргоо > Нэвтрэх аргууд** хэсэгт тохируулна.

## Хувь хүмүүс ба оюутны бүртгэл (2-р үе шат)

### `people_find_duplicates`

- Зориулалт: нэг хүн мэт харагдах хувь хүмүүсийг жагсаана. Шалгуур нь ижил регистрийн дугаар (хайлтын хэш), эсвэл ижил латин нэр ба төрсөн огноо. Нэгтгэсэн хувь хүмүүсийг хасна.
- Сонголтууд: `--limit=100` (хэвлэх бүлгийн тоо).
- Аудит: бүртгэхгүй (зөвхөн унших)
- Exit code: давхардлын нэр дэвшигч байвал 2.
- Дараагийн алхам: бүлэг бүрийг удирдлагын самбарын **Хувь хүмүүс** хэсэгт хянаж, нэг хүн бол үлдээх хувь хүний хуудаснаас **Давхардлыг нэгтгэх**-ийг ажиллуулна. Нэгтгэлийг буцаах боломжгүй ([админы гарын авлагын 14-р бүлэг](../admin/14-merge-and-invitations.md)).
- Жишээ: `uv run manage.py people_find_duplicates --limit=50`

## Элсэлт (3-р үе шат)

### `admission_matriculate`

- Зориулалт: элсэлтийн үеийн баталгаажсан өргөдөл гаргагчдад оюутны бүртгэл (шинэ оюутны код) үүсгэнэ. Удирдлагын самбарын **Элсэлт > Өргөдлүүд** дээрх бөөн **Оюутны бүртгэл үүсгэх**-тэй ижил (`MatriculateApplicant`). Өргөдөл гаргагч бүрийг тусад нь боловсруулдаг тул нэг алдаа бусдыг зогсоохгүй.
- Аргумент/сонголт: `cycle` элсэлтийн үеийн код, `--term=` (заавал; элсэх улирлын код, жишээ нь `2027-SP`; элссэн огноо нь улирлын эхний өдөр), `--actor=` (заавал; `Тэнцсэн өргөдөл гаргагчид оюутны бүртгэл үүсгэх` эрхтэй бүртгэл; зөвхөн тэр бүртгэлийн хамрах хүрээн дэх өргөдөл гаргагчдыг боловсруулна), `--dry-run` (зөвхөн жагсаалт).
- Аудит: бүртгэнэ (үе, улирал, нэр дэвшигч, үүсгэсэн, амжилтгүй өргөдлийн дугаарууд). Өргөдөл гаргагч бүрд мөн бизнесийн аудитын бичлэг (`application.matriculated`) үүснэ.
- Exit code: үе эсвэл улирлын код үл мэдэгдэх эсвэл `--actor` байхгүй бол 1, өргөдөл гаргагч амжилтгүй болсон бол 2.
- Жишээ: `uv run manage.py admission_matriculate DEMO-2027-REG --term=2027-SP --actor=admissions@example.ac.kr --dry-run`
- Алдаа гарвал: `Only accepted offers without a student record ...` нь өргөдөл гаргагч аль хэдийн бүртгэлтэй эсвэл баталгаажуулаагүй гэсэн үг; `The program is not in effect on the admission date.` нь хөтөлбөр элссэн огноонд хүчингүй гэсэн үг (Лавлах мэдээлэл > Хөтөлбөрүүд хэсэгт хөтөлбөрийн хүчинтэй хугацааг шалгана); `not in your scope` нь өргөдөл `--actor` бүртгэлийн хамрах хүрээнээс гадуур гэсэн үг.

### `admission_expire_drafts`

- Зориулалт: хаагдсан үеийн ноорог өргөдлүүд болон тохируулсан хугацаанд (**Тохиргоо > Элсэлт > Хөндөгдөөгүй ноорогийг хүчингүй болгох хугацаа (хоног)**, анхдагч 90) өөрчлөгдөөгүй ноорогуудыг **Хугацаа дууссан** гэж тэмдэглэнэ. Хугацаа дууссан өргөдөл ижил үед шинэ өргөдөл гаргахад саад болохгүй.
- Хэзээ: өдөр бүр 03:10-д төлөвлөгдсөн (Celery beat-ийн `admission.expire_drafts` ажил энэ командыг ажиллуулна).
- Сонголтууд: `--dry-run` (зөвхөн тоолно).
- Аудит: бүртгэнэ (хугацаа дуусгасан тоо)
- Жишээ: `uv run manage.py admission_expire_drafts --dry-run`

## Хичээлийн бүлэг (4-р үе шат)

### `section_copy`

- Зориулалт: шинэ улирлын төлөвлөлтийг өмнөх улирлын бүлгүүдээс эхлүүлнэ. Удирдлагын самбарын **Бүлгүүд > Өөр улирлаас хуулах**-тай ижил (`CopySections`). Цуцлагдаагүй бүлгүүдийг ноорог болгон багш (ажилласаар байгаа бол), хичээлийн цаг ба танхим, суудлын хуваарилалт (чөлөөлөх цагийг улирлын эхлэх огнооны зөрүүгээр шилжүүлнэ) болон хичээлийн хөтөлбөрийн (хаалттай ноорог болгон) хамт хуулна. Хичээлийн хувилбарыг шинэ хичээллэх хугацааны эхэнд хүчинтэй хувилбараар солино.
- Аргумент/сонголт: `from-term`, `to-term` улирлын кодууд (жишээ нь `2026-FA`), `--org-unit=` (зөвхөн энэ бүтцийн нэгжийн кодын бүлгүүд; давтаж болно), `--dry-run` (хуулбарыг гүйлгээн дотор хийгээд буцаадаг тул тайлан яг таарна), `--actor=` (заавал; зөвхөн тэр бүртгэлийн `Бүлэг төлөвлөх` эрхийн хамрах хүрээн дэх бүлгүүдийг хуулна).
- Аудит: бүртгэнэ (эх ба зорилтот улирал, хуулсан, алгассан, хянах шаардлагатай тоо; бодит хуулбар мөн бизнесийн аудитын үйл явдал `sections.copied`-ийг бүртгэнэ)
- Гаралтыг унших: `skipped` нь зорилтот улиралд ижил бүлгийн код аль хэдийн байгаа эсвэл хүчинтэй хичээлийн хувилбар байхгүй гэсэн үг; `note` нь бүлгийг хуулсан боловч ямар нэг зүйл орхигдсон гэсэн үг (танхим аль хэдийн эзлэгдсэн тул танхимгүй хуулсан, ажлаас гарсан багш гэх мэт). Хичээллэх хугацааг кодоор тааруулна; байхгүй бол бүлэг бүтэн улирлын хичээллэх хугацаанд орно.
- Exit code: үл мэдэгдэх улирлын код эсвэл `--actor` байхгүй бол 1.
- Жишээ: `uv run manage.py section_copy 2026-FA 2027-FA --actor=academic@example.ac.kr --dry-run`

### `schedule_check_conflicts`

- Зориулалт: хичээлийн хуваарийг нийтлэхээс өмнө улирлын бүлгүүдийг шалгана. Танхим болон багшийн давхар захиалгыг DB аль хэдийн хориглодог; энэ нь DB-ийн зөвшөөрдөг асуудлуудыг олно: танхимын багтаамжаас их суудлын тоо, хичээллэх хугацааны эхлэх огноонд хүчингүй хичээлийн хувилбар, ажлаас гарсан багш, суудлын тооноос хэтэрсэн суудлын хуваарилалт, хичээллэх хугацаанаас гадуурх хичээлийн огноо. Нөөцөөс сэргээх гэх мэт хязгаарлалтгүйгээр орж ирсэн өгөгдөл дэх танхимын давхцлыг ч шалгана.
- Аргументууд: `term` улирлын код.
- Аудит: бүртгэхгүй (зөвхөн унших)
- Exit code: асуудал байвал 2, үл мэдэгдэх улирлын код бол 1. Багш, танхим эсвэл хичээлийн цаг хараахан байхгүй бүлгүүдийг зөвхөн мэдээлэл болгон харуулна (`Note`).
- Жишээ: `uv run manage.py schedule_check_conflicts 2027-SP`

## Хичээл сонголт (5-р үе шат)

### `registration_preflight`

- Зориулалт: хичээл сонголтыг нээхээс өмнө улирлыг шалгана. Хичээл сонголт болон нэмэх/хасах хугацаа, дүрмийн багц, нийтэлсэн бүлгийн тоо, суудлын тоо 0 бүлгүүд, суудлын тооноос хэтэрсэн суудлын хуваарилалт, хичээллэх хугацааны эхлэх огноонд хүчингүй хичээлийн хувилбар, кредитийн хязгаарт хамрагдаагүй идэвхтэй оюутны тоо болон хичээл сонголтын хоригтой оюутны тоог харуулна.
- Аргументууд: `term` улирлын код (жишээ нь `2027-SP`).
- Аудит: бүртгэхгүй (зөвхөн унших)
- Exit code: асуудал байвал 2. Дүрмийн багц байхгүй бол асуудал биш, мэдээлэл болгон харуулна (дүрмийн анхдагч утга үйлчилнэ).
- Жишээ: `uv run manage.py registration_preflight 2027-SP`

### `registration_simulate`

- Зориулалт: оюутан одоо (эсвэл тодорхой цагт) бүлэгт бүртгүүлбэл юу болохыг дүрэм тус бүрээр харуулна. Юу ч хадгалахгүй, оролдлого бүртгэхгүй. "Яагаад бүртгүүлж чадахгүй байна вэ?" гэсэн асуултад ашиглана.
- Аргументууд: `student-number` оюутны код, `section` `course code-section code` (жишээ нь `CSE2010-01`).
- Сонголтууд: `--term=` (улирлын код; анхдагч нь тэр бүлэгтэй хамгийн сүүлийн улирал), `--at=` (үнэлэх цаг; жишээ нь `"2027-02-10 10:00 Asia/Seoul"`).
- Аудит: бүртгэхгүй (зөвхөн унших)
- Гаралтыг унших: дүрэм тус бүрээр тэнцсэн/тэнцээгүй, хориглох/анхааруулах болон мэдэгдэл. Онцгой зөвшөөрөлд хамрагдсан дүрэм тэнцээгүй гэж харагдах боловч хориглохгүй. Суудлын тоог дүрмийн хүснэгтийн доор тусад нь харуулна.
- Exit code: бүртгэлээс татгалзах байсан бол 2.
- Жишээ: `uv run manage.py registration_simulate 202612345 CSE2010-01 --at="2027-02-10 10:00 Asia/Seoul"`

### `waitlist_promote`

- Зориулалт: сул суудалтай бүлгүүдэд хүлээлгийн жагсаалтын оюутнуудыг дарааллаар нь бүртгэнэ. Дэвшүүлэхдээ бүх дүрмийг дахин шалгана; дүрэм хангаагүй хүлээлгийн бичлэгийг жагсаалтаас хасна (шалтгааныг тэмдэглэнэ). Хичээл сонголт болон нэмэх/хасах хугацаа хоёулаа хаагдсан бүлгүүдийн хүлээлгийн жагсаалтын хугацаа дуусна. Оюутнууд үр дүнг и-мэйлээр хүлээн авна.
- Аргумент/сонголт: `term?` улирлын код (анхдагч: хүлээлгийн бичлэгтэй бүх улирал), `--actor=`.
- Аудит: бүртгэнэ (бүлэг, дэвшүүлсэн, хассан, хугацаа дууссан тоо)
- Хэзээ: хасалт, цуцлалт эсвэл суудлын хуваарилалт чөлөөлөгдөхөд холбогдох бүлгийг дарааллын ажил шууд боловсруулна. Энэ команд нь алдагдсан зүйлийг боловсруулах цаг тутмын төлөвлөгдсөн хамгаалалт юм.
- Жишээ: `uv run manage.py waitlist_promote 2027-SP --actor=registrar@example.ac.kr`

### `registration_release_reserved_seats`

- Зориулалт: чөлөөлөх цаг нь өнгөрсөн суудлын хуваарилалтыг (жишээ нь мэргэжлийн оюутнуудад нөөцөлсөн суудал) боловсруулсан гэж тэмдэглэж, тэдгээр бүлгийн хүлээлгийн жагсаалтын дэвшүүлэх ажлыг дараалалд оруулна. Нөөцөлсөн суудал чөлөөлөх цаг өнгөрмөгц тооцоонд ерөнхий суудал болдог тул энэ команд зөвхөн суудлыг хүлээлгийн жагсаалтад шилжүүлнэ.
- Аудит: бүртгэхгүй (5 минут тутам ажиллана; дэвшүүлэлтийн үр дүн хичээлийн бүртгэлийн бичлэгт байна)
- Хэзээ: төлөвлөгдсөн (5 минут тутам, Celery beat-ийн ажил `registration.release_reserved_seats`). Дэвшүүлэх ажил нь бүлэг тус бүрийн `registration.promote_waitlist` (Redis түгжээгээр бүлэг тус бүрт нэг удаад нэг).
- Жишээ: `uv run manage.py registration_release_reserved_seats`

## Дүн (6-р үе шат)

### `term_close`

- Зориулалт: улирлыг хаана. Улирлын бүх дүн баталгаажсан байх ёстой. Оюутны хэсэг (100) тус бүрээр улирлын дүнгийн бүртгэлийг (кредит, улирлын ба нийт голч дүн) тооцоолж, сурлагын байдал (хэвийн, академик сануулга, хасалтын хяналт) болон онц сурлагын эрхийг тогтооно (Celery chord-ийн `grading.close_term_records` ажлууд); дараа нь дуусгах ажил `grading.finish_term_close` хөтөлбөр тус бүрээр онц сурлагыг эрэмбэлж, улирлын дүнгийн бүртгэлийг албан ёсны бүртгэл болгон хааж, улирлыг **Дүн хаагдсан** төлөвт оруулна. Явцыг `job_batches`-д хадгалж, **Дүн > Улирлын дүнгийн бүртгэлүүд** жагсаалтын дээр харуулна. Дуусахад эхлүүлсэн ажилтан и-мэйл хүлээн авна. Удирдлагын самбарын **Дүн > Улирлын дүнгийн бүртгэлүүд > Улирал хаах**-тай ижил.
- Аргумент/сонголт: `term` улирлын код, `--dry-run` (зөвхөн улирлыг хааж болох эсэхийг шалгана), `--reason=` (бичлэгт хадгалах шалтгаан), `--actor=`.
- Аудит: бүртгэнэ (оюутны тоо, баталгаажаагүй дүнтэй бүлгийн тоо, багцын id). Хаалт дуусахад `term.closed` аудитын бичлэг академик сануулга, хасалтын хяналт болон онц сурлагын тоог хадгална.
- Exit code: зарим бүлэгт баталгаажаагүй дүн байвал 2 (бүлэг тус бүрийн баталгаажаагүй тоог хэвлэнэ). Улирал нийтлэгдсэн төлөвт биш бол 1.
- Хэзээ: дүн оруулах, баталгаажуулах ажил дууссаны дараа. Багцыг Flower болон улирлын дүнгийн бүртгэлийн дэлгэцээр хянана. Celery worker-гүй бол улирлын төлөв өөрчлөгдөхгүй. Өгөгдлийн сангийн алдаагаар амжилтгүй болсон хэсгийг 3 хүртэл удаа дахин оролдоно; дахиад амжилтгүй бол багц амжилтгүй хэвээр үлдэж, улирал өөрчлөгдөхгүй (шалтгааныг засаад дахин ажиллуулна; дахин ажиллуулахад ижил үр дүн гарна).
- Жишээ: `uv run manage.py term_close 2026-FA --dry-run`, `uv run manage.py term_close 2026-FA --reason="Fall 2026 grades closed" --actor=registrar@example.ac.kr`

### `grades_recalculate`

- Зориулалт: улирлын дүнгийн бүртгэлийг (кредит, улирлын ба нийт голч дүн) баталгаажсан дүнгээс дахин тооцоолно. Өөрчилсөн дүнгийн бодлогыг (голч дүнгийн аравтын орон, давтан судлалтын боловсруулалт) өнгөрсөн улирлуудад хэрэгжүүлэхэд ашиглана. Сурлагын байдал болон онц сурлага улирал хаах үед тогтоосон утгаа хадгална. Батлагдсан дүнгийн өөрчлөлт тухайн оюутныг автоматаар дахин тооцоолдог тул үүнд энэ команд хэрэггүй.
- Сонголтууд: `--term=` (тэр улиралд дүнтэй оюутнууд, тэр улирлаас хойш), `--student-number=` (нэг оюутан), `--reason=` (заавал), `--actor=`.
- Аудит: бүртгэнэ (оюутны тоо, шалтгаан)
- Exit code: шалтгаангүй, эсвэл үл мэдэгдэх улирлын код, оюутны код бол 1.
- Жишээ: `uv run manage.py grades_recalculate --term=2026-SP --reason="GPA changed to three decimal places"`

### `grades_remind_missing`

- Хэзээ: дүн оруулах хугацаа хаагдахаас хэдэн өдрийн өмнө. Шаардлагатай бол төлөвлөгөөнд нэмнэ.

## LMS холболт (12-р үе шат)

### `lms_sync`

- Зориулалт: нийтэлсэн бүлгүүдийг платформ руу илгээнэ (хичээл үүсгэх ба холбох, багш нар, бүртгүүлсэн оюутнууд). Удирдлагын самбарын **Хичээлийн холбоосууд > Дахин синхрончлох**-ын хийдэг зүйлийг бүтэн улиралд хийнэ. Аль хэдийн холбогдсон бүлгүүдийг зөвхөн дахин баталгаажуулна (idempotent). Алхам бүрийг **Синхрончлолын бүртгэлүүд**-д хадгална.
- Аргумент/сонголт: `{platform}` платформын код, `--term=` (улирлын код, анхдагч нь дуусаагүй бүх улирал), `--section=` (нэг хичээлийн код-бүлгийн код, жишээ нь `CSE2010-01`), `--dry-run` (илгээх байсан зүйлийг зөвхөн "skipped" гэж бүртгэнэ), `--actor=`.
- Аудит: бүртгэнэ (платформ, бүлэг, гишүүн, алдаа)
- Exit code: үл мэдэгдэх платформ эсвэл улирлын код бол 1, аль нэг бүлэг амжилтгүй болсон бол 2 (бүлэг тус бүрийн алдааг хэвлэнэ).
- Хэзээ: улирал эхлэхээс өмнө, шинэ платформыг идэвхжүүлсний дараа.
- Жишээ: `uv run manage.py lms_sync DEMO --term=2026-FA --dry-run`

### `lms_reconcile`

- Зориулалт: платформын хичээлийн нэрсийн жагсаалтыг оюутны мэдээллийн системийн бүртгэлийн жагсаалттай харьцуулж, дутуу гишүүдийг нэмж, илүүг хасна. Хараахан холбогдоогүй бүлгүүдийг бүтнээр нь синхрончилно. Зөрүүг синхрончлолын бүртгэлд хадгална (`reconcile`, `payload` дахь `missing` ба `extra`).
- Аргумент/сонголт: `{platform?}` (орхивол бүх идэвхтэй платформ), `--term=` (анхдагч нь дуусаагүй улирлууд), `--dry-run` (зөвхөн зөрүүг бүртгэнэ), `--actor=`.
- Аудит: бүртгэнэ (платформ тус бүрийн бүлэг, нэмсэн/хассан/амжилтгүй тоо)
- Exit code: үл мэдэгдэх платформ эсвэл улирлын код, эсвэл идэвхтэй платформ байхгүй бол 1, аль нэг бүлэг амжилтгүй болсон бол 2.
- Хэзээ: өдөр бүр 02:30-д `lms.reconcile` ажлаар (Celery beat) төлөвлөгдсөн. Платформын тасалдлын дараа гараар ажиллуулна.

### `api_issue_token`

- Зориулалт: бүртгэлд API холболтын токен олгоно ([ADR 0004-django](../../../../porting/decisions/0004-django-api-tokens.md)); ихэвчлэн зөвхөн шаардлагатай эрхтэй үйлчилгээний бүртгэлд (LMS: `lms.manage`, BI: `reports.view`). Токеныг стандарт гаралтын эхний мөрөнд **нэг удаа** хэвлэнэ; өгөгдлийн сан зөвхөн түүний digest-ийг хадгална. Хүсэлтүүд үүнийг `Authorization: Token <token>` толгойгоор илгээнэ.
- Аргумент/сонголт: `{email}` бүртгэлийн и-мэйл, `--days=` (хүчинтэй хугацаа 1-ээс 365 хоног, анхдагч `API_TOKEN_TTL_DAYS` = 90), `--reason=` (юунд зориулсан, аудитад бүртгэнэ), `--actor=`.
- Аудит: бүртгэнэ (`api.token_issued`: түлхүүрийн угтвар ба дуусах хугацаа; токеныг өөрийг нь хэзээ ч биш)
- Exit code: үл мэдэгдэх эсвэл идэвхгүй бүртгэл, эсвэл хүрээнээс гарсан хугацаа бол 1.
- Жишээ: `uv run manage.py api_issue_token moodle-sync@example.ac.kr --days=365 --reason="Moodle callbacks" --actor=admin@example.ac.kr`

### `api_revoke_tokens`

- Зориулалт: бүртгэлийн API токенуудыг (бүгдийг, эсвэл `--key=`-ээр нэгийг) хүчингүй болгоно. `--list` нь зөвхөн токенуудыг (түлхүүрийн угтвар, олгосон ба дуусах цаг) жагсаана.
- Аргумент/сонголт: `{email}`, `--key=` (түлхүүрийн угтвар), `--list`, `--reason=`, `--actor=`.
- Аудит: бүртгэнэ (`api.token_revoked`: хүчингүй болгосон түлхүүрийн угтварууд)
- Exit code: үл мэдэгдэх бүртгэл эсвэл `--key`-тэй токен байхгүй бол 1.
- Хэзээ: холболт дуусах, токен алдагдсан байж болзошгүй, эсвэл хариуцсан хүн солигдох үед.

## Ашиглалтын шалгалт ба цэвэрлэгээ (13-р үе шат)

- Аудит: байхгүй (зөвхөн унших)
- Exit code: аль нэг шалгалт амжилтгүй бол 2.
- Хэзээ: байршуулсны дараа шууд, тасалдал сэжиглэгдэх үед, мониторингоос тогтмол. Ачаалал тэнцвэржүүлэгч `/api/v1/health/`-ийг ашиглана.

- Сонголтууд: `--table=` (record_changes, activity_log, security_events-ийн аль нэг; давтаж болно), `--actor=`.

### `audit_verify_chain`

- Зориулалт: аудитын мөрүүдийн агуулгын хэш болон гинжийг дахин тооцоолж хуурамчаар өөрчлөлт, устгал болон дарааллын өөрчлөлтийг олно. Хүснэгт тус бүрээр шалгасан мөр, битүүмжилсэн мөр, зөрүү болон эхний зөрүүтэй id-г хэвлэнэ.
- Сонголтууд: `--table=`.
- Аудит: байхгүй (зөвхөн унших)
- Exit code: зөрүү байвал 2.
- Хэзээ: нөөцлөхөөс өмнө, аюулгүй байдлын хяналтын үеэр, цэвэрлэсний дараа.

### `audit_prune`

- Зориулалт: хадгалах хугацаа нь өнгөрсөн **битүүмжилсэн** аудитын мөрүүдийг устгана. Схемийн эзэмшигчийн холболтоор `app.audit_maintenance = on`-той гүйлгээнд ажиллана. Битүүмжлэгдээгүй мөрүүдийг хадгална (эхлээд `audit_seal` ажиллуулна). Устгал бүр аюулгүй байдлын үйл явдал `audit.pruned`-ийг (хүснэгт, хязгаар огноо, устгасан мөр, id-ийн хүрээ, хилийн мөрийн `chain_hash`) бүртгэнэ.
- Сонголтууд: `--before=YYYY-MM-DD` (заавал; тэр өдрийн шөнө дундаас өмнөх мөрүүд), `--table=`, `--dry-run` (зөвхөн тоолно), `--actor=`.
- Аудит: бүртгэнэ (хязгаар огноо, хүснэгт тус бүрийн устгасан мөр ба id-ийн хүрээ)
- Хэзээ: хадгалах бодлогын дагуу, нөөцөлсний дараа.
- Жишээ

  ```bash
  uv run manage.py audit_prune --before=2023-03-01 --dry-run
  uv run manage.py audit_prune --before=2023-03-01 --table=record_changes --actor=ops@example.edu
  ```

### `media_prune_orphans`

- Зориулалт: эзэмшигч нь байхаа больсон медиа мөрүүд болон хувийн хадгалалт дээрх мөргүй директоруудыг (`<media id>/`) устгана (хувь хүний зураг, өргөдлийн баримт, тодорхойлолтын PDF, шалгалтын нотлох баримт).
- Сонголтууд: `--dry-run` (зөвхөн жагсаалт), `--actor=`.
- Аудит: бүртгэнэ (мөр, директор)
- Хэзээ: сар бүр эсвэл их хэмжээний устгалтын дараа.

## Хувийн мэдээллийн шифрлэлтийн түлхүүр (0-р үе шат)

### `pii_generate_key`

- Зориулалт: `PII_ENCRYPTION_KEY` болон `PII_HASH_KEY`-ийн шинэ түлхүүрүүдийг (32 байт, `base64:...`) хэвлэнэ. Юу ч хадгалахгүй.
- Аудит: бүртгэхгүй
- Анхааруулга: `PII_HASH_KEY`-г өөрчилбөл бүх хайлтын хэш (`*_hash`) хүчингүй болно. Зөвхөн шифрлэлтийн түлхүүрийг солино: хуучин түлхүүрийг `PII_PREVIOUS_KEYS` руу шилжүүлээд `pii_reencrypt` ажиллуулна.
- Жишээ

  ```bash
  uv run manage.py pii_generate_key
  ```

### `pii_reencrypt`

- Зориулалт: түлхүүр сольсны дараа өмнөх түлхүүрээр шифрлэгдсэн хувийн мэдээллийг одоогийн түлхүүрээр дахин шифрлэнэ. Бичлэгийн хэсгүүд дээр Celery ажлын бүлэг хэлбэрээр ажиллана. Одоогийн түлхүүр дээр байгаа бичлэгүүдэд хүрэхгүй.
- Аргументууд: шифрлэгдсэн хувийн мэдээллийн талбартай модель (`app_label.Model`, жишээ нь `person.Person`).
- Сонголтууд: `--chunk=500` (ажил тус бүрийн бичлэг), `--dry-run` (зөвхөн өмнөх түлхүүр ашиглаж буй бичлэгүүдийг тоолно), `--force` (баталгаажуулалтгүй), `--actor=`.
- Аудит: бүртгэнэ (багцын ID, ажлын тоо / урьдчилсан тоо)
- Шалгах: ажлуудыг Flower-оор хянана. Дуусч, `--dry-run` 0 гэж мэдээлсний дараа өмнөх түлхүүрийг `PII_PREVIOUS_KEYS`-ээс хасна.
- Жишээ

  ```bash
  uv run manage.py pii_reencrypt person.Person --dry-run
  uv run manage.py pii_reencrypt person.Person --force --actor=ops@example.edu
  ```

## Хэлний дэмжлэг (0-р үе шат)

### `i18n_missing`

- Зориулалт: орчуулах мөрүүдийг эх кодоос `makemessages`-ийн адил (файл бичихгүйгээр) гаргаж, бүх каталогтой (глобал `locale/` болон апп тус бүрийн `locale/`) харьцуулж, хэл тус бүрээр дутуу мөрүүд (каталогт байхгүй, хоосон `msgstr`, fuzzy, ялгаатай орлуулах тэмдэгт) болон хуучирсан бичлэгүүдийг жагсаана.
- Аргумент/сонголт: `[locale]` (зөвхөн нэг хэл, жишээ нь `ko`, `zh-hans`, `lo`), `--strict` (мөр дутуу бол exit code 2; CI-д ашиглана), `--no-extract` (зөвхөн каталогуудыг шалгана, эх кодыг уншихгүй).
- Аудит: бүртгэхгүй
- Шаардлага: GNU gettext (`xgettext`, `msguniq`).
- Жишээ

  ```bash
  uv run manage.py i18n_missing --strict
  uv run manage.py i18n_missing lo
  ```

### `i18n_export`

- Зориулалт: орчуулагчдад зориулсан хүснэгт бичнэ (`.xlsx` эсвэл `.csv`, өргөтгөлөөр сонгоно). Баганууд: `catalog` (каталогийн байршил), `context`, `source` (англи msgid), `source_plural`, `translation`, `note` (анхны түлхүүр).
- Аргумент/сонголт: `{locale} {path}`, `--missing` (зөвхөн орчуулгагүй мөрүүд).
- Аудит: бүртгэхгүй
- Жишээ: `uv run manage.py i18n_export ko storage/ko.xlsx --missing`

### `i18n_import`

- Зориулалт: орчуулагчдын бөглөсөн хүснэгтийг каталогууд (`.po`) руу буцааж бичээд хөрвүүлнэ (`.mo`). Зөвхөн каталогт байгаа мөрүүдийг (ижил каталог, контекст болон англи текст) оруулна; хоосон орчуулгыг алгасна.
- Аргумент/сонголт: `{locale} {path}`, `--dry-run` (бичигдэх мөрүүдийг жагсаана), `--actor=`.
- Аудит: бүртгэнэ (хэл, орчуулгын тоо)
- Тэмдэглэл: каталогууд репозиторид байна. Оруулсны дараа `.po`-ийн өөрчлөлтийг commit хийнэ.

### `i18n_makemessages`

- Зориулалт: бүх каталог (ko, zh_Hans, lo) эх кодтой таарахын тулд `makemessages`-ийг репозиторийн үндсээс ажиллуулна. Апп өөрийн `locale/`-тэй бол мөрүүд тэнд, үгүй бол глобал `locale/` руу орно. `.venv`, `tests`, `docs` зэрэг директоруудыг алгасна.
- Сонголтууд: Django-гийн `makemessages`-тэй ижил (`-l`, `--no-obsolete`, ...).
- Аудит: бүртгэхгүй
- Жишээ: `uv run manage.py i18n_makemessages`

## Шалгалтууд (0-р үе шат)

### `pdf_sample`

- Зориулалт: Хангыль, CJK, лао, тай, деванагари, кирилл болон латин бичгийг холилдуулсан хүснэгтийг PDF болгон үүсгэж, фонт болон PDF үйлчилгээтэй (Gotenberg) холболтыг шалгана.
- Аргумент: `[path]` (анхдагч `pdf-sample.pdf`, хувийн файлын хадгалалт `PRIVATE_MEDIA_ROOT`-тэй харьцангуй).
- Аудит: бүртгэхгүй
- Алдаа гарвал: exit code 1. Холболтын алдаа бол `GOTENBERG_URL`, `GOTENBERG_TIMEOUT` болон Gotenberg контейнерийг шалгана.
- Жишээ: `uv run manage.py pdf_sample`

### `naming_check`

- Зориулалт: өгөгдлийн сангийн схем болон эх кодыг [нэршлийн дүрэм](../../../development/naming.md)-тэй тулгаж шалгана. Бодит өгөгдлийн сангийн каталог (схемүүд `public`, `audit`, `reporting`) дахь хүснэгт ба баганын нэр, Ninefruits аппуудын миграцын файлын нэр, удирдлагын командын нэр (`context_action`) болон орчуулгын каталогуудын (`.po`) msgid, msgctxt-ийг шалгана.
- Дүрмүүд: snake_case, хориглосон дагавар (`_old`, `_new`, `_backup`, `_tmp`, огноо, тоо), хэлний код агуулсан нэр, цагийн бүсгүй цагийн багана (`timestamp without time zone`), boolean баганын нэр (`is_`, `has_`, `can_` эсвэл үйл үг), огнооны баганын нэр (`_date`), семантик түлхүүр хэлбэртэй msgid (`registration.errors.x`). Django болон багцуудын тодорхойлсон хүснэгтүүдийг (`django_*`, allauth, Celery beat, `settings`, `cache`, `jobs`, `media` гэх мэт) хасна.
- Сонголтууд: `--database=` (шалгах өгөгдлийн сангийн холболт, анхдагч `default`), `--skip-database` (зөвхөн файлын шалгалт, өгөгдлийн сангүй).
- Аудит: бүртгэхгүй
- Exit code: асуудал олдвол 2.
- Жишээ

  ```bash
  uv run manage.py naming_check
  ```
