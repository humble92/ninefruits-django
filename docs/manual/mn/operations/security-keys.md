# Түлхүүрийн удирдлага

- Зориулалт: МТ-ийн ашиглалтын ажилтнууд
- Холбогдох: [суулгалт](installation.md), [командын лавлах](commands.md), [байршуулалтын хяналтын хуудас](deployment-checklist.md)

| Түлхүүр | Зориулалт | Алдвал | Солих |
|---|---|---|---|
| `DJANGO_SECRET_KEY` | Сесс, CSRF, гарын үсэг (нууц үг шинэчлэх холбоос, и-мэйл баталгаажуулах холбоос, санасан төхөөрөмжийн күүки), и-мэйлийн хоёр шатлалт кодын хэш, хоёр шатлалт баталгаажуулалтын нууцын (баталгаажуулах аппын TOTP нууц, сэргээх код) болон SSO client secret-ийн шифрлэлт | Бүх хэрэглэгч системээс гарна, илгээсэн холбоосууд ажиллахаа больно, бүртгүүлсэн баталгаажуулах апп болон сэргээх код ажиллахаа больно (хэрэглэгч тус бүрийн хоёр шатлалт баталгаажуулалтыг шинэчлэх шаардлагатай), SSO client secret-ийг дахин оруулах шаардлагатай | Өмнөх түлхүүрийг `DJANGO_SECRET_KEY_FALLBACKS`-д хийгээд солино (доорх журам) |
| `PII_ENCRYPTION_KEY` | Регистрийн дугаар зэрэг хувийн мэдээллийн шифрлэлт (AES-256-GCM) | **Шифрлэгдсэн хувийн мэдээллийг сэргээх боломжгүй** | Өмнөх түлхүүрийг `PII_PREVIOUS_KEYS`-д хийгээд солино (доорх журам) |
| `PII_HASH_KEY` | Хувийн мэдээллийг яг таарцаар хайх хэш (HMAC-SHA256) | Хайлт ажиллахаа больно (өгөгдөл хэвээр үлдэнэ) | Зарчмын хувьд солихгүй |

`DJANGO_SECRET_KEY`-г `uv run python -c "import secrets; print(secrets.token_urlsafe(50))"`-ээр, хоёр хувийн мэдээллийн түлхүүрийг `uv run manage.py pii_generate_key`-ээр үүсгэнэ.

Хадгалах зарчим

- Гурван түлхүүрийг серверийн тохиргооноос гадна нууц хадгалалтад (Vault, үүлэн нууц менежер гэх мэт) эсвэл битүүмжилсэн офлайн хадгалалтад дор хаяж хоёр хуулбараар хадгална.
- Нөөц файлуудтай хамт хадгалахгүй. Өгөгдлийн сангийн нөөц алдагдсан ч түлхүүргүйгээр унших боломжгүй байх ёстой.
- Хөгжүүлэлтийн `.env` эсвэл тестийн тохиргооны түлхүүрийг production-д хэзээ ч ашиглахгүй.
- Веб процессууд (gunicorn), Celery worker-ууд болон Celery beat бүгд ижил түлхүүрийн утгыг унших ёстой. Түлхүүрийг өөрчилсний дараа гурвууланг нь хамт дахин эхлүүлнэ.

## `DJANGO_SECRET_KEY` солих

Төлөвлөгөөт солилт эсвэл түлхүүрийг мэдэх хүмүүс өөрчлөгдөх үед ашиглана. Django-гийн `SECRET_KEY_FALLBACKS`-д тулгуурладаг тул өмнөх түлхүүрийг хадгалж байх хугацаанд хэн ч системээс гарахгүй. Энэ нь анхны системийн (Laravel) `APP_PREVIOUS_KEYS`-тэй ижил арга.

1. Шинэ түлхүүр үүсгэнэ: `uv run python -c "import secrets; print(secrets.token_urlsafe(50))"`.
2. Одоогийн түлхүүрийг `DJANGO_SECRET_KEY_FALLBACKS`-ийн эхэнд (хэд хэдэн бол таслалаар тусгаарлана), шинэ түлхүүрийг `DJANGO_SECRET_KEY`-д хийнэ.
   ```
   DJANGO_SECRET_KEY=<new key>
   DJANGO_SECRET_KEY_FALLBACKS=<previous key>
   ```
3. gunicorn, Celery worker-ууд болон beat-ийг дахин эхлүүлнэ (Docker: `docker compose restart app worker beat`).
4. Хоёр шатлалт баталгаажуулалтын нууц болон SSO client secret-ийг шинэ түлхүүрээр дахин шифрлэнэ. `uv run manage.py security_reencrypt_secrets --dry-run`-аар тоог шалгаад `--dry-run`-гүйгээр ажиллуулж, дараа нь `--dry-run` 0 гэж мэдээлж буйг баталгаажуулна. Энэ алхмаас өмнө өмнөх түлхүүрийг хасвал баталгаажуулах апп болон сэргээх код ажиллахаа больно.
5. Өмнөх түлхүүрийг хэр удаан хадгалахаа шийднэ. Дараах зүйлс зөвхөн түүнийг хадгалж байх хугацаанд хүчинтэй:

   | Зүйл | Өмнөх түлхүүрийг хадгалж байх үед | Хассаны дараа |
   |---|---|---|
   | Нэвтрэлтийн сесс | Солилтын дараах анхны хүсэлтээр шинэ түлхүүр рүү шилжинэ | Зөвхөн энэ хооронд ашиглагдаагүй сессүүд гарна |
   | Нууц үг шинэчлэх холбоос, и-мэйл баталгаажуулах холбоос | Хүчинтэй (3 хоног) | Дахин хүсэх шаардлагатай |
   | Санасан төхөөрөмжийн күүки | Хүчинтэй (аюулгүй байдлын тохиргооны санах хугацаа, анхдагч 30 хоног) | Дараагийн нэвтрэлтэд хоёр шатлалт баталгаажуулалтыг дахин асууна |
   | И-мэйлийн хоёр шатлалт код | Солилтын өмнөхөн илгээсэн код таарахгүй (10 минут хүчинтэй) | Адил |

   Дор хаяж 3 хоног, эсвэл санасан төхөөрөмжүүдийг хадгалахын тулд санах хугацааны турш хадгална.
6. Хугацаа дуусахад өмнөх түлхүүрийг `DJANGO_SECRET_KEY_FALLBACKS`-ээс хасаж, 3-р алхмын адил дахин эхлүүлнэ.
7. Өмнөх түлхүүрийг нөөцийн хадгалах хугацааны турш битүүмжлэн хадгална. Хуучин нөөц дэх хоёр шатлалт баталгаажуулалтын нууцууд түүгээр шифрлэгдсэн. Хуучин нөөцийг сэргээхдээ тэр түлхүүрийг `DJANGO_SECRET_KEY_FALLBACKS`-д хийж 4-р алхмыг ажиллуулна.

### Түлхүүр алдагдсан бол

1. 1-ээс 4-р алхмыг нэн даруй гүйцэтгэнэ (өмнөх түлхүүр зөвхөн 4-р алхмын дахин шифрлэлтэд хэрэгтэй).
2. 4-р алхам дуусмагц өмнөх түлхүүрийг хасаж дахин эхлүүлнэ. Бүх сесс дуусч, илгээсэн холбоос болон санасан төхөөрөмжүүд хүчингүй болно (зорьсон үр дүн).
3. Алдагдсан хугацааны нэвтрэлт болон удирдлагын ажлыг аюулгүй байдлын бүртгэлээс хянана ([аудит ба засвар үйлчилгээ](audit-and-maintenance.md)).

## Хувийн мэдээллийн түлхүүр солих

1. `uv run manage.py pii_generate_key`-ээр шинэ түлхүүр үүсгэнэ (гаралтаас зөвхөн `PII_ENCRYPTION_KEY`-г ашиглана).
2. Одоогийн түлхүүрийг `PII_PREVIOUS_KEYS`-д (хэд хэдэн бол таслалаар тусгаарлана), шинэ түлхүүрийг `PII_ENCRYPTION_KEY`-д хийнэ.
3. Процессуудад тохиргоог дахин уншуулна: gunicorn болон Celery worker-уудыг дахин эхлүүлнэ (Docker: `docker compose restart app worker beat`).
4. Хувийн мэдээлэлтэй загвар тус бүрээр `uv run manage.py pii_reencrypt {app.Model} --dry-run`-аар бичлэгийн тоог шалгаад (жишээ нь `person.Person`), `--force`-гүйгээр ажиллуулна (баталгаажуулалтад хариулна).
5. Flower ажлууд дууссаныг харуулж, `--dry-run` 0 гэж мэдээлсний дараа өмнөх түлхүүрийг `PII_PREVIOUS_KEYS`-ээс хасна.
6. Өмнөх түлхүүрийг нөөцийн хадгалах хугацааны турш битүүмжлэн хадгална (хуучин нөөцийг сэргээхэд хэрэгтэй).

`PII_HASH_KEY`-г өөрчилбөл хадгалсан бүх хайлтын хэш буруу болж, регистрийн болон паспортын дугаараар яг таарцаар хайх боломжгүй болно. Зарчмын хувьд солихгүй.
